## 29.12.4.1 events_waits_current 表

events_waits_current 表包含当前等待事件。该表每个线程存储一行，显示线程最近被监控等待事件的当前状态，因此没有用于配置表大小的系统变量。

在包含等待事件行的表中，events_waits_current 是最基础的。其他包含等待事件行的表在逻辑上派生自当前事件。例如，events_waits_history 和 events_waits_history_long 表分别是已结束的最近等待事件的集合，每个线程和全局范围内的行数都有最大限制。

有关三个等待事件表之间关系的更多信息，请参见第 29.9 节"当前和历史事件的 Performance Schema 表"。

有关配置是否收集等待事件的信息，请参见第 29.12.4 节"Performance Schema 等待事件表"。

### Performance Schema 等待事件表

events_waits_current 表具有以下列：

- **THREAD_ID, EVENT_ID**

  与事件关联的线程和事件开始时的线程当前事件号。THREAD_ID 和 EVENT_ID 值合在一起唯一标识该行。没有两行具有相同的值对。

- **END_EVENT_ID**

  事件开始时此列设置为 NULL，事件结束时更新为线程当前事件号。

- **EVENT_NAME**

  产生事件的工具的名称。这是来自 setup_instruments 表的 NAME 值。工具名称可能有多个部分并形成层次结构，如第 29.6 节"Performance Schema 工具命名约定"中所述。

- **SOURCE**

  包含产生事件的被检测代码的源文件名称和发生检测的文件中的行号。这使您能够检查源代码以确定涉及的确切代码。例如，如果互斥锁或锁被阻止，您可以检查发生这种情况的上下文。

- **TIMER_START, TIMER_END, TIMER_WAIT**

  事件的计时信息。这些值的单位是皮秒（万亿分之一秒）。TIMER_START 和 TIMER_END 值指示事件计时何时开始和结束。TIMER_WAIT 是事件经过的时间（持续时间）。

  如果事件未完成，TIMER_END 是当前计时器值，TIMER_WAIT 是到目前为止经过的时间（TIMER_END − TIMER_START）。

  如果事件由具有 TIMED = NO 的工具产生，则不收集计时信息，TIMER_START、TIMER_END 和 TIMER_WAIT 都为 NULL。

  有关皮秒作为事件时间单位以及影响时间值的因素的讨论，请参见第 29.4.1 节"Performance Schema 事件计时"。

- **SPINS**

  对于互斥锁，自旋轮数。如果值为 NULL，代码不使用自旋轮或未检测自旋。

- **OBJECT_SCHEMA, OBJECT_NAME, OBJECT_TYPE, OBJECT_INSTANCE_BEGIN**

  这些列标识"被作用的"对象。这意味着什么取决于对象类型。

  对于同步对象（cond、mutex、rwlock）：

  - OBJECT_SCHEMA、OBJECT_NAME 和 OBJECT_TYPE 为 NULL。

  - OBJECT_INSTANCE_BEGIN 是内存中同步对象的地址。

  对于文件 I/O 对象：

  - OBJECT_SCHEMA 为 NULL。

  - OBJECT_NAME 是文件名。

  - OBJECT_TYPE 是 FILE。

  - OBJECT_INSTANCE_BEGIN 是内存中的地址。

  对于套接字对象：

  - OBJECT_NAME 是套接字的 IP:PORT 值。

  - OBJECT_INSTANCE_BEGIN 是内存中的地址。

  对于表 I/O 对象：

  - OBJECT_SCHEMA 是包含该表的模式的名称。

  - OBJECT_NAME 是表名。

  - OBJECT_TYPE 对于持久基表是 TABLE，对于临时表是 TEMPORARY TABLE。

  - OBJECT_INSTANCE_BEGIN 是内存中的地址。

  OBJECT_INSTANCE_BEGIN 值本身没有意义，除了不同的值表示不同的对象。OBJECT_INSTANCE_BEGIN 可用于调试。例如，它可以与 GROUP BY OBJECT_INSTANCE_BEGIN 一起使用，以查看 1,000 个互斥锁（例如保护 1,000 个页面或数据块）上的负载是否均匀分布或仅命中几个瓶颈。如果在日志文件或其他调试或性能工具中看到相同的对象地址，这可以帮助您与其他信息源关联。

- **INDEX_NAME**

  使用的索引的名称。PRIMARY 表示表主索引。NULL 表示未使用索引。

- **NESTING_EVENT_ID**

  此事件嵌套在其中的事件的 EVENT_ID 值。

- **NESTING_EVENT_TYPE**

  嵌套事件类型。值为 TRANSACTION、STATEMENT、STAGE 或 WAIT。

- **OPERATION**

  执行的操作类型，例如 lock、read 或 write。

- **NUMBER_OF_BYTES**

  操作读取或写入的字节数。对于表 I/O 等待（wait/io/table/sql/handler 工具的事件），NUMBER_OF_BYTES 表示行数。如果值大于 1，则事件是批量 I/O 操作。以下讨论描述了单独行报告和反映批量 I/O 的报告之间的区别。

  MySQL 使用嵌套循环实现执行连接。Performance Schema 检测的工作是为连接中的每个表提供行计数和累积执行时间。假设执行以下形式的连接查询，使用表连接顺序 t1、t2、t3：
  SELECT ... FROM t1 JOIN t2 ON ... JOIN t3 ON ...

  表"扇出"是在连接处理期间添加表时行数的增加或减少。如果表 t3 的扇出大于 1，则大多数行获取操作是针对该表的。假设连接从 t1 访问 10 行，从 t2 每行访问 20 行（来自 t1），从 t3 每行访问 30 行（来自表 t2）。使用单行报告，检测操作的总数为：
  10 + (10 * 20) + (10 * 20 * 30) = 6210

  通过按扫描聚合操作（即，按来自 t1 和 t2 的行的唯一组合），可以实现检测操作数量的显著减少。使用批量 I/O 报告，Performance Schema 为最内层表 t3 的每次扫描而不是每行生成一个事件，检测行操作的数量减少到：
  10 + (10 * 20) + (10 * 20) = 410

  这是 93% 的减少，说明批量报告策略如何通过减少报告调用数量来显著降低表 I/O 的 Performance Schema 开销。权衡是事件计时的准确性较低。与按行报告中的单个行操作的时间不同，批量 I/O 的计时包括用于连接缓冲、聚合和向客户端返回行等操作的时间。

  要进行批量 I/O 报告，必须满足以下条件：

  - 查询执行访问查询块的最内层表（对于单表查询，该表计为最内层）

  - 查询执行不请求表中的单行（例如，eq_ref 访问阻止使用批量报告）

  - 查询执行不评估包含表访问的子查询

- **FLAGS**

  保留供将来使用。

events_waits_current 表具有以下索引：

- (THREAD_ID, EVENT_ID) 上的主键

events_waits_current 表允许 TRUNCATE TABLE。它删除行。
