### 17.6.1.6 InnoDB 中的 AUTO_INCREMENT 处理

InnoDB 提供了一种可配置的锁定机制，可以显著提高向具有 AUTO_INCREMENT 列的表中添加行的 SQL 语句的可扩展性和性能。要在 InnoDB 表中使用 AUTO_INCREMENT 机制，必须将 AUTO_INCREMENT 列定义为某个索引的第一列或唯一列，以便可以在表上执行等效的索引 SELECT MAX(ai_col) 查找来获取最大列值。该索引不需要是 PRIMARY KEY 或 UNIQUE，但为了避免 AUTO_INCREMENT 列中出现重复值，建议使用这些索引类型。

本节描述 AUTO_INCREMENT 锁定模式、不同 AUTO_INCREMENT 锁定模式设置的使用含义，以及 InnoDB 如何初始化 AUTO_INCREMENT 计数器。

InnoDB AUTO_INCREMENT 锁定模式

本节描述用于生成自增值的 AUTO_INCREMENT 锁定模式，以及每种锁定模式如何影响复制。自增锁定模式在启动时使用 innodb_autoinc_lock_mode 变量进行配置。

以下术语用于描述 innodb_autoinc_lock_mode 设置：

- "INSERT-like" 语句

所有在表中生成新行的语句，包括 INSERT、INSERT ... SELECT、REPLACE、REPLACE ... SELECT 和 LOAD DATA。包括"简单插入"、"批量插入"和"混合模式"插入。

- "简单插入"

可以提前确定要插入的行数的语句（在最初处理语句时）。这包括不具有嵌套子查询的单行和多行 INSERT 和 REPLACE 语句，但不包括 INSERT ... ON DUPLICATE KEY UPDATE。

- "批量插入"

要插入的行数（以及所需的自增值数）事先不知道的语句。这包括 INSERT ... SELECT、REPLACE ... SELECT 和 LOAD DATA 语句，但不包括普通 INSERT。InnoDB 在处理每一行时一次为 AUTO_INCREMENT 列分配一个新值。

- "混合模式"插入

这些是"简单插入"语句，为某些（但不是全部）新行指定自增值。以下是一个示例，其中 c1 是表 t1 的 AUTO_INCREMENT 列：
INSERT INTO t1 (c1,c2) VALUES (1,'a'), (NULL,'b'), (5,'c'), (NULL,'d');

另一种"混合模式"插入是 INSERT ... ON DUPLICATE KEY UPDATE，在最坏的情况下实际上是 INSERT 后跟 UPDATE，其中为 AUTO_INCREMENT 列分配的值在更新阶段可能被使用也可能不被使用。

innodb_autoinc_lock_mode 变量有三种可能的设置。设置为 0、1 或 2，分别对应"传统"、"连续"或"交错"锁定模式。交错锁定模式（innodb_autoinc_lock_mode=2）是默认值。

MySQL 26.10 中交错锁定模式的默认设置反映了从基于语句的复制到基于行的复制作为默认复制类型的转变。基于语句的复制需要连续自增锁定模式，以确保对于给定的 SQL 语句序列，自增值以可预测和可重复的顺序分配，而基于行的复制对 SQL 语句的执行顺序不敏感。

- innodb_autoinc_lock_mode = 0（"传统"锁定模式）

传统锁定模式提供了在引入 innodb_autoinc_lock_mode 变量之前存在的相同行为。提供传统锁定模式选项是为了向后兼容、性能测试以及解决"混合模式"插入的问题，因为可能存在语义差异。

在此锁定模式下，所有"INSERT-like"语句都获得一个特殊的表级 AUTO-INC 锁，用于插入具有 AUTO_INCREMENT 列的表。此锁通常保持到语句结束（而不是事务结束），以确保对于给定的 INSERT 语句序列，自增值以可预测和可重复的顺序分配，并确保任何给定语句分配的自增值是连续的。

在基于语句的复制的情况下，这意味着当 SQL 语句在副本服务器上复制时，为自增列使用的值与源服务器上的值相同。多个 INSERT 语句执行的结果是确定性的，副本复制与源相同的数据。如果由多个 INSERT 语句生成的自增值是交错的，两个并发 INSERT 语句的结果将是非确定性的，无法使用基于语句的复制可靠地传播到副本服务器。

为了说明这一点，请考虑使用此表的示例：
CREATE TABLE t1 (
  c1 INT(11) NOT NULL AUTO_INCREMENT,
  c2 VARCHAR(10) DEFAULT NULL,
  PRIMARY KEY (c1)
) ENGINE=InnoDB;

假设有两个事务在运行，每个都向具有 AUTO_INCREMENT 列的表中插入行。一个事务使用 INSERT ... SELECT 语句插入 1000 行，另一个使用简单 INSERT 语句插入一行：
Tx1: INSERT INTO t1 (c2) SELECT 1000 rows from another table ...
Tx2: INSERT INTO t1 (c2) VALUES ('xxx');

InnoDB 无法提前判断从 Tx1 中 INSERT 语句的 SELECT 检索多少行，它在语句进行时一次为自增值分配一个。使用表级锁，保持到语句结束，一次只能执行一个引用表 t1 的 INSERT 语句，不同语句生成的自增数不会交错。Tx1 INSERT ... SELECT 语句生成的自增值是连续的，INSERT 语句在 Tx2 中使用的（单个）自增值要么小于要么大于 Tx1 使用的所有值，取决于哪个语句先执行。

只要 SQL 语句在从二进制日志重放时以相同的顺序执行（使用基于语句的复制时，或在恢复场景中），结果与 Tx1 和 Tx2 首次运行时的结果相同。因此，保持到语句结束的表级锁使使用自增的 INSERT 语句对基于语句的复制是安全的。但是，当多个事务同时执行插入语句时，这些表级锁限制了并发性和可扩展性。

在前面的示例中，如果没有表级锁，Tx2 中 INSERT 使用的自增列值取决于语句执行的确切时间。如果 Tx2 的 INSERT 在 Tx1 的 INSERT 运行时执行（而不是在它开始之前或完成之后），两个 INSERT 语句分配的特定自增值是非确定性的，可能因运行而异。

在连续锁定模式下，InnoDB 可以避免为"简单插入"语句使用表级 AUTO-INC 锁，其中行数事先已知，同时仍保持确定性执行和基于语句的复制的安全性。

如果不使用二进制日志重放 SQL 语句作为恢复或复制的一部分，可以使用交错锁定模式来消除所有表级 AUTO-INC 锁的使用，以获得更大的并发性和性能，代价是允许语句分配的自增数中出现间隙，并可能有并发执行语句分配的数交错。

- innodb_autoinc_lock_mode = 1（"连续"锁定模式）

在此模式下，"批量插入"使用特殊的 AUTO-INC 表级锁并保持到语句结束。这适用于所有 INSERT ... SELECT、REPLACE ... SELECT 和 LOAD DATA 语句。一次只能执行一个持有 AUTO-INC 锁的语句。如果批量插入操作的源表与目标表不同，则在从源表选择的第一行上获取共享锁后，在目标表上获取 AUTO-INC 锁。如果批量插入操作的源和目标是同一个表，则在对所有选定行获取共享锁后获取 AUTO-INC 锁。

"简单插入"（要插入的行数事先已知）通过在互斥锁（轻量级锁）的控制下获取所需数量的自增值来避免表级 AUTO-INC 锁，该互斥锁仅在分配过程期间保持，而不是直到语句完成。除非另一个事务持有 AUTO-INC 锁，否则不使用表级 AUTO-INC 锁。如果另一个事务持有 AUTO-INC 锁，"简单插入"等待 AUTO-INC 锁，就像它是"批量插入"一样。

此锁定模式确保，在存在 INSERT 语句的情况下，其中行数事先不知道（并且自增数在语句进行时分配），任何"INSERT-like"语句分配的所有自增值都是连续的，操作对基于语句的复制是安全的。

简而言之，此锁定模式显著提高了可扩展性，同时对基于语句的复制是安全的。此外，与"传统"锁定模式一样，任何给定语句分配的自增数是连续的。与"传统"模式相比，对于任何使用自增的语句，语义没有变化，除了一个重要的例外。

例外是"混合模式"插入，其中用户为多行"简单插入"中的某些（但不是全部）行的 AUTO_INCREMENT 列提供显式值。对于这样的插入，InnoDB 分配的自增值比要插入的行数多。但是，所有自动分配的值都是连续生成的（因此高于）最近执行的前一个语句生成的自增值。"多余"数字会丢失。

- innodb_autoinc_lock_mode = 2（"交错"锁定模式）

在此锁定模式下，没有"INSERT-like"语句使用表级 AUTO-INC 锁，多个语句可以同时执行。这是最快和最可扩展的锁定模式，但在使用基于语句的复制或恢复场景时不安全，此时 SQL 语句从二进制日志重放。

在此锁定模式下，自增值保证在所有并发执行的"INSERT-like"语句中是唯一的且单调递增的。但是，因为多个语句可以同时生成数字（即，数字的分配在语句之间交错），为任何给定语句插入的行生成的值可能不是连续的。

如果唯一执行的语句是"简单插入"，其中要插入的行数事先已知，则为单个语句生成的数字中没有间隙，除了"混合模式"插入。但是，当执行"批量插入"时，任何给定语句分配的自增值中可能存在间隙。

InnoDB AUTO_INCREMENT 锁定模式使用含义

- 将自增与复制一起使用

如果使用基于语句的复制，将 innodb_autoinc_lock_mode 设置为 0 或 1，并在源和其副本上使用相同的值。如果使用 innodb_autoinc_lock_mode = 2（"交错"）或源和副本不使用相同锁定模式的配置，则不能保证副本上的自增值与源上的相同。

如果使用基于行的或混合格式复制，所有自增锁定模式都是安全的，因为基于行的复制对 SQL 语句的执行顺序不敏感（混合格式对任何对基于语句的复制不安全的语句使用基于行的复制）。

- "丢失"的自增值和序列间隙

在所有锁定模式（0、1 和 2）中，如果生成自增值的事务回滚，这些自增值会"丢失"。一旦为自增列生成值，就无法回滚，无论"INSERT-like"语句是否完成，也无论包含的事务是否回滚。这样丢失的值不会被重用。因此，表的 AUTO_INCREMENT 列中存储的值可能存在间隙。

意外的服务器退出也可能导致 InnoDB 为持久 AUTO_INCREMENT 计数器存储保留的未使用值丢失。与回滚相关的间隙不同，这种类型的间隙可能发生在服务器退出时没有活跃事务使用的表上。间隙的最大大小由 innodb_autoinc_preallocate 系统变量控制。

- 为 AUTO_INCREMENT 列指定 NULL 或 0

在所有锁定模式（0、1 和 2）中，如果用户在 INSERT 中为 AUTO_INCREMENT 列指定 NULL 或 0，InnoDB 将该行视为未指定该值，并为其生成新值。

- 为 AUTO_INCREMENT 列分配负值

在所有锁定模式（0、1 和 2）中，如果为 AUTO_INCREMENT 列分配负值，自增机制的行为是未定义的。

- 如果 AUTO_INCREMENT 值变得大于指定整数类型的最大整数

在所有锁定模式（0、1 和 2）中，如果值变得大于可以存储在指定整数类型中的最大整数，自增机制的行为是未定义的。

- "批量插入"中的自增值间隙

将 innodb_autoinc_lock_mode 设置为 0（"传统"）或 1（"连续"）时，任何给定语句生成的自增值是连续的，没有间隙，因为表级 AUTO-INC 锁保持到语句结束，一次只能执行一个这样的语句。

将 innodb_autoinc_lock_mode 设置为 2（"交错"）时，"批量插入"生成的自增值中可能存在间隙，但仅当存在并发执行的"INSERT-like"语句时。

对于锁定模式 1 或 2，连续语句之间可能出现间隙，因为对于批量插入，每个语句所需的自增值的确切数量可能不知道，过度估计是可能的。

- "混合模式"插入分配的自增值

考虑"混合模式"插入，其中"简单插入"为某些（但不是全部）结果行指定自增值。这样的语句在锁定模式 0、1 和 2 中的行为不同。例如，假设 c1 是表 t1 的 AUTO_INCREMENT 列，最近自动生成的序列号是 100。
mysql> CREATE TABLE t1 (
    -> c1 INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    -> c2 CHAR(1)
    -> ) ENGINE = INNODB;

现在，考虑以下"混合模式"插入语句：
mysql> INSERT INTO t1 (c1,c2) VALUES (1,'a'), (NULL,'b'), (5,'c'), (NULL,'d');

将 innodb_autoinc_lock_mode 设置为 0（"传统"）时，四个新行是：
mysql> SELECT c1, c2 FROM t1 ORDER BY c2;
+-----+------+
| c1 | c2    |
+-----+------+
|   1 | a    |
| 101 | b    |
|   5 | c    |
| 102 | d    |
+-----+------+

下一个可用的自增值是 103，因为自增值一次分配一个，而不是在语句执行开始时全部分配。无论是否存在并发执行的"INSERT-like"语句（任何类型），此结果都是真实的。

将 innodb_autoinc_lock_mode 设置为 1（"连续"）时，四个新行也是：
mysql> SELECT c1, c2 FROM t1 ORDER BY c2;
+-----+------+
| c1 | c2    |
+-----+------+
|   1 | a    |
| 101 | b    |
|   5 | c    |
| 102 | d    |
+-----+------+

但是，在这种情况下，下一个可用的自增值是 105，而不是 103，因为在处理语句时分配了四个自增值，但只使用了两个。无论是否存在并发执行的"INSERT-like"语句（任何类型），此结果都是真实的。

将 innodb_autoinc_lock_mode 设置为 2（"交错"）时，四个新行是：
mysql> SELECT c1, c2 FROM t1 ORDER BY c2;
+-----+------+
| c1 | c2    |
+-----+------+
|   1 | a    |
|   x | b    |
|   5 | c    |
|   y | d    |
+-----+------+

x 和 y 的值是唯一的且大于任何先前生成的行。但是，x 和 y 的具体值取决于并发执行的语句生成的自增值数。

最后，考虑以下语句，在最近生成的序列号为 100 时发出：
mysql> INSERT INTO t1 (c1,c2) VALUES (1,'a'), (NULL,'b'), (101,'c'), (NULL,'d');

对于任何 innodb_autoinc_lock_mode 设置，此语句生成重复键错误 23000（Can't write; duplicate key in table），因为 101 为行 (NULL, 'b') 分配，插入行 (101, 'c') 失败。

- 在 INSERT 语句序列中间修改 AUTO_INCREMENT 列值

如果将 AUTO_INCREMENT 列值修改为大于当前最大自增值的值，新值会被持久化，后续 INSERT 操作从新的更大值开始分配自增值。以下示例演示了此行为：
mysql> CREATE TABLE t1 (
    -> c1 INT NOT NULL AUTO_INCREMENT,
    -> PRIMARY KEY (c1)
    -> ) ENGINE = InnoDB;

mysql> INSERT INTO t1 VALUES(0), (0), (3);

mysql> SELECT c1 FROM t1;
+----+
| c1 |
+----+
| 1 |
| 2 |
| 3 |
+----+

mysql> UPDATE t1 SET c1 = 4 WHERE c1 = 1;

mysql> SELECT c1 FROM t1;
+----+
| c1 |
+----+
| 2 |
| 3 |
| 4 |
+----+

mysql> INSERT INTO t1 VALUES(0);

mysql> SELECT c1 FROM t1;
+----+
| c1 |
+----+
| 2 |
| 3 |
| 4 |
| 5 |
+----+

InnoDB AUTO_INCREMENT 计数器初始化

本节描述 InnoDB 如何初始化 AUTO_INCREMENT 计数器。

如果为 InnoDB 表指定 AUTO_INCREMENT 列，内存中的表对象包含一个称为自增计数器的特殊计数器，在为列分配新值时使用。

InnoDB 以批处理方式在数据字典中持久化自增计数器。当计数器超过先前持久化的值时，InnoDB 持久化当前值加上由 innodb_autoinc_preallocate 系统变量配置的值数。更大的设置减少了持久元数据更新的频率。

在正常关闭后的服务器重启时，InnoDB 使用存储在数据字典中的当前最大自增值初始化内存中的自增计数器。

在完成由 SHUTDOWN 命令启动的正常关闭之前，InnoDB 持久化当前计数器值。因此，无论 innodb_fast_shutdown 设置如何，预分配不会在正常关闭后导致间隙。

在崩溃恢复期间的服务器重启时，InnoDB 使用存储在数据字典中的值初始化内存中的自增计数器。如果在持久化值包含未使用的预分配值时发生意外退出，这些值在重启后会被跳过。使用 innodb_autoinc_preallocate=N 和 auto_increment_increment=Y，产生的间隙不大于 max(N,Y)。将 innodb_autoinc_preallocate 设置为 0 可防止由此预分配机制导致的间隙。对于占用不超过两个字节的 AUTO_INCREMENT 整数列，预分配也被禁用。

InnoDB 使用等效于 SELECT MAX(ai_col) FROM table_name FOR UPDATE 语句初始化自增计数器的唯一情况是导入没有 .cfg 元数据文件的表。否则，如果存在 .cfg 元数据文件，则从该文件读取当前最大自增计数器值。除了计数器值初始化外，等效于 SELECT MAX(ai_col) FROM table_name 语句用于确定表的当前最大自增计数器值，当尝试使用 ALTER TABLE ... AUTO_INCREMENT = N 语句将计数器值设置为小于或等于持久化计数器值的值时。例如，删除某些记录后，可能尝试将计数器值设置为较小的值。在这种情况下，必须搜索表以确保新计数器值不小于或等于实际当前最大计数器值。

服务器重启不会取消 AUTO_INCREMENT = N 表选项的效果。如果将自增计数器初始化为特定值，或者将自增计数器值更改为更大的值，新值会在服务器重启后持久化。

注意

ALTER TABLE ... AUTO_INCREMENT = N 只能将自增计数器值更改为大于当前最大值的值。

当前最大自增值被持久化，防止先前分配的值被重用。

如果 SHOW TABLE STATUS 语句在自增计数器初始化之前检查表，InnoDB 打开表并使用存储在数据字典中的当前最大自增值初始化计数器值。该值随后存储在内存中供后续插入或更新使用。计数器值的初始化使用对表的普通排他锁定读，持续到事务结束。当初始化新创建的表的自增计数器时，如果用户指定的自增值大于 0，InnoDB 遵循相同的过程。

自增计数器初始化后，如果在插入行时不显式指定自增值，InnoDB 隐式增加计数器并将新值分配给列。如果插入显式指定自增列值的行，且该值大于当前最大计数器值，计数器设置为指定的值。

InnoDB 在服务器运行时使用内存中的自增计数器。当服务器停止并重启时，InnoDB 重新初始化自增计数器，如前所述。

auto_increment_offset 变量确定 AUTO_INCREMENT 列值的起点。默认设置是 1。

auto_increment_increment 变量控制连续列值之间的间隔。默认设置是 1。

## 17.6.1.6 InnoDB 中的 AUTO_INCREMENT 处理

注意

当 AUTO_INCREMENT 整数列用尽值时，后续的 INSERT 操作会返回重复键错误。这是 MySQL 的通用行为。
