### 17.6.3.2 File-Per-Table Tablespaces

File-per-table tablespace 包含单个 InnoDB 表的数据和索引，并以单个数据文件的形式存储在文件系统中。

File-per-table tablespace 的特性在本节的以下主题中描述：

- File-Per-Table Tablespace Configuration

- File-Per-Table Tablespace Data Files

- File-Per-Table Tablespace Advantages

- File-Per-Table Tablespace Disadvantages

#### File-Per-Table Tablespace Configuration

InnoDB 默认在 file-per-table tablespace 中创建表。此行为由 innodb_file_per_table 变量控制。禁用 innodb_file_per_table 会导致 InnoDB 在系统 tablespace 中创建表。

innodb_file_per_table 设置可以在选项文件中指定，或在运行时使用 SET GLOBAL 语句进行配置。在运行时更改设置需要足够的权限来设置全局系统变量。请参见第 7.1.9.1 节"System Variable Privileges"。

选项文件：

```
[mysqld]
innodb_file_per_table=ON
```

在运行时使用 SET GLOBAL：

```
mysql> SET GLOBAL innodb_file_per_table=ON;
```

#### File-Per-Table Tablespace Data Files

File-per-table tablespace 在 MySQL 数据目录下的模式目录中以 .ibd 数据文件的形式创建。.ibd 文件以表名命名（table_name.ibd）。例如，表 test.t1 的数据文件在 MySQL 数据目录下的 test 目录中创建：

```
mysql> USE test;

mysql> CREATE TABLE t1 (
    ->     id INT PRIMARY KEY AUTO_INCREMENT,
    ->     name VARCHAR(100)
    ->     ) ENGINE = InnoDB;

mysql> EXIT;

$> cd /path/to/mysql/data/test
$> ls
t1.ibd
```

您可以使用 CREATE TABLE 语句的 DATA DIRECTORY 子句隐式创建 file-per-table tablespace 数据文件，该文件位于数据目录之外。有关更多信息，请参见第 17.6.1.2 节"Creating Tables Externally"。

#### File-Per-Table Tablespace Advantages

与共享 tablespace（如系统 tablespace 或通用 tablespace）相比，file-per-table tablespace 具有以下优势。

- 截断或删除在 file-per-table tablespace 中创建的表后，磁盘空间会返回给操作系统。截断或删除存储在共享 tablespace 中的表会在共享 tablespace 数据文件中创建可用空间，该空间只能用于 InnoDB 数据。换句话说，截断或删除表后，共享 tablespace 数据文件的大小不会缩小。

- 对驻留在共享 tablespace 中的表执行表复制 ALTER TABLE 操作可能会增加 tablespace 占用的磁盘空间量。此类操作可能需要与表中的数据加索引一样多的额外空间。对于 file-per-table tablespace，此空间不会像返回给操作系统那样被释放。

- 在驻留于 file-per-table tablespace 中的表上执行 TRUNCATE TABLE 时性能更好。

- File-per-table tablespace 数据文件可以在单独的存储设备上创建，用于 I/O 优化、空间管理或备份目的。请参见第 17.6.1.2 节"Creating Tables Externally"。

- 您可以从另一个 MySQL 实例导入驻留在 file-per-table tablespace 中的表。请参见第 17.6.1.3 节"Importing InnoDB Tables"。

- 在 file-per-table tablespace 中创建的表支持与 DYNAMIC 和 COMPRESSED 行格式相关的功能，系统 tablespace 不支持这些功能。请参见第 17.10 节"InnoDB Row Formats"。

- 存储在单个 tablespace 数据文件中的表在发生数据损坏、备份或二进制日志不可用或 MySQL 服务器实例无法重启时，可以节省恢复时间并提高成功恢复的机会。

- 在 file-per-table tablespace 中创建的表可以使用 MySQL Enterprise Backup 快速备份或恢复，而不会中断其他 InnoDB 表的使用。这对于备份计划不同或需要较少频繁备份的表很有益处。有关详细信息，请参见 Making a Partial Backup。

- File-per-table tablespace 允许通过监控 tablespace 数据文件的大小来监控文件系统上的表大小。

- 当 innodb_flush_method 设置为 O_DIRECT 时，常见的 Linux 文件系统不允许对单个文件（如共享 tablespace 数据文件）进行并发写入。因此，在结合此设置使用 file-per-table tablespace 时，可能会获得性能改进。

- 共享 tablespace 中的表受到 64TB tablespace 大小限制的限制。相比之下，每个 file-per-table tablespace 都有 64TB 的大小限制，为单个表的增长提供了充足的空间。

#### File-Per-Table Tablespace Disadvantages

与共享 tablespace（如系统 tablespace 或通用 tablespace）相比，file-per-table tablespace 具有以下劣势。

- 使用 file-per-table tablespace，每个表可能有未使用的空间，该空间只能由同一表的行利用，如果管理不当，可能导致空间浪费。

- fsync 操作在多个 file-per-table 数据文件上执行，而不是在单个共享 tablespace 数据文件上执行。由于 fsync 操作是按文件进行的，多个表的写入操作无法合并，这可能导致 fsync 操作总数增加。

- 如果 file-per-table tablespace 中有许多表，mysqld 必须为每个 file-per-table tablespace 保持一个打开的文件句柄，这可能会影响性能。

- 当每个表都有自己的数据文件时，需要更多的文件描述符。

- 可能会出现更多碎片，这可能会阻碍 DROP TABLE 和表扫描性能。但是，如果碎片得到管理，file-per-table tablespace 可以改进这些操作的性能。

- 删除驻留在 file-per-table tablespace 中的表时会扫描缓冲池，对于大型缓冲池，这可能需要几秒钟。扫描使用广泛的内部锁执行，这可能会延迟其他操作。

- innodb_autoextend_increment 变量定义了当自动扩展的共享 tablespace 文件满时扩展其大小的增量，不适用于 file-per-table tablespace 文件，后者无论 innodb_autoextend_increment 设置如何都会自动扩展。初始 file-per-table tablespace 扩展量较小，之后扩展以 4MB 的增量进行。
