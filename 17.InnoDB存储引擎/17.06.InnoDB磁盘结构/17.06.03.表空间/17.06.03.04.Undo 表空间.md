### 17.6.3.4 撤销表空间

撤销表空间包含撤销日志，这是包含有关如何撤销事务对聚集索引记录所做最新更改的信息的记录集合。

撤销表空间在本节的以下主题中进行了描述：

- 默认撤销表空间

- 撤销表空间大小

- 添加撤销表空间

- 撤销表空间创建恢复

- 删除撤销表空间

- 移动撤销表空间

- 配置回滚段数量

- 截断撤销表空间

#### 默认撤销表空间

当 MySQL 实例初始化时，会创建两个默认撤销表空间。默认撤销表空间在初始化时创建，以为必须存在的回滚段提供位置，然后才能接受 SQL 语句。支持撤销表空间的自动截断需要至少两个撤销表空间。请参阅截断撤销表空间。

默认撤销表空间在 innodb_undo_directory 变量定义的位置创建。如果 innodb_undo_directory 变量未定义，默认撤销表空间在数据目录中创建。默认撤销表空间数据文件命名为 undo_001 和 undo_002。在数据字典中定义的对应撤销表空间名称为 innodb_undo_001 和 innodb_undo_002。

可以在运行时使用 SQL 语句创建其他撤销表空间。请参阅添加撤销表空间。

> **重要**
>
> 不要从文件系统中删除隐式创建的撤销表空间文件。初始化后必须至少保留一个活跃的撤销表空间可用，以便 InnoDB 在撤销表空间恢复期间更新数据字典。如果在启动时未找到撤销表空间，服务器报告 No undo tablespaces found. Can not continue operation. 并且启动无法继续。

#### 撤销表空间大小

初始撤销表空间大小通常为 16MiB。当通过截断操作创建新撤销表空间时，初始大小可能会有所不同。在这种情况下，如果文件扩展大小大于 16MB，且上一次文件扩展发生在最后一秒内，新撤销表空间将以 innodb_max_undo_log_size 变量定义的大小的四分之一创建。

撤销表空间至少扩展 16MB。为了处理激进的增长，如果上一次文件扩展发生在少于 0.1 秒前，文件扩展大小会翻倍。扩展大小的翻倍可以发生多次，最大为 256MB。如果上一次文件扩展发生在超过 0.1 秒前，扩展大小会减半，这也可以发生多次，最小为 16MB。如果为撤销表空间定义了 AUTOEXTEND_SIZE 选项，它将按 AUTOEXTEND_SIZE 设置和上述逻辑确定的扩展大小中的较大值进行扩展。有关 AUTOEXTEND_SIZE 选项的信息，请参阅第 17.6.3.9 节"表空间 AUTOEXTEND_SIZE 配置"。

#### 添加撤销表空间

由于撤销日志在长时间运行的事务期间可能会变得很大，创建其他撤销表空间可以帮助防止单个撤销表空间变得过大。可以在运行时使用 CREATE UNDO TABLESPACE 语法创建其他撤销表空间。

```
CREATE UNDO TABLESPACE tablespace_name ADD DATAFILE 'file_name.ibu';
```

撤销表空间文件名必须具有 .ibu 扩展名。定义撤销表空间文件名时不允许指定相对路径。允许使用完全限定路径，但路径必须为 InnoDB 所知。已知路径是由 innodb_directories 变量定义的路径。建议使用唯一的撤销表空间文件名，以避免在移动或克隆数据时可能出现的文件名冲突。

> **注意**
>
> 在复制环境中，源和每个副本必须有自己的撤销表空间文件目录。将撤销表空间文件的创建复制到公共目录会导致文件名冲突。

在启动时，扫描由 innodb_directories 变量定义的目录以查找撤销表空间文件。（扫描也会遍历子目录。）由 innodb_data_home_dir、innodb_undo_directory 和 datadir 变量定义的目录会自动附加到 innodb_directories 值，无论是否显式定义了 innodb_directories 变量。因此，撤销表空间可以驻留在由这些变量中的任何一个定义的路径中。

如果撤销表空间文件名不包括路径，撤销表空间将在由 innodb_undo_directory 变量定义的目录中创建。如果该变量未定义，撤销表空间将在数据目录中创建。

> **注意**
>
> InnoDB 恢复过程在重做恢复之前和打开其他数据文件之前扫描已知目录以查找撤销表空间文件。如果在已知目录中找不到在数据字典中记录的撤销表空间，InnoDB 会自动重新创建它。重新创建的撤销表空间被分配一个新的空间 ID，必须在数据字典中记录。因此，恢复期间必须至少保留一个活跃的撤销表空间可用。已知目录要求也支持撤销表空间可移植性。请参阅移动撤销表空间。

要在相对于数据目录的路径中创建撤销表空间，请将 innodb_undo_directory 变量设置为相对路径，并在创建撤销表空间时仅指定文件名。

要查看撤销表空间名称和路径，请查询 INFORMATION_SCHEMA.FILES：

```
SELECT TABLESPACE_NAME, FILE_NAME FROM INFORMATION_SCHEMA.FILES
  WHERE FILE_TYPE LIKE 'UNDO LOG';
```

MySQL 实例支持最多 127 个撤销表空间，包括 MySQL 实例初始化时创建的两个默认撤销表空间。

可以使用 DROP UNDO TABLESPACE 语法删除撤销表空间。请参阅删除撤销表空间。

#### 撤销表空间创建恢复

撤销表空间创建是崩溃安全的。在 CREATE UNDO TABLESPACE 操作期间，InnoDB 在初始化回滚段时在表空间文件头中将新撤销表空间标记为不可用。初始化完成时清除不可用标志。

在创建撤销表空间文件之前，InnoDB 写入一个 DDL 日志条目，如果 DDL 事务未提交，则请求删除该文件。如果服务器在创建文件之后但在新撤销表空间记录到数据字典之前退出，恢复会重放 DDL 日志条目并删除该文件。如果恢复发现在数据字典中记录的撤销表空间的文件头仍标记为不可用，它会删除并重新创建撤销表空间。CREATE UNDO TABLESPACE 不创建本地 undo_space_number_trunc.log 文件。

#### 删除撤销表空间

使用 CREATE UNDO TABLESPACE 语法创建的撤销表空间可以在运行时使用 DROP UNDO TABLESPACE 语法删除。

撤销表空间必须为空才能删除。要清空撤销表空间，必须首先使用 ALTER UNDO TABLESPACE 语法将撤销表空间标记为不活跃，以便表空间不再用于为新事务分配回滚段。

```
ALTER UNDO TABLESPACE tablespace_name SET INACTIVE;
```

撤销表空间标记为不活跃后，当前使用撤销表空间中回滚段的事务被允许完成，以及在这些事务完成之前启动的任何事务也被允许完成。事务完成后，清除系统释放撤销表空间中的回滚段，撤销表空间被截断到其初始大小。（截断撤销表空间时使用相同的过程。请参阅截断撤销表空间。）撤销表空间为空后，可以删除它。

```
DROP UNDO TABLESPACE tablespace_name;
```

> **注意**
>
> 或者，撤销表空间可以保持为空状态，稍后如果需要，可以通过发出 ALTER UNDO TABLESPACE tablespace_name SET ACTIVE 语句来重新激活。

撤销表空间的状态可以通过查询信息架构 INNODB_TABLESPACES 表来监控。

```
SELECT NAME, STATE FROM INFORMATION_SCHEMA.INNODB_TABLESPACES
  WHERE NAME LIKE 'tablespace_name';
```

不活跃状态表示撤销表空间中的回滚段不再被新事务使用。空状态表示撤销表空间为空且准备好被删除，或准备好使用 ALTER UNDO TABLESPACE tablespace_name SET ACTIVE 语句再次激活。尝试删除不为空的撤销表空间会返回错误。

MySQL 实例初始化时创建的默认撤销表空间（innodb_undo_001 和 innodb_undo_002）无法删除。但是，可以使用 ALTER UNDO TABLESPACE tablespace_name SET INACTIVE 语句将其设置为不活跃。在默认撤销表空间可以设置为不活跃之前，必须有一个撤销表空间来替代它。支持撤销表空间的自动截断需要始终至少有两个活跃的撤销表空间。

#### 移动撤销表空间

使用 CREATE UNDO TABLESPACE 语法创建的撤销表空间可以在服务器离线时移动到任何已知目录。已知目录是由 innodb_directories 变量定义的目录。由 innodb_data_home_dir、innodb_undo_directory 和 datadir 定义的目录会自动附加到 innodb_directories 值，无论是否显式定义了 innodb_directories 变量。这些目录及其子目录在启动时被扫描以查找撤销表空间文件。移动到这些目录中任何一个的撤销表空间文件在启动时被发现并被假定为已移动的撤销表空间。

移动到 InnoDB 不知道的目录的撤销表空间在启动时不被发现。InnoDB 将表空间视为丢失并自动重新创建它；未知目录中的文件不被使用。要成功移动撤销表空间，请确保目标目录包含在 innodb_directories 中，然后重新启动服务器。

MySQL 实例初始化时创建的默认撤销表空间（innodb_undo_001 和 innodb_undo_002）必须驻留在由 innodb_undo_directory 变量定义的目录中。如果 innodb_undo_directory 变量未定义，默认撤销表空间驻留在数据目录中。如果默认撤销表空间在服务器离线时被移动，服务器必须以 innodb_undo_directory 变量配置为新目录的方式启动。

撤销日志的 I/O 模式使撤销表空间成为 SSD 存储的良好候选。

#### 配置回滚段数量

innodb_rollback_segments 变量定义分配给每个撤销表空间和全局临时表空间的回滚段数量。innodb_rollback_segments 变量可以在启动时或服务器运行时配置。

innodb_rollback_segments 的默认设置为 128，这也是最大值。有关回滚段支持的事务数量的信息，请参阅第 17.6.6 节"撤销日志"。

#### 截断撤销表空间

有两种截断撤销表空间的方法，可以单独使用或结合使用来管理撤销表空间大小。一种方法是自动的，使用配置变量启用。另一种方法是手动的，使用 SQL 语句执行。

自动方法不需要监控撤销表空间大小，一旦启用，它会执行撤销表空间的停用、截断和重新激活，无需手动干预。如果您想控制何时将撤销表空间离线以进行截断，手动截断方法可能更可取。例如，您可能想避免在峰值工作负载时间截断撤销表空间。

##### 自动截断

撤销表空间的自动截断需要至少两个活跃的撤销表空间，这确保一个撤销表空间保持活跃，而另一个被离线以进行截断。默认情况下，MySQL 实例初始化时创建两个撤销表空间。

要自动截断撤销表空间，请启用 innodb_undo_log_truncate 变量。例如：

```
mysql> SET GLOBAL innodb_undo_log_truncate=ON;
```

启用 innodb_undo_log_truncate 变量时，超过由 innodb_max_undo_log_size 变量定义的大小限制的撤销表空间将被截断。innodb_max_undo_log_size 变量是动态的，默认值为 1073741824 字节（1024 MiB）。

```
mysql> SELECT @@innodb_max_undo_log_size;
+----------------------------+
| @@innodb_max_undo_log_size |
+----------------------------+
|                 1073741824 |
+----------------------------+
```

启用 innodb_undo_log_truncate 变量时：

1. 超过 innodb_max_undo_log_size 设置的默认和用户定义的撤销表空间被标记为截断。撤销表空间的选择以循环方式执行，以避免每次都截断相同的撤销表空间。

2. 驻留在所选撤销表空间中的回滚段被设置为不活跃，以便它们不被分配给新事务。当前使用回滚段的现有事务被允许完成。

3. 清除系统通过释放不再使用的撤销日志来清空回滚段。

4. 撤销表空间中的所有回滚段被释放后，截断操作运行并将撤销表空间截断到 16MB。

   innodb_undo_directory 变量定义默认撤销表空间文件的位置。如果 innodb_undo_directory 变量未定义，默认撤销表空间驻留在数据目录中。所有撤销表空间文件（包括使用 CREATE UNDO TABLESPACE 语法创建的用户定义撤销表空间）的位置可以通过查询信息架构 FILES 表来确定：

   ```
   SELECT TABLESPACE_NAME, FILE_NAME FROM INFORMATION_SCHEMA.FILES WHERE FILE_TYPE LIKE 'UNDO LOG';
   ```

5. 回滚段被重新激活，以便可以分配给新事务。

##### 手动截断

撤销表空间的手动截断需要至少三个活跃的撤销表空间。始终需要两个活跃的撤销表空间以支持自动截断可能被启用的可能性。最少三个撤销表空间满足此要求，同时允许一个撤销表空间被手动离线。

要手动启动撤销表空间的截断，通过发出以下语句停用撤销表空间：

```
ALTER UNDO TABLESPACE tablespace_name SET INACTIVE;
```

撤销表空间标记为不活跃后，当前使用撤销表空间中回滚段的事务被允许完成，以及在这些事务完成之前启动的任何事务也被允许完成。事务完成后，清除系统释放撤销表空间中的回滚段，撤销表空间被截断到其初始大小，撤销表空间状态从不活跃变为空。

> **注意**
>
> 当 ALTER UNDO TABLESPACE tablespace_name SET INACTIVE 语句停用撤销表空间时，清除线程在下一个机会查找该撤销表空间。一旦找到撤销表空间并标记为截断，清除线程以增加的频率返回以快速清空和截断撤销表空间。

要检查撤销表空间的状态，请查询信息架构 INNODB_TABLESPACES 表。

```
SELECT NAME, STATE FROM INFORMATION_SCHEMA.INNODB_TABLESPACES
  WHERE NAME LIKE 'tablespace_name';
```

撤销表空间处于空状态后，可以通过发出以下语句重新激活它：

```
ALTER UNDO TABLESPACE tablespace_name SET ACTIVE;
```

处于空状态的撤销表空间也可以被删除。请参阅删除撤销表空间。

##### 加快撤销表空间的自动截断

清除线程负责清空和截断撤销表空间。默认情况下，清除线程每调用清除 128 次时查找一次要截断的撤销表空间。清除线程查找要截断的撤销表空间的频率由 innodb_purge_rseg_truncate_frequency 变量控制，其默认设置为 128。

```
mysql> SELECT @@innodb_purge_rseg_truncate_frequency;
+----------------------------------------+
| @@innodb_purge_rseg_truncate_frequency |
+----------------------------------------+
|                                    128 |
+----------------------------------------+
```

要增加频率，请降低 innodb_purge_rseg_truncate_frequency 设置。例如，要让清除线程每调用清除 32 次时查找一次撤销表空间，请将 innodb_purge_rseg_truncate_frequency 设置为 32。

```
mysql> SET GLOBAL innodb_purge_rseg_truncate_frequency=32;
```

##### 截断撤销表空间文件的性能影响

截断撤销表空间时，撤销表空间中的回滚段被停用。其他撤销表空间中的活跃回滚段承担整个系统负载的责任，这可能导致轻微的性能下降。性能受影响的程度取决于多个因素：

- 撤销表空间数量

- 撤销日志数量

- 撤销表空间大小

- I/O 子系统的速度

- 现有长时间运行的事务

- 系统负载

避免潜在性能影响的最简单方法是增加撤销表空间的数量。

##### 监控撤销表空间截断

为与撤销日志截断相关的后台活动提供了撤销和清除子系统计数器。有关计数器名称和描述，请查询信息架构 INNODB_METRICS 表。

```
SELECT NAME, SUBSYSTEM, COMMENT FROM INFORMATION_SCHEMA.INNODB_METRICS WHERE NAME LIKE '%truncate%';
```

有关启用计数器和查询计数器数据的信息，请参阅第 17.15.6 节"InnoDB INFORMATION_SCHEMA 指标表"。

##### 撤销表空间截断限制

检查点之间对同一撤销表空间的截断操作数限制为 64。该限制防止由过多撤销表空间截断操作引起的潜在问题，例如在繁忙系统上 innodb_max_undo_log_size 设置过低时可能发生的情况。如果超过限制，撤销表空间仍可以设置为不活跃，但在下一个检查点之后才会被截断。在 MySQL 26.10 中，限制为 50000。

##### 撤销表空间截断恢复

撤销表空间截断操作在截断进行时在其文件头中将撤销表空间标记为不可用。截断完成时清除该标志。如果在操作期间发生系统故障，启动检测不可用标志，删除不完整的撤销表空间文件，使用新的空间 ID 重新创建表空间，并更新数据字典。

从 MySQL 26.10 开始，撤销表空间截断不创建 undo_space_number_trunc.log 标记文件。为了向后兼容，启动继续识别由 innodb_log_group_home_dir 定义的服务器日志目录中的旧标记文件。这样的文件可能在由早期服务器版本执行的中断的撤销表空间创建或截断操作后保留。如果对应的撤销表空间在数据字典中记录，InnoDB 会重新创建它；否则，InnoDB 删除撤销表空间文件。恢复成功完成后，旧标记文件被删除。
