### 8.4.1.7 Kerberos 可插拔身份验证

身份验证插件

注意

Kerberos 可插拔身份验证是 MySQL Enterprise Edition（商业产品）中包含的扩展。要了解有关商业产品的更多信息，请参阅 https://www.mysql.com/products/。

MySQL Enterprise Edition 支持一种身份验证方法，使用户能够使用 Kerberos 向 MySQL Server 进行身份验证，前提是适当的 Kerberos 票证可用或可以获得。

此身份验证方法在 MySQL 26.10 中可用于 Linux 上的 MySQL 服务器和客户端。它在应用程序可以访问 Microsoft Active Directory（默认启用 Kerberos）的 Linux 环境中很有用。客户端插件也在 Windows 上受支持。服务器端插件仍然仅在 Linux 上受支持。

注意

MySQL Shell 和 MySQL Router 目前都不支持创建内部管理的 MySQL 账户以用于 Kerberos。但是，MySQL Shell 支持使用 Kerberos 连接到 MySQL Server。MySQL Router 支持使用现有 Kerberos 认证的 MySQL 账户进行引导和元数据访问。MySQL Router 还支持使用 Kerberos 向 MySQL Server 进行身份验证的应用程序连接。

Kerberos 可插拔身份验证提供以下功能：

- 外部身份验证：Kerberos 身份验证使 MySQL Server 能够接受来自在 MySQL 授权表之外定义的用户的连接，这些用户已获得适当的 Kerberos 票证。

- 安全性：Kerberos 使用票证以及对称密钥密码学，实现无需通过网络发送密码的身份验证。Kerberos 身份验证支持无用户和无密码场景。

#### Kerberos 可插拔身份验证的前提条件

要使用 MySQL 的 Kerberos 可插拔身份验证，必须满足以下前提条件：

- Kerberos 服务必须可用，以便 Kerberos 身份验证插件与其通信。

- 要由 MySQL 进行身份验证的每个 Kerberos 用户（主体）必须存在于 KDC 服务器管理的数据库中。

- Kerberos 客户端库必须在使用服务器端或客户端 Kerberos 身份验证插件的系统上可用。此外，GSSAPI 用作访问 Kerberos 身份验证的接口，因此必须有 GSSAPI 库可用。

#### MySQL 用户的 Kerberos 身份验证工作原理

本节概述了 MySQL 和 Kerberos 如何协同工作以对 MySQL 用户进行身份验证。有关显示如何设置 MySQL 账户以使用 Kerberos 身份验证插件的示例，请参阅使用 Kerberos 可插拔身份验证。

这里假设熟悉 Kerberos 概念和操作。以下列表简要定义了几个常见的 Kerberos 术语。您可能还会发现 RFC 4120 的词汇表部分有帮助。

- 主体：一个命名实体，例如用户或服务器。在本讨论中，某些与主体相关的术语经常出现：

  - SPN：服务主体名称；代表服务的主体的名称。

  - UPN：用户主体名称；代表用户的主体的名称。

- KDC：密钥分发中心，包括 AS 和 TGS：

  - AS：身份验证服务器；提供获取其他票证所需的初始票证授予票证。

  - TGS：票证授予服务器；为拥有有效 TGT 的 Kerberos 客户端提供其他票证。

- TGT：票证授予票证；呈现给 TGS 以获取服务票证以进行服务访问。

- ST：服务票证；提供对服务（例如 MySQL 服务器提供的服务）的访问。

使用 Kerberos 进行身份验证需要 KDC 服务器，例如由 Microsoft Active Directory 提供的服务器。

MySQL 中的 Kerberos 身份验证使用通用安全服务应用程序编程接口 (GSSAPI)，这是一个安全抽象接口。Kerberos 是可以通过该抽象接口使用的特定安全协议的实例。使用 GSSAPI，应用程序向 Kerberos 进行身份验证以获取服务凭证，然后依次使用这些凭证来启用对其他服务的安全访问。

在 Windows 上，authentication_kerberos_client 身份验证插件支持两种模式，客户端用户可以在运行时设置或在选项文件中指定：

- SSPI 模式：安全支持提供程序接口 (SSPI) 实现 GSSAPI（请参阅 SSPI 模式下 Windows 客户端的命令）。SSPI 虽然在线路级别与 GSSAPI 兼容，但仅支持 Windows 单点登录场景，特别是指登录的用户。SSPI 是大多数 Windows 客户端上的默认模式。

- GSSAPI 模式：通过 Windows 上的 MIT Kerberos 库支持 GSSAPI（请参阅 GSSAPI 模式下 Windows 客户端的命令）。

使用 Kerberos 身份验证插件，应用程序和 MySQL 服务器能够使用 Kerberos 身份验证协议相互对用户和 MySQL 服务进行身份验证。这样，用户和服务器都能够验证彼此的身份。没有密码通过网络发送，Kerberos 协议消息受到保护，防止窃听和重放攻击。

Kerberos 身份验证遵循以下步骤，其中服务器端和客户端部分分别使用 authentication_kerberos 和 authentication_kerberos_client 身份验证插件执行：

1. MySQL 服务器向客户端应用程序发送其服务主体名称。此 SPN 必须在 Kerberos 系统中注册，并使用 authentication_kerberos_service_principal 系统变量在服务器端配置。

2. 使用 GSSAPI，客户端应用程序创建 Kerberos 客户端身份验证会话并与 Kerberos KDC 交换 Kerberos 消息：

   - 客户端从身份验证服务器获取票证授予票证。

   - 使用 TGT，客户端从票证授予服务获取 MySQL 的服务票证。

   如果 TGT、ST 或两者已在本地缓存，可以跳过此步骤或部分跳过。客户端可以选择使用客户端 keytab 文件来获取 TGT 和 ST，而无需提供密码。

3. 使用 GSSAPI，客户端应用程序向 MySQL 服务器呈现 MySQL ST。

4. 使用 GSSAPI，MySQL 服务器创建 Kerberos 服务器端身份验证会话。服务器验证用户身份和用户请求的有效性。它使用在其服务 keytab 文件中配置的服务密钥对 ST 进行身份验证，以确定身份验证是成功还是失败，并将身份验证结果返回给客户端。

应用程序能够使用提供的用户名和密码进行身份验证，或使用本地缓存的 TGT 或 ST（例如使用 kinit 或类似工具创建的）。因此，此设计涵盖了从完全无用户和无密码连接（其中 Kerberos 服务票证从本地存储的 Kerberos 缓存获得）到提供用户名和密码的连接（用于从 KDC 获取有效的 Kerberos 服务票证以发送到 MySQL 服务器）的用例范围。

如前所述，MySQL Kerberos 身份验证使用两种 keytab 文件：

- 在客户端主机上，客户端 keytab 文件可用于获取 TGT 和 ST，而无需提供密码。请参阅 Kerberos 身份验证的客户端配置参数。

- 在 MySQL 服务器主机上，服务器端服务 keytab 文件用于验证 MySQL 服务器从客户端接收的服务票证。keytab 文件名使用 authentication_kerberos_service_key_tab 系统变量配置。

有关 keytab 文件的信息，请参阅 https://web.mit.edu/kerberos/krb5-latest/doc/basic/keytab_def.html。

#### 安装 Kerberos 可插拔身份验证

本节描述如何安装服务器端 Kerberos 身份验证插件。有关安装插件的一般信息，请参阅第 7.6.1 节"安装和卸载插件"。

注意

服务器端插件仅在 Linux 系统上受支持。在 Windows 系统上，仅支持客户端插件，可在 Windows 系统上用于连接到使用 Kerberos 身份验证的 Linux 服务器。

要被服务器使用，插件库文件必须位于 MySQL 插件目录中（plugin_dir 系统变量命名的目录）。如有必要，通过在服务器启动时设置 plugin_dir 的值来配置插件目录位置。

服务器端插件库文件基本名称是 authentication_kerberos。Unix 和类 Unix 系统的文件名后缀是 .so。

要在服务器启动时加载插件，使用 --plugin-load-add 选项来命名包含它的库文件。使用此插件加载方法，每次服务器启动时都必须给出该选项。此外，为您希望配置的任何插件提供的系统变量指定值。该插件公开这些系统变量，使其操作能够被配置：

- authentication_kerberos_service_principal：MySQL 服务主体名称 (SPN)。此名称发送给尝试使用 Kerberos 进行身份验证的客户端。SPN 必须存在于 KDC 服务器管理的数据库中。默认值是 mysql/host_name@realm_name。

- authentication_kerberos_service_key_tab：用于对从客户端接收的票证进行身份验证的 keytab 文件。此文件必须存在并包含 SPN 的有效密钥，否则客户端身份验证将失败。默认值是数据目录中的 mysql.keytab。

有关所有 Kerberos 身份验证系统变量的详细信息，请参阅第 8.4.1.13 节"可插拔身份验证系统变量"。

要加载和配置插件，请在 my.cnf 文件中放入类似以下的行，使用适合您的安装的系统变量值：

```
[mysqld]
plugin-load-add=authentication_kerberos.so
authentication_kerberos_service_principal=mysql/krbauth.example.com@MYSQL.LOCAL
authentication_kerberos_service_key_tab=/var/mysql/data/mysql.keytab
```

修改 my.cnf 后，重启服务器以使新设置生效。

或者，要在运行时加载插件，使用此语句：

```
INSTALL PLUGIN authentication_kerberos
  SONAME 'authentication_kerberos.so';
```

INSTALL PLUGIN 立即加载插件，并将其注册在 mysql.plugins 系统表中，以使服务器在每次后续正常启动时加载它，而无需 --plugin-load-add。

当您在运行时安装插件而不在 my.cnf 文件中配置其系统变量时，系统变量 authentication_kerberos_service_key_tab 设置为数据目录中 mysql.keytab 的默认值。此系统变量的值无法在运行时更改，因此如果需要指定不同的文件，需要将设置添加到 my.cnf 文件中，然后重启 MySQL 服务器。例如：

```
[mysqld]
authentication_kerberos_service_key_tab=/var/mysql/data/mysql.keytab
```

如果 keytab 文件不在正确的位置或不包含有效的 SPN 密钥，MySQL 服务器不会验证这一点，但客户端会返回身份验证错误，直到您解决问题。

authentication_kerberos_service_principal 系统变量可以在运行时使用 SET PERSIST 语句进行设置和持久化，而无需重启服务器：

```
SET PERSIST authentication_kerberos_service_principal='mysql/krbauth.example.com@MYSQL.LOCAL';
```

SET PERSIST 为运行中的 MySQL 实例设置值。它还保存该值，使其在后续服务器重启时保留。要为运行中的 MySQL 实例更改值而不使其在后续重启时保留，使用 GLOBAL 关键字而不是 PERSIST。请参阅第 15.7.6.1 节"变量赋值的 SET 语法"。

要验证插件安装，检查信息模式 PLUGINS 表或使用 SHOW PLUGINS 语句（请参阅第 7.6.2 节"获取服务器插件信息"）。例如：

```
mysql> SELECT PLUGIN_NAME, PLUGIN_STATUS
       FROM INFORMATION_SCHEMA.PLUGINS
       WHERE PLUGIN_NAME = 'authentication_kerberos';
+-------------------------+---------------+
| PLUGIN_NAME             | PLUGIN_STATUS |
+-------------------------+---------------+
| authentication_kerberos | ACTIVE        |
+-------------------------+---------------+
```

如果插件初始化失败，检查服务器错误日志以获取诊断消息。

要将 MySQL 账户与 Kerberos 插件关联，请参阅使用 Kerberos 可插拔身份验证。

##### 验证 Kerberos 可用性

以下示例显示如何测试 Active Directory 中 Kerberos 的可用性。该示例做出以下假设：

- Active Directory 运行在名为 krbauth.example.com 的主机上，IP 地址为 198.51.100.11。

- MySQL 相关的 Kerberos 身份验证使用 MYSQL.LOCAL 域，并且也使用 MYSQL.LOCAL 作为领域名称。

- 一个名为 karl@MYSQL.LOCAL 的主体已向 KDC 注册。（在后续讨论中，此主体名称与使用 Kerberos 向 MySQL 服务器进行身份验证的 MySQL 账户相关联。）

满足这些假设后，按照以下步骤进行：

1. 验证 Kerberos 库已在操作系统中安装和正确配置。例如，要配置 MYSQL.LOCAL 域和领域以在 MySQL 身份验证期间使用，/etc/krb5.conf Kerberos 配置文件应包含类似以下内容：

   ```
   [realms]
     MYSQL.LOCAL = {
       kdc = krbauth.example.com
       admin_server = krbauth.example.com
       default_domain = MYSQL.LOCAL
     }
   ```

2. 您可能需要为服务器主机添加 /etc/hosts 条目：

   ```
   198.51.100.11 krbauth krbauth.example.com
   ```

3. 检查 Kerberos 身份验证是否正常工作：

   a. 使用 kinit 向 Kerberos 进行身份验证：

      ```
      $> kinit karl@MYSQL.LOCAL
      Password for karl@MYSQL.LOCAL: (enter password here)
      ```

      该命令对名为 karl@MYSQL.LOCAL 的 Kerberos 主体进行身份验证。当命令提示时输入主体的密码。KDC 返回一个 TGT，该 TGT 在客户端缓存以供其他 Kerberos 感知应用程序使用。

   b. 使用 klist 检查 TGT 是否正确获得。输出应类似于以下内容：

      ```
      $> klist
      Ticket cache: FILE:/tmp/krb5cc_244306
      Default principal: karl@MYSQL.LOCAL

      Valid starting         Expires                Service principal
      03/23/2021 08:18:33    03/23/2021 18:18:33    krbtgt/MYSQL.LOCAL@MYSQL.LOCAL
      ```

##### 创建使用 Kerberos 身份验证的 MySQL 账户

使用 authentication_kerberos 身份验证插件的 MySQL 身份验证基于 Kerberos 用户主体名称 (UPN)。这里的说明假设名为 karl 的 MySQL 用户使用 Kerberos 向 MySQL 进行身份验证，Kerberos 领域名为 MYSQL.LOCAL，用户主体名为 karl@MYSQL.LOCAL。此 UPN 必须在多个地方注册：

- Kerberos 管理员应将用户名注册为 Kerberos 主体。此名称包括领域名称。客户端使用主体名称和密码向 Kerberos 进行身份验证并获取票证授予票证 (TGT)。

- MySQL DBA 应创建与 Kerberos 主体名称相对应的账户，并使用 Kerberos 插件进行身份验证。

假设 Kerberos 用户主体名称已由适当的服务管理员注册，并且如前所述在安装 Kerberos 可插拔身份验证中，MySQL 服务器已使用服务器端 Kerberos 插件的适当配置设置启动。要创建与 user@realm_name 的 Kerberos UPN 相对应的 MySQL 账户，MySQL DBA 使用类似以下的语句：

```
CREATE USER user
  IDENTIFIED WITH authentication_kerberos
  BY 'realm_name';
```

由 user 命名的账户可以包括或省略主机名部分。如果省略主机名，它默认为 % 如常。realm_name 作为 mysql.user 系统表中账户的 authentication_string 值存储。

要创建与 UPN karl@MYSQL.LOCAL 相对应的 MySQL 账户，使用此语句：

```
CREATE USER 'karl'
  IDENTIFIED WITH authentication_kerberos
  BY 'MYSQL.LOCAL';
```

如果 MySQL 必须为此账户构造 UPN，例如获取或验证票证（TGT 或 ST），它通过组合账户名称（忽略任何主机名部分）和领域名称来执行此操作。例如，从前面的 CREATE USER 语句产生的完整账户名称是 'karl'@'%'。MySQL 从用户名部分 karl（忽略主机名部分）和领域名称 MYSQL.LOCAL 构造 UPN 以生成 karl@MYSQL.LOCAL。

注意

观察到当创建使用 authentication_kerberos 进行身份验证的账户时，CREATE USER 语句不包括 UPN 领域作为用户名的一部分。相反，在 BY 子句中将领域（本例中为 MYSQL.LOCAL）指定为身份验证字符串。这与创建使用 authentication_ldap_sasl SASL LDAP 身份验证插件与 GSSAPI/Kerberos 身份验证方法的账户不同。对于此类账户，CREATE USER 语句确实包括 UPN 领域作为用户名的一部分。请参阅创建使用 GSSAPI/Kerberos 进行 LDAP 身份验证的 MySQL 账户。

设置账户后，客户端可以使用它连接到 MySQL 服务器。该过程取决于客户端主机运行的是 Linux 还是 Windows，如以下讨论所示。

authentication_kerberos 的使用受到限制，即不支持具有相同用户部分但不同领域部分的 UPN。例如，您不能创建与这两个 UPN 都相对应的 MySQL 账户：

```
kate@MYSQL.LOCAL
kate@EXAMPLE.COM
```

两个 UPN 都有 kate 的用户部分，但在领域部分中不同（MYSQL.LOCAL 对比 EXAMPLE.COM）。这是不允许的。

##### 使用 MySQL 账户连接到 MySQL 服务器

设置使用 Kerberos 进行身份验证的 MySQL 账户后，客户端可以按如下方式使用它连接到 MySQL 服务器：

1. 使用用户主体名称 (UPN) 及其密码向 Kerberos 进行身份验证以获取票证授予票证 (TGT)。

2. 使用 TGT 获取 MySQL 的服务票证 (ST)。

3. 通过呈现 MySQL ST 向 MySQL 服务器进行身份验证。

第一步（向 Kerberos 进行身份验证）可以通过各种方式执行：

- 在连接到 MySQL 之前：

  - 在 Linux 上或在 GSSAPI 模式下的 Windows 上，调用 kinit 以获取 TGT 并将其保存在 Kerberos 凭证缓存中。

  - 在 SSPI 模式下的 Windows 上，身份验证可能已在登录时完成，这将登录用户的 TGT 保存在 Windows 内存中缓存。kinit 不被使用，也没有 Kerberos 缓存。

- 连接到 MySQL 时，客户端程序本身可以获取 TGT，如果它能够确定所需的 Kerberos UPN 和密码：

  - 该信息可以来自命令选项或操作系统等来源。

  - 在 Linux 上，客户端还可以使用 keytab 文件或 /etc/krb5.conf 配置文件。GSSAPI 模式下的 Windows 客户端使用配置文件。SSPI 模式下的 Windows 客户端都不使用。

连接到 MySQL 服务器的客户端命令的详细信息因 Linux 和 Windows 而异，因此每个主机类型都单独讨论，但这些命令属性无论主机类型如何都适用：

- 每个显示的命令包括以下选项，但在某些条件下可以省略每个选项：

- --default-auth 选项指定客户端身份验证插件的名称 (authentication_kerberos_client)。当指定 --user 选项时可以省略此选项，因为在这种情况下 MySQL 可以从 MySQL 服务器发送的用户账户信息确定插件。

- --plugin-dir 选项向客户端程序指示 authentication_kerberos_client 插件的位置。如果插件安装在默认（编译的）位置，可以省略此选项。

- 命令还应包括任何其他选项，例如 --host 或 --port，这些选项是指定要连接到哪个 MySQL 服务器所必需的。

- 在单行上输入每个命令。如果命令包括 --password 选项以请求密码，在提示时输入与 MySQL 用户关联的 Kerberos UPN 的密码。

##### Linux 客户端的连接命令

在 Linux 上，连接到 MySQL 服务器的适当客户端命令取决于命令是使用 Kerberos 缓存中的 TGT 进行身份验证，还是基于 MySQL 用户名和 UPN 密码的命令选项：

- 在调用 MySQL 客户端程序之前，客户端用户可以独立于 MySQL 从 KDC 获取 TGT。例如，客户端用户可以使用 kinit 通过提供 Kerberos 用户主体名称和主体密码向 Kerberos 进行身份验证：

  ```
  $> kinit karl@MYSQL.LOCAL
  Password for karl@MYSQL.LOCAL: (enter password here)
  ```

  UPN 的生成 TGT 被缓存并可供其他 Kerberos 感知应用程序（例如使用客户端 Kerberos 身份验证插件的程序）使用。在这种情况下，调用客户端而不指定用户名或密码选项：

  ```
  mysql
    --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
  ```

  客户端插件在缓存中找到 TGT，使用它获取 MySQL ST，并使用 ST 向 MySQL 服务器进行身份验证。

  如上所述，当 UPN 的 TGT 被缓存时，客户端命令中不需要用户名和密码选项。如果命令包括它们，它们的处理方式如下：

  - 此命令包括用户名选项：

    ```
    mysql
      --default-auth=authentication_kerberos_client
      --plugin-dir=path/to/plugin/directory
      --user=karl
    ```

    在这种情况下，如果选项指定的用户名与 TGT 中 UPN 的用户名部分不匹配，身份验证失败。

  - 此命令包括密码选项，您在提示时输入：

    ```
    mysql
      --default-auth=authentication_kerberos_client
      --plugin-dir=path/to/plugin/directory
      --password
    ```

    在这种情况下，客户端插件忽略密码。因为身份验证基于 TGT，即使用户提供的密码不正确，它也可以成功。因此，如果找到有效的 TGT 导致密码被忽略，插件会产生警告。

- 如果 Kerberos 缓存中不包含 TGT，客户端 Kerberos 认证插件本身可以从 KDC 获取 TGT。使用 MySQL 用户名和密码选项调用客户端，然后在提示时输入 UPN 密码：
  ```
  mysql --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
    --user=karl
    --password
  ```

  客户端 Kerberos 认证插件将用户名 (karl) 和用户账户中指定的领域 (MYSQL.LOCAL) 组合在一起构造 UPN (karl@MYSQL.LOCAL)。客户端插件使用 UPN 和密码获取 TGT，使用 TGT 获取 MySQL ST，并使用 ST 向 MySQL 服务器进行认证。

  或者，假设 Kerberos 缓存中不包含 TGT，且命令指定了密码选项但没有用户名选项：
  ```
  mysql --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
    --password
  ```

  客户端 Kerberos 认证插件使用操作系统登录名作为 MySQL 用户名。它将该用户名和用户 MySQL 账户中的领域组合在一起构造 UPN。客户端插件使用 UPN 和密码获取 TGT，使用 TGT 获取 MySQL ST，并使用 ST 向 MySQL 服务器进行认证。

如果不确定 TGT 是否存在，可以使用 klist 进行检查。

注意

当客户端 Kerberos 认证插件本身获取 TGT 时，客户端用户可能不希望 TGT 被重用。如 Kerberos 认证的客户端配置参数 中所述，可以使用本地 /etc/krb5.conf 文件使客户端插件在完成后销毁 TGT。

## Windows 客户端在 SSPI 模式下的连接命令

在 Windows 上，使用默认客户端插件选项 (SSPI) 时，连接到 MySQL 服务器的适当客户端命令取决于命令是基于 MySQL 用户名和 UPN 密码的命令选项进行认证，还是使用来自 Windows 内存缓存的 TGT。有关 Windows 上 GSSAPI 模式的详细信息，请参见 Windows 客户端在 GSSAPI 模式下的命令。

命令可以显式指定 MySQL 用户名和 UPN 密码的选项，或者命令可以省略这些选项：

- 此命令包含 MySQL 用户名和 UPN 密码的选项：
  ```
  mysql --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
    --user=karl
    --password
  ```

  客户端 Kerberos 认证插件将用户名 (karl) 和用户账户中指定的领域 (MYSQL.LOCAL) 组合在一起构造 UPN (karl@MYSQL.LOCAL)。客户端插件使用 UPN 和密码获取 TGT，使用 TGT 获取 MySQL ST，并使用 ST 向 MySQL 服务器进行认证。

  Windows 内存缓存中的任何信息都被忽略；用户名和密码选项值优先。

- 此命令包含 UPN 密码的选项但不包含 MySQL 用户名的选项：
  ```
  mysql
    --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
    --password
  ```

  客户端 Kerberos 认证插件使用登录用户名作为 MySQL 用户名，并将该用户名和用户 MySQL 账户中的领域组合在一起构造 UPN。客户端插件使用 UPN 和密码获取 TGT，使用 TGT 获取 MySQL ST，并使用 ST 向 MySQL 服务器进行认证。

- 此命令不包含 MySQL 用户名或 UPN 密码的选项：
  ```
  mysql
    --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
  ```

  客户端插件从 Windows 内存缓存获取 TGT，使用 TGT 获取 MySQL ST，并使用 ST 向 MySQL 服务器进行认证。

  此方法要求客户端主机是 Windows Server Active Directory (AD) 域的一部分。如果不是这样，通过手动输入 AD 服务器和领域作为 DNS 服务器和前缀来帮助 MySQL 客户端发现 AD 域的 IP 地址：

  1. 启动 console.exe 并选择"网络和共享中心"。

  2. 从"网络和共享中心"窗口的侧边栏中，选择"更改适配器设置"。

  3. 在"网络连接"窗口中，右键单击要配置的网络或 VPN 连接，然后选择"属性"。

  4. 从"网络"选项卡中，找到并单击"Internet 协议版本 4 (TCP/IPv4)"，然后单击"属性"。

  5. 在"Internet 协议版本 4 (TCP/IPv4) 属性"对话框中单击"高级"。"高级 TCP/IP 设置"对话框打开。

  6. 从"DNS"选项卡中，添加 Active Directory 服务器和领域作为 DNS 服务器和前缀。

- 此命令包含 MySQL 用户名的选项但不包含 UPN 密码的选项：
  ```
  mysql
    --default-auth=authentication_kerberos_client
    --plugin-dir=path/to/plugin/directory
    --user=karl
  ```

  客户端 Kerberos 认证插件将用户名选项指定的名称与登录用户名进行比较。如果名称相同，插件使用登录用户 TGT 进行认证。如果名称不同，认证失败。

## Windows 客户端在 GSSAPI 模式下的连接命令

在 Windows 上，客户端用户必须使用 plugin_authentication_kerberos_client_mode 插件选项显式指定 GSSAPI 模式以启用通过 MIT Kerberos 库的支持。默认模式是 SSPI（请参见 Windows 客户端在 SSPI 模式下的命令）。

可以通过以下方式指定 GSSAPI 模式：

- 在调用选项文件中的 MySQL 客户端程序之前。插件变量名可以使用下划线或破折号：
  ```
  [mysql]
  plugin_authentication_kerberos_client_mode=GSSAPI
  ```

  或：
  ```
  [mysql]
  plugin-authentication-kerberos-client-mode=GSSAPI
  ```

- 在运行时从命令行使用 mysql 或 mysqldump 客户端程序。例如，以下命令（使用下划线或破折号）会导致 mysql 通过 Windows 上的 MIT Kerberos 库连接到服务器。
  ```
  mysql [connection-options] --plugin_authentication_kerberos_client_mode=GSSAPI
  ```

  或：
  ```
  mysql [connection-options] --plugin-authentication-kerberos-client-mode=GSSAPI
  ```

- 客户端用户可以从 MySQL Workbench 和某些 MySQL 连接器中选择 GSSAPI 模式。在运行 Windows 的客户端主机上，可以覆盖以下内容的默认位置：

  - 通过设置 KRB5_CONFIG 环境变量来设置 Kerberos 配置文件。

  - 通过 KRB5CCNAME 环境变量设置默认凭证缓存名称（例如，KRB5CCNAME=DIR:/mydir/）。

  有关特定客户端插件信息，请参见 https://dev.mysql.com/doc/ 处的文档。

连接到 MySQL 服务器的适当客户端命令取决于命令是使用来自 MIT Kerberos 缓存的 TGT 进行认证，还是基于 MySQL 用户名和 UPN 密码的命令选项进行认证。Windows 上通过 MIT 库的 GSSAPI 支持类似于 Linux 上的 GSSAPI（请参见 Linux 客户端的命令），但有以下例外：

- 票证始终从 Windows 主机上的 MIT Kerberos 缓存中检索或放入。

- kinit 在具有狭窄权限和特定角色的 Windows 功能账户上运行。客户端用户不知道 kinit 密码。有关概述，请参见 https://docs.oracle.com/en/java/javase/11/tools/kinit.html。

- 如果客户端用户提供密码，Windows 上的 MIT Kerberos 库会决定是使用它还是依赖现有票证。

- Kerberos 认证的客户端配置参数 中描述的 destroy_tickets 参数不受支持，因为 Windows 上的 MIT Kerberos 库不支持从配置文件读取其值所需的 API 成员 (get_profile_boolean)。

## Kerberos 认证的客户端配置参数

本节仅适用于运行 Linux 的客户端主机，不适用于运行 Windows 的客户端主机。

注意

运行 Windows 的客户端主机，其中 authentication_kerberos_client 客户端 Kerberos 插件设置为 GSSAPI 模式，通常支持客户端配置参数，但 Windows 上的 MIT Kerberos 库不支持本节中描述的 destroy_tickets 参数。

如果在 MySQL 客户端应用程序调用时不存在有效的票证授予票证 (TGT)，应用程序本身可能会获取并缓存 TGT。如果在 Kerberos 认证过程中客户端应用程序导致 TGT 被缓存，任何添加的此类 TGT 都可以在不再需要后通过设置适当的配置参数来销毁。

authentication_kerberos_client 客户端 Kerberos 插件读取本地 /etc/krb5.conf 文件。如果此文件缺失或无法访问，会发生错误。假设该文件可访问，它可以包含一个可选的 [appdefaults] 部分来提供插件使用的信息。将信息放在该部分的 mysql 部分中。例如：
```
[appdefaults]
mysql = {
  destroy_tickets = true
}
```

客户端插件在 mysql 部分中识别这些参数：

- destroy_tickets 值指示客户端插件是否在获取并使用 TGT 后销毁它。默认情况下，destroy_tickets 为 false，但可以设置为 true 以避免 TGT 重用。（此设置仅适用于由客户端插件创建的 TGT，不适用于由其他插件创建或在 MySQL 外部创建的 TGT。）

在客户端主机上，可以使用客户端 keytab 文件来获取 TGT 和 TS，而无需提供密码。有关 keytab 文件的信息，请参见 https://web.mit.edu/kerberos/krb5-latest/doc/basic/keytab_def.html。

## Kerberos 认证调试

AUTHENTICATION_KERBEROS_CLIENT_LOG 环境变量启用或禁用 Kerberos 认证的调试输出。

注意

尽管名称中有 CLIENT，AUTHENTICATION_KERBEROS_CLIENT_LOG 环境变量同样适用于服务器端插件和客户端插件。

在服务器端，允许的值为 0（关闭）和 1（打开）。日志消息被写入服务器错误日志，受服务器错误日志记录详细程度级别的限制。例如，如果使用基于优先级的日志过滤，log_error_verbosity 系统变量控制详细程度，如 7.4.2.5 节"基于优先级的错误日志过滤 (log_filter_internal)" 中所述。

在客户端，允许的值为 1 到 5，并写入标准错误输出。下表显示每个日志级别值的含义。

| 日志级别 | 含义 |
| --- | --- |
| 1 或未设置 | 无日志记录 |
| 2 | 错误消息 |
| 3 | 错误和警告消息 |
| 4 | 错误、警告和信息消息 |
| 5 | 错误、警告、信息和调试消息 |
