### 8.4.1.6 LDAP 可插拔身份验证

注意

LDAP 可插拔身份验证是 MySQL Enterprise Edition（商业产品）中包含的扩展。要了解有关商业产品的更多信息，请参阅 https://www.mysql.com/products/。

MySQL Enterprise Edition 支持一种身份验证方法，该方法使 MySQL Server 能够使用 LDAP（轻量级目录访问协议）通过访问目录服务（如 X.500）来验证 MySQL 用户。MySQL 使用 LDAP 获取用户、凭证和组信息。

LDAP 可插拔身份验证提供以下功能：

- 外部身份验证：LDAP 身份验证使 MySQL Server 能够接受来自在 LDAP 目录中定义的用户（而不是在 MySQL 授权表中定义的用户）的连接。

- 代理用户支持：LDAP 身份验证可以根据外部用户所属的 LDAP 组，向 MySQL 返回与客户端程序传递的外部用户名不同的用户名。这意味着 LDAP 插件可以返回定义外部 LDAP 验证用户应具有的权限的 MySQL 用户。例如，如果 joe 的 LDAP 组是 developer，则名为 joe 的 LDAP 用户可以连接并具有名为 developer 的 MySQL 用户的权限。

- 安全性：使用 TLS，与 LDAP 服务器的连接可以是安全的。

服务器和客户端插件可用于简单和基于 SASL 的 LDAP 身份验证。在 Microsoft Windows 上，不支持基于 SASL 的 LDAP 身份验证的服务器插件，但支持客户端插件。

| 客户端插件名称 | mysql_clear_password |
| 库文件名 | authentication_ldap_simple.so |

每个服务器端 LDAP 插件与特定的客户端插件配合使用：

- 服务器端 authentication_ldap_simple 插件执行简单 LDAP 身份验证。对于使用此插件的帐户的连接，客户端程序使用客户端 mysql_clear_password 插件，该插件以明文形式将密码发送到服务器。不使用密码哈希或加密，因此建议在 MySQL 客户端和服务器之间使用安全连接以防止密码泄露。

- 服务器端 authentication_ldap_sasl 插件执行基于 SASL 的 LDAP 身份验证。对于使用此插件的帐户的连接，客户端程序使用客户端 authentication_ldap_sasl_client 插件。客户端和服务器端 SASL LDAP 插件使用 SASL 消息在 LDAP 协议中安全传输凭证，以避免在 MySQL 客户端和服务器之间发送明文密码。

  在 Microsoft Windows 平台上，基于 SASL 的 LDAP 身份验证支持服务器插件和客户端插件。

服务器端 LDAP 身份验证插件仅包含在 MySQL Enterprise Edition 中。它们不包含在 MySQL 社区发行版中。客户端 SASL LDAP 插件包含在所有发行版中，包括社区发行版，并且如前所述，客户端 mysql_clear_password 插件内置于 libmysqlclient 客户端库中，该库也包含在所有发行版中。这使来自任何发行版的客户端能够连接到已加载适当服务器端插件的服务器。

#### LDAP 可插拔身份验证的先决条件

要为 MySQL 使用 LDAP 可插拔身份验证，必须满足以下先决条件：

- LDAP 服务器必须可用，以便 LDAP 身份验证插件与其通信。

- 要由 MySQL 验证的 LDAP 用户必须存在于 LDAP 服务器管理的目录中。

- 在使用服务器端 authentication_ldap_sasl 或 authentication_ldap_simple 插件的系统上，必须提供 LDAP 客户端库。目前，支持的库是 Windows 本机 LDAP 库或非 Windows 系统上的 OpenLDAP 库。

- 要使用基于 SASL 的 LDAP 身份验证：

  - LDAP 服务器必须配置为与 SASL 服务器通信。

  - 在使用客户端 authentication_ldap_sasl_client 插件的系统上，必须提供 SASL 客户端库。目前，唯一支持的库是 Cyrus SASL 库。

  - 要使用特定的 SASL 身份验证方法，该方法所需的任何其他服务都必须可用。例如，要使用 GSSAPI/Kerberos，必须提供 GSSAPI 库和 Kerberos 服务。

#### MySQL 用户的 LDAP 身份验证工作原理

本节概述了 MySQL 和 LDAP 如何协同工作来验证 MySQL 用户。有关显示如何设置 MySQL 帐户以使用特定 LDAP 身份验证插件的示例，请参阅使用 LDAP 可插拔身份验证。有关 LDAP 插件可用的身份验证方法的信息，请参阅 LDAP 身份验证方法。

客户端连接到 MySQL 服务器，提供 MySQL 客户端用户名和密码：

- 对于简单 LDAP 身份验证，客户端和服务器端插件以明文形式通信密码。建议在 MySQL 客户端和服务器之间使用安全连接以防止密码泄露。

- 对于基于 SASL 的 LDAP 身份验证，客户端和服务器端插件避免在 MySQL 客户端和服务器之间发送明文密码。例如，插件可能使用 SASL 消息在 LDAP 协议中安全传输凭证。对于 GSSAPI 身份验证方法，客户端和服务器端插件使用 Kerberos 安全通信，而不直接使用 LDAP 消息。

如果客户端用户名和主机名与任何 MySQL 帐户都不匹配，连接将被拒绝。

如果存在匹配的 MySQL 帐户，则会进行 LDAP 身份验证。LDAP 服务器查找与用户匹配的条目，并根据 LDAP 密码验证该条目：

- 如果 MySQL 帐户命名了 LDAP 用户可分辨名称 (DN)，LDAP 身份验证使用该值和客户端提供的 LDAP 密码。（要将 LDAP 用户 DN 与 MySQL 帐户关联，请在创建帐户的 CREATE USER 语句中包含指定身份验证字符串的 BY 子句。）

- 如果 MySQL 帐户未命名 LDAP 用户 DN，LDAP 身份验证使用客户端提供的用户名和 LDAP 密码。在这种情况下，身份验证插件首先使用根 DN 和密码作为凭证绑定到 LDAP 服务器，以根据客户端用户名查找用户 DN，然后根据 LDAP 密码验证该用户 DN。如果根 DN 和密码设置为不正确的值，或为空（未设置）且 LDAP 服务器不允许匿名连接，则使用根凭证的绑定失败。

如果 LDAP 服务器找不到匹配项或找到多个匹配项，身份验证失败，客户端连接被拒绝。

如果 LDAP 服务器找到单个匹配项，LDAP 身份验证成功（假设密码正确），LDAP 服务器返回 LDAP 条目，身份验证插件根据该条目确定已验证用户的名称：

- 如果 LDAP 条目具有组属性（默认情况下为 cn 属性），插件将其值作为已验证的用户名返回。

- 如果 LDAP 条目没有组属性，身份验证插件将客户端用户名作为已验证的用户名返回。

MySQL 服务器比较客户端用户名与已验证用户名，以确定是否为客户端会话进行代理：

- 如果名称相同，则不进行代理：使用与客户端用户名匹配的 MySQL 帐户进行权限检查。

- 如果名称不同，则进行代理：MySQL 查找与已验证用户名匹配的帐户。该帐户成为代理用户，用于权限检查。与客户端用户名匹配的 MySQL 帐户被视为外部代理用户。

#### 安装 LDAP 可插拔身份验证

本节描述如何安装服务器端 LDAP 身份验证插件。有关安装插件的一般信息，请参阅第 7.6.1 节"安装和卸载插件"。

要使服务器可用，插件库文件必须位于 MySQL 插件目录（由 plugin_dir 系统变量命名的目录）中。如有必要，通过在服务器启动时设置 plugin_dir 的值来配置插件目录位置。

服务器端插件库文件基名为 authentication_ldap_simple 和 authentication_ldap_sasl。文件名后缀因平台而异（例如，Unix 和类 Unix 系统为 .so，Windows 为 .dll）。

注意

在 Microsoft Windows 上，不支持基于 SASL 的 LDAP 身份验证的服务器插件，但支持客户端插件。在其他平台上，支持服务器和客户端插件。

要在服务器启动时加载插件，请使用 --plugin-load-add 选项来命名包含它们的库文件。使用此插件加载方法，每次服务器启动时都必须给出这些选项。此外，为您希望配置的任何插件提供的系统变量指定值。

每个服务器端 LDAP 插件都公开一组系统变量，这些变量使其操作能够被配置。设置其中大多数是可选的，但您必须设置指定 LDAP 服务器主机的变量（以便插件知道连接到何处）和 LDAP 绑定操作的基础可分辨名称（以限制搜索范围并获得更快的搜索）。有关所有 LDAP 系统变量的详细信息，请参阅第 8.4.1.13 节"可插拔身份验证系统变量"。

要加载插件并为 LDAP 绑定操作设置 LDAP 服务器主机和基础可分辨名称，请在 my.cnf 文件中放置如下所示的行，根据需要调整平台的 .so 后缀：

```
[mysqld]
plugin-load-add=authentication_ldap_simple.so
authentication_ldap_simple_server_host=127.0.0.1
authentication_ldap_simple_bind_base_dn="dc=example,dc=com"
plugin-load-add=authentication_ldap_sasl.so
authentication_ldap_sasl_server_host=127.0.0.1
authentication_ldap_sasl_bind_base_dn="dc=example,dc=com"
```

修改 my.cnf 后，重启服务器以使新设置生效。

或者，要在运行时加载插件，请使用这些语句，根据需要调整平台的 .so 后缀：

```
INSTALL PLUGIN authentication_ldap_simple
  SONAME 'authentication_ldap_simple.so';
INSTALL PLUGIN authentication_ldap_sasl
  SONAME 'authentication_ldap_sasl.so';
```

INSTALL PLUGIN 立即加载插件，并将其注册在 mysql.plugins 系统表中，以使服务器在每次后续正常启动时加载它，而无需 --plugin-load-add。

在运行时安装插件后，它们公开的系统变量变为可用，您可以将它们的设置添加到 my.cnf 文件中以为后续重启配置插件。例如：

```
[mysqld]
authentication_ldap_simple_server_host=127.0.0.1
authentication_ldap_simple_bind_base_dn="dc=example,dc=com"
authentication_ldap_sasl_server_host=127.0.0.1
authentication_ldap_sasl_bind_base_dn="dc=example,dc=com"
```

修改 my.cnf 后，重启服务器以使新设置生效。

要在运行时设置和持久化每个值而不是在启动时，请使用这些语句：

```
SET PERSIST authentication_ldap_simple_server_host='127.0.0.1';
SET PERSIST authentication_ldap_simple_bind_base_dn='dc=example,dc=com';
SET PERSIST authentication_ldap_sasl_server_host='127.0.0.1';
SET PERSIST authentication_ldap_sasl_bind_base_dn='dc=example,dc=com';
```

SET PERSIST 为运行中的 MySQL 实例设置值。它还保存该值，使其在后续服务器重启时保留。要为运行中的 MySQL 实例更改值而不使其在后续重启时保留，请使用 GLOBAL 关键字而不是 PERSIST。请参阅第 15.7.6.1 节"变量赋值的 SET 语法"。

要验证插件安装，请检查信息模式 PLUGINS 表或使用 SHOW PLUGINS 语句（请参阅第 7.6.2 节"获取服务器插件信息"）。例如：

```
mysql> SELECT PLUGIN_NAME, PLUGIN_STATUS
       FROM INFORMATION_SCHEMA.PLUGINS
       WHERE PLUGIN_NAME LIKE '%ldap%';
+----------------------------+---------------+
| PLUGIN_NAME                | PLUGIN_STATUS |
+----------------------------+---------------+
| authentication_ldap_sasl   | ACTIVE        |
| authentication_ldap_simple | ACTIVE        |
+----------------------------+---------------+
```

如果插件无法初始化，请检查服务器错误日志以获取诊断消息。

要将 MySQL 帐户与 LDAP 插件关联，请参阅使用 LDAP 可插拔身份验证。

SELinux 的其他说明

在运行 EL6 或 EL 且启用了 SELinux 的系统上，需要更改 SELinux 策略以使 MySQL LDAP 插件能够与 LDAP 服务通信：

1. 创建一个包含以下内容的文件 mysqlldap.te：

```
module mysqlldap 1.0;

require {
        type ldap_port_t;
        type mysqld_t;
        class tcp_socket name_connect;
}

#============= mysqld_t ==============

allow mysqld_t ldap_port_t:tcp_socket name_connect;
```

2. 将安全策略模块编译为二进制表示：

```
checkmodule -M -m mysqlldap.te -o mysqlldap.mod
```

3. 创建 SELinux 策略模块包：

```
semodule_package -m mysqlldap.mod     -o mysqlldap.pp
```

4. 安装模块包：

```
semodule -i mysqlldap.pp
```

5. 进行 SELinux 策略更改后，重启 MySQL 服务器：

```
service mysqld restart
```

#### 卸载 LDAP 可插拔身份验证

卸载 LDAP 身份验证插件的方法取决于您的安装方式：

- 如果您在服务器启动时使用 --plugin-load-add 选项安装了插件，请在不使用这些选项的情况下重启服务器。

- 如果您在运行时使用 INSTALL PLUGIN 安装了插件，它们在服务器重启后仍保持安装状态。要卸载它们，请使用 UNINSTALL PLUGIN：

```
UNINSTALL PLUGIN authentication_ldap_simple;
UNINSTALL PLUGIN authentication_ldap_sasl;
```

此外，从 my.cnf 文件中删除设置 LDAP 插件相关系统变量的任何启动选项。如果您使用 SET PERSIST 来持久化 LDAP 系统变量，请使用 RESET PERSIST 来删除设置。

#### LDAP 可插拔身份验证和 ldap.conf

对于使用 OpenLDAP 的安装，ldap.conf 文件为 LDAP 客户端提供全局默认值。可以在此文件中设置选项以影响 LDAP 客户端，包括 LDAP 身份验证插件。OpenLDAP 按以下优先级顺序使用配置选项：

- LDAP 客户端指定的配置。

- ldap.conf 文件中指定的配置。要禁用此文件的使用，请设置 LDAPNOINIT 环境变量。

- OpenLDAP 库内置默认值。

如果库默认值或 ldap.conf 值不能产生适当的选项值，LDAP 身份验证插件可能能够设置相关变量以直接影响 LDAP 配置。例如，LDAP 插件可以覆盖 ldap.conf 以获取如下参数：

- TLS 配置：系统变量可用于启用 TLS 并控制 CA 配置，例如简单 LDAP 身份验证的 authentication_ldap_simple_tls 和 authentication_ldap_simple_ca_path，以及 SASL LDAP 身份验证的 authentication_ldap_sasl_tls 和 authentication_ldap_sasl_ca_path。

- LDAP 引荐。请参阅 LDAP 搜索引荐。

有关 ldap.conf 的更多信息，请参阅 ldap.conf(5) 手册页。

#### 为 LDAP 可插拔身份验证设置超时

对于 MySQL 帐户使用 LDAP 可插拔身份验证连接到 MySQL 服务器，LDAP 服务器必须可用且正常运行。MySQL 和 LDAP 服务器之间的交互涉及两个步骤。首先，MySQL 服务器通过 TCP 建立与 LDAP 服务器的连接。其次，MySQL 服务器通过连接向 LDAP 服务器发送 LDAP 绑定请求，并在验证帐户之前等待回复。如果任一步骤失败，MySQL 帐户无法连接到 MySQL 服务器。

默认情况下，短期超时（取代主机系统的超时值）应用于连接和响应步骤。在所有情况下，如果超时过期，帐户用户会收到通知，表示其连接到 MySQL 的尝试被拒绝。客户端和服务器日志可以提供其他信息。在客户端，设置以下环境变量以提升详细级别，然后重启 MySQL 客户端：

```
AUTHENTICATION_LDAP_CLIENT_LOG=5
export AUTHENTICATION_LDAP_CLIENT_LOG
```

以下系统变量仅在 Linux 平台上支持基于 SASL 和简单 LDAP 身份验证的默认超时。

表 8.22 基于 SASL 和简单 LDAP 身份验证的系统变量

| 系统变量名称 | 默认超时值 |
|-----------|---------|
| authentication_ldap_sasl_connect_timeout | 30 秒 |
| authentication_ldap_sasl_response_timeout | 30 秒 |
| authentication_ldap_simple_connect_timeout | 30 秒 |
| authentication_ldap_simple_response_timeout | 30 秒 |

LDAP 身份验证的超时值可在服务器启动时和运行时调整。如果使用其中一个变量将超时设置为零，您可以有效地禁用它，MySQL 服务器将恢复为使用主机系统的默认超时。

注意

在以下条件组合下，authentication_ldap_sasl_connect_timeout 设置的实际等待时间会加倍，因为（在内部）服务器必须调用 TCP 连接两次：

- LDAP 服务器离线。

- authentication_ldap_sasl_connect_timeout 的值大于零。

- 正在使用连接池（具体来说，authentication_ldap_sasl_max_pool_size 系统变量的值大于零，这启用了池）。

#### 使用 LDAP 可插拔身份验证

本节描述如何启用 MySQL 帐户使用 LDAP 可插拔身份验证连接到 MySQL 服务器。假设服务器正在运行适当的服务器端插件，如安装 LDAP 可插拔身份验证中所述，并且客户端主机上提供了适当的客户端插件。

本节不描述 LDAP 配置或管理。假设您熟悉这些主题。

两个服务器端 LDAP 插件各自与特定的客户端插件配合使用：

- 服务器端 authentication_ldap_simple 插件执行简单 LDAP 身份验证。对于使用此插件的帐户的连接，客户端程序使用客户端 mysql_clear_password 插件，该插件以明文形式将密码发送到服务器。不使用密码哈希或加密，因此建议在 MySQL 客户端和服务器之间使用安全连接以防止密码泄露。

- 服务器端 authentication_ldap_sasl 插件执行基于 SASL 的 LDAP 身份验证。对于使用此插件的帐户的连接，客户端程序使用客户端 authentication_ldap_sasl_client 插件。客户端和服务器端 SASL LDAP 插件使用 SASL 消息在 LDAP 协议中安全传输凭证，以避免在 MySQL 客户端和服务器之间发送明文密码。

MySQL 用户的 LDAP 身份验证的总体要求：

- 必须存在要验证的每个用户的 LDAP 目录条目。

- 必须存在指定服务器端 LDAP 身份验证插件的 MySQL 用户帐户，并可选地命名关联的 LDAP 用户可分辨名称 (DN)。（要将 LDAP 用户 DN 与 MySQL 帐户关联，请在创建帐户的 CREATE USER 语句中包含 BY 子句。）如果帐户未命名 LDAP 字符串，LDAP 身份验证使用客户端指定的用户名来查找 LDAP 条目。

- 客户端程序使用适合于 MySQL 帐户使用的服务器端身份验证插件的连接方法进行连接。对于 LDAP 身份验证，连接需要 MySQL 用户名和 LDAP 密码。此外，对于使用服务器端 authentication_ldap_simple 插件的帐户，使用 --enable-cleartext-plugin 选项调用客户端程序以启用客户端 mysql_clear_password 插件。

此处的说明假设以下场景：

- MySQL 用户 betsy 和 boris 分别向 betsy_ldap 和 boris_ldap 的 LDAP 条目进行身份验证。（MySQL 和 LDAP 用户名不必不同。在本讨论中使用不同名称有助于澄清操作上下文是 MySQL 还是 LDAP。）

- LDAP 条目使用 uid 属性指定用户名。这可能因 LDAP 服务器而异。某些 LDAP 服务器使用 cn 属性而不是 uid 来表示用户名。要更改属性，请适当修改 authentication_ldap_simple_user_search_attr 或 authentication_ldap_sasl_user_search_attr 系统变量。

- 这些 LDAP 条目在 LDAP 服务器管理的目录中可用，以提供唯一标识每个用户的可分辨名称值：

```
uid=betsy_ldap,ou=People,dc=example,dc=com
uid=boris_ldap,ou=People,dc=example,dc=com
```

- 创建 MySQL 帐户的 CREATE USER 语句在 BY 子句中命名 LDAP 用户，以指示 MySQL 帐户针对哪个 LDAP 条目进行身份验证。

设置使用 LDAP 身份验证的帐户的说明取决于使用哪个服务器端 LDAP 插件。以下部分描述了几个使用场景。

#### 简单 LDAP 身份验证（不使用代理）

本节中概述的过程要求 authentication_ldap_simple_group_search_attr 设置为空字符串，如下所示：

```
SET GLOBAL.authentication_ldap_simple_group_search_attr='';
```

否则，默认使用代理。

要为简单 LDAP 身份验证设置 MySQL 帐户，请使用 CREATE USER 语句指定 authentication_ldap_simple 插件，可选地包括 LDAP 用户可分辨名称 (DN)，如下所示：

```
CREATE USER user
  IDENTIFIED WITH authentication_ldap_simple
  [BY 'LDAP user DN'];
```

假设 MySQL 用户 betsy 在 LDAP 目录中有此条目：

```
uid=betsy_ldap,ou=People,dc=example,dc=com
```

然后为 betsy 创建 MySQL 帐户的语句如下所示：

```
CREATE USER 'betsy'@'localhost'
  IDENTIFIED WITH authentication_ldap_simple
  AS 'uid=betsy_ldap,ou=People,dc=example,dc=com';
```

在 BY 子句中指定的身份验证字符串不包括 LDAP 密码。必须由客户端用户在连接时提供。

客户端通过提供 MySQL 用户名和 LDAP 密码，以及启用客户端 mysql_clear_password 插件来连接到 MySQL 服务器：

```
$> mysql --user=betsy --password --enable-cleartext-plugin
Enter password: betsy_ldap_password
```

注意

客户端 mysql_clear_password 身份验证插件保持密码不变，因此客户端程序以明文形式将其发送到 MySQL 服务器。这使密码能够按原样传递到 LDAP 服务器。明文密码是必需的，以使用不带 SASL 的服务器端 LDAP 库，但在某些配置中可能是安全问题。这些措施可以最小化风险：

- 为了降低无意中使用 mysql_clear_password 插件的可能性，MySQL 客户端必须显式启用它（例如，使用 --enable-cleartext-plugin 选项）。请参阅第 8.4.1.3 节"客户端明文可插拔身份验证"。

- 为了避免在启用 mysql_clear_password 插件时密码泄露，MySQL 客户端应该使用加密连接连接到 MySQL 服务器。参见第 8.3.1 节"配置 MySQL 使用加密连接"。

认证过程如下：

1. 客户端插件将 betsy 和 betsy_password 作为客户端用户名和 LDAP 密码发送到 MySQL 服务器。

2. 连接尝试匹配 'betsy'@'localhost' 账户。服务器端 LDAP 插件发现该账户的认证字符串为 'uid=betsy_ldap,ou=People,dc=example,dc=com' 来命名 LDAP 用户 DN。插件将此字符串和 LDAP 密码发送到 LDAP 服务器。

3. LDAP 服务器找到 betsy_ldap 的 LDAP 条目，密码匹配，因此 LDAP 认证成功。

4. LDAP 条目没有组属性，所以服务器端插件返回客户端用户名（betsy）作为认证用户。这与客户端提供的用户名相同，因此不会发生代理，客户端会话使用 'betsy'@'localhost' 账户进行权限检查。

如果 CREATE USER 语句不包含 BY 子句来指定 betsy_ldap LDAP 可分辨名称，认证尝试将使用客户端提供的用户名（本例中为 betsy）。如果不存在 betsy 的 LDAP 条目，认证将失败。

## 基于 SASL 的 LDAP 认证（不使用代理）

本节中概述的过程要求将 authentication_ldap_sasl_group_search_attr 设置为空字符串，如下所示：

```
SET GLOBAL.authentication_ldap_sasl_group_search_attr='';
```

否则，默认使用代理。

要为 SASL LDAP 认证设置 MySQL 账户，使用 CREATE USER 语句指定 authentication_ldap_sasl 插件，可选地包括 LDAP 用户可分辨名称（DN），如下所示：

```
CREATE USER user
  IDENTIFIED WITH authentication_ldap_sasl
  [BY 'LDAP user DN'];
```

假设 MySQL 用户 boris 在 LDAP 目录中有此条目：

```
uid=boris_ldap,ou=People,dc=example,dc=com
```

那么为 boris 创建 MySQL 账户的语句如下所示：

```
CREATE USER 'boris'@'localhost'
  IDENTIFIED WITH authentication_ldap_sasl
  AS 'uid=boris_ldap,ou=People,dc=example,dc=com';
```

BY 子句中指定的认证字符串不包括 LDAP 密码。客户端用户必须在连接时提供该密码。

客户端通过提供 MySQL 用户名和 LDAP 密码连接到 MySQL 服务器：

```
$> mysql --user=boris --password
Enter password: boris_ldap_password
```

对于服务器端 authentication_ldap_sasl 插件，客户端使用客户端 authentication_ldap_sasl_client 插件。如果客户端程序找不到客户端插件，请指定 --plugin-dir 选项，该选项指定安装插件库文件的目录。

boris 的认证过程与之前为 betsy 描述的简单 LDAP 认证类似，不同之处在于客户端和服务器端 SASL LDAP 插件使用 SASL 消息在 LDAP 协议内安全传输凭据，以避免在 MySQL 客户端和服务器之间发送明文密码。

## 使用代理的 LDAP 认证

LDAP 认证插件支持代理，使用户能够以一个用户身份连接到 MySQL 服务器，但假设另一个用户的权限。本节描述基本的 LDAP 插件代理支持。LDAP 插件还支持指定组偏好和代理用户映射；参见 LDAP 认证组偏好和映射规范。

此处描述的代理实现基于使用 LDAP 组属性值将使用 LDAP 认证的连接 MySQL 用户映射到定义不同权限集的其他 MySQL 账户。用户不直接通过定义权限的账户连接。相反，他们通过使用 LDAP 认证的默认代理账户连接，使得所有外部登录都映射到持有权限的代理 MySQL 账户。任何使用代理账户连接的用户都被映射到这些代理 MySQL 账户之一，其权限决定了允许外部用户执行的数据库操作。

此处的说明假设以下场景：

- LDAP 条目分别使用 uid 和 cn 属性指定用户名和组值。要使用不同的用户和组属性名称，请设置相应的插件特定系统变量：

  - 对于 authentication_ldap_simple 插件：设置 authentication_ldap_simple_user_search_attr 和 authentication_ldap_simple_group_search_attr。

  - 对于 authentication_ldap_sasl 插件：设置 authentication_ldap_sasl_user_search_attr 和 authentication_ldap_sasl_group_search_attr。

- 这些 LDAP 条目在 LDAP 服务器管理的目录中可用，以提供唯一标识每个用户的可分辨名称值：
  ```
  uid=basha,ou=People,dc=example,dc=com,cn=accounting
  uid=basil,ou=People,dc=example,dc=com,cn=front_office
  ```

  在连接时，组属性值成为认证用户名，因此它们命名 accounting 和 front_office 代理账户。

- 示例假设使用 SASL LDAP 认证。对于简单 LDAP 认证，请进行适当的调整。

创建默认代理 MySQL 账户：

```
CREATE USER ''@'%'
  IDENTIFIED WITH authentication_ldap_sasl;
```

代理账户定义没有 AS 'auth_string' 子句来命名 LDAP 用户 DN。因此：

- 当客户端连接时，客户端用户名成为要搜索的 LDAP 用户名。

- 匹配的 LDAP 条目应该包括一个组属性，命名定义客户端应该拥有的权限的代理 MySQL 账户。

注意

如果您的 MySQL 安装有匿名用户，他们可能与默认代理用户冲突。有关此问题的更多信息以及处理方法，参见默认代理用户和匿名用户冲突。

创建代理账户并向每个账户授予它应该拥有的权限：

```
CREATE USER 'accounting'@'localhost'
  IDENTIFIED WITH mysql_no_login;
CREATE USER 'front_office'@'localhost'
  IDENTIFIED WITH mysql_no_login;
GRANT ALL PRIVILEGES
  ON accountingdb.*
  TO 'accounting'@'localhost';
GRANT ALL PRIVILEGES
  ON frontdb.*
  TO 'front_office'@'localhost';
```

代理账户使用 mysql_no_login 认证插件来防止客户端使用这些账户直接登录到 MySQL 服务器。相反，使用 LDAP 认证的用户应该使用默认的 ''@'%' 代理账户。（这假设 mysql_no_login 插件已安装。有关说明，参见第 8.4.1.8 节"无登录可插拔认证"。）有关保护代理账户免受直接使用的替代方法，参见防止直接登录到代理账户。

向代理账户授予每个代理账户的 PROXY 权限：

```
GRANT PROXY
  ON 'accounting'@'localhost'
  TO ''@'%';
GRANT PROXY
  ON 'front_office'@'localhost'
  TO ''@'%';
```

使用 mysql 命令行客户端以 basha 身份连接到 MySQL 服务器。

```
$> mysql --user=basha --password
Enter password: basha_password (basha LDAP password)
```

认证过程如下：

1. 服务器使用默认的 ''@'%' 代理账户为客户端用户 basha 认证连接。

2. 匹配的 LDAP 条目是：
   ```
   uid=basha,ou=People,dc=example,dc=com,cn=accounting
   ```

3. 匹配的 LDAP 条目有组属性 cn=accounting，因此 accounting 成为认证的代理用户。

4. 认证用户与客户端用户名 basha 不同，结果是 basha 被视为 accounting 的代理，basha 假设代理 accounting 账户的权限。以下查询返回如下所示的输出：
   ```
   mysql> SELECT USER(), CURRENT_USER(), @@proxy_user;
   +-----------------+----------------------+--------------+
   | USER()          | CURRENT_USER()       | @@proxy_user |
   +-----------------+----------------------+--------------+
   | basha@localhost | accounting@localhost | ''@'%'       |
   +-----------------+----------------------+--------------+
   ```

这演示了 basha 使用授予代理 accounting MySQL 账户的权限，以及代理通过默认代理用户账户进行。

现在以 basil 身份连接：

```
$> mysql --user=basil --password
Enter password: basil_password (basil LDAP password)
```

basil 的认证过程与之前为 basha 描述的类似：

1. 服务器使用默认的 ''@'%' 代理账户为客户端用户 basil 认证连接。

2. 匹配的 LDAP 条目是：
   ```
   uid=basil,ou=People,dc=example,dc=com,cn=front_office
   ```

3. 匹配的 LDAP 条目有组属性 cn=front_office，因此 front_office 成为认证的代理用户。

4. 认证用户与客户端用户名 basil 不同，结果是 basil 被视为 front_office 的代理，basil 假设代理 front_office 账户的权限。以下查询返回如下所示的输出：
   ```
   mysql> SELECT USER(), CURRENT_USER(), @@proxy_user;
   +-----------------+------------------------+--------------+
   | USER()          | CURRENT_USER()         | @@proxy_user |
   +-----------------+------------------------+--------------+
   | basil@localhost | front_office@localhost | ''@'%'       |
   +-----------------+------------------------+--------------+
   ```

这演示了 basil 使用授予代理 front_office MySQL 账户的权限，以及代理通过默认代理用户账户进行。

## LDAP 认证组偏好和映射规范

如 LDAP 认证与代理中所述，基本的 LDAP 认证代理通过插件使用 LDAP 服务器返回的第一个组名作为 MySQL 代理用户账户名的原则工作。这种简单的功能不能在 LDAP 服务器返回多个组名时指定关于使用哪个组名的任何偏好，也不能指定除组名之外的任何名称作为代理用户名。

对于使用 LDAP 认证的 MySQL 账户，认证字符串可以指定以下信息以启用更大的代理灵活性：

- 按偏好顺序的组列表，使得插件使用列表中与 LDAP 服务器返回的组匹配的第一个组名。

- 从组名到代理用户名的映射，使得匹配的组名可以提供指定的名称用作代理用户。这提供了使用组名作为代理用户的替代方案。

考虑以下 MySQL 代理账户定义：

```
CREATE USER ''@'%'
  IDENTIFIED WITH authentication_ldap_sasl
  AS '+ou=People,dc=example,dc=com#grp1=usera,grp2,grp3=userc';
```

认证字符串有一个用户 DN 后缀 ou=People,dc=example,dc=com，前缀为 + 字符。因此，如 LDAP 认证用户 DN 后缀中所述，完整用户 DN 从指定的用户 DN 后缀加上客户端用户名作为 uid 属性构造。

认证字符串的其余部分以 # 开头，表示组偏好和映射信息的开始。认证字符串的这部分按顺序 grp1、grp2、grp3 列出组名。LDAP 插件将该列表与 LDAP 服务器返回的组名集合进行比较，按列表顺序查找与返回名称的匹配。插件使用第一个匹配，或者如果没有匹配，认证失败。

假设 LDAP 服务器返回组 grp3、grp2 和 grp7。LDAP 插件使用 grp2，因为它是认证字符串中与之匹配的第一个组，即使它不是 LDAP 服务器返回的第一个组。如果 LDAP 服务器返回 grp4、grp2 和 grp1，插件使用 grp1，即使 grp2 也匹配。grp1 的优先级高于 grp2，因为它在认证字符串中列出得更早。

假设插件找到了组名匹配，它执行从该组名到 MySQL 代理用户名的映射（如果存在）。对于示例代理账户，映射如下进行：

- 如果匹配的组名是 grp1 或 grp3，这些在认证字符串中分别与用户名 usera 和 userc 相关联。插件使用相应的关联用户名作为代理用户名。

- 如果匹配的组名是 grp2，认证字符串中没有关联的用户名。插件使用 grp2 作为代理用户名。

如果 LDAP 服务器以 DN 格式返回组，LDAP 插件解析组 DN 以从中提取组名。

要指定 LDAP 组偏好和映射信息，这些原则适用：

- 以 # 前缀字符开始认证字符串的组偏好和映射部分。

- 组偏好和映射规范是一个或多个项的列表，由逗号分隔。每个项的形式为 group_name=user_name 或 group_name。项应按组名偏好顺序列出。对于插件从 LDAP 服务器返回的组名集合中选择为匹配的组名，两种语法的效果如下不同：

  - 对于指定为 group_name=user_name（带用户名）的项，组名映射到用户名，该用户名用作 MySQL 代理用户名。

  - 对于指定为 group_name（不带用户名）的项，组名用作 MySQL 代理用户名。

- 要引用包含特殊字符（如空格）的组或用户名，请用双引号（"）字符围绕它。例如，如果项的组和用户名为 my group name 和 my user name，它必须在组映射中使用引号编写：
  ```
  "my group name"="my user name"
  ```

  如果项的组和用户名为 my_group_name 和 my_user_name（不包含特殊字符），可以但不必使用引号编写。以下任何一个都有效：
  ```
  my_group_name=my_user_name
  my_group_name="my_user_name"
  "my_group_name"=my_user_name
  "my_group_name"="my_user_name"
  ```

- 要转义字符，在其前面加上反斜杠（\）。这特别有用于包括文字双引号或反斜杠，否则不会包括文字。

- 认证字符串中不需要存在用户 DN，但如果存在，它必须在组偏好和映射部分之前。用户 DN 可以作为完整用户 DN 给出，或作为带有 + 前缀字符的用户 DN 后缀。（参见 LDAP 认证用户 DN 后缀。）

## LDAP 认证用户 DN 后缀

LDAP 认证插件允许提供用户 DN 信息的认证字符串以 + 前缀字符开头：

- 在没有 + 字符的情况下，认证字符串值按原样处理，不进行修改。

- 如果认证字符串以 + 开头，插件从客户端发送的用户名以及认证字符串中指定的 DN（移除 +）构造完整用户 DN 值。在构造的 DN 中，客户端用户名成为指定 LDAP 用户名的属性的值。默认为 uid；要更改属性，修改相应的系统变量（authentication_ldap_simple_user_search_attr 或 authentication_ldap_sasl_user_search_attr）。认证字符串按给定的方式存储在 mysql.user 系统表中，完整用户 DN 在认证前动态构造。

此账户认证字符串在开头没有 +，因此它被视为完整用户 DN：

```
CREATE USER 'baldwin'
  IDENTIFIED WITH authentication_ldap_simple
  AS 'uid=admin,ou=People,dc=example,dc=com';
```

客户端使用账户中指定的用户名（baldwin）连接。在这种情况下，该名称不被使用，因为认证字符串没有前缀，因此完全指定用户 DN。

此账户认证字符串在开头有 +，因此它被视为仅用户 DN 的一部分：

```
CREATE USER 'accounting'
  IDENTIFIED WITH authentication_ldap_simple
  AS '+ou=People,dc=example,dc=com';
```

客户端使用账户中指定的用户名（accounting）连接，在这种情况下它被用作 uid 属性以及认证字符串来构造用户 DN：

```
uid=accounting,ou=People,dc=example,dc=com
```

前面示例中的账户有非空用户名，因此客户端始终使用与账户定义中指定的相同名称连接到 MySQL 服务器。如果账户有空用户名，例如 LDAP 认证与代理中描述的默认匿名 ''@'%' 代理账户，客户端可能使用不同的用户名连接到 MySQL 服务器。但原则是相同的：如果认证字符串以 + 开头，插件使用客户端发送的用户名以及认证字符串来构造用户 DN。

## LDAP 认证方法

LDAP 认证插件使用可配置的认证方法。相应的系统变量和可用方法选择是插件特定的：

- 对于 authentication_ldap_simple 插件：设置 authentication_ldap_simple_auth_method_name 系统变量来配置方法。允许的选择是 SIMPLE 和 AD-FOREST。

- 对于 authentication_ldap_sasl 插件：设置 authentication_ldap_sasl_auth_method_name 系统变量来配置方法。允许的选择是 SCRAM-SHA-1、SCRAM-SHA-256 和 GSSAPI。（要确定主机系统上实际可用的 SASL LDAP 方法，请检查 Authentication_ldap_sasl_supported_methods 状态变量的值。）

有关每种允许方法的信息，参见系统变量描述。另外，根据方法，可能需要额外的配置，如以下部分所述。

## GSSAPI/Kerberos 认证方法

通用安全服务应用程序编程接口（GSSAPI）是一个安全抽象接口。Kerberos 是可以通过该抽象接口使用的特定安全协议的实例。使用 GSSAPI，应用程序向 Kerberos 认证以获取服务凭据，然后依次使用这些凭据来启用对其他服务的安全访问。

一个这样的服务是 LDAP，由客户端和服务器端 SASL LDAP 认证插件使用。当 authentication_ldap_sasl_auth_method_name 系统变量设置为 GSSAPI 时，这些插件使用 GSSAPI/Kerberos 认证方法。在这种情况下，插件使用 Kerberos 安全通信，不直接使用 LDAP 消息。然后服务器端插件与 LDAP 服务器通信以解释 LDAP 认证消息并检索 LDAP 组。

GSSAPI/Kerberos 在 Linux 上的 MySQL 服务器和客户端支持作为 LDAP 认证方法。它在 Linux 环境中很有用，其中应用程序可以通过启用 Kerberos 的 Microsoft Active Directory 访问 LDAP。

以下讨论提供了有关使用 GSSAPI 方法的配置要求的信息。假设熟悉 Kerberos 概念和操作。以下列表简要定义了几个常见的 Kerberos 术语。您可能还会发现 RFC 4120 的术语表部分有帮助。

- 主体：一个命名实体，例如用户或服务器。

- KDC：密钥分发中心，包括 AS 和 TGS：

  - AS：认证服务器；提供获取额外票证所需的初始票证授予票证。

  - TGS：票证授予服务器；向拥有有效 TGT 的 Kerberos 客户端提供额外票证。

- TGT：票证授予票证；呈现给 TGS 以获取服务票证用于服务访问。

使用 Kerberos 的 LDAP 认证需要 KDC 服务器和 LDAP 服务器。此要求可以以不同方式满足：

- Active Directory 包括两个服务器，在 Active Directory LDAP 服务器中默认启用 Kerberos 认证。

- OpenLDAP 提供 LDAP 服务器，但可能需要单独的 KDC 服务器，需要额外的 Kerberos 设置。

Kerberos 也必须在客户端主机上可用。客户端使用密码联系 AS 以获取 TGT。客户端然后使用 TGT 从 TGS 获取对其他服务（如 LDAP）的访问。

以下部分讨论在 MySQL 中使用 GSSAPI/Kerberos 进行 SASL LDAP 认证的配置步骤：

- 验证 Kerberos 和 LDAP 可用性

- 为 GSSAPI/Kerberos 配置服务器端 SASL LDAP 认证插件

- 创建使用 GSSAPI/Kerberos 进行 LDAP 认证的 MySQL 账户

- 使用 MySQL 账户连接到 MySQL 服务器

- LDAP 认证的客户端配置参数

### 验证 Kerberos 和 LDAP 可用性

以下示例显示如何测试 Active Directory 中 Kerberos 的可用性。该示例做出这些假设：

- Active Directory 在名为 ldap_auth.example.com 的主机上运行，IP 地址为 198.51.100.10。

- MySQL 相关的 Kerberos 认证和 LDAP 查询使用 MYSQL.LOCAL 域。

- 一个名为 bredon@MYSQL.LOCAL 的主体已向 KDC 注册。（在后面的讨论中，此主体名称也与使用 GSSAPI/Kerberos 向 MySQL 服务器认证的 MySQL 账户相关联。）

满足这些假设后，按照此过程：

1. 验证 Kerberos 库已安装并在操作系统中正确配置。例如，要配置 MYSQL.LOCAL 域以在 MySQL 认证期间使用，/etc/krb5.conf Kerberos 配置文件应包含类似以下内容：
   ```
   [realms]
     MYSQL.LOCAL = {
       kdc = ldap_auth.example.com
       admin_server = ldap_auth.example.com
       default_domain = MYSQL.LOCAL
     }
   ```

2. 您可能需要为服务器主机向 /etc/hosts 添加条目：
   ```
   198.51.100.10 ldap_auth ldap_auth.example.com
   ```

3. 检查 Kerberos 认证是否正确工作：

   a. 使用 kinit 向 Kerberos 认证：
      ```
      $> kinit bredon@MYSQL.LOCAL
      Password for bredon@MYSQL.LOCAL: (enter password here)
      ```

      该命令为名为 bredon@MYSQL.LOCAL 的 Kerberos 主体认证。当命令提示时输入主体的密码。KDC 返回一个 TGT，该 TGT 在客户端缓存以供其他 Kerberos 感知应用程序使用。

   b. 使用 klist 检查 TGT 是否正确获取。输出应类似于以下内容：
      ```
      $> klist
      Ticket cache: FILE:/tmp/krb5cc_244306
      Default principal: bredon@MYSQL.LOCAL

      Valid starting        Expires               Service principal
      03/23/2021 08:18:33   03/23/2021 18:18:33   krbtgt/MYSQL.LOCAL@MYSQL.LOCAL
      ```

4. 使用此命令检查 ldapsearch 是否与 Kerberos TGT 一起工作，该命令在 MYSQL.LOCAL 域中搜索用户：
   ```
   ldapsearch -h 198.51.100.10 -Y GSSAPI -b "dc=MYSQL,dc=LOCAL"
   ```

### 为 GSSAPI/Kerberos 配置服务器端 SASL LDAP 认证插件

假设 LDAP 服务器可通过 Kerberos 访问，如上所述，配置服务器端 SASL LDAP 认证插件以使用 GSSAPI/Kerberos 认证方法。（有关一般 LDAP 插件安装信息，参见安装 LDAP 可插拔认证。）以下是服务器 my.cnf 文件可能包含的插件相关设置的示例：

```
[mysqld]
plugin-load-add=authentication_ldap_sasl.so
authentication_ldap_sasl_auth_method_name="GSSAPI"
authentication_ldap_sasl_server_host=198.51.100.10
authentication_ldap_sasl_server_port=389
authentication_ldap_sasl_bind_root_dn="cn=admin,cn=users,dc=MYSQL,dc=LOCAL"
authentication_ldap_sasl_bind_root_pwd="password"
authentication_ldap_sasl_bind_base_dn="cn=users,dc=MYSQL,dc=LOCAL"
authentication_ldap_sasl_user_search_attr="sAMAccountName"
```

这些选项文件设置配置 SASL LDAP 插件如下：

- --plugin-load-add 选项加载插件（根据您的平台调整 .so 后缀）。如果您之前使用 INSTALL PLUGIN 语句加载了插件，此选项是不必要的。

- authentication_ldap_sasl_auth_method_name 必须设置为 GSSAPI 以使用 GSSAPI/Kerberos 作为 SASL LDAP 认证方法。

- authentication_ldap_sasl_server_host 和 authentication_ldap_sasl_server_port 指示用于认证的 Active Directory 服务器主机的 IP 地址和端口号。

- authentication_ldap_sasl_bind_root_dn 和 authentication_ldap_sasl_bind_root_pwd 配置用于组搜索功能的根 DN 和密码。此功能是必需的，但用户可能没有搜索权限。在这种情况下，有必要提供根 DN 信息：

  - 在 DN 选项值中，admin 应该是具有执行用户搜索权限的管理 LDAP 账户的名称。

### 8.4.1.6 LDAP 可插拔身份验证

- 在密码选项值中，password 应该是管理员账户密码。

- authentication_ldap_sasl_bind_base_dn 表示用户 DN 基础路径，以便搜索在 MYSQL.LOCAL 域中查找用户。

- authentication_ldap_sasl_user_search_attr 指定标准 Active Directory 搜索属性 sAMAccountName。此属性用于搜索以匹配登录名；属性值与用户 DN 值不同。

#### 创建使用 GSSAPI/Kerberos 进行 LDAP 身份验证的 MySQL 账户

使用 SASL LDAP 身份验证插件和 GSSAPI/Kerberos 方法的 MySQL 身份验证基于作为 Kerberos 主体的用户。以下讨论使用名为 bredon@MYSQL.LOCAL 的主体作为此用户，该用户必须在多个位置注册：

- Kerberos 管理员应将用户名注册为 Kerberos 主体。此名称应包含域名。客户端使用主体名称和密码向 Kerberos 进行身份验证并获取 TGT。

- LDAP 管理员应在 LDAP 条目中注册用户名。例如：
  uid=bredon,dc=MYSQL,dc=LOCAL

  注意

  在 Active Directory（默认使用 Kerberos 作为身份验证方法）中，创建用户会同时创建 Kerberos 主体和 LDAP 条目。

- MySQL DBA 应创建一个账户，该账户的用户名为 Kerberos 主体名称，并使用 SASL LDAP 插件进行身份验证。

假设 Kerberos 主体和 LDAP 条目已由相应的服务管理员注册，并且如前面在"安装 LDAP 可插拔身份验证"和"为 GSSAPI/Kerberos 配置服务器端 SASL LDAP 身份验证插件"中所述，MySQL 服务器已使用服务器端 SASL LDAP 插件的适当配置设置启动。MySQL DBA 随后创建一个与 Kerberos 主体名称相对应的 MySQL 账户，包括域名。

  注意

  SASL LDAP 插件为 Kerberos 身份验证使用常量用户 DN，并忽略从 MySQL 配置的任何用户 DN。这有某些含义：

  - 对于任何使用 GSSAPI/Kerberos 身份验证的 MySQL 账户，CREATE USER 或 ALTER USER 语句中的身份验证字符串应不包含用户 DN，因为它没有效果。

  - 因为身份验证字符串不包含用户 DN，它应包含组映射信息，以使用户能够作为代理用户处理，该用户映射到所需的被代理用户。有关使用 LDAP 身份验证插件进行代理的信息，请参阅"LDAP 身份验证与代理"。

以下语句创建一个名为 bredon@MYSQL.LOCAL 的代理用户，该用户承担名为 proxied_krb_usr 的被代理用户的权限。其他应具有相同权限的 GSSAPI/Kerberos 用户可以类似地创建为同一被代理用户的代理用户。

```
-- 创建代理账户
CREATE USER 'bredon@MYSQL.LOCAL'
  IDENTIFIED WITH authentication_ldap_sasl
  BY '#krb_grp=proxied_krb_user';

-- 创建被代理账户并授予其权限；
-- 使用 mysql_no_login 插件防止直接登录
CREATE USER 'proxied_krb_user'
  IDENTIFIED WITH mysql_no_login;
GRANT ALL
  ON krb_user_db.*
  TO 'proxied_krb_user';

-- 向代理账户授予
-- 被代理账户的 PROXY 权限
GRANT PROXY
  ON 'proxied_krb_user'
  TO 'bredon@MYSQL.LOCAL';
```

仔细观察第一个 CREATE USER 语句和 GRANT PROXY 语句中代理账户名称的引用：

- 对于大多数 MySQL 账户，用户和主机是账户名称的单独部分，因此分别引用为 'user_name'@'host_name'。

- 对于 LDAP Kerberos 身份验证，账户名称的用户部分包括主体域，因此 'bredon@MYSQL.LOCAL' 作为单个值引用。因为没有给出主机部分，完整的 MySQL 账户名称使用默认的 '%' 作为主机部分：'bredon@MYSQL.LOCAL'@'%'

  注意

  创建使用 authentication_ldap_sasl SASL LDAP 身份验证插件和 GSSAPI/Kerberos 身份验证方法进行身份验证的账户时，CREATE USER 语句将领域作为用户名的一部分包括在内。这与创建使用 authentication_kerberos Kerberos 插件的账户不同。对于此类账户，CREATE USER 语句不将领域作为用户名的一部分包括在内。而是在 BY 子句中将领域指定为身份验证字符串。请参阅"创建使用 Kerberos 身份验证的 MySQL 账户"。

被代理账户使用 mysql_no_login 身份验证插件来防止客户端使用该账户直接登录到 MySQL 服务器。相反，预期使用 LDAP 进行身份验证的用户使用 bredon@MYSQL.LOCAL 代理账户。（这假设 mysql_no_login 插件已安装。有关说明，请参阅第 8.4.1.8 节"无登录可插拔身份验证"。）有关保护被代理账户免受直接使用的替代方法，请参阅"防止直接登录到被代理账户"。

#### 使用 MySQL 账户连接到 MySQL 服务器

设置使用 GSSAPI/Kerberos 进行身份验证的 MySQL 账户后，客户端可以使用它连接到 MySQL 服务器。Kerberos 身份验证可以在调用 MySQL 客户端程序之前或在调用时进行：

- 在调用 MySQL 客户端程序之前，客户端用户可以独立于 MySQL 从 KDC 获取 TGT。例如，客户端用户可以使用 kinit 通过提供 Kerberos 主体名称和主体密码向 Kerberos 进行身份验证：
  ```
  $> kinit bredon@MYSQL.LOCAL
  Password for bredon@MYSQL.LOCAL: (在此输入密码)
  ```

  生成的 TGT 被缓存并可供其他 Kerberos 感知应用程序使用，例如使用客户端 SASL LDAP 身份验证插件的程序。在这种情况下，MySQL 客户端程序使用 TGT 向 MySQL 服务器进行身份验证，因此调用客户端时不指定用户名或密码：
  ```
  mysql --default-auth=authentication_ldap_sasl_client
  ```

  如上所述，当 TGT 被缓存时，客户端命令中不需要用户名和密码选项。如果命令包含它们，它们的处理方式如下：

  - 如果命令包含用户名，如果该名称与 TGT 中的主体名称不匹配，身份验证将失败。

  - 如果命令包含密码，客户端插件将忽略它。因为身份验证基于 TGT，即使用户提供的密码不正确，它也可能成功。因此，如果找到有效的 TGT 导致密码被忽略，插件会产生警告。

- 如果 Kerberos 缓存不包含 TGT，客户端 SASL LDAP 身份验证插件本身可以从 KDC 获取 TGT。使用与 MySQL 账户关联的 Kerberos 主体的名称和密码的选项调用客户端（在一行上输入命令，然后在提示时输入主体密码）：
  ```
  mysql --default-auth=authentication_ldap_sasl_client
    --user=bredon@MYSQL.LOCAL
    --password
  ```

- 如果 Kerberos 缓存不包含 TGT 且客户端命令未将主体名称指定为用户名，身份验证将失败。

如果不确定 TGT 是否存在，可以使用 klist 检查。

身份验证过程如下：

1. 客户端使用 TGT 使用 Kerberos 进行身份验证。

2. 服务器查找主体的 LDAP 条目，并使用它为 bredon@MYSQL.LOCAL MySQL 代理账户验证连接。

3. 代理账户身份验证字符串中的组映射信息（'#krb_grp=proxied_krb_user'）指示经过身份验证的被代理用户应为 proxied_krb_user。

4. bredon@MYSQL.LOCAL 被视为 proxied_krb_user 的代理，以下查询返回如下所示的输出：
   ```
   mysql> SELECT USER(), CURRENT_USER(), @@proxy_user;
   +------------------------------+--------------------+--------------------------+
   | USER()                       | CURRENT_USER()     | @@proxy_user             |
   +------------------------------+--------------------+--------------------------+
   | bredon@MYSQL.LOCAL@localhost | proxied_krb_user@% | 'bredon@MYSQL.LOCAL'@'%' |
   +------------------------------+--------------------+--------------------------+
   ```

   USER() 值表示用于客户端命令的用户名（bredon@MYSQL.LOCAL）和客户端连接的主机（localhost）。

   CURRENT_USER() 值是被代理用户账户的完整名称，由 proxied_krb_user 用户部分和 % 主机部分组成。

   @@proxy_user 值表示用于连接到 MySQL 服务器的账户的完整名称，由 bredon@MYSQL.LOCAL 用户部分和 % 主机部分组成。

   这表明代理通过 bredon@MYSQL.LOCAL 代理用户账户进行，并且 bredon@MYSQL.LOCAL 承担授予 proxied_krb_user 被代理用户账户的权限。

一旦获得 TGT，它会在客户端缓存，可以在过期前使用，无需再次指定密码。无论如何获得 TGT，客户端插件都使用它来获取服务票证并与服务器端插件通信。

  注意

  当客户端身份验证插件本身获得 TGT 时，客户端用户可能不希望 TGT 被重用。如"LDAP 身份验证的客户端配置参数"中所述，本地 /etc/krb5.conf 文件可用于使客户端插件在完成后销毁 TGT。

服务器端插件无法访问 TGT 本身或用于获取它的 Kerberos 密码。

LDAP 身份验证插件无法控制缓存机制（存储在本地文件、内存等中），但 Kerberos 实用程序（如 kswitch）可能可用于此目的。

#### LDAP 身份验证的客户端配置参数

authentication_ldap_sasl_client 客户端 SASL LDAP 插件读取本地 /etc/krb5.conf 文件。如果此文件缺失或无法访问，会发生错误。假设文件可访问，它可以包含可选的 [appdefaults] 部分以提供插件使用的信息。将信息放在部分的 mysql 部分内。例如：

```
[appdefaults]
  mysql = {
    ldap_server_host = "ldap_host.example.com"
    ldap_destroy_tgt = true
  }
```

客户端插件在 mysql 部分中识别这些参数：

- ldap_server_host 值指定 LDAP 服务器主机，当该主机与 [realms] 部分中指定的 KDC 服务器主机不同时可能很有用。默认情况下，插件使用 KDC 服务器主机作为 LDAP 服务器主机。

- ldap_destroy_tgt 值指示客户端插件是否在获取和使用 TGT 后销毁它。默认情况下，ldap_destroy_tgt 为 false，但可以设置为 true 以避免 TGT 重用。（此设置仅适用于由客户端插件创建的 TGT，不适用于由其他插件创建或在 MySQL 外部创建的 TGT。）

#### LDAP 搜索引荐

LDAP 服务器可以配置为将 LDAP 搜索委托给另一个 LDAP 服务器，这种功能称为 LDAP 引荐。假设服务器 a.example.com 持有"dc=example,dc=com"根 DN，并希望将搜索委托给另一个服务器 b.example.com。为了启用此功能，a.example.com 将配置一个具有这些属性的命名引荐对象：

```
dn: dc=subtree,dc=example,dc=com
objectClass: referral
objectClass: extensibleObject
dc: subtree
ref: ldap://b.example.com/dc=subtree,dc=example,dc=com
```

启用 LDAP 引荐的一个问题是，当搜索基础 DN 是根 DN 且未设置引荐对象时，搜索可能因 LDAP 操作错误而失败。MySQL DBA 可能希望避免 LDAP 身份验证插件出现此类引荐错误，即使 LDAP 引荐可能在 ldap.conf 配置文件中全局设置。要在特定于插件的基础上配置 LDAP 服务器在与每个插件通信时是否应使用 LDAP 引荐，请设置 authentication_ldap_simple_referral 和 authentication_ldap_sasl_referral 系统变量。将任一变量设置为 ON 或 OFF 会导致相应的 LDAP 身份验证插件告诉 LDAP 服务器在 MySQL 身份验证期间是否使用引荐。每个变量都有特定于插件的效果，不影响与 LDAP 服务器通信的其他应用程序。两个变量默认都为 OFF。
