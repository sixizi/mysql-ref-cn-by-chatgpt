## 8.2.3 授权表

### 授权表

mysql 系统数据库包含多个授权表，其中包含有关用户账户及其所持有的权限的信息。本节描述这些表。有关系统数据库中其他表的信息，请参见第 7.3 节"mysql 系统架构"。

本节讨论授权表的基础结构以及服务器在与客户端交互时如何使用其内容。但是，通常不应直接修改授权表。当使用账户管理语句（如 CREATE USER、GRANT 和 REVOKE）来设置账户和控制每个账户可用的权限时，修改会间接发生。请参见第 15.7.1 节"账户管理语句"。使用这些语句执行账户操作时，服务器会代表你修改授权表。

> **注意**
>
> 不建议使用 INSERT、UPDATE 或 DELETE 等语句直接修改授权表，这样做风险自负。服务器可以自由忽略因此类修改而变得格式错误的行。
>
> 对于任何修改授权表的操作，服务器都会检查该表是否具有预期的结构，如果不符合则产生错误。要将表更新为预期的结构，请执行 MySQL 升级过程。请参见第 3 章"升级 MySQL"。

### 授权表概述

这些 mysql 数据库表包含授权信息：

- user：用户账户、静态全局权限和其他非权限列。

- global_grants：动态全局权限。

- db：数据库级权限。

- tables_priv：表级权限。

- columns_priv：列级权限。

- procs_priv：存储过程和函数权限。

- proxies_priv：代理用户权限。

- default_roles：默认用户角色。

- role_edges：角色子图的边。

- password_history：密码更改历史。

有关静态和动态全局权限之间差异的信息，请参见"静态与动态权限"。

授权表使用 InnoDB 存储引擎且是事务性的。每个语句要么对所有指定用户成功，要么在发生任何错误时回滚且无任何影响。

每个授权表包含作用域列和权限列：

- 作用域列确定表中每一行的作用域；即该行适用的上下文。例如，Host 和 User 值为 'h1.example.net' 和 'bob' 的 user 表行适用于从主机 h1.example.net 向服务器进行的身份验证连接，其中客户端指定的用户名为 bob。类似地，Host、User 和 Db 列值为 'h1.example.net'、'bob' 和 'reports' 的 db 表行适用于 bob 从主机 h1.example.net 连接以访问 reports 数据库的情况。tables_priv 和 columns_priv 表包含作用域列，指示每一行适用的表或表/列组合。procs_priv 作用域列指示每一行适用的存储例程。

- 权限列指示表行授予的权限；即它允许执行的操作。服务器组合各个授权表中的信息以形成用户权限的完整描述。第 8.2.7 节"访问控制，第 2 阶段：请求验证"描述了这些规则。

此外，授权表可能包含用于作用域或权限评估以外目的的列。

服务器按以下方式使用授权表：

- user 表作用域列确定是否拒绝或允许传入连接。对于允许的连接，user 表中授予的任何权限指示用户的静态全局权限。此表中授予的任何权限适用于服务器上的所有数据库。

  > **警告**
  >
  > 由于任何静态全局权限被视为所有数据库的权限，任何静态全局权限都使用户能够使用 SHOW DATABASES 或通过检查 INFORMATION_SCHEMA 的 SCHEMATA 表来查看所有数据库名称，除了已通过部分撤销在数据库级别受限的数据库。

- global_grants 表列出了对用户账户的动态全局权限的当前分配。对于每一行，作用域列确定哪个用户具有权限列中命名的权限。

- db 表作用域列确定哪些用户可以从哪些主机访问哪些数据库。权限列确定允许的操作。在数据库级别授予的权限适用于数据库及数据库中的所有对象，如表和存储程序。

- tables_priv 和 columns_priv 表类似于 db 表，但更精细：它们在表和列级别而不是数据库级别应用。在表级别授予的权限适用于表及其所有列。在列级别授予的权限仅适用于特定列。

- procs_priv 表适用于存储例程（存储过程和函数）。在例程级别授予的权限仅适用于单个过程或函数。

- proxies_priv 表指示哪些用户可以充当其他用户的代理，以及用户是否可以将 PROXY 权限授予其他用户。

- default_roles 和 role_edges 表包含有关角色关系的信息。

- password_history 表保留以前选择的密码，以启用对密码重用的限制。请参见第 8.2.15 节"密码管理"。

服务器在启动时将授权表的内容读入内存。可以通过发出 FLUSH PRIVILEGES 语句或执行 mysqladmin flush-privileges 或 mysqladmin reload 命令来告诉它重新加载表。授权表的更改生效如第 8.2.13 节"权限更改何时生效"所示。

修改账户时，最好验证更改是否具有预期效果。要检查给定账户的权限，请使用 SHOW GRANTS 语句。例如，要确定授予用户名和主机名值为 bob 和 pc84.example.com 的账户的权限，请使用此语句：

```
SHOW GRANTS FOR 'bob'@'pc84.example.com';
```

要显示账户的非权限属性，请使用 SHOW CREATE USER：

```
SHOW CREATE USER 'bob'@'pc84.example.com';
```

### user 和 db 授权表

服务器在访问控制的第一和第二阶段都使用 mysql 数据库中的 user 和 db 表（请参见第 8.2 节"访问控制和账户管理"）。user 和 db 表中的列如下所示。

**表 8.4 user 和 db 表列**

| 表名 | user | db |
|------|------|-----|
| 作用域列 | Host<br/>User | Host<br/>Db<br/>User |
| 权限列 | Select_priv<br/>Insert_priv<br/>Update_priv<br/>Delete_priv<br/>Index_priv<br/>Alter_priv<br/>Create_priv<br/>Drop_priv<br/>Grant_priv<br/>Create_view_priv<br/>Show_view_priv<br/>Create_routine_priv<br/>Alter_routine_priv<br/>Execute_priv<br/>Trigger_priv<br/>Event_priv<br/>Create_tmp_table_priv<br/>Lock_tables_priv<br/>References_priv<br/>Reload_priv<br/>Shutdown_priv<br/>Process_priv<br/>File_priv<br/>Show_db_priv<br/>Super_priv<br/>Repl_slave_priv<br/>Repl_client_priv<br/>Create_user_priv<br/>Create_tablespace_priv<br/>Create_role_priv<br/>Drop_role_priv | Select_priv<br/>Insert_priv<br/>Update_priv<br/>Delete_priv<br/>Index_priv<br/>Alter_priv<br/>Create_priv<br/>Drop_priv<br/>Grant_priv<br/>Create_view_priv<br/>Show_view_priv<br/>Create_routine_priv<br/>Alter_routine_priv<br/>Execute_priv<br/>Trigger_priv<br/>Event_priv<br/>Create_tmp_table_priv<br/>Lock_tables_priv<br/>References_priv |
| 安全列 | ssl_type<br/>ssl_cipher<br/>x509_issuer<br/>x509_subject<br/>plugin<br/>authentication_string<br/>password_expired<br/>password_last_changed<br/>password_lifetime<br/>account_locked<br/>Password_reuse_history<br/>Password_reuse_time<br/>Password_require_current<br/>User_attributes | |
| 资源控制列 | max_questions<br/>max_updates<br/>max_connections<br/>max_user_connections | |

user 表 plugin 和 authentication_string 列存储身份验证插件和凭证信息。

服务器使用账户行的 plugin 列中命名的插件来对该账户的连接尝试进行身份验证。

plugin 列必须非空。在启动时以及运行时执行 FLUSH PRIVILEGES 时，服务器检查 user 表行。对于任何 plugin 列为空的行，服务器会向错误日志写入以下形式的警告：

```
[Warning] User entry 'user_name'@'host_name' has an empty plugin
value. The user will be ignored and no one can login with this user
anymore.
```

要为缺少插件的账户分配插件，请使用 ALTER USER 语句。

password_expired 列允许 DBA 使账户密码过期并要求用户重置其密码。默认 password_expired 值为 'N'，但可以使用 ALTER USER 语句设置为 'Y'。账户密码过期后，该账户在后续连接到服务器时执行的所有操作都会导致错误，直到用户发出 ALTER USER 语句来建立新的账户密码。

> **注意**
>
> 虽然可以通过将过期密码设置为其当前值来"重置"它，但作为良好策略的问题，最好选择不同的密码。DBA 可以通过建立适当的密码重用策略来强制不重用。请参见"密码重用策略"。

password_last_changed 是一个 TIMESTAMP 列，指示密码上次更改的时间。该值仅对使用 MySQL 内置身份验证插件（sha256_password 或 caching_sha2_password）的账户非 NULL。对于其他账户（如使用外部身份验证系统进行身份验证的账户），该值为 NULL。

password_last_changed 由 CREATE USER、ALTER USER 和 SET PASSWORD 语句以及创建账户或更改账户密码的 GRANT 语句更新。

password_lifetime 指示账户密码生命周期，以天为单位。如果密码超过其生命周期（使用 password_last_changed 列进行评估），当客户端使用该账户连接时，服务器认为密码已过期。大于零的值 N 意味着必须每 N 天更改一次密码。值 0 禁用自动密码过期。如果值为 NULL（默认值），则应用全局过期策略，如 default_password_lifetime 系统变量所定义。

account_locked 指示账户是否被锁定（请参见第 8.2.20 节"账户锁定"）。

Password_reuse_history 是账户的 PASSWORD HISTORY 选项的值，或默认历史的 NULL。

Password_reuse_time 是账户的 PASSWORD REUSE INTERVAL 选项的值，或默认间隔的 NULL。

Password_require_current 对应于账户的 PASSWORD REQUIRE 选项的值，如下表所示。

**表 8.5 允许的 Password_require_current 值**

| Password_require_current 值 | 对应的 PASSWORD REQUIRE 选项 |
|-----|-----|
| 'Y' | PASSWORD REQUIRE CURRENT |
| 'N' | PASSWORD REQUIRE CURRENT OPTIONAL |
| NULL | PASSWORD REQUIRE CURRENT DEFAULT |

User_attributes 是一个 JSON 格式的列，存储未存储在其他列中的账户属性。INFORMATION_SCHEMA 通过 USER_ATTRIBUTES 表公开这些属性。

User_attributes 列可能包含这些属性：

- additional_password：辅助密码（如果有）。请参见"双密码支持"。

- Restrictions：限制列表（如果有）。限制由部分撤销操作添加。属性值是一个元素数组，每个元素都有 Database 和 Restrictions 键，指示受限数据库的名称和对其适用的限制（请参见第 8.2.12 节"使用部分撤销的权限限制"）。

- Password_locking：失败登录跟踪和临时账户锁定的条件（如果有）（请参见"失败登录跟踪和临时账户锁定"）。Password_locking 属性根据 CREATE USER 和 ALTER USER 语句的 FAILED_LOGIN_ATTEMPTS 和 PASSWORD_LOCK_TIME 选项进行更新。属性值是一个哈希，具有 failed_login_attempts 和 password_lock_time_days 键，指示为账户指定的此类选项的值。如果缺少键，其值隐式为 0。如果键值隐式或显式为 0，则禁用相应的功能。

- multi_factor_authentication：mysql.user 系统表中的行有一个 plugin 列，指示身份验证插件。对于单因素身份验证，该插件是唯一的身份验证因素。对于双因素或三因素形式的多因素身份验证，该插件对应于第一个身份验证因素，但必须为第二和第三因素存储其他信息。multi_factor_authentication 属性保存此信息。

  multi_factor_authentication 值是一个数组，其中每个数组元素是一个哈希，使用这些属性描述身份验证因素：

  - plugin：身份验证插件的名称。

  - authentication_string：身份验证字符串值。

  - passwordless：一个标志，表示用户是否应在没有密码的情况下使用（仅使用安全令牌作为身份验证方法）。

  - requires_registration：一个标志，定义用户账户是否已注册安全令牌。

  第一和第二数组元素描述多因素身份验证因素 2 和 3。

如果不适用任何属性，User_attributes 为 NULL。

示例：具有辅助密码和部分撤销数据库权限的账户在列值中具有 additional_password 和 Restrictions 属性：

```
mysql> SELECT User_attributes FROM mysql.User WHERE User = 'u'\G
*************************** 1. row ***************************
User_attributes: {"Restrictions":
                   [{"Database": "mysql", "Privileges": ["SELECT"]}],
                  "additional_password": "hashed_credentials"}
```

要确定存在哪些属性，请使用 JSON_KEYS() 函数：

```
SELECT User, Host, JSON_KEYS(User_attributes)
FROM mysql.user WHERE User_attributes IS NOT NULL;
```

要提取特定属性（如 Restrictions），请执行以下操作：

```
SELECT User, Host, User_attributes->>'$.Restrictions'
FROM mysql.user WHERE User_attributes->>'$.Restrictions' <> '';
```

以下是为 multi_factor_authentication 存储的信息类型的示例：

```
{
    "multi_factor_authentication": [
      {
         "plugin": "authentication_ldap_simple",
         "passwordless": 0,
         "authentication_string": "ldap auth string",
         "requires_registration": 0
      },
      {
         "plugin": "authentication_webauthn",
         "passwordless": 0,
         "authentication_string": "",
         "requires_registration": 1
      }
    ]
}
```

### tables_priv 和 columns_priv 授权表

在访问控制的第二阶段，服务器执行请求验证以确保每个客户端对其发出的每个请求都有足够的权限。除了 user 和 db 授权表外，服务器还可能查询 tables_priv 和 columns_priv 表以处理涉及表的请求。后者的表在表和列级别提供更精细的权限控制。它们具有下表所示的列。

**表 8.6 tables_priv 和 columns_priv 表列**

| 表名 | tables_priv | columns_priv |
|------|------|-----|
| 作用域列 | Host<br/>Db<br/>User<br/>Table_name | Host<br/>Db<br/>User<br/>Table_name<br/>Column_name |
| 权限列 | Table_priv<br/>Column_priv | Column_priv |
| 其他列 | Timestamp<br/>Grantor | Timestamp<br/>Grantor |

Timestamp 和 Grantor 列分别设置为当前时间戳和 CURRENT_USER 值，但在其他方面未使用。

### procs_priv 授权表

对于涉及存储例程的请求验证，服务器可能查询 procs_priv 表，该表具有下表所示的列。

**表 8.7 procs_priv 表列**

| 表名 | procs_priv |
|------|------|
| 作用域列 | Host<br/>Db<br/>User<br/>Routine_name<br/>Routine_type |
| 权限列 | Proc_priv |
| 其他列 | Timestamp<br/>Grantor |

Routine_type 列是一个 ENUM 列，值为 'FUNCTION' 或 'PROCEDURE'，用于指示行所指的例程类型。此列使权限能够为具有相同名称的函数和过程分别授予。

Timestamp 和 Grantor 列未使用。

### proxies_priv 授权表

proxies_priv 表记录有关代理账户的信息。它具有这些列：

- Host、User：代理账户；即具有代理账户的 PROXY 权限的账户。

- Proxied_host、Proxied_user：被代理账户。

- Grantor、Timestamp：未使用。

- With_grant：代理账户是否可以将 PROXY 权限授予其他账户。

要使账户能够将 PROXY 权限授予其他账户，它必须在 proxies_priv 表中有一行，其中 With_grant 设置为 1，Proxied_host 和 Proxied_user 设置为指示可以授予权限的账户。例如，MySQL 安装期间创建的 'root'@'localhost' 账户在 proxies_priv 表中有一行，该行启用为 ''@''（即所有用户和所有主机）授予 PROXY 权限。这使 root 能够设置代理用户，以及将设置代理用户的权限委派给其他账户。请参见第 8.2.19 节"代理用户"。

### global_grants 授权表

global_grants 表列出了对用户账户的动态全局权限的当前分配。该表具有这些列：

- USER、HOST：授予权限的账户的用户名和主机名。

- PRIV：权限名称。

- WITH_GRANT_OPTION：账户是否可以将权限授予其他账户。

### default_roles 授权表

default_roles 表列出默认用户角色。它具有这些列：

- HOST、USER：应用默认角色的账户或角色。

- DEFAULT_ROLE_HOST、DEFAULT_ROLE_USER：默认角色。

### role_edges 授权表

role_edges 表列出角色子图的边。它具有这些列：

- FROM_HOST、FROM_USER：被授予角色的账户。

- TO_HOST、TO_USER：授予给账户的角色。

- WITH_ADMIN_OPTION：账户是否可以使用 WITH ADMIN OPTION 将角色授予和从其他账户撤销。

### password_history 授权表

password_history 表包含有关密码更改的信息。它具有这些列：

- Host、User：发生密码更改的账户。

- Password_timestamp：密码更改发生的时间。

- Password：新密码哈希值。

password_history 表为每个账户累积足够数量的非空密码，以使 MySQL 能够对账户密码历史长度和重用间隔进行检查。当发生密码更改尝试时，会自动修剪超出两个限制的条目。

> **注意**
>
> 空密码不计入密码历史，可以随时重用。

如果账户被重命名，其条目将被重命名以匹配。如果账户被删除或其身份验证插件被更改，其条目将被删除。

### 授权表作用域列属性

授权表中的作用域列包含字符串。每个的默认值是空字符串。下表显示了每列中允许的字符数。

**表 8.8 授权表作用域列长度**

| 列名 | 最大允许字符数 |
|------|------|
| Host、Proxied_host | 255 |
| User、Proxied_user | 32 |
| Db | 64 |
| Table_name | 64 |
| Column_name | 64 |
| Routine_name | 64 |

Host 和 Proxied_host 值在存储到授权表之前被转换为小写。

对于访问检查目的，User、Proxied_user、authentication_string、Db 和 Table_name 值的比较区分大小写。Host、Proxied_host、Column_name 和 Routine_name 值的比较不区分大小写。

### 授权表权限列属性

user 和 db 表将每个权限列在单独的列中，声明为 ENUM('N','Y') DEFAULT 'N'。换句话说，每个权限可以被禁用或启用，默认为禁用。

tables_priv、columns_priv 和 procs_priv 表将权限列声明为 SET 列。这些列中的值可以包含表控制的权限的任何组合。只有列值中列出的那些权限才被启用。

**表 8.9 SET 类型权限列值**

| 表名 | 列名 | 可能的 SET 元素 |
|------|------|------|
| tables_priv | Table_priv | 'Select'、'Insert'、'Update'、'Delete'、'Create'、'Drop'、'Grant'、'References'、'Index'、'Alter'、'Create View'、'Show view'、'Trigger' |
| tables_priv | Column_priv | 'Select'、'Insert'、'Update'、'References' |
| columns_priv | Column_priv | 'Select'、'Insert'、'Update'、'References' |
| procs_priv | Proc_priv | 'Execute'、'Alter Routine'、'Grant' |

只有 user 和 global_grants 表指定管理权限，如 RELOAD、SHUTDOWN 和 SYSTEM_VARIABLES_ADMIN。管理操作是对服务器本身的操作，不是特定于数据库的，因此没有理由在其他授权表中列出这些权限。因此，服务器只需查询 user 和 global_grants 表来确定用户是否可以执行管理操作。

FILE 权限也仅在 user 表中指定。它本身不是管理权限，但用户在服务器主机上读取或写入文件的能力与所访问的数据库无关。

### 授权表并发

为了允许对 MySQL 授权表的并发 DML 和 DDL 操作，以前在 MySQL 授权表上获取行锁的读操作作为非锁定读执行。在 MySQL 授权表上作为非锁定读执行的操作包括：

- SELECT 语句和其他只读语句，通过联接列表和子查询从授权表读取数据，包括 SELECT ... FOR SHARE 语句，使用任何事务隔离级别。

- DML 操作从授权表读取数据（通过联接列表或子查询）但不修改它们，使用任何事务隔离级别。

不再在从授权表读取数据时获取行锁的语句在使用基于语句的复制时执行时报告警告。

使用 -binlog_format=mixed 时，从授权表读取数据的 DML 操作作为行事件写入二进制日志，以使操作对混合模式复制安全。

读取授权表数据的 SELECT ... FOR SHARE 语句报告警告。使用 FOR SHARE 子句时，授权表不支持读锁。

使用 SERIALIZABLE 隔离级别执行的从授权表读取数据的 DML 操作报告警告。使用 SERIALIZABLE 隔离级别时通常会获取的读锁在授权表上不受支持。
