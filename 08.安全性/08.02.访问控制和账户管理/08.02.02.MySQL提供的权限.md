## 8.2.2 MySQL 提供的权限

授予 MySQL 账户的权限决定了该账户可以执行哪些操作。MySQL 权限在应用的上下文和操作级别上有所不同：

- 管理权限使用户能够管理 MySQL 服务器的运行。这些权限是全局的，因为它们不特定于某个特定数据库。

- 数据库权限适用于数据库及其中的所有对象。这些权限可以为特定数据库授予，也可以全局授予以适用于所有数据库。

- 数据库对象（如表、索引、视图和存储例程）的权限可以为数据库内的特定对象授予，为数据库内给定类型的所有对象授予（例如，数据库中的所有表），或为所有数据库中给定类型的所有对象全局授予。

权限还在是否为静态权限（内置于服务器）或动态权限（在运行时定义）方面有所不同。权限是静态还是动态会影响其是否可以授予用户账户和角色。有关静态权限和动态权限之间差异的信息，请参见"静态权限与动态权限"。

账户权限信息存储在 mysql 系统数据库的授权表中。有关这些表的结构和内容的描述，请参见第 8.2.3 节"授权表"。MySQL 服务器在启动时将授权表的内容读入内存，并在第 8.2.13 节"权限变更何时生效"中指示的情况下重新加载它们。服务器基于授权表的内存副本做出访问控制决策。

> 重要
>
> 某些 MySQL 版本引入了对授权表的更改以添加新权限或功能。为了确保您可以利用任何新功能，在升级 MySQL 时将授权表更新为当前结构。请参见第 3 章"升级 MySQL"。

### 静态权限描述

静态权限内置于服务器，与在运行时定义的动态权限相对。以下列表描述了 MySQL 中可用的每个静态权限。

特定的 SQL 语句可能比此处指示的有更具体的权限要求。如果是这样，相关语句的描述会提供详细信息。

- ALL, ALL PRIVILEGES

  这些权限说明符是"给定权限级别上所有可用权限"的简写（GRANT OPTION 除外）。例如，在全局或表级别授予 ALL 会授予所有全局权限或所有表级权限。

- ALTER

  启用使用 ALTER TABLE 语句更改表的结构。ALTER TABLE 还需要 CREATE 和 INSERT 权限。重命名表需要对旧表的 ALTER 和 DROP，以及对新表的 CREATE 和 INSERT。

- ALTER ROUTINE

  启用用于修改或删除存储例程（存储过程和函数）的语句。对于在授予权限的范围内且用户不是命名为例程 DEFINER 的用户的例程，还启用对例程属性（除例程定义外）的访问。

- CREATE

  启用用于创建新数据库和表的语句。

- CREATE ROLE

  启用使用 CREATE ROLE 语句。（CREATE USER 权限也启用 CREATE ROLE 语句的使用。）请参见第 8.2.10 节"使用角色"。

  CREATE ROLE 和 DROP ROLE 权限不如 CREATE USER 强大，因为它们只能用于创建和删除账户。它们不能像 CREATE USER 那样用于修改账户属性或重命名账户。请参见"用户和角色互换性"。

- CREATE ROUTINE

  启用用于创建存储例程（存储过程和函数）的语句。对于在授予权限的范围内且用户不是命名为例程 DEFINER 的用户的例程，还启用对例程属性（除例程定义外）的访问。

- CREATE TABLESPACE

  启用用于创建、修改或删除表空间和日志文件组的语句。

- CREATE TEMPORARY TABLES

  启用使用 CREATE TEMPORARY TABLE 语句创建临时表。

  会话创建临时表后，服务器不再对该表执行进一步的权限检查。创建会话可以对表执行任何操作，如 DROP TABLE、INSERT、UPDATE 或 SELECT。有关更多信息，请参见第 15.1.25.2 节"CREATE TEMPORARY TABLE 语句"。

- CREATE USER

  启用使用 ALTER USER、CREATE ROLE、CREATE USER、DROP ROLE、DROP USER、RENAME USER 和 REVOKE ALL PRIVILEGES 语句。

- CREATE VIEW

  启用使用 CREATE VIEW 语句。

- DELETE

  启用从数据库中的表删除行。

- DROP

  启用用于删除（移除）现有数据库、表和视图的语句。在分区表上使用 ALTER TABLE ... DROP PARTITION 语句需要 DROP 权限。TRUNCATE TABLE 也需要 DROP 权限。

- DROP ROLE

  启用使用 DROP ROLE 语句。（CREATE USER 权限也启用 DROP ROLE 语句的使用。）请参见第 8.2.10 节"使用角色"。

  CREATE ROLE 和 DROP ROLE 权限不如 CREATE USER 强大，因为它们只能用于创建和删除账户。它们不能像 CREATE USER 那样用于修改账户属性或重命名账户。请参见"用户和角色互换性"。

- EVENT

  启用用于为事件调度程序创建、修改、删除或显示事件的语句。

- EXECUTE

  启用用于执行存储例程（存储过程和函数）的语句。对于在授予权限的范围内且用户不是命名为例程 DEFINER 的用户的例程，还启用对例程属性（除例程定义外）的访问。

- FILE

  影响以下操作和服务器行为：

  - 启用使用 LOAD DATA 和 SELECT ... INTO OUTFILE 语句以及 LOAD_FILE() 函数在服务器主机上读取和写入文件。具有 FILE 权限的用户可以读取服务器主机上任何世界可读或 MySQL 服务器可读的文件。（这意味着用户可以读取任何数据库目录中的任何文件，因为服务器可以访问这些文件中的任何一个。）

  - 启用在 MySQL 服务器具有写入访问权限的任何目录中创建新文件。这包括包含实现权限表的文件的服务器数据目录。

  - 启用对 CREATE TABLE 语句使用 DATA DIRECTORY 或 INDEX DIRECTORY 表选项。

  作为安全措施，服务器不会覆盖现有文件。

  要限制可以读取和写入文件的位置，请将 secure_file_priv 系统变量设置为特定目录。请参见第 7.1.8 节"服务器系统变量"。

- GRANT OPTION

  启用您向其他用户授予或从其他用户撤销您自己拥有的权限。

- INDEX

  启用用于创建或删除（移除）索引的语句。INDEX 适用于现有表。如果您对表具有 CREATE 权限，可以在 CREATE TABLE 语句中包含索引定义。

- INSERT

  启用向数据库中的表插入行。INSERT 也是 ANALYZE TABLE、OPTIMIZE TABLE 和 REPAIR TABLE 表维护语句所需的。

- LOCK TABLES

  启用使用显式 LOCK TABLES 语句锁定您具有 SELECT 权限的表。这包括使用写入锁，这会阻止其他会话读取锁定的表。

- PROCESS

  PROCESS 权限控制对在服务器内执行的线程信息的访问（即，关于会话执行的语句的信息）。使用 SHOW PROCESSLIST 语句、mysqladmin processlist 命令、Information Schema PROCESSLIST 表和 Performance Schema processlist 表可用的线程信息的访问方式如下：

  - 具有 PROCESS 权限，用户可以访问所有线程的信息，即使是属于其他用户的线程。

  - 没有 PROCESS 权限，非匿名用户可以访问其自己线程的信息，但不能访问其他用户的线程，匿名用户无法访问线程信息。

  > 注意
  >
  > Performance Schema threads 表也提供线程信息，但表访问使用不同的权限模型。请参见第 29.12.23.10 节"threads 表"。

  PROCESS 权限还启用使用 SHOW ENGINE 语句、访问 INFORMATION_SCHEMA InnoDB 表（名称以 INNODB_ 开头的表）以及访问 INFORMATION_SCHEMA FILES 表。

- PROXY

  启用一个用户模拟或被称为另一个用户。请参见第 8.2.19 节"代理用户"。

- REFERENCES

  创建外键约束需要对父表的 REFERENCES 权限。

- RELOAD

  RELOAD 启用以下操作：

  - 使用 FLUSH 语句。

  - 使用等同于 FLUSH 操作的 mysqladmin 命令：flush-hosts、flush-logs、flush-privileges、flush-status、flush-tables、refresh 和 reload。

    reload 命令告诉服务器将授权表重新加载到内存中。flush-privileges 是 reload 的同义词。refresh 命令关闭并重新打开日志文件并刷新所有表。其他 flush-xxx 命令执行类似于 refresh 的功能，但更具体，在某些情况下可能更可取。例如，如果您只想刷新日志文件，flush-logs 是比 refresh 更好的选择。

  - 使用执行各种 FLUSH 操作的 mysqldump 选项：--flush-logs 和 --source-data。

  - 使用 RESET BINARY LOGS AND GTIDS 和 RESET REPLICA 语句。

- REPLICATION CLIENT

  启用使用 SHOW BINARY LOG STATUS、SHOW REPLICA STATUS 和 SHOW BINARY LOGS 语句。

- REPLICATION SLAVE

  启用账户请求对复制源服务器上的数据库所做的更新，使用 SHOW REPLICAS、SHOW RELAYLOG EVENTS 和 SHOW BINLOG EVENTS 语句。此权限也是使用 mysqlbinlog 选项 --read-from-remote-server (-R) 和 --read-from-remote-source 所需的。将此权限授予由副本用于连接到当前服务器作为其复制源服务器的账户。

- SELECT

  启用从数据库中的表选择行。SELECT 语句仅在实际访问表时才需要 SELECT 权限。某些 SELECT 语句不访问表，可以在没有任何数据库权限的情况下执行。例如，您可以使用 SELECT 作为简单计算器来评估不引用表的表达式：

  ```
  SELECT 1+1;
  SELECT PI()*2;
  ```

  SELECT 权限也是读取列值的其他语句所需的。例如，SELECT 对于在 UPDATE 语句中 col_name=expr 赋值右侧引用的列或在 DELETE 或 UPDATE 语句的 WHERE 子句中命名的列是必需的。

  SELECT 权限对于与 EXPLAIN 一起使用的表或视图是必需的，包括视图定义中的任何基础表。

- SHOW DATABASES

  启用账户通过发出 SHOW DATABASE 语句查看数据库名称。没有此权限的账户只能看到它们具有某些权限的数据库，如果服务器以 --skip-show-database 选项启动，则根本无法使用该语句。

  > 注意
  >
  > 因为任何静态全局权限被视为所有数据库的权限，任何静态全局权限使用户能够使用 SHOW DATABASES 查看所有数据库名称或通过检查 INFORMATION_SCHEMA 的 SCHEMATA 表，除了在数据库级别被部分撤销限制的数据库。

- SHOW VIEW

  启用使用 SHOW CREATE VIEW 语句。此权限也是与 EXPLAIN 一起使用的视图所需的。

- SHUTDOWN

  启用使用 SHUTDOWN 和 RESTART 语句、mysqladmin shutdown 命令以及 mysql_shutdown() C API 函数。

- SUPER

  SUPER 是一个强大而深远的权限，不应轻易授予。如果账户只需要执行 SUPER 操作的子集，可能可以通过改为授予一个或多个动态权限来实现所需的权限集，每个权限都赋予更有限的功能。请参见"动态权限描述"。

  > 注意
  >
  > SUPER 已弃用，您应该期望它在 MySQL 的未来版本中被移除。请参见"从 SUPER 迁移账户到动态权限"。

  SUPER 影响以下操作和服务器行为：

  - 启用运行时系统变量更改：

    - 启用使用 SET GLOBAL 和 SET PERSIST 对全局系统变量进行服务器配置更改。

      对应的动态权限是 SYSTEM_VARIABLES_ADMIN。

    - 启用设置需要特殊权限的受限会话系统变量。

      对应的动态权限是 SESSION_VARIABLES_ADMIN。

    请参见第 7.1.9.1 节"系统变量权限"。

  - 启用对全局事务特性的更改（请参见第 15.3.7 节"SET TRANSACTION 语句"）。

    对应的动态权限是 SYSTEM_VARIABLES_ADMIN。

  - 启用账户启动和停止复制，包括组复制。

    对应的动态权限是用于常规复制的 REPLICATION_SLAVE_ADMIN，用于组复制的 GROUP_REPLICATION_ADMIN。

  - 启用使用 CHANGE REPLICATION SOURCE TO 和 CHANGE REPLICATION FILTER 语句。

    对应的动态权限是 REPLICATION_SLAVE_ADMIN。

  - 启用通过 PURGE BINARY LOGS 和 BINLOG 语句进行二进制日志控制。

    对应的动态权限是 BINLOG_ADMIN。

  - 启用在执行视图或存储程序时设置有效授权 ID。具有此权限的用户可以在视图或存储程序的 DEFINER 属性中指定任何账户。

    对应的动态权限是 SET_ANY_DEFINER 和 ALLOW_NONEXISTENT_DEFINER。

  - 启用使用 CREATE SERVER、ALTER SERVER 和 DROP SERVER 语句。

  - 启用使用 mysqladmin debug 命令。

  - 启用 InnoDB 加密密钥轮换。

    对应的动态权限是 ENCRYPTION_KEY_ADMIN。

  - 启用执行已弃用的版本令牌函数。

    对应的动态权限是已弃用的 VERSION_TOKEN_ADMIN。

  - 启用授予和撤销角色、使用 GRANT 语句的 WITH ADMIN OPTION 子句以及 ROLES_GRAPHML() 函数结果中的非空 <graphml> 元素内容。

    对应的动态权限是 ROLE_ADMIN。

  - 启用对不允许非 SUPER 账户的客户端连接的控制：

    - 启用使用 KILL 语句或 mysqladmin kill 命令杀死属于其他账户的线程。（账户始终可以杀死其自己的线程。）

    - 当 SUPER 客户端连接时，服务器不执行 init_connect 系统变量内容。

    - 即使达到由 max_connections 系统变量配置的连接限制，服务器也接受来自 SUPER 客户端的一个连接。

    - 处于离线模式（offline_mode 启用）的服务器在下一个客户端请求时不会终止 SUPER 客户端连接，并接受来自 SUPER 客户端的新连接。

    - 即使启用了 read_only 系统变量，也可以执行更新。这适用于显式表更新以及隐式更新表的账户管理语句（如 GRANT 和 REVOKE）的使用。

    前述连接控制操作的对应动态权限是 CONNECTION_ADMIN。

  如果启用了二进制日志，您可能还需要 SUPER 权限来创建或修改存储函数，如第 27.9 节"存储程序二进制日志"中所述。

- TRIGGER

  启用触发器操作。您必须对表具有此权限才能为该表创建、删除、执行或显示触发器。

  当触发器被激活（由具有对与触发器关联的表执行 INSERT、UPDATE 或 DELETE 语句的权限的用户）时，触发器执行需要定义触发器的用户仍然对该表具有 TRIGGER 权限。

- UPDATE

  启用更新数据库中表中的行。

- USAGE

  此权限说明符代表"无权限"。它在全局级别与 GRANT 一起使用，以指定诸如 WITH GRANT OPTION 之类的子句，而不在权限列表中命名特定账户权限。SHOW GRANTS 显示 USAGE 以指示账户在权限级别上没有权限。

### 动态权限描述

动态权限在运行时定义，与内置于服务器的静态权限相对。以下列表描述了 MySQL 中可用的每个动态权限。

大多数动态权限在服务器启动时定义。其他权限由特定组件或插件定义，如权限描述中所示。在这种情况下，除非启用定义它的组件或插件，否则权限不可用。

特定的 SQL 语句可能比此处指示的有更具体的权限要求。如果是这样，相关语句的描述会提供详细信息。

- ALLOW_NONEXISTENT_DEFINER

  启用覆盖安全检查，这些检查旨在防止可能（无意中）导致存储对象变成孤立或导致采用当前孤立的存储对象的操作。没有此权限，任何尝试使用 CREATE PROCEDURE、CREATE FUNCTION、CREATE TRIGGER、CREATE EVENT 或 CREATE VIEW 生成孤立 SQL 过程、函数或视图的尝试都会导致错误。使用 CREATE PROCEDURE、CREATE FUNCTION、CREATE TRIGGER、CREATE EVENT 或 CREATE VIEW 生成孤立对象的尝试也需要 SET_ANY_DEFINER 以及 ALLOW_NONEXISTENT_DEFINER，以便允许与当前用户不同的定义者。

  有关详细信息，请参见"孤立存储对象"。

- APPLICATION_PASSWORD_ADMIN

  对于双密码功能，此权限启用对适用于您自己账户的 ALTER USER 和 SET PASSWORD 语句使用 RETAIN CURRENT PASSWORD 和 DISCARD OLD PASSWORD 子句。此权限是操作您自己的辅助密码所必需的，因为大多数用户只需要一个密码。

  如果允许账户操作所有账户的辅助密码，应该授予 CREATE USER 权限而不是 APPLICATION_PASSWORD_ADMIN。

  有关使用双密码的更多信息，请参见第 8.2.15 节"密码管理"。

- AUDIT_ABORT_EXEMPT

  允许被审计日志过滤器中的"中止"项阻止的查询。此权限由 audit_log 插件定义；请参见第 8.4.6 节"MySQL Enterprise 审计插件（已弃用）"。

  使用 SYSTEM_USER 权限创建的账户在创建时会自动分配 AUDIT_ABORT_EXEMPT 权限。当您执行升级过程时，如果没有现有账户分配了该权限，AUDIT_ABORT_EXEMPT 权限也会分配给具有 SYSTEM_USER 权限的现有账户。因此，具有 SYSTEM_USER 权限的账户可用于在审计配置错误后重新获得对系统的访问权限。

- AUDIT_ADMIN

  启用审计日志配置。此权限由 audit_log 插件定义；请参见第 8.4.6 节"MySQL Enterprise 审计插件（已弃用）"。

- BACKUP_ADMIN

### 8.2.2 MySQL 提供的权限

启用 LOCK INSTANCE FOR BACKUP 语句的执行和对 Performance Schema log_status 表的访问。

注意

除了 BACKUP_ADMIN 外，还需要对 log_status 表的 SELECT 权限才能访问它。

在从早期版本就地升级到 MySQL 26.10 时，BACKUP_ADMIN 权限会自动授予具有 RELOAD 权限的用户。

- AUTHENTICATION_POLICY_ADMIN

authentication_policy 系统变量对 CREATE USER 和 ALTER USER 语句的身份验证相关子句的使用方式施加了某些限制。具有 AUTHENTICATION_POLICY_ADMIN 权限的用户不受这些限制的约束。（对于原本不被允许的语句会发出警告。）

有关 authentication_policy 施加的限制的详细信息，请参阅该变量的说明。

- BINLOG_ADMIN

通过 PURGE BINARY LOGS 和 BINLOG 语句启用二进制日志控制。

- BINLOG_ENCRYPTION_ADMIN

启用设置 binlog_encryption 系统变量，该变量激活或停用二进制日志文件和中继日志文件的加密。BINLOG_ADMIN、SYSTEM_VARIABLES_ADMIN 或 SESSION_VARIABLES_ADMIN 权限不提供此功能。相关的系统变量 binlog_rotate_encryption_master_key_at_startup 在服务器重新启动时自动轮换二进制日志主密钥，不需要此权限。

- CLONE_ADMIN

启用 CLONE 语句的执行。包括 BACKUP_ADMIN 和 SHUTDOWN 权限。

- CONNECTION_ADMIN

启用使用 KILL 语句或 mysqladmin kill 命令来终止属于其他账户的线程。（账户始终可以终止自己的线程。）

启用设置与客户端连接相关的系统变量，或绕过与客户端连接相关的限制。需要 CONNECTION_ADMIN 来激活 MySQL Server 的离线模式，通过将 offline_mode 系统变量的值更改为 ON 来完成。

CONNECTION_ADMIN 权限使具有该权限的管理员能够绕过这些系统变量的影响：

- init_connect：当 CONNECTION_ADMIN 客户端连接时，服务器不执行 init_connect 系统变量内容。

- max_connections：即使达到由 max_connections 系统变量配置的连接限制，服务器也接受来自 CONNECTION_ADMIN 客户端的一个连接。

- offline_mode：处于离线模式的服务器（offline_mode 已启用）在下一个客户端请求时不会终止 CONNECTION_ADMIN 客户端连接，并接受来自 CONNECTION_ADMIN 客户端的新连接。

- read_only：即使启用了 read_only 系统变量，CONNECTION_ADMIN 客户端的更新也可以执行。这适用于显式表更新和隐式更新表的账户管理语句，如 GRANT 和 REVOKE。

Group Replication 组成员需要 CONNECTION_ADMIN 权限，以便在涉及的某个服务器处于离线模式时不会终止 Group Replication 连接。如果使用 MySQL 通信栈（group_replication_communication_stack = MYSQL），没有此权限，处于离线模式的成员将被逐出该组。

- CREATE_SPATIAL_REFERENCE_SYSTEM

启用使用 CREATE SPATIAL REFERENCE SYSTEM、CREATE OR REPLACE SPATIAL REFERENCE SYSTEM 和 DROP SPATIAL REFERENCE SYSTEM 语句。尝试在没有此权限（或 SUPER 权限）的情况下执行这些语句中的任何一个现在会引发错误 ER_CMD_NEED_SUPER_OR_CREATE_SPATIAL_REFERENCE_SYSTEM。

此权限的使用旨在取代为此目的使用 SUPER，应将其视为已弃用。

- ENCRYPTION_KEY_ADMIN

启用 InnoDB 加密密钥轮换。

- EXPORT_QUERY_RESULTS

允许用户将查询结果导出到 OCI 或 AWS 对象存储。

仅适用于 MySQL HeatWave。

- FIREWALL_ADMIN

启用用户为任何用户管理防火墙规则。此权限由 MYSQL_FIREWALL 插件定义；请参阅第 8.4.9 节"MySQL Enterprise Firewall"。

- FIREWALL_EXEMPT

具有此权限的用户免受防火墙限制。此权限由 MYSQL_FIREWALL 插件定义；请参阅第 8.4.9 节"MySQL Enterprise Firewall"。

- FIREWALL_USER

启用用户更新自己的防火墙规则。此权限由 MySQL Enterprise Firewall 插件定义（请参阅第 8.4.9.1 节"MySQL Enterprise Firewall 插件"）。

与防火墙插件一样，此权限已弃用，因此可能在 MySQL 的未来版本中被删除。MySQL Enterprise Firewall 组件（请参阅第 8.4.9.2 节"MySQL Enterprise Firewall 组件"）不支持 FIREWALL_USER，该组件取代了该插件。

- FLUSH_OPTIMIZER_COSTS

启用使用 FLUSH OPTIMIZER_COSTS 语句。

- FLUSH_PRIVILEGES

启用使用 FLUSH PRIVILEGES 语句。

已弃用，与 FLUSH PRIVILEGES 语句一起；预期此权限将在 MySQL 的未来版本中被删除。授予 FLUSH_PRIVILEGES 权限会触发弃用警告。

- FLUSH_STATUS

启用使用 FLUSH STATUS 语句。

- FLUSH_TABLES

启用使用 FLUSH TABLES 语句。

- FLUSH_USER_RESOURCES

启用使用 FLUSH USER_RESOURCES 语句。

- GROUP_REPLICATION_ADMIN

启用账户使用 START GROUP REPLICATION 和 STOP GROUP REPLICATION 语句启动和停止 Group Replication，更改 group_replication_consistency 系统变量的全局设置，以及使用 group_replication_set_write_concurrency() 和 group_replication_set_communication_protocol() 函数。将此权限授予用于管理作为复制组成员的服务器的账户。

- GROUP_REPLICATION_STREAM

允许用户账户用于建立 Group Replication 的组通信连接。当 MySQL 通信栈用于 Group Replication 时（group_replication_communication_stack=MYSQL），必须将其授予恢复用户。

- INNODB_REDO_LOG_ARCHIVE

启用账户激活和停用重做日志存档。

- INNODB_REDO_LOG_ENABLE

启用使用 ALTER INSTANCE {ENABLE|DISABLE} INNODB REDO_LOG 语句启用或停用重做日志记录。

请参阅禁用重做日志记录。

- MANAGE_DATA_MASKING_POLICY

启用账户使用 CREATE MASKING POLICY、SHOW CREATE MASKING POLICY 和 DROP MASKING POLICY 管理掩码策略。

- MASKING_DICTIONARIES_ADMIN

启用账户使用 masking_dictionary_term_add() 和 masking_dictionary_term_remove() 组件函数添加和删除字典术语。账户还需要此动态权限才能使用 masking_dictionary_remove() 函数删除完整字典，该函数删除当前在 mysql.masking_dictionaries 表中与命名字典关联的所有术语。

请参阅第 8.5 节"MySQL Enterprise Data Masking"。

- MYSQL_REST_SERVICE_ADMIN

授予控制 MySQL REST Service 组件生命周期的权限。

启用执行 mysql_rest_service_start()、mysql_rest_service_stop() 和 mysql_rest_service_restart() 生命周期函数。此权限由 MySQL REST Service 组件定义，仅在安装该组件时可用。

MYSQL_REST_SERVICE_ADMIN 不授权对 MySQL REST Service 系统变量的更改。此类更改需要用于分配全局或持久化系统变量的常规权限。

卸载组件会注销此动态权限，但不会从 mysql.global_grants 中删除现有权限分配。

请参阅第 7.5.10 节"MySQL REST Service 组件"。

- NDB_STORED_USER

启用用户或角色及其权限在加入给定 NDB Cluster 时立即在所有启用 NDB 的 MySQL 服务器之间共享和同步。仅当启用 NDB 存储引擎时，此权限才可用。

对给定用户或角色所做的任何权限更改或撤销都会立即与所有连接的 MySQL 服务器（SQL 节点）同步。您应该意识到，不能保证来自不同 SQL 节点的多个影响权限的语句在所有 SQL 节点上以相同的顺序执行。因此，强烈建议从单个指定的 SQL 节点执行所有用户管理。

NDB_STORED_USER 是全局权限，必须使用 ON *.* 授予或撤销。尝试为此权限设置任何其他范围会导致错误。此权限可以授予大多数应用程序和管理用户，但不能授予系统保留账户，如 mysql.session@localhost 或 mysql.infoschema@localhost。

被授予 NDB_STORED_USER 权限的用户存储在 NDB 中（因此由所有 SQL 节点共享），具有此权限的角色也是如此。仅被授予具有 NDB_STORED_USER 的角色的用户不存储在 NDB 中；每个 NDB 存储用户必须显式授予该权限。

有关这在 NDB 中如何工作的更详细信息，请参阅第 25.6.13 节"权限同步和 NDB_STORED_USER"。

- OPTIMIZE_LOCAL_TABLE

启用使用 OPTIMIZE LOCAL TABLE 和 OPTIMIZE NO_WRITE_TO_BINLOG TABLE 语句。

- OPTION_TRACKER_OBSERVER

此权限提供对 mysql_option.option_usage 表的写入访问权限；权限和表都由 Option Tracker 组件提供。有关更多信息，请参阅第 7.5.9 节"Option Tracker 组件"。

- OPTION_TRACKER_UPDATER

此权限是对 mysql_option.option_usage 表进行写入访问所必需的；权限和表都由 Option Tracker 组件提供。有关更多信息，请参阅第 7.5.9 节"Option Tracker 组件"。

- PASSWORDLESS_USER_ADMIN

此权限适用于无密码用户账户：

- 对于账户创建，执行 CREATE USER 创建无密码账户的用户必须拥有 PASSWORDLESS_USER_ADMIN 权限。

- 在复制上下文中，PASSWORDLESS_USER_ADMIN 权限适用于复制用户，并启用为无密码身份验证配置的用户账户的 ALTER USER ... MODIFY 语句的复制。

有关无密码身份验证的信息，请参阅 WebAuthn 无密码身份验证。

- PERSIST_RO_VARIABLES_ADMIN

对于也具有 SYSTEM_VARIABLES_ADMIN 的用户，PERSIST_RO_VARIABLES_ADMIN 启用使用 SET PERSIST_ONLY 将全局系统变量持久化到数据目录中的 mysqld-auto.cnf 选项文件。此语句类似于 SET PERSIST，但不修改运行时全局系统变量值。这使 SET PERSIST_ONLY 适合配置只能在服务器启动时设置的只读系统变量。

另请参阅第 7.1.9.1 节"系统变量权限"。

- REPLICATION_APPLIER

启用账户充当复制通道的 PRIVILEGE_CHECKS_USER，以及在 mysqlbinlog 输出中执行 BINLOG 语句。将此权限授予使用 CHANGE REPLICATION SOURCE TO 分配的账户，以为复制通道提供安全上下文，并处理这些通道上的复制错误。除了 REPLICATION_APPLIER 权限外，您还必须给予账户所需的权限来执行复制通道接收的事务或 mysqlbinlog 输出中包含的事务，例如更新受影响的表。有关更多信息，请参阅第 19.3.3 节"复制权限检查"。

- REPLICATION_SLAVE_ADMIN

启用账户连接到复制源服务器，使用 START REPLICA 和 STOP REPLICA 语句启动和停止复制，以及使用 CHANGE REPLICATION SOURCE TO 和 CHANGE REPLICATION FILTER 语句。将此权限授予副本用于连接到当前服务器作为其复制源服务器的账户。此权限不适用于 Group Replication；对于该功能，请使用 GROUP_REPLICATION_ADMIN。

- RESOURCE_GROUP_ADMIN

启用资源组管理，包括创建、修改和删除资源组，以及将线程和语句分配给资源组。具有此权限的用户可以执行与资源组相关的任何操作。

- RESOURCE_GROUP_USER

启用将线程和语句分配给资源组。具有此权限的用户可以使用 SET RESOURCE GROUP 语句和 RESOURCE_GROUP 优化器提示。

- ROLE_ADMIN

启用授予和撤销角色，使用 GRANT 语句的 WITH ADMIN OPTION 子句，以及 ROLES_GRAPHML() 函数结果中的非空 <graphml> 元素内容。需要设置 mandatory_roles 系统变量的值。

- SENSITIVE_VARIABLES_OBSERVER

启用持有者在 Performance Schema 表 global_variables、session_variables、variables_by_thread 和 persisted_variables 中查看敏感系统变量的值，发出 SELECT 语句以返回其值，以及在会话跟踪器中跟踪连接的更改。没有此权限的用户无法查看或跟踪这些系统变量值。请参阅持久化敏感系统变量。

- SERVICE_CONNECTION_ADMIN

启用连接到仅允许管理连接的网络接口（请参阅第 7.1.12.1 节"连接接口"）。

- SESSION_VARIABLES_ADMIN

对于大多数系统变量，设置会话值不需要特殊权限，任何用户都可以执行以影响当前会话。对于某些系统变量，设置会话值可能会对当前会话外产生影响，因此是受限操作。对于这些，SESSION_VARIABLES_ADMIN 权限启用用户设置会话值。

如果系统变量受限且需要特殊权限来设置会话值，变量说明会指示该限制。示例包括 binlog_format、sql_log_bin 和 sql_log_off。

SESSION_VARIABLES_ADMIN 权限是 SYSTEM_VARIABLES_ADMIN 和 SUPER 权限的子集。具有这两个权限之一的用户也被允许设置受限会话变量，并通过隐含方式有效地拥有 SESSION_VARIABLES_ADMIN，无需显式授予 SESSION_VARIABLES_ADMIN。

另请参阅第 7.1.9.1 节"系统变量权限"。

- SET_ANY_DEFINER

启用在执行视图或存储程序时设置有效授权 ID。具有此权限的用户可以为 CREATE PROCEDURE、CREATE FUNCTION、CREATE TRIGGER、CREATE EVENT、ALTER EVENT、CREATE VIEW 和 ALTER VIEW 指定任何账户作为 DEFINER 属性。没有此权限，只能指定有效的身份验证 ID。

存储程序使用指定账户的权限执行，因此请确保遵循第 27.8 节"存储对象访问控制"中列出的风险最小化指南。

- SHOW_ROUTINE

启用用户访问所有存储例程（存储过程和函数）的定义和属性，即使用户未被命名为例程 DEFINER。此访问包括：

- Information Schema ROUTINES 表的内容。

- SHOW CREATE FUNCTION 和 SHOW CREATE PROCEDURE 语句。

- SHOW FUNCTION CODE 和 SHOW PROCEDURE CODE 语句。

- SHOW FUNCTION STATUS 和 SHOW PROCEDURE STATUS 语句。

SHOW_ROUTINE 可以改为授予范围更受限的权限，允许访问例程定义。（即，管理员可以从不需要它的用户撤销全局 SELECT，并改为授予 SHOW_ROUTINE。）这使账户能够备份存储例程，而无需广泛的权限。

- SKIP_QUERY_REWRITE

具有此权限的用户发出的查询不受 Rewriter 插件重写的影响（请参阅第 7.6.4 节"Rewriter Query Rewrite 插件"）。

此权限应授予发出不应被重写的管理或控制语句的用户，以及用于应用来自复制源的语句的 PRIVILEGE_CHECKS_USER 账户（请参阅第 19.3.3 节"复制权限检查"）。

- SYSTEM_USER

SYSTEM_USER 权限区分系统用户和常规用户：

- 具有 SYSTEM_USER 权限的用户是系统用户。

- 没有 SYSTEM_USER 权限的用户是常规用户。

SYSTEM_USER 权限对给定用户可以应用其他权限的账户以及用户是否受到其他账户保护产生影响：

- 系统用户可以修改系统和常规账户。即，具有对常规账户执行给定操作的适当权限的用户通过拥有 SYSTEM_USER 可以对系统账户执行该操作。系统账户只能由具有适当权限的系统用户修改，不能由常规用户修改。

- 具有适当权限的常规用户可以修改常规账户，但不能修改系统账户。常规账户可以由具有适当权限的系统和常规用户修改。

这也意味着具有 SYSTEM_USER 权限的用户创建的数据库对象不能由没有该权限的用户修改或删除。这也适用于定义者具有此权限的例程。

有关更多信息，请参阅第 8.2.11 节"账户类别"。

SYSTEM_USER 权限对系统账户提供的防止常规账户修改的保护不适用于对 mysql 系统架构具有权限的常规账户，因此可以直接修改该架构中的授权表。为获得完全保护，不要向常规账户授予 mysql 架构权限。请参阅保护系统账户免受常规账户操纵。

如果使用 audit_log 插件（请参阅第 8.4.6 节"MySQL Enterprise Audit Plugin（已弃用）"），具有 SYSTEM_USER 权限的账户会自动分配 AUDIT_ABORT_EXEMPT 权限，该权限允许其查询即使在过滤器中配置的"中止"项会阻止它们也能执行。因此，具有 SYSTEM_USER 权限的账户可用于在审计配置错误后重新获得对系统的访问权限。

- SYSTEM_VARIABLES_ADMIN

影响以下操作和服务器行为：

- 启用运行时系统变量更改：

  - 启用使用 SET GLOBAL 和 SET PERSIST 对全局系统变量进行服务器配置更改。

  - 如果用户也具有 PERSIST_RO_VARIABLES_ADMIN，启用使用 SET PERSIST_ONLY 对全局系统变量进行服务器配置更改。

  - 启用设置需要特殊权限的受限会话系统变量。实际上，SYSTEM_VARIABLES_ADMIN 隐含 SESSION_VARIABLES_ADMIN，无需显式授予 SESSION_VARIABLES_ADMIN。

  另请参阅第 7.1.9.1 节"系统变量权限"。

- 启用全局事务特性的更改（请参阅第 15.3.7 节"SET TRANSACTION 语句"）。

- TABLE_ENCRYPTION_ADMIN

启用用户在启用 table_encryption_privilege_check 时覆盖默认加密设置；请参阅为架构和通用表空间定义加密默认值。

- TELEMETRY_LOG_ADMIN

启用遥测日志配置。此权限由 telemetry_log 插件定义，该插件通过 MySQL HeatWave on AWS 部署。

- TP_CONNECTION_ADMIN

启用使用特权连接连接到服务器。当达到由 thread_pool_max_transactions_limit 定义的限制时，不允许新连接，除非被 thread_pool_longrun_trx_limit 覆盖。特权连接忽略事务限制，并允许连接到服务器以增加事务限制、删除限制或终止运行的事务。默认情况下，此权限不授予任何用户。要建立特权连接，启动连接的用户必须具有 TP_CONNECTION_ADMIN 权限。

特权连接可以在达到由 thread_pool_max_transactions_limit 定义的限制时执行语句和启动事务。特权连接被放置在 Admin 线程组中。请参阅特权连接。

- TRANSACTION_GTID_TAG

在复制源服务器上将 gtid_next 系统变量设置为 AUTOMATIC:TAG 或 UUID:TAG:NUMBER 时需要。此外，还需要至少 SYSTEM_VARIABLES_ADMIN、SESSION_VARIABLES_ADMIN 或 REPLICATION_APPLIER 之一才能在源上将 gtid_next 设置为这些值之一。

REPLICATION_CHECKS_APPLIER 还必须具有此权限以及 REPLICATION_APPLIER 权限才能将 gtid_next 设置为 AUTOMATIC:TAG。这在启动复制应用程序线程时进行检查。

此权限也是设置 gtid_purged 服务器系统变量所必需的。

有关使用标记 GTID 的更多信息，请参阅 gtid_next 的说明，以及第 19.1.4 节"在线服务器上更改 GTID 模式"。

- VERSION_TOKEN_ADMIN

启用执行 Version Tokens 函数。此权限已弃用。它由 version_tokens 插件定义（也已弃用）；请参阅 Version Tokens。

- XA_RECOVER_ADMIN

启用执行 XA RECOVER 语句；请参阅第 15.3.8.1 节"XA 事务 SQL 语句"。

在 MySQL 26.10 之前，任何用户都可以执行 XA RECOVER 语句来发现未完成的准备 XA 事务的 XID 值，可能导致非启动者的用户提交或回滚 XA 事务。在 MySQL 26.10 中，XA RECOVER 仅允许具有 XA_RECOVER_ADMIN 权限的用户执行，该权限预期仅授予需要它的管理用户。例如，如果 XA 应用程序崩溃并且需要查找应用程序启动的未完成事务以便可以回滚它们，这可能是 XA 应用程序管理员的情况。此权限要求防止用户发现除自己的未完成准备 XA 事务的 XID 值。它不影响 XA 事务的正常提交或回滚，因为启动它的用户知道其 XID。

## 权限授予指南

仅向账户授予其需要的权限是个好主意。在授予 FILE 和管理权限时应特别谨慎：

- FILE 可被滥用以将 MySQL 服务器可以在服务器主机上读取的任何文件读入数据库表。这包括所有世界可读文件和服务器数据目录中的文件。然后可以使用 SELECT 访问该表以将其内容传输到客户端主机。

- GRANT OPTION 启用用户将其权限授予其他用户。具有不同权限和 GRANT OPTION 权限的两个用户能够组合权限。

- ALTER 可用于通过重命名表来破坏权限系统。

- SHUTDOWN 可被滥用以通过终止服务器来完全拒绝其他用户的服务。

- PROCESS 可用于查看当前执行的语句的纯文本，包括设置或更改密码的语句。

- SUPER 可用于终止其他会话或更改服务器的运行方式。

- 为 mysql 系统数据库本身授予的权限可用于更改密码和其他访问权限信息：

  - 密码存储为加密形式，因此恶意用户无法简单地读取它们来了解纯文本密码。但是，对 mysql.user 系统表 authentication_string 列具有写入访问权限的用户可以更改账户的密码，然后使用该账户连接到 MySQL 服务器。

  - 为 mysql 系统数据库授予的 INSERT 或 UPDATE 启用用户添加权限或分别修改现有权限。

  - 为 mysql 系统数据库授予的 DROP 启用用户删除权限表，甚至数据库本身。

## 静态权限与动态权限

MySQL 支持静态和动态权限：

- 静态权限内置于服务器中。它们始终可用于授予用户账户，无法注销。

- 动态权限可以在运行时注册和注销。这影响其可用性：未注册的动态权限无法授予。

例如，SELECT 和 INSERT 权限是静态的且始终可用，而动态权限仅在实现它的组件已启用时才可用。

## 8.2.2 MySQL 提供的权限

本节的其余部分描述了动态权限在 MySQL 中的工作原理。讨论中使用术语"组件"，但同样适用于插件。

> 注意
>
> 服务器管理员应该了解哪些服务器组件定义了动态权限。对于 MySQL 发行版，定义动态权限的组件文档会描述这些权限。
>
> 第三方组件也可能定义动态权限；管理员应该理解这些权限，并且不要安装可能会冲突或危害服务器操作的组件。例如，如果两个组件定义了同名的权限，则它们会相互冲突。组件开发者可以通过选择基于组件名称前缀的权限名称来降低这种情况发生的可能性。

服务器在内存中维护已注册的动态权限集合。注销发生在服务器关闭时。

通常，定义动态权限的组件在安装时会在其初始化序列期间注册这些权限。卸载时，组件不会注销其已注册的动态权限。（这是当前的做法，不是要求。也就是说，组件可以但不会在任何时间注销它们注册的权限。）

对于尝试注册已注册的动态权限，不会发生警告或错误。考虑以下语句序列：

```
INSTALL COMPONENT 'my_component';
UNINSTALL COMPONENT 'my_component';
INSTALL COMPONENT 'my_component';
```

第一个 INSTALL COMPONENT 语句注册组件 my_component 定义的任何权限，但 UNINSTALL COMPONENT 不会注销它们。对于第二个 INSTALL COMPONENT 语句，它注册的组件权限被发现已经注册，但不会发生警告或错误。

动态权限仅在全局级别应用。服务器在 mysql.global_grants 系统表中存储有关动态权限分配给用户账户的当前信息：

- 服务器在服务器启动期间自动注册 global_grants 中命名的权限（除非给定了 --skip-grant-tables 选项）。

- GRANT 和 REVOKE 语句修改 global_grants 的内容。

### 授权表

- global_grants 中列出的动态权限分配是持久的。它们不会在服务器关闭时被移除。

示例：以下语句向用户 u1 授予在副本上控制复制（包括 Group Replication）和修改系统变量所需的权限：

```
GRANT REPLICATION_SLAVE_ADMIN, GROUP_REPLICATION_ADMIN, BINLOG_ADMIN
ON *.* TO 'u1'@'localhost';
```

授予的动态权限出现在 SHOW GRANTS 语句的输出和 INFORMATION_SCHEMA USER_PRIVILEGES 表中。

对于全局级别的 GRANT 和 REVOKE，任何未被识别为静态权限的命名权限都会针对当前已注册的动态权限集合进行检查，如果找到则被授予。否则，会发生错误以指示未知的权限标识符。

对于 GRANT 和 REVOKE，全局级别的 ALL [PRIVILEGES] 的含义包括所有静态全局权限以及所有当前已注册的动态权限：

- 全局级别的 GRANT ALL 授予所有静态全局权限和所有当前已注册的动态权限。在 GRANT 语句执行后注册的动态权限不会被追溯授予任何账户。

- 全局级别的 REVOKE ALL 撤销所有已授予的静态全局权限和所有已授予的动态权限。

FLUSH PRIVILEGES 语句读取 global_grants 表以获取动态权限分配，并注册在其中找到的任何未注册的权限。

有关 MySQL Server 和 MySQL 发行版中包含的组件提供的动态权限的描述，请参见第 8.2.2 节"MySQL 提供的权限"。

### 将账户从 SUPER 迁移到动态权限

在 MySQL 26.10 中，许多以前需要 SUPER 权限的操作现在也与范围更有限的动态权限相关联。（有关这些权限的描述，请参见第 8.2.2 节"MySQL 提供的权限"。）每个这样的操作可以通过授予相关的动态权限而不是 SUPER 来允许账户执行。这一变化通过使 DBA 能够避免授予 SUPER 并更紧密地定制用户权限来改进安全性。SUPER 现已弃用；预计它将在 MySQL 的未来版本中被移除。

当 SUPER 被移除时，以前需要 SUPER 的操作将失败，除非授予 SUPER 的账户被迁移到适当的动态权限。使用以下说明来实现该目标，以便账户在 SUPER 移除之前做好准备：

1. 执行此查询以识别被授予 SUPER 的账户：

```
SELECT GRANTEE FROM INFORMATION_SCHEMA.USER_PRIVILEGES
WHERE PRIVILEGE_TYPE = 'SUPER';
```

2. 对于前面的查询识别的每个账户，确定它需要 SUPER 的操作。然后授予与这些操作相对应的动态权限，并撤销 SUPER。

例如，如果 'u1'@'localhost' 需要 SUPER 来进行二进制日志清除和系统变量修改，这些语句对账户进行所需的更改：

```
GRANT BINLOG_ADMIN, SYSTEM_VARIABLES_ADMIN ON *.* TO 'u1'@'localhost';
REVOKE SUPER ON *.* FROM 'u1'@'localhost';
```

修改所有适用的账户后，第一步中的 INFORMATION_SCHEMA 查询应该产生空结果集。
