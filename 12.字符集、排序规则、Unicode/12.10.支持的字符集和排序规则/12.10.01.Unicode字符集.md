### 12.10.1 Unicode 字符集

本节描述了 Unicode 字符集可用的排序规则及其区分属性。有关 Unicode 的常规信息，请参见第 12.9 节"Unicode 支持"。

MySQL 支持多个 Unicode 字符集：

- utf8mb4：Unicode 字符集的 UTF-8 编码，每个字符使用一到四个字节。

- utf8mb3：Unicode 字符集的 UTF-8 编码，每个字符使用一到三个字节。此字符集已弃用；请改用 utf8mb4。

- utf8：utf8mb3 的已弃用别名。请改用 utf8mb4。

注意

utf8 预计在未来版本中将成为 utf8mb4 的别名。

- ucs2：Unicode 字符集的 UCS-2 编码，每个字符使用两个字节。已弃用；预计在 MySQL 的未来版本中将移除对此字符集的支持。

- utf16：Unicode 字符集的 UTF-16 编码，每个字符使用两个或四个字节。类似于 ucs2，但具有对补充字符的扩展。

- utf16le：Unicode 字符集的 UTF-16LE 编码。类似于 utf16，但采用小端字节序而非大端字节序。

- utf32：Unicode 字符集的 UTF-32 编码，每个字符使用四个字节。

注意

utf8mb3 字符集已弃用，您应该预期它将在未来的 MySQL 版本中被移除。请改用 utf8mb4。utf8 目前是 utf8mb3 的别名，但现在已弃用，utf8 预计随后将成为对 utf8mb4 的引用。utf8mb3 也将在信息架构表的列中和 SQL SHOW 语句的输出中显示，以代替 utf8。

为了避免关于 utf8 含义的歧义，请考虑为字符集引用明确指定 utf8mb4。

utf8mb4、utf16、utf16le 和 utf32 支持基本多文种平面 (BMP) 字符和位于 BMP 外的补充字符。utf8mb3 和 ucs2 仅支持 BMP 字符。

大多数 Unicode 字符集都有一个通用排序规则（在名称中由 _general 表示或由不存在语言说明符表示）、一个二进制排序规则（在名称中由 _bin 表示）和多个特定于语言的排序规则（由语言说明符表示）。例如，对于 utf8mb4，utf8mb4_general_ci 和 utf8mb4_bin 是其通用和二进制排序规则，utf8mb4_danish_ci 是其特定于语言的排序规则之一。

大多数字符集都有一个二进制排序规则。utf8mb4 是一个例外，它有两个：utf8mb4_bin 和 utf8mb4_0900_bin。这两个二进制排序规则具有相同的排序顺序，但由其填充属性和排序权重特征区分。请参见排序规则填充属性和字符排序权重。

utf16le 的排序规则支持受限。仅有的可用排序规则是 utf16le_general_ci 和 utf16le_bin。这些类似于 utf16_general_ci 和 utf16_bin。

#### Unicode 排序规则算法 (UCA) 版本

MySQL 根据 http://www.unicode.org/reports/tr10/ 中描述的 Unicode 排序规则算法 (UCA) 实现 xxx_unicode_ci 排序规则。排序规则使用版本 4.0.0 UCA 权重键：http://www.unicode.org/Public/UCA/4.0.0/allkeys-4.0.0.txt。xxx_unicode_ci 排序规则仅对 Unicode 排序规则算法提供部分支持。某些字符不受支持，组合标记不完全受支持。这影响越南语、约鲁巴语和纳瓦霍语等语言。在字符串比较中，组合字符被视为与用单个 unicode 字符书写的相同字符不同，这两个字符被视为具有不同的长度（例如，由 CHAR_LENGTH() 函数返回或在结果集元数据中）。

基于高于 4.0.0 的 UCA 版本的 Unicode 排序规则在排序规则名称中包含版本。示例：

- utf8mb4_unicode_520_ci 基于 UCA 5.2.0 权重键 (http://www.unicode.org/Public/UCA/5.2.0/allkeys.txt)，

- utf8mb4_0900_ai_ci 基于 UCA 9.0.0 权重键 (http://www.unicode.org/Public/UCA/9.0.0/allkeys.txt)。

LOWER() 和 UPPER() 函数根据其参数的排序规则执行大小写折叠。仅在 Unicode 版本高于 4.0.0 中具有大写和小写版本的字符仅在参数排序规则使用足够高的 UCA 版本时才由这些函数转换。

#### 排序规则填充属性

基于 UCA 9.0.0 及更高版本的排序规则比基于 UCA 9.0.0 之前版本的排序规则更快。它们还具有 NO PAD 的填充属性，与基于 UCA 9.0.0 之前版本的排序规则中使用的 PAD SPACE 相对。对于非二进制字符串的比较，NO PAD 排序规则将字符串末尾的空格视为任何其他字符（请参见比较中的尾部空格处理）。

要确定排序规则的填充属性，请使用 INFORMATION_SCHEMA COLLATIONS 表，该表具有 PAD_ATTRIBUTE 列。例如：

```
mysql> SELECT COLLATION_NAME, PAD_ATTRIBUTE
       FROM INFORMATION_SCHEMA.COLLATIONS
       WHERE CHARACTER_SET_NAME = 'utf8mb4';
+----------------------------+---------------+
| COLLATION_NAME             | PAD_ATTRIBUTE |
+----------------------------+---------------+
| utf8mb4_general_ci         | PAD SPACE     |
| utf8mb4_bin                | PAD SPACE     |
| utf8mb4_unicode_ci         | PAD SPACE     |
| utf8mb4_icelandic_ci       | PAD SPACE     |
...
| utf8mb4_0900_ai_ci         | NO PAD        |
| utf8mb4_de_pb_0900_ai_ci   | NO PAD        |
| utf8mb4_is_0900_ai_ci      | NO PAD        |
...
| utf8mb4_ja_0900_as_cs      | NO PAD        |
| utf8mb4_ja_0900_as_cs_ks   | NO PAD        |
| utf8mb4_0900_as_ci         | NO PAD        |
| utf8mb4_ru_0900_ai_ci      | NO PAD        |
| utf8mb4_ru_0900_as_cs      | NO PAD        |
| utf8mb4_zh_0900_as_cs      | NO PAD        |
| utf8mb4_0900_bin           | NO PAD        |
+----------------------------+---------------+
```

具有 NO PAD 排序规则的非二进制字符串值 (CHAR、VARCHAR 和 TEXT) 的比较与其他排序规则在尾部空格方面有所不同。例如，'a' 和 'a ' 比较为不同的字符串，而不是相同的字符串。这可以使用 utf8mb4 的二进制排序规则看到。utf8mb4_bin 的填充属性是 PAD SPACE，而 utf8mb4_0900_bin 的填充属性是 NO PAD。因此，涉及 utf8mb4_0900_bin 的操作不会添加尾部空格，涉及带有尾部空格的字符串的比较对于两个排序规则可能不同：

```
mysql> CREATE TABLE t1 (c CHAR(10) COLLATE utf8mb4_bin);
Query OK, 0 rows affected (0.03 sec)

mysql> INSERT INTO t1 VALUES('a');
Query OK, 1 row affected (0.01 sec)

mysql> SELECT * FROM t1 WHERE c = 'a ';
+------+
| c    |
+------+
| a    |
+------+
1 row in set (0.00 sec)

mysql> ALTER TABLE t1 MODIFY c CHAR(10) COLLATE utf8mb4_0900_bin;
Query OK, 0 rows affected (0.02 sec)
Records: 0 Duplicates: 0 Warnings: 0

mysql> SELECT * FROM t1 WHERE c = 'a ';
Empty set (0.00 sec)
```

#### 特定于语言的排序规则

如果仅基于 Unicode 排序规则算法 (UCA) 的排序对某种语言不能很好地工作，MySQL 会实现特定于语言的 Unicode 排序规则。特定于语言的排序规则是基于 UCA 的，具有额外的语言定制规则。此部分后面会出现此类规则的示例。有关特定语言排序的问题，http://unicode.org 在 http://www.unicode.org/cldr/charts/30/collation/index.html 提供通用区域设置数据存储库 (CLDR) 排序规则图表。

例如，非特定于语言的 utf8mb4_0900_ai_ci 和特定于语言的 utf8mb4_LOCALE_0900_ai_ci Unicode 排序规则各具有以下特征：

- 排序规则基于 UCA 9.0.0 和 CLDR v30，不区分重音和大小写。这些特征由排序规则名称中的 _0900、_ai 和 _ci 表示。例外：utf8mb4_la_0900_ai_ci 不基于 CLDR，因为古典拉丁文未在 CLDR 中定义。

- 排序规则适用于范围 [U+0, U+10FFFF] 中的所有字符。

- 如果排序规则不是特定于语言的，它按默认顺序（如下所述）对所有字符（包括补充字符）进行排序。如果排序规则是特定于语言的，它根据特定于语言的规则正确排序该语言的字符，并按默认顺序排序不在该语言中的字符。

- 默认情况下，排序规则根据表中分配的权重值对在 DUCET 表（默认 Unicode 排序规则元素表）中列出代码点的字符进行排序。排序规则使用根据 UCA 构造的隐式权重值对在 DUCET 表中没有列出代码点的字符进行排序。

- 对于非特定于语言的排序规则，缩写序列中的字符被视为单独的字符。对于特定于语言的排序规则，缩写可能会改变字符排序顺序。

MySQL 为挪威语的两个主要变体提供排序规则：对于博克马尔语，您可以使用 utf8mb4_nb_0900_ai_ci 和 utf8mb4_nb_0900_as_cs；对于新挪威语，MySQL 现在提供 utf8mb4_nn_0900_ai_ci 和 utf8mb4_nn_0900_as_cs。

对于不区分重音的古典拉丁文排序规则，I 和 J 比较相等，U 和 V 比较相等。I 和 J 以及 U 和 V 在基本字母级别上比较相等。换句话说，J 被视为带重音的 I，U 被视为带重音的 V。

MySQL 为用西里尔字符书写的蒙古语提供排序规则，utf8mb4_mn_cyrl_0900_ai_ci 和 utf8mb4_mn_cyrl_0900_as_cs。

西班牙语排序规则可用于现代和传统西班牙语。对于两者，ñ（n 加波浪号）是 n 和 o 之间的单独字母。此外，对于传统西班牙语，ch 是 c 和 d 之间的单独字母，ll 是 l 和 m 之间的单独字母。

传统西班牙语排序规则也可用于阿斯图里亚斯语和加利西亚语。MySQL 还为加利西亚语提供 utf8mb4_gl_0900_ai_ci 和 utf8mb4_gl_0900_as_cs 排序规则。（这些与 utf8mb4_es_0900_ai_ci 和 utf8mb4_es_0900_as_cs 分别相同的排序规则。）

瑞典语排序规则包括瑞典语规则。例如，在瑞典语中，以下关系成立，这不是德语或法语使用者期望的：

Ü = Y < Ö

#### _general_ci 与 _unicode_ci 排序规则

对于任何 Unicode 字符集，使用 xxx_general_ci 排序规则执行的操作比使用 xxx_unicode_ci 排序规则的操作更快。例如，utf8mb4_general_ci 排序规则的比较更快，但略微不那么正确，比 utf8mb4_unicode_ci 的比较。原因是 utf8mb4_unicode_ci 支持映射，例如扩展；即当一个字符比较等于其他字符的组合时。例如，在德语和其他一些语言中，ß 等于 ss。utf8mb4_unicode_ci 也支持缩写和可忽略字符。utf8mb4_general_ci 是一个不支持扩展、缩写或可忽略字符的旧排序规则。它只能进行字符之间的一对一比较。

为了进一步说明，以下等式在 utf8mb4_general_ci 和 utf8mb4_unicode_ci 中都成立（有关这在比较或搜索中的影响，请参见第 12.8.6 节"排序规则效果示例"）：

Ä = A
Ö = O
Ü = U

排序规则之间的区别在于这对 utf8mb4_general_ci 成立：

ß = s

而这对 utf8mb4_unicode_ci 成立，它支持德语 DIN-1 排序（也称为字典顺序）：

ß = ss

如果使用 utf8mb4_unicode_ci 的排序对某种语言不能很好地工作，MySQL 会实现特定于语言的 Unicode 排序规则。例如，utf8mb4_unicode_ci 对德语字典顺序和法语都能很好地工作，因此无需创建特殊的 utf8mb4 排序规则。

utf8mb4_general_ci 对德语和法语也令人满意，除了 ß 等于 s，而不是 ss。如果这对您的应用程序可以接受，您应该使用 utf8mb4_general_ci，因为它更快。如果这不可以接受（例如，如果您需要德语字典顺序），请使用 utf8mb4_unicode_ci，因为它更准确。

如果您需要德语 DIN-2（电话簿）排序，请使用 utf8mb4_german2_ci 排序规则，它将以下字符集比较为相等：

Ä = Æ = AE
Ö = Œ = OE
Ü = UE
ß = ss

utf8mb4_german2_ci 类似于 latin1_german2_ci，但后者不将 Æ 比较为等于 AE，也不将 Œ 比较为等于 OE。没有对应于 latin1_german_ci 的 utf8mb4_german_ci 用于德语字典顺序，因为 utf8mb4_general_ci 就足够了。

#### 字符排序权重

字符的排序权重确定如下：

- 对于除 _bin（二进制）排序规则外的所有 Unicode 排序规则，MySQL 执行表查找以找到字符的排序权重。

- 对于除 utf8mb4_0900_bin 外的 _bin 排序规则，权重基于代码点，可能添加了前导零字节。

- 对于 utf8mb4_0900_bin，权重是 utf8mb4 编码字节。排序顺序与 utf8mb4_bin 相同，但速度快得多。

排序权重可以使用 WEIGHT_STRING() 函数显示。（请参见第 14.8 节"字符串函数和运算符"。）如果排序规则使用权重查找表，但表中不存在字符（例如，因为它是"新"字符），排序权重确定变得更复杂：

- 对于通用排序规则中的 BMP 字符 (xxx_general_ci)，权重是代码点。

- 对于 UCA 排序规则中的 BMP 字符（例如，xxx_unicode_ci 和特定于语言的排序规则），应用以下算法：
  ```
  if (code >= 0x3400 && code <= 0x4DB5)
    base= 0xFB80; /* CJK Ideograph Extension */
  else if (code >= 0x4E00 && code <= 0x9FA5)
    base= 0xFB40; /* CJK Ideograph */
  else
    base= 0xFBC0; /* All other characters */
  aaaa= base + (code >> 15);
  bbbb= (code & 0x7FFF) | 0x8000;
  ```

  结果是两个排序元素的序列，aaaa 后跟 bbbb。例如：
  ```
  mysql> SELECT HEX(WEIGHT_STRING(_ucs2 0x04CF COLLATE ucs2_unicode_ci));
  +----------------------------------------------------------+
  | HEX(WEIGHT_STRING(_ucs2 0x04CF COLLATE ucs2_unicode_ci)) |
  +----------------------------------------------------------+
  | FBC084CF                                                 |
  +----------------------------------------------------------+
  ```

  因此，U+04cf 西里尔小字母 PALOCHKA (ӏ) 在所有 UCA 4.0.0 排序规则中大于 U+04c0 西里尔字母 PALOCHKA (Ӏ)。使用 UCA 5.2.0 排序规则，所有 palochka 一起排序。

- 对于通用排序规则中的补充字符，权重是 0xfffd 替换字符的权重。对于 UCA 4.0.0 排序规则中的补充字符，其排序权重是 0xfffd。也就是说，对于 MySQL，所有补充字符彼此相等，并且大于几乎所有 BMP 字符。

  带有 Deseret 字符和 COUNT(DISTINCT) 的示例：
  ```
  CREATE TABLE t (s1 VARCHAR(5) CHARACTER SET utf32 COLLATE utf32_unicode_ci);
  INSERT INTO t VALUES (0xfffd);    /* REPLACEMENT CHARACTER */
  INSERT INTO t VALUES (0x010412); /* DESERET CAPITAL LETTER BEE */
  INSERT INTO t VALUES (0x010413); /* DESERET CAPITAL LETTER TEE */
  SELECT COUNT(DISTINCT s1) FROM t;
  ```

  结果是 2，因为在 MySQL xxx_unicode_ci 排序规则中，替换字符的权重为 0x0dc6，而 Deseret Bee 和 Deseret Tee 的权重都为 0xfffd。（如果改用 utf32_general_ci 排序规则，结果是 1，因为所有三个字符在该排序规则中的权重都是 0xfffd。）

  带有楔形文字字符和 WEIGHT_STRING() 的示例：
  ```
  /*
  INSERT 字符串中的四个字符是
  00000041 # LATIN CAPITAL LETTER A
  0001218F # CUNEIFORM SIGN KAB
  000121A7 # CUNEIFORM SIGN KISH
  00000042 # LATIN CAPITAL LETTER B
  */
  CREATE TABLE t (s1 CHAR(4) CHARACTER SET utf32 COLLATE utf32_unicode_ci);
  INSERT INTO t VALUES (0x000000410001218f000121a700000042);
  SELECT HEX(WEIGHT_STRING(s1)) FROM t;
  ```

  结果是：
  ```
  0E33 FFFD FFFD 0E4A
  ```

  0E33 和 0E4A 是 UCA 4.0.0 中的主权重。FFFD 是 KAB 的权重，也是 KISH 的权重。

  所有补充字符相等的规则不是最优的，但预计不会造成麻烦。这些字符非常罕见，因此多字符字符串完全由补充字符组成的情况非常罕见。在日本，由于补充字符是晦涩的汉字表意文字，典型用户不关心它们的顺序。如果您真的想按 MySQL 规则排序行，其次按代码点值排序，这很容易：
  ```
  ORDER BY s1 COLLATE utf32_unicode_ci, s1 COLLATE utf32_bin
  ```

- 对于基于高于 4.0.0 的 UCA 版本的补充字符（例如，xxx_unicode_520_ci），补充字符不一定都具有相同的排序权重。某些具有来自 UCA allkeys.txt 文件的显式权重。其他具有根据此算法计算的权重：
  ```
  aaaa= base + (code >> 15);
  bbbb= (code & 0x7FFF) | 0x8000;
  ```

"按字符代码值排序"和"按字符二进制表示排序"之间存在差异，这种差异仅在 utf16_bin 中出现，因为代理。

假设 utf16_bin（utf16 的二进制排序规则）是"逐字节"而不是"逐字符"的二进制比较。如果是这样，utf16_bin 中的字符顺序将与 utf8mb4_bin 中的顺序不同。例如，以下图表显示两个罕见字符。第一个字符在范围 E000-FFFF 中，因此它大于代理但小于补充。第二个字符是补充。

| 代码点 | 字符 | utf8mb4 | utf16 |
|--------|------|---------|-------|
| 0FF9D | HALFWIDTH KATAKANA LETTER N | EF BE 9D | FF 9D |
| 10384 | UGARITIC LETTER DELTA | F0 90 8E 84 | D8 00 DF 84 |

图表中的两个字符按代码点值排序，因为 0xff9d < 0x10384。它们按 utf8mb4 值排序，因为 0xef < 0xf0。但如果我们使用逐字节比较，它们不按 utf16 值排序，因为 0xff > 0xd8。

所以 MySQL 的 utf16_bin 排序规则不是"逐字节"。它是"按代码点"。当 MySQL 在 utf16 中看到补充字符编码时，它转换为字符的代码点值，然后进行比较。因此，utf8mb4_bin 和 utf16_bin 具有相同的排序。这与 SQL:2008 标准对 UCS_BASIC 排序规则的要求一致："UCS_BASIC 是一种排序规则，其中排序完全由被排序字符串中字符的 Unicode 标量值确定。它适用于 UCS 字符集。由于每个字符集都是 UCS 字符集的子集，UCS_BASIC 排序规则可能适用于每个字符集。注 11：字符的 Unicode 标量值是其代码点作为无符号整数处理。"

如果字符集是 ucs2，比较是逐字节的，但 ucs2 字符串不应该包含代理。
