### 7.9.1.6 使用服务器日志查找 mysqld 中的错误原因

注意，在启用通用查询日志启动 mysqld 之前，应该用 myisamchk 检查所有表。参见第 7 章，MySQL 服务器管理。

如果 mysqld 死亡或挂起，应该启用通用查询日志启动 mysqld。参见第 7.4.3 节，"通用查询日志"。当 mysqld 再次死亡时，可以检查日志文件的末尾，查找导致 mysqld 死亡的查询。

如果使用默认的通用查询日志文件，日志存储在数据库目录中，文件名为 host_name.log。在大多数情况下，导致 mysqld 死亡的是日志文件中的最后一条查询，但如果可能的话，应该通过重新启动 mysqld 并从 mysql 命令行工具执行找到的查询来验证。如果这样做有效，还应该测试所有未完成的复杂查询。

也可以尝试对所有耗时较长的 SELECT 语句使用 EXPLAIN 命令，以确保 mysqld 正确使用了索引。参见第 15.8.2 节，"EXPLAIN 语句"。

可以通过启用慢查询日志启动 mysqld 来查找执行时间较长的查询。参见第 7.4.5 节，"慢查询日志"。

如果在错误日志中（通常是名为 host_name.err 的文件）找到文本 mysqld restarted，可能已经找到了导致 mysqld 失败的查询。如果发生这种情况，应该用 myisamchk 检查所有表（参见第 7 章，MySQL 服务器管理），并测试 MySQL 日志文件中的查询，看是否有一条失败。如果找到这样的查询，首先尝试升级到最新的 MySQL 版本。如果这没有帮助，请报告一个 bug，参见第 1.6 节，"如何报告 Bug 或问题"。

如果已经设置 myisam_recover_options 系统变量启动了 mysqld，当 MyISAM 表被标记为"未正确关闭"或"已崩溃"时，MySQL 会自动检查并尝试修复这些表。如果发生这种情况，MySQL 会在 hostname.err 文件中写入一条条目"Warning: Checking table ..."，如果表需要修复，后面会跟随 Warning: Repairing table。如果收到大量这样的错误，而 mysqld 之前没有意外死亡，那么出现了问题，需要进一步调查。参见第 7.1.7 节，"服务器命令选项"。

当服务器检测到 MyISAM 表损坏时，它会向错误日志写入额外信息，例如源文件的名称和行号，以及访问该表的线程列表。例如：Got an error from thread_id=1, mi_dynrec.c:368。这是包含在 bug 报告中的有用信息。

调试 MySQL 客户端

如果 mysqld 意外死亡，这不是一个好兆头，但在这种情况下，不应该调查 Checking table... 消息，而应该尝试找出 mysqld 死亡的原因。
