### 7.6.3.3 线程池操作

线程池由多个线程组组成，每个线程组管理一组客户端连接。当建立连接时，线程池以轮询方式将连接分配给线程组。

线程池公开了可用于配置其操作的系统变量：

- thread_pool_algorithm：用于调度的并发算法。

- thread_pool_dedicated_listeners：在每个线程组中专用一个监听线程来监听来自分配给该组的连接的传入语句。

- thread_pool_high_priority_connection：如何为会话调度语句执行。

- thread_pool_max_active_query_threads：每个组允许的活跃线程数。

- thread_pool_max_transactions_limit：线程池插件允许的最大事务数。

- thread_pool_max_unused_threads：允许的睡眠线程数。

- thread_pool_prio_kickup_timer：线程池将等待执行的语句从低优先级队列移动到高优先级队列之前的时间。

- thread_pool_query_threads_per_group：线程组中允许的查询线程数（默认为单个查询线程）。如果由于长时间运行的事务导致响应时间变慢，请考虑增加该值。

- thread_pool_size：线程池中的线程组数。这是控制线程池性能的最重要参数。

- thread_pool_stall_limit：执行语句被认为停滞之前的时间。

- thread_pool_transaction_delay：启动新事务之前的延迟期。

要配置线程组的数量，请使用 thread_pool_size 系统变量。默认组数为 16。有关设置此变量的指南，请参见第 7.6.3.4 节"线程池调优"。

每个组的最大线程数为 4096（在某些系统上为 4095，其中一个线程在内部使用）。

线程池将连接和线程分开，因此连接和执行来自这些连接的语句的线程之间没有固定的关系。这与默认的线程处理模型不同，默认模型将一个线程与一个连接关联，使得给定的线程执行来自其连接的所有语句。

默认情况下，线程池尝试确保每个组中最多有一个线程在任何时间执行，但有时为了获得最佳性能会允许更多线程临时执行：

- 每个线程组都有一个监听线程，用于监听来自分配给该组的连接的传入语句。当语句到达时，线程组要么立即开始执行它，要么将其排队以供稍后执行：

  - 如果语句是唯一接收的语句，并且没有排队或当前执行的语句，则立即执行。

    立即执行可以通过配置 thread_pool_transaction_delay 来延迟，该参数对事务具有限流效果。有关此变量的更多信息，请参阅下面讨论中的说明。

  - 如果由于并发排队或执行的语句，语句无法立即开始执行，则进行排队。

- thread_pool_transaction_delay 变量指定以毫秒为单位的事务延迟。工作线程在执行新事务之前睡眠指定的时间。

  事务延迟可用于并行事务由于资源争用而影响其他操作性能的情况。例如，如果并行事务影响索引创建或在线缓冲池调整大小操作，您可以配置事务延迟以减少这些操作运行时的资源争用。延迟对事务具有限流效果。

  thread_pool_transaction_delay 设置不影响从特权连接（分配给 Admin 线程组的连接）发出的查询。这些查询不受配置的事务延迟的限制。

- 如果立即执行，监听线程执行它。（这意味着该组中暂时没有线程在监听。）如果语句快速完成，执行线程返回监听语句。否则，线程池认为语句停滞并启动另一个线程作为监听线程（如果必要则创建它）。为了确保没有线程组被停滞的语句阻塞，线程池有一个后台线程定期监控线程组状态。

  通过使用监听线程执行可以立即开始的语句，如果语句快速完成，就无需创建额外的线程。这确保了在并发线程数较少的情况下可能的最高效执行。

  当线程池插件启动时，它为每个组创建一个线程（监听线程），加上后台线程。根据需要创建额外的线程来执行语句。

- thread_pool_stall_limit 系统变量的值确定了前一项中"快速完成"的含义。线程被认为停滞之前的默认时间为 60ms，但可以设置为最多 6s。此参数可配置，使您能够达到适合服务器工作负载的平衡。较短的等待值允许线程更快地启动。较短的值也更有利于避免死锁情况。较长的等待值对于包含长时间运行语句的工作负载很有用，以避免在当前语句执行时启动过多新语句。

- 如果 thread_pool_max_active_query_threads 为 0，则应用默认算法如上所述来确定每个组的最大活跃线程数。默认算法考虑停滞的线程，可能会临时允许更多活跃线程。如果 thread_pool_max_active_query_threads 大于 0，它对每个组的活跃线程数设置限制。

- 线程池专注于限制并发短时间运行语句的数量。在执行语句达到停滞时间之前，它防止其他语句开始执行。如果语句执行超过停滞时间，允许它继续但不再防止其他语句启动。这样，线程池尝试确保在每个线程组中永远不会有超过一个短时间运行的语句，尽管可能有多个长时间运行的语句。让长时间运行的语句防止其他语句执行是不可取的，因为可能需要等待的时间量没有限制。例如，在复制源服务器上，向副本发送二进制日志事件的线程实际上永远运行。

- 语句在遇到磁盘 I/O 操作或用户级锁（行锁或表锁）时会被阻塞。阻塞会导致线程组变得未使用，因此有回调到线程池以确保线程池可以立即在此组中启动新线程来执行另一个语句。当被阻塞的线程返回时，线程池允许它立即重新启动。

- 有两个队列，一个高优先级队列和一个低优先级队列。事务中的第一个语句进入低优先级队列。事务的任何后续语句如果事务正在进行（其语句已开始执行），则进入高优先级队列，否则进入低优先级队列。队列分配可以通过启用 thread_pool_high_priority_connection 系统变量来影响，该变量导致会话的所有排队语句进入高优先级队列。

  对于非事务性存储引擎的语句，或如果启用了自动提交的事务性引擎的语句，被视为低优先级语句，因为在这种情况下每个语句都是一个事务。因此，给定 InnoDB 和 MyISAM 表的语句混合，线程池优先处理 InnoDB 的语句而不是 MyISAM 的语句，除非启用了自动提交。启用自动提交后，所有语句都具有低优先级。

- 当线程组选择排队的语句执行时，它首先查看高优先级队列，然后查看低优先级队列。如果找到语句，则将其从队列中移除并开始执行。

- 如果语句在低优先级队列中停留太长时间，线程池会将其移动到高优先级队列。thread_pool_prio_kickup_timer 系统变量的值控制移动之前的时间。对于每个线程组，每 10ms（每秒 100 个）最多有一个语句从低优先级队列移动到高优先级队列。

- 线程池重用最活跃的线程以获得更好的 CPU 缓存使用。这是一个小调整，对性能有很大影响。

- 当线程执行来自用户连接的语句时，Performance Schema 工具将线程活动记录到用户连接。否则，Performance Schema 将活动记录到线程池。

以下是线程组可能启动多个线程来执行语句的条件示例：

- 一个线程开始执行语句，但运行时间足够长被认为停滞。线程组允许另一个线程开始执行另一个语句，即使第一个线程仍在执行。

- 一个线程开始执行语句，然后被阻塞并将其报告回线程池。线程组允许另一个线程开始执行另一个语句。

- 一个线程开始执行语句，被阻塞，但没有报告它被阻塞，因为阻塞不发生在用线程池回调进行工具化的代码中。在这种情况下，线程对线程组来说似乎仍在运行。如果阻塞持续足够长的时间使语句被认为停滞，该组允许另一个线程开始执行另一个语句。

线程池设计为可在不断增加的连接数上扩展。它还设计为避免可能由限制活跃执行语句数量而产生的死锁。重要的是不向线程池报告的线程不会阻止其他语句执行，从而导致线程池死锁。此类语句的示例如下：

- 长时间运行的语句。这些会导致所有资源仅被少数语句使用，它们可能会阻止所有其他语句访问服务器。

- 读取二进制日志并将其发送到副本的二进制日志转储线程。这是一种长时间运行的"语句"，运行时间很长，不应阻止其他语句执行。

- 在行锁、表锁、睡眠或任何其他阻塞活动上被阻塞的语句，这些活动尚未被 MySQL Server 或存储引擎报告回线程池。

在每种情况下，为了防止死锁，当语句不快速完成时，它被移动到停滞类别，以便线程组可以允许另一个语句开始执行。通过这种设计，当线程执行或被阻塞较长时间时，线程池将线程移动到停滞类别，在语句执行的其余时间内，它不会阻止其他语句执行。

可能发生的最大线程数是 max_connections 和 thread_pool_size 的总和。这可能发生在所有连接都处于执行模式且为每个组创建额外线程以监听更多语句的情况下。这不一定是经常发生的状态，但理论上是可能的。

#### 特权连接

如果已达到 thread_pool_max_transactions_limit 定义的限制，并且新连接或使用现有连接的新事务似乎挂起，直到一个或多个现有事务完成，尽管对 thread_pool_longrun_trx_limit 进行了任何调整，以至于所有现有连接都被阻塞或长时间运行，访问服务器的唯一方式可能是使用特权连接。

要建立特权连接，启动连接的用户必须具有 TP_CONNECTION_ADMIN 权限。特权连接忽略 thread_pool_max_transactions_limit 定义的限制，并允许连接到服务器以增加限制、移除限制或杀死运行中的事务。TP_CONNECTION_ADMIN 权限必须显式授予。默认情况下不授予任何用户。

特权连接可以执行语句和启动事务，并被分配给指定为 Admin 线程组的线程组。

查询 performance_schema.tp_thread_group_stats 表时，该表报告每个线程组的统计信息，Admin 线程组统计信息在结果集的最后一行中报告。例如，如果 SELECT * FROM performance_schema.tp_thread_group_stats 返回 17 行（每个线程组一行），Admin 线程组统计信息在第 17 行中报告。
