### 7.1.10 服务器状态变量

MySQL 服务器维护许多状态变量，提供有关其操作的信息。您可以使用 SHOW [GLOBAL | SESSION] STATUS 语句查看这些变量及其值（参见第 15.7.7.39 节"SHOW STATUS 语句"）。可选的 GLOBAL 关键字聚合所有连接的值，SESSION 显示当前连接的值。

```
mysql> SHOW GLOBAL STATUS;
+-----------------------------------+------------+
| Variable_name                     | Value      |
+-----------------------------------+------------+
| Aborted_clients                   | 0          |
| Aborted_connects                  | 0          |
| Bytes_received                    | 155372598 |
| Bytes_sent                        | 1176560426 |
...
| Connections                       | 30023      |
| Created_tmp_disk_tables           | 0          |
| Created_tmp_files                 | 3          |
| Created_tmp_tables                | 2          |
...
| Threads_created                   | 217        |
| Threads_running                   | 88         |
| Uptime                            | 1389872    |
+-----------------------------------+------------+
```

许多状态变量由 FLUSH STATUS 语句重置为 0。

本节提供每个状态变量的描述。有关状态变量摘要，请参见第 7.1.6 节"服务器状态变量参考"。有关特定于 NDB Cluster 的状态变量的信息，请参见 NDB Cluster 状态变量。

状态变量具有以下含义。

- Aborted_clients

  因客户端未正确关闭连接而被中止的连接数。参见第 B.3.2.9 节"通信错误和中止连接"。

- Aborted_connects

  连接到 MySQL 服务器的失败尝试次数。参见第 B.3.2.9 节"通信错误和中止连接"。

  有关其他连接相关信息，请检查 Connection_errors_xxx 状态变量和 host_cache 表。

- Authentication_ldap_sasl_supported_methods

  实现 SASL LDAP 身份验证的 authentication_ldap_sasl 插件支持多种身份验证方法，但根据主机系统配置，可能并非所有方法都可用。Authentication_ldap_sasl_supported_methods 变量提供对支持的方法的可发现性。其值是由空格分隔的支持的方法名称组成的字符串。示例："SCRAM-SHA 1 SCRAM-SHA-256 GSSAPI"

- Binlog_cache_disk_use

  使用临时二进制日志缓存但超过 binlog_cache_size 值并使用临时文件存储事务语句的事务数。

  导致二进制日志事务缓存写入磁盘的非事务性语句数在 Binlog_stmt_cache_disk_use 状态变量中单独跟踪。

- Acl_cache_items_count

  缓存的权限对象数。每个对象是用户及其活跃角色的权限组合。

- Binlog_cache_use

  使用二进制日志缓存的事务数。

- Binlog_stmt_cache_disk_use

  使用二进制日志语句缓存但超过 binlog_stmt_cache_size 值并使用临时文件存储这些语句的非事务性语句数。

- Binlog_stmt_cache_use

  使用二进制日志语句缓存的非事务性语句数。

- Bytes_received

  从所有客户端接收的字节数。

- Bytes_sent

  发送到所有客户端的字节数。

- Caching_sha2_password_rsa_public_key

  caching_sha2_password 身份验证插件用于基于 RSA 密钥对的密码交换的公钥。仅当服务器成功初始化由 caching_sha2_password_private_key_path 和 caching_sha2_password_public_key_path 系统变量命名的文件中的私钥和公钥时，该值才非空。Caching_sha2_password_rsa_public_key 的值来自后者文件。

- Com_xxx

  Com_xxx 语句计数器变量指示每个 xxx 语句被执行的次数。每种语句类型都有一个状态变量。例如，Com_delete 和 Com_update 分别计数 DELETE 和 UPDATE 语句。Com_delete_multi 和 Com_update_multi 类似，但适用于使用多表语法的 DELETE 和 UPDATE 语句。

  即使准备语句参数未知或执行期间发生错误，所有 Com_stmt_xxx 变量也会增加。换句话说，它们的值对应于发出的请求数，而不是成功完成的请求数。例如，因为状态变量在每次服务器启动时初始化且不会跨重启持久化，跟踪 RESTART 和 SHUTDOWN 语句的 Com_restart 和 Com_shutdown 变量通常值为零，但如果 RESTART 或 SHUTDOWN 语句被执行但失败，则可能非零。

  Com_stmt_xxx 状态变量如下：

  - Com_stmt_prepare

  - Com_stmt_execute

  - Com_stmt_fetch

  - Com_stmt_send_long_data

  - Com_stmt_reset

  - Com_stmt_close

  这些变量代表准备语句命令。它们的名称指的是网络层中使用的 COM_xxx 命令集。换句话说，每当执行准备语句 API 调用（如 mysql_stmt_prepare()、mysql_stmt_execute() 等）时，它们的值都会增加。但是，Com_stmt_prepare、Com_stmt_execute 和 Com_stmt_close 也分别为 PREPARE、EXECUTE 或 DEALLOCATE PREPARE 增加。此外，较旧的语句计数器变量 Com_prepare_sql、Com_execute_sql 和 Com_dealloc_sql 的值为 PREPARE、EXECUTE 和 DEALLOCATE PREPARE 语句增加。Com_stmt_fetch 代表从游标获取时发出的网络往返总数。

  Com_stmt_reprepare 指示服务器自动重新准备语句的次数，例如在对语句引用的表或视图进行元数据更改后。重新准备操作会增加 Com_stmt_reprepare 和 Com_stmt_prepare。

  Com_explain_other 指示执行的 EXPLAIN FOR CONNECTION 语句数。参见第 10.8.4 节"获取命名连接的执行计划信息"。

  Com_change_repl_filter 指示执行的 CHANGE REPLICATION FILTER 语句数。

  Com_create_library、Com_drop_library、Com_alter_library、Com_show_create_library 和 Com_show_library_status 分别指示执行的 CREATE LIBRARY、DROP LIBRARY、ALTER LIBRARY、SHOW CREATE LIBRARY 和 SHOW LIBRARY STATUS 语句的数量。这些变量仅在安装了 MLE 组件时存在（参见第 7.5.7 节"多语言引擎组件 (MLE)"）。

- Compression

  客户端连接是否在客户端/服务器协议中使用压缩。

  此状态变量已弃用；预计在 MySQL 的未来版本中将其删除。参见配置旧版连接压缩。

- Compression_algorithm

  当前连接到服务器所使用的压缩算法的名称。该值可以是 protocol_compression_algorithms 系统变量值中允许的任何算法。例如，如果连接不使用压缩，该值为 uncompressed，如果连接使用 zlib 算法，则为 zlib。

  有关更多信息，请参见第 6.2.8 节"连接压缩控制"。

- Compression_level

  当前连接到服务器所使用的压缩级别。对于 zlib 连接，该值为 6（默认 zlib 算法压缩级别），对于 zstd 连接为 1 到 22，对于未压缩连接为 0。

  有关更多信息，请参见第 6.2.8 节"连接压缩控制"。

- Component_connection_control_delay_generated

  由 component_connection_control 生成的延迟数。每当触发延迟时更新；每当设置 component_connection_control.failed_connections_threshold 时重置为 0。

  参见第 8.4.2 节"连接控制组件"了解更多信息。

- Component_connection_control_exempted_unknown_users

  由 component_connection_control.exempt_unknown_users 豁免的失败 TCP 连接数。

  参见第 8.4.2 节"连接控制组件"了解更多信息。

- Connection_errors_xxx

  这些变量提供有关客户端连接过程中发生的错误的信息。它们仅是全局的，代表从所有主机的连接聚合的错误计数。这些变量跟踪主机缓存未计算的错误（参见第 7.1.12.3 节"DNS 查询和主机缓存"），例如与 TCP 连接无关的错误、在连接过程早期发生的错误（甚至在知道 IP 地址之前）或不特定于任何特定 IP 地址的错误（例如内存不足条件）。

  - Connection_errors_accept

    在监听端口上调用 accept() 期间发生的错误数。

  - Connection_errors_internal

    由于服务器内部错误（例如无法启动新线程或内存不足条件）而拒绝的连接数。

  - Connection_errors_max_connections

    因服务器 max_connections 限制已达到而拒绝的连接数。

  - Connection_errors_peer_address

    搜索连接客户端 IP 地址时发生的错误数。

  - Connection_errors_select

    在监听端口上调用 select() 或 poll() 期间发生的错误数。（此操作的失败不一定意味着客户端连接被拒绝。）

  - Connection_errors_tcpwrap

    被 libwrap 库拒绝的连接数。

- Connections

  连接到 MySQL 服务器的连接尝试次数（成功或失败）。

- Count_hit_query_past_global_connection_memory_status_limit

  使用任何连接的查询导致总内存消耗超过 global_connection_memory_status_limit 的次数。当查询将总内存消耗从小于 global_connection_memory_status_limit 增加到大于此数量时，此值会增加；当执行查询但总内存消耗已经超过此限制时，状态变量不会增加。

- Count_hit_query_past_connection_memory_status_limit

  使用当前连接的查询导致总内存消耗超过 connection_memory_limit 的次数。对于在连接内执行的查询，当此类查询将总内存消耗从小于 connection_memory_limit 增加到大于此数量时，此值会增加；当执行查询但总内存消耗已经超过此限制时，状态变量不会增加。

- Count_hit_tmp_table_size

  因 TempTable 引擎达到 tmp_table_size 限制或 MEMORY 引擎达到 tmp_table_size 和 max_heap_table_size 中较小值而从内存转换为磁盘的内部临时表数。

- Created_tmp_disk_tables

  服务器在执行语句时创建的内部磁盘临时表数。

  您可以通过比较 Created_tmp_disk_tables 和 Created_tmp_tables 值来比较创建的内部磁盘临时表数与创建的内部临时表总数。

  注意

  由于已知限制，Created_tmp_disk_tables 不计算在内存映射文件中创建的磁盘临时表。默认情况下，TempTable 存储引擎溢出机制在内存映射文件中创建内部临时表。此行为由 temptable_max_mmap 变量控制。

  另请参见第 10.4.4 节"MySQL 中的内部临时表使用"。

- Created_tmp_files

  mysqld 创建的临时文件数。

- Created_tmp_tables

  服务器在执行语句时创建的内部临时表数。

  您可以通过比较 Created_tmp_disk_tables 和 Created_tmp_tables 值来比较创建的内部磁盘临时表数与创建的内部临时表总数。

  另请参见第 10.4.4 节"MySQL 中的内部临时表使用"。

  SHOW STATUS 语句的每次调用都使用内部临时表并增加全局 Created_tmp_tables 值。

- Current_tls_ca

  服务器用于新连接的 SSL 上下文中的活跃 ssl_ca 值。如果系统变量已更改但随后未执行 ALTER INSTANCE RELOAD TLS 以从上下文相关系统变量值重新配置 SSL 上下文并更新相应的状态变量，则此上下文值可能与当前 ssl_ca 系统变量值不同。（此潜在值差异适用于每个对应的上下文相关系统和状态变量对。参见加密连接的服务器端运行时配置和监控。）

  Current_tls_xxx 状态变量值也可通过 Performance Schema tls_channel_status 表获得。参见第 29.12.22.11 节"tls_channel_status 表"。

- Current_tls_capath

  服务器用于新连接的 TLS 上下文中的活跃 ssl_capath 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_cert

  服务器用于新连接的 TLS 上下文中的活跃 ssl_cert 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_cipher

  服务器用于新连接的 TLS 上下文中的活跃 ssl_cipher 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_ciphersuites

  服务器用于新连接的 TLS 上下文中的活跃 tls_ciphersuites 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_crl

  服务器用于新连接的 TLS 上下文中的活跃 ssl_crl 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

  注意

  重新加载 TLS 上下文时，OpenSSL 会在该过程中重新加载包含 CRL（证书撤销列表）的文件。如果 CRL 文件很大，服务器会分配大量内存（文件大小的十倍），在加载新实例且旧实例尚未释放时会翻倍。进程驻留内存在释放大分配后不会立即减少，因此如果您使用大 CRL 文件重复发出 ALTER INSTANCE RELOAD TLS 语句，进程驻留内存使用量可能会因此增长。

- Current_tls_crlpath

  服务器用于新连接的 TLS 上下文中的活跃 ssl_crlpath 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_key

  服务器用于新连接的 TLS 上下文中的活跃 ssl_key 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Current_tls_version

  服务器用于新连接的 TLS 上下文中的活跃 tls_version 值。有关此状态变量与其对应系统变量之间关系的说明，请参见 Current_tls_ca 的描述。

- Delayed_errors

  此状态变量已弃用（因为不支持 DELAYED 插入）；预计在未来版本中将其删除。

- Delayed_insert_threads

  此状态变量已弃用（因为不支持 DELAYED 插入）；预计在未来版本中将其删除。

- Delayed_writes

  此状态变量已弃用（因为不支持 DELAYED 插入）；预计在未来版本中将其删除。

- Deprecated_use_i_s_processlist_count

  自上次重启以来访问 information_schema.processlist 表的次数。

- Deprecated_use_i_s_processlist_last_timestamp

  一个时间戳，指示自上次重启以来最后一次访问 information_schema.processlist 表的时间。显示自 Unix 纪元以来的微秒数。

- dragnet.Status

  最近一次分配给 dragnet.log_error_filter_rules 系统变量的结果，如果未发生此类分配，则为空。

- Error_log_buffered_bytes

  Performance Schema error_log 表中当前使用的字节数。该值可能会减少，例如，如果新事件无法容纳直到丢弃旧事件，但新事件小于旧事件。

- Error_log_buffered_events

  Performance Schema error_log 表中当前存在的事件数。与 Error_log_buffered_bytes 一样，该值可能会减少。

- Error_log_expired_events

  从 Performance Schema error_log 表中丢弃以为新事件腾出空间的事件数。

- Error_log_latest_write

  最后一次写入 Performance Schema error_log 表的时间。

- Flush_commands

  服务器刷新表的次数，无论是因为用户执行了 FLUSH TABLES 语句还是由于内部服务器操作。它也会因接收 COM_REFRESH 数据包而增加。这与 Com_flush 相反，Com_flush 指示已执行的 FLUSH 语句数，无论是 FLUSH TABLES、FLUSH LOGS 等。

- Global_connection_memory

  所有用户连接到服务器使用的内存。系统线程或 MySQL root 账户使用的内存包含在总数中，但此类线程或用户不受因内存使用而断开连接的限制。除非启用了 global_connection_memory_tracking（默认禁用），否则不计算此内存。Performance Schema 也必须启用。

  您可以通过设置 connection_memory_chunk_size 来间接控制此变量的更新频率。

- Handler_commit

  内部 COMMIT 语句的数量。

- Handler_delete

  从表中删除行的次数。

- Handler_external_lock

  服务器为每次调用其 external_lock() 函数增加此变量，该函数通常在访问表实例的开始和结束时发生。存储引擎之间可能存在差异。此变量可用于例如发现对于访问分区表的语句有多少分区在锁定发生前被修剪：检查计数器增加了多少，减去 2（表本身的 2 次调用），然后除以 2 以获得锁定的分区数。

- Handler_mrr_init

  服务器使用存储引擎自己的多范围读取实现进行表访问的次数。

- Handler_prepare

  两阶段提交操作的准备阶段的计数器。

- Handler_read_first

  读取索引中第一个条目的次数。如果此值很高，则表明服务器正在执行大量全索引扫描（例如，SELECT col1 FROM foo，假设 col1 被索引）。

- Handler_read_key

  基于键读取行的请求数。如果此值很高，这是表明您的表为查询正确索引的好指示。

- Handler_read_last

  读取索引中最后一个键的请求数。使用 ORDER BY，服务器发出第一个键请求，然后是多个下一个键请求，而使用 ORDER BY DESC，服务器发出最后一个键请求，然后是多个上一个键请求。

- Handler_read_next

  按键顺序读取下一行的请求数。如果您使用范围约束查询索引列或执行索引扫描，此值会增加。

- Handler_read_prev

  按键顺序读取上一行的请求数。此读取方法主要用于优化 ORDER BY ... DESC。

- Handler_read_rnd

  基于固定位置读取行的请求数。如果您执行大量需要对结果进行排序的查询，此值会很高。您可能有许多需要 MySQL 扫描整个表的查询，或者您有不正确使用键的连接。

- Handler_read_rnd_next

  读取数据文件中下一行的请求数。如果您执行大量表扫描，此值会很高。通常这表明您的表没有正确索引或您的查询没有编写为利用您拥有的索引。

- Handler_rollback

  存储引擎执行回滚操作的请求数。

- Handler_savepoint

  存储引擎放置保存点的请求数。

- Handler_savepoint_rollback

  存储引擎回滚到保存点的请求数。

- Handler_update

  更新表中行的请求数。

- Handler_write

  在表中插入行的请求数。

- Innodb_buffer_pool_dump_status

  记录 InnoDB 缓冲池中保存的页面的操作进度，由 innodb_buffer_pool_dump_at_shutdown 或 innodb_buffer_pool_dump_now 的设置触发。

  有关相关信息和示例，请参见第 17.8.3.6 节"保存和恢复缓冲池状态"。

- Innodb_buffer_pool_load_status

  通过读入对应于较早时间点的一组页面来预热 InnoDB 缓冲池的操作进度，由 innodb_buffer_pool_load_at_startup 或 innodb_buffer_pool_load_now 的设置触发。如果操作引入过多开销，您可以通过设置 innodb_buffer_pool_load_abort 来取消它。

  有关相关信息和示例，请参见第 17.8.3.6 节"保存和恢复缓冲池状态"。

- Innodb_buffer_pool_bytes_data

  InnoDB 缓冲池中包含数据的总字节数。该数字包括脏页和干净页。对于比 Innodb_buffer_pool_pages_data 更准确的内存使用计算，当压缩表导致缓冲池保存不同大小的页面时。

- Innodb_buffer_pool_pages_data

  InnoDB 缓冲池中包含数据的页面数。该数字包括脏页和干净页。使用压缩表时，报告的 Innodb_buffer_pool_pages_data 值可能大于 Innodb_buffer_pool_pages_total（Bug #59550）。

- Innodb_buffer_pool_bytes_dirty

  InnoDB 缓冲池中脏页中当前保存的总字节数。对于比 Innodb_buffer_pool_pages_dirty 更准确的内存使用计算，当压缩表导致缓冲池保存不同大小的页面时。

- Innodb_buffer_pool_pages_dirty

  InnoDB 缓冲池中当前的脏页数。

- Innodb_buffer_pool_pages_flushed

  从 InnoDB 缓冲池刷新页面的请求数。

- Innodb_buffer_pool_pages_free

  InnoDB 缓冲池中的空闲页面数。

- Innodb_buffer_pool_pages_latched

  InnoDB 缓冲池中的锁定页面数。这些是当前正在读取或写入的页面，或因某种其他原因无法刷新或删除的页面。此变量的计算成本很高，因此仅在服务器构建时定义了 UNIV_DEBUG 系统时才可用。

- Innodb_buffer_pool_pages_misc

  InnoDB 缓冲池中因被分配用于管理开销（例如行锁或自适应哈希索引）而繁忙的页面数。此值也可以计算为 Innodb_buffer_pool_pages_total − Innodb_buffer_pool_pages_free − Innodb_buffer_pool_pages_data。使用压缩表时，Innodb_buffer_pool_pages_misc 可能报告越界值（Bug #59550）。

- Innodb_buffer_pool_pages_total

  InnoDB 缓冲池的总大小，以页面为单位。使用压缩表时，报告的 Innodb_buffer_pool_pages_data 值可能大于 Innodb_buffer_pool_pages_total（Bug #59550）

- Innodb_buffer_pool_read_ahead

  由读取预先加载后台线程读入 InnoDB 缓冲池的页面数。

- Innodb_buffer_pool_read_ahead_evicted

  由读取预先加载后台线程读入 InnoDB 缓冲池但随后被驱逐而未被查询访问的页面数。

- Innodb_buffer_pool_read_ahead_rnd

  InnoDB 启动的"随机"读取预先加载数。当查询以随机顺序扫描表的大部分时会发生这种情况。

- Innodb_buffer_pool_read_requests

  逻辑读取请求的数量。

- Innodb_buffer_pool_reads

  InnoDB 无法从缓冲池满足且必须直接从磁盘读取的逻辑读取数。

• Innodb_buffer_pool_resize_status

调整 InnoDB 缓冲池大小的操作状态，通过动态设置 innodb_buffer_pool_size 参数触发。innodb_buffer_pool_size 参数是动态的，允许在不重启服务器的情况下调整缓冲池大小。相关信息请参见配置 InnoDB 缓冲池大小在线。

• Innodb_buffer_pool_resize_status_code

报告用于跟踪在线缓冲池调整大小操作的状态代码。每个状态代码代表调整大小操作中的一个阶段。状态代码包括：

- 0：没有调整大小操作进行中
- 1：开始调整大小
- 2：禁用 AHI（自适应哈希索引）
- 3：撤回块
- 4：获取全局锁
- 5：调整池大小
- 6：调整哈希大小
- 7：调整大小失败

可以将此状态变量与 Innodb_buffer_pool_resize_status_progress 结合使用来跟踪调整大小操作每个阶段的进度。Innodb_buffer_pool_resize_status_progress 变量报告一个百分比值，指示当前阶段的进度。

有关更多信息，请参见监控在线缓冲池调整大小进度。

• Innodb_buffer_pool_resize_status_progress

报告一个百分比值，指示在线缓冲池调整大小操作当前阶段的进度。此变量与 Innodb_buffer_pool_resize_status_code 结合使用，后者报告指示在线缓冲池调整大小操作当前阶段的状态代码。

百分比值在处理每个缓冲池实例后更新。当状态代码（由 Innodb_buffer_pool_resize_status_code 报告）从一个状态更改为另一个状态时，百分比值重置为 0。

相关信息请参见监控在线缓冲池调整大小进度。

服务器用于使用 SSL 的连接的验证模式。该值是一个位掩码；位在 openssl/ssl.h 头文件中定义：
```
# define SSL_VERIFY_NONE                 0x00
# define SSL_VERIFY_PEER                 0x01
# define SSL_VERIFY_FAIL_IF_NO_PEER_CERT 0x02
# define SSL_VERIFY_CLIENT_ONCE          0x04
```

SSL_VERIFY_PEER 表示服务器请求客户端证书。如果客户端提供证书，服务器执行验证，仅在验证成功时才继续。SSL_VERIFY_CLIENT_ONCE 表示仅在初始握手期间执行客户端证书请求。

- Table_open_cache_triggers_hits

带触发器的打开表的缓存命中次数。当数据修改操作在表缓存中的未使用表列表中找到带触发器的表时，此数字增加 1。当此类表是只读操作（如 SELECT）的主体时，该表被视为没有触发器，Table_open_cache_hits 增加。

- Table_open_cache_triggers_misses

带触发器的打开表的缓存未命中次数。当待处理的数据修改操作在表缓存中具有触发器的未使用表列表中未找到带触发器的表时，此数字增加 1。如果表上的待处理操作是只读的（如 SELECT 语句），该表被视为没有触发器，Table_open_cache_misses 增加。

- Table_open_cache_triggers_overflows

带触发器的打开表的缓存溢出次数。当给定表缓存实例中带触发器的表数超过最大值时，此数字增加 1。即，当 Table_open_cache_triggers_hits 超过每个缓存实例的带触发器表的最大数量时，此状态变量增加；此最大值由 table_open_cache_triggers / table_open_cache_instances 确定。

注意

Table_open_cache_triggers_hits 仅受数据修改操作影响。因此，当只读操作（如 SELECT）访问带触发器的表时，Table_open_cache_triggers_overflows 也不受影响。对带触发器的表的只读操作增加 Table_open_cache_hits；如果 Table_open_cache_hits 随后超过由 table_open_cache / table_open_cache_instances 确定的限制，则 Table_open_cache_overflows 增加。
