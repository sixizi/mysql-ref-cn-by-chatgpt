### 7.1.11 服务器 SQL 模式

MySQL 服务器可以在不同的 SQL 模式下运行，并可以根据 sql_mode 系统变量的值为不同的客户端应用不同的模式。数据库管理员可以设置全局 SQL 模式以匹配站点服务器的运行要求，每个应用程序可以设置其会话 SQL 模式以满足自己的要求。

模式影响 MySQL 支持的 SQL 语法和执行的数据验证检查。这使得在不同的环境中使用 MySQL 以及将 MySQL 与其他数据库服务器一起使用变得更容易。

有关 MySQL 中服务器 SQL 模式的常见问题解答，请参见第 A.3 节"MySQL 26.10 常见问题解答：服务器 SQL 模式"。

使用 InnoDB 表时，还应考虑 innodb_strict_mode 系统变量。它为 InnoDB 表启用额外的错误检查。

#### 设置 SQL 模式

MySQL 26.10 中的默认 SQL 模式包括以下模式：ONLY_FULL_GROUP_BY、STRICT_TRANS_TABLES、NO_ZERO_IN_DATE、NO_ZERO_DATE、ERROR_FOR_DIVISION_BY_ZERO 和 NO_ENGINE_SUBSTITUTION。

要在服务器启动时设置 SQL 模式，请在命令行上使用 --sql-mode="modes" 选项，或在选项文件（如 Unix 操作系统上的 my.cnf 或 Windows 上的 my.ini）中使用 sql-mode="modes"。modes 是由逗号分隔的不同模式列表。要显式清除 SQL 模式，请在命令行上使用 --sql-mode="" 或在选项文件中使用 sql-mode=""。

注意

MySQL 安装程序可能在安装过程中配置 SQL 模式。

如果 SQL 模式与默认值或您的预期不同，请检查服务器在启动时读取的选项文件中的设置。

要在运行时更改 SQL 模式，请使用 SET 语句设置全局或会话 sql_mode 系统变量：

```
SET GLOBAL sql_mode = 'modes';
SET SESSION sql_mode = 'modes';
```

设置 GLOBAL 变量需要 SYSTEM_VARIABLES_ADMIN 权限（或已弃用的 SUPER 权限），并影响从该时间起连接的所有客户端的操作。设置 SESSION 变量仅影响当前客户端。每个客户端可以随时更改其会话 sql_mode 值。

要确定当前的全局或会话 sql_mode 设置，请选择其值：

```
SELECT @@GLOBAL.sql_mode;
SELECT @@SESSION.sql_mode;
```

重要

SQL 模式和用户定义的分区。在创建分区表并向其中插入数据后更改服务器 SQL 模式可能会导致此类表的行为发生重大变化，并可能导致数据丢失或损坏。强烈建议您在创建使用用户定义分区的表后永远不要更改 SQL 模式。

复制分区表时，源和副本上的 SQL 模式不同也可能导致问题。为获得最佳结果，应始终在源和副本上使用相同的服务器 SQL 模式。

有关更多信息，请参见第 26.6 节"分区的限制和局限"。

#### 最重要的 SQL 模式

最重要的 sql_mode 值可能是这些：

- ANSI

此模式更改语法和行为以更严格地符合标准 SQL。它是本节末尾列出的特殊组合模式之一。

- STRICT_TRANS_TABLES

如果无法将值按给定方式插入事务表，则中止该语句。对于非事务表，如果该值出现在单行语句或多行语句的第一行中，则中止该语句。本节后面提供了更多详细信息。

- TRADITIONAL

使 MySQL 的行为类似于"传统"SQL 数据库系统。此模式的简单描述是"在将不正确的值插入列时给出错误而不是警告"。它是本节末尾列出的特殊组合模式之一。

注意

启用 TRADITIONAL 模式后，INSERT 或 UPDATE 在发生错误时立即中止。如果您使用的是非事务存储引擎，这可能不是您想要的，因为在错误之前所做的数据更改可能不会被回滚，导致"部分完成"的更新。

当本手册提到"严格模式"时，它指的是启用了 STRICT_TRANS_TABLES 或 STRICT_ALL_TABLES 中的一个或两个的模式。

#### SQL 模式完整列表

以下列表描述了所有支持的 SQL 模式：

- ALLOW_INVALID_DATES

不执行日期的完整检查。仅检查月份是否在 1 到 12 的范围内，日期是否在 1 到 31 的范围内。这对于在三个不同字段中获取年、月和日并准确存储用户插入的内容而不进行日期验证的 Web 应用程序可能很有用。此模式适用于 DATE 和 DATETIME 列。它不适用于 TIMESTAMP 列，TIMESTAMP 列始终需要有效日期。

禁用 ALLOW_INVALID_DATES 时，服务器要求月份和日期值合法，而不仅仅是在 1 到 12 和 1 到 31 的范围内。禁用严格模式时，无效日期（如 '2004-04-31'）被转换为 '0000-00-00' 并生成警告。启用严格模式时，无效日期会生成错误。要允许此类日期，请启用 ALLOW_INVALID_DATES。

- ANSI_QUOTES

将 " 视为标识符引用字符（如 ` 引用字符），而不是字符串引用字符。启用此模式后，您仍然可以使用 ` 来引用标识符。启用 ANSI_QUOTES 后，您不能使用双引号来引用文字字符串，因为它们被解释为标识符。

- ERROR_FOR_DIVISION_BY_ZERO

ERROR_FOR_DIVISION_BY_ZERO 模式影响除以零的处理，包括 MOD(N,0)。对于数据更改操作（INSERT、UPDATE），其效果还取决于是否启用了严格 SQL 模式。

- 如果未启用此模式，除以零会插入 NULL 并不产生警告。

- 如果启用了此模式，除以零会插入 NULL 并产生警告。

- 如果启用了此模式和严格模式，除以零会产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，除以零会插入 NULL 并产生警告。

对于 SELECT，除以零返回 NULL。启用 ERROR_FOR_DIVISION_BY_ZERO 也会产生警告，无论是否启用了严格模式。

ERROR_FOR_DIVISION_BY_ZERO 已弃用。ERROR_FOR_DIVISION_BY_ZERO 不是严格模式的一部分，但应与严格模式结合使用，并且默认启用。如果启用了 ERROR_FOR_DIVISION_BY_ZERO 但未启用严格模式，或反之亦然，则会发生警告。

由于 ERROR_FOR_DIVISION_BY_ZERO 已弃用，您应该期望在未来的 MySQL 版本中将其作为单独的模式名称删除，其效果包含在严格 SQL 模式的效果中。

- HIGH_NOT_PRECEDENCE

NOT 运算符的优先级使得诸如 NOT a BETWEEN b AND c 之类的表达式被解析为 NOT (a BETWEEN b AND c)。在 MySQL 的某些较早版本中，该表达式被解析为 (NOT a) BETWEEN b AND c。可以通过启用 HIGH_NOT_PRECEDENCE SQL 模式来获得旧的更高优先级行为。

```
mysql> SET sql_mode = '';
mysql> SELECT NOT 1 BETWEEN -5 AND 5;
        -> 0
mysql> SET sql_mode = 'HIGH_NOT_PRECEDENCE';
mysql> SELECT NOT 1 BETWEEN -5 AND 5;
        -> 1
```

- IGNORE_SPACE

允许函数名称和 ( 字符之间有空格。这导致内置函数名称被视为保留字。因此，与函数名称相同的标识符必须按第 11.2 节"模式对象名称"中的说明进行引用。例如，因为存在 COUNT() 函数，在以下语句中使用 count 作为表名会导致错误：

```
mysql> CREATE TABLE count (i INT);
ERROR 1064 (42000): You have an error in your SQL syntax
```

表名应该被引用：

```
mysql> CREATE TABLE `count` (i INT);
Query OK, 0 rows affected (0.00 sec)
```

IGNORE_SPACE SQL 模式适用于内置函数，不适用于可加载函数或存储函数。无论是否启用 IGNORE_SPACE，在可加载函数或存储函数名称后有空格总是允许的。

有关 IGNORE_SPACE 的进一步讨论，请参见第 11.2.5 节"函数名称解析和解析"。

- INTERPRET_UTF8_AS_UTF8MB4

控制已弃用的 utf8 字符集别名和 utf8_* 排序规则别名在 SQL 语句中的解释方式。此模式默认禁用。禁用时，utf8 表示 utf8mb3，utf8_xxx 表示 utf8mb3_xxx。启用时，utf8 表示 utf8mb4，utf8_xxx 表示 utf8mb4_xxx。字符集和排序规则名称不区分大小写。

该模式适用于 DDL 和 DML 语句，包括 _utf8 字符集引入符。SHOW CREATE 语句显示在 DDL 处理期间选择的规范名称，EXPLAIN 反映在 DML 处理期间选择的名称。

启用此模式时，别名 utf8_general_mysql500_ci 和 utf8_tolower_ci 被拒绝，因为不存在相应的 utf8mb4 排序规则。如果需要这些排序规则之一，请显式指定 utf8mb3_general_mysql500_ci 或 utf8mb3_tolower_ci。

存储过程、存储函数和触发器定义保留定义时生效的 SQL 模式。因此，当它们执行时，它们的 utf8 别名使用该保留模式进行解释。

此模式不影响客户端 --default-character-set 选项、服务器启动字符集和排序规则选项或从 Index.xml 读取的外部字符集定义。

- NO_AUTO_VALUE_ON_ZERO

NO_AUTO_VALUE_ON_ZERO 影响 AUTO_INCREMENT 列的处理。通常，您通过向列中插入 NULL 或 0 来生成该列的下一个序列号。NO_AUTO_VALUE_ON_ZERO 抑制 0 的此行为，以便仅 NULL 生成下一个序列号。

如果 0 已存储在表的 AUTO_INCREMENT 列中，此模式可能很有用。（顺便说一下，存储 0 不是推荐的做法。）例如，如果您使用 mysqldump 转储表然后重新加载它，MySQL 通常在遇到 0 值时生成新的序列号，导致表的内容与转储的表不同。在重新加载转储文件之前启用 NO_AUTO_VALUE_ON_ZERO 可以解决此问题。因此，mysqldump 会自动在其输出中包含启用 NO_AUTO_VALUE_ON_ZERO 的语句。

- NO_BACKSLASH_ESCAPES

启用此模式会禁用在字符串和标识符中使用反斜杠字符 (\) 作为转义字符。启用此模式后，反斜杠变成普通字符，LIKE 表达式的默认转义序列被更改，以便不使用转义字符。

- NO_DIR_IN_CREATE

创建表时，忽略所有 INDEX DIRECTORY 和 DATA DIRECTORY 指令。此选项在副本服务器上很有用。

- NO_ENGINE_SUBSTITUTION

控制当 CREATE TABLE 或 ALTER TABLE 等语句指定已禁用或未编译的存储引擎时是否自动替换默认存储引擎。

默认情况下，NO_ENGINE_SUBSTITUTION 已启用。

由于存储引擎可以在运行时插入，不可用的引擎的处理方式相同：

禁用 NO_ENGINE_SUBSTITUTION 时，对于 CREATE TABLE，使用默认引擎，如果所需引擎不可用，则会发生警告。对于 ALTER TABLE，会发生警告，表不被更改。

启用 NO_ENGINE_SUBSTITUTION 时，如果所需引擎不可用，会发生错误，表不被创建或更改。

- NO_UNSIGNED_SUBTRACTION

整数值之间的减法，其中一个是 UNSIGNED 类型，默认情况下会产生无符号结果。如果结果本来是负数，则会发生错误：

```
mysql> SET sql_mode = '';
Query OK, 0 rows affected (0.00 sec)

mysql> SELECT CAST(0 AS UNSIGNED) - 1;
ERROR 1690 (22003): BIGINT UNSIGNED value is out of range in '(cast(0 as unsigned) - 1)'
```

如果启用了 NO_UNSIGNED_SUBTRACTION SQL 模式，结果是负数：

```
mysql> SET sql_mode = 'NO_UNSIGNED_SUBTRACTION';
mysql> SELECT CAST(0 AS UNSIGNED) - 1;
+-------------------------+
| CAST(0 AS UNSIGNED) - 1 |
+-------------------------+
|                      -1 |
+-------------------------+
```

如果此类操作的结果用于更新 UNSIGNED 整数列，结果会被裁剪到列类型的最大值，或者如果启用了 NO_UNSIGNED_SUBTRACTION，则被裁剪到 0。启用严格 SQL 模式时，会发生错误，列保持不变。

启用 NO_UNSIGNED_SUBTRACTION 时，减法结果是有符号的，即使任何操作数是无符号的。例如，比较表 t1 中列 c2 的类型与表 t2 中列 c2 的类型：

```
mysql> SET sql_mode='';
mysql> CREATE TABLE test (c1 BIGINT UNSIGNED NOT NULL);
mysql> CREATE TABLE t1 SELECT c1 - 1 AS c2 FROM test;
mysql> DESCRIBE t1;
+-------+---------------------+------+-----+---------+-------+
| Field | Type                | Null | Key | Default | Extra |
+-------+---------------------+------+-----+---------+-------+
| c2    | bigint(21) unsigned | NO   |     | 0       |       |
+-------+---------------------+------+-----+---------+-------+

mysql> SET sql_mode='NO_UNSIGNED_SUBTRACTION';
mysql> CREATE TABLE t2 SELECT c1 - 1 AS c2 FROM test;
mysql> DESCRIBE t2;
+-------+------------+------+-----+---------+-------+
| Field | Type       | Null | Key | Default | Extra |
+-------+------------+------+-----+---------+-------+
| c2    | bigint(21) | NO   |     | 0       |       |
+-------+------------+------+-----+---------+-------+
```

这意味着 BIGINT UNSIGNED 在所有上下文中都不是 100% 可用的。请参见第 14.10 节"转换函数和运算符"。

- NO_ZERO_DATE

NO_ZERO_DATE 模式影响服务器是否允许 '0000-00-00' 作为有效日期。其效果还取决于是否启用了严格 SQL 模式。

- 如果未启用此模式，'0000-00-00' 被允许，插入不产生警告。

- 如果启用了此模式，'0000-00-00' 被允许，插入产生警告。

- 如果启用了此模式和严格模式，'0000-00-00' 不被允许，插入产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，'0000-00-00' 被允许，插入产生警告。

NO_ZERO_DATE 已弃用。NO_ZERO_DATE 不是严格模式的一部分，但应与严格模式结合使用，并且默认启用。如果启用了 NO_ZERO_DATE 但未启用严格模式，或反之亦然，则会发生警告。

由于 NO_ZERO_DATE 已弃用，您应该期望在未来的 MySQL 版本中将其作为单独的模式名称删除，其效果包含在严格 SQL 模式的效果中。

- NO_ZERO_IN_DATE

NO_ZERO_IN_DATE 模式影响服务器是否允许年份部分非零但月份或日期部分为 0 的日期。（此模式影响诸如 '2010-00-01' 或 '2010-01-00' 之类的日期，但不影响 '0000-00-00'。要控制服务器是否允许 '0000-00-00'，请使用 NO_ZERO_DATE 模式。）NO_ZERO_IN_DATE 的效果还取决于是否启用了严格 SQL 模式。

- 如果未启用此模式，允许包含零部分的日期，插入不产生警告。

- 如果启用了此模式，包含零部分的日期被插入为 '0000-00-00' 并产生警告。

- 如果启用了此模式和严格模式，不允许包含零部分的日期，插入产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，包含零部分的日期被插入为 '0000-00-00' 并产生警告。

NO_ZERO_IN_DATE 已弃用。NO_ZERO_IN_DATE 不是严格模式的一部分，但应与严格模式结合使用，并且默认启用。如果启用了 NO_ZERO_IN_DATE 但未启用严格模式，或反之亦然，则会发生警告。

由于 NO_ZERO_IN_DATE 已弃用，您应该期望在未来的 MySQL 版本中将其作为单独的模式名称删除，其效果包含在严格 SQL 模式的效果中。

- ONLY_FULL_GROUP_BY

拒绝选择列表、HAVING 条件或 ORDER BY 列表引用非聚合列的查询，这些列既未在 GROUP BY 子句中命名，也不是函数依赖的（由 GROUP BY 列唯一确定）。

MySQL 对标准 SQL 的扩展允许在 HAVING 子句中引用选择列表中的别名表达式。无论是否启用 ONLY_FULL_GROUP_BY，HAVING 子句都可以引用别名。

有关其他讨论和示例，请参见第 14.19.3 节"MySQL 对 GROUP BY 的处理"。

- PAD_CHAR_TO_FULL_LENGTH

默认情况下，从 CHAR 列值检索时会修剪尾随空格。如果启用了 PAD_CHAR_TO_FULL_LENGTH，则不会进行修剪，检索的 CHAR 值会被填充到其完整长度。此模式不适用于 VARCHAR 列，VARCHAR 列在检索时保留尾随空格。

注意

PAD_CHAR_TO_FULL_LENGTH 已弃用。预期它将在 MySQL 的未来版本中被删除。

```
mysql> CREATE TABLE t1 (c1 CHAR(10));
Query OK, 0 rows affected (0.37 sec)

mysql> INSERT INTO t1 (c1) VALUES('xy');
Query OK, 1 row affected (0.01 sec)

mysql> SET sql_mode = '';
Query OK, 0 rows affected (0.00 sec)

mysql> SELECT c1, CHAR_LENGTH(c1) FROM t1;
+------+-----------------+
| c1   | CHAR_LENGTH(c1) |
+------+-----------------+
| xy   |                2 |
+------+-----------------+
1 row in set (0.00 sec)

mysql> SET sql_mode = 'PAD_CHAR_TO_FULL_LENGTH';
Query OK, 0 rows affected (0.00 sec)

mysql> SELECT c1, CHAR_LENGTH(c1) FROM t1;
+------------+-----------------+
| c1         | CHAR_LENGTH(c1) |
+------------+-----------------+
| xy         |              10 |
+------------+-----------------+
1 row in set (0.00 sec)
```

- PIPES_AS_CONCAT

将 || 视为字符串连接运算符（与 CONCAT() 相同），而不是 OR 的同义词。

- REAL_AS_FLOAT

将 REAL 视为 FLOAT 的同义词。默认情况下，MySQL 将 REAL 视为 DOUBLE 的同义词。

- STRICT_ALL_TABLES

为所有存储引擎启用严格 SQL 模式。无效的数据值被拒绝。有关详细信息，请参见严格 SQL 模式。

- STRICT_TRANS_TABLES

为事务存储引擎启用严格 SQL 模式，并在可能的情况下为非事务存储引擎启用。有关详细信息，请参见严格 SQL 模式。

- TIME_TRUNCATE_FRACTIONAL

控制当将具有小数秒部分的 TIME、DATE 或 TIMESTAMP 值插入具有相同类型但小数位数较少的列时是否进行舍入或截断。默认行为是使用舍入。如果启用此模式，则进行截断。以下语句序列说明了差异：

```
CREATE TABLE t (id INT, tval TIME(1));
SET sql_mode='';
INSERT INTO t (id, tval) VALUES(1, 1.55);
SET sql_mode='TIME_TRUNCATE_FRACTIONAL';
INSERT INTO t (id, tval) VALUES(2, 1.55);
```

生成的表内容如下所示，其中第一个值已进行舍入，第二个值已进行截断：

```
mysql> SELECT id, tval FROM t ORDER BY id;
+------+------------+
| id   | tval       |
+------+------------+
|    1 | 00:00:01.6 |
|    2 | 00:00:01.5 |
+------+------------+
```

另请参见第 13.2.6 节"时间值中的小数秒"。

#### 组合 SQL 模式

以下特殊模式作为前面列表中的模式值组合的简写提供。

- ANSI

等同于 REAL_AS_FLOAT、PIPES_AS_CONCAT、ANSI_QUOTES、IGNORE_SPACE 和 ONLY_FULL_GROUP_BY。

ANSI 模式还导致服务器为具有外部引用 S(outer_ref) 的集合函数 S 无法在已解析外部引用的外部查询中聚合的查询返回错误。这是这样的查询：

```
SELECT * FROM t1 WHERE t1.a IN (SELECT MAX(t1.b) FROM t2 WHERE ...);
```

这里，MAX(t1.b) 无法在外部查询中聚合，因为它出现在该查询的 WHERE 子句中。标准 SQL 在这种情况下需要错误。如果未启用 ANSI 模式，服务器将 S(outer_ref) 在此类查询中的处理方式与解释 S(const) 的方式相同。

请参见第 1.7 节"MySQL 标准合规性"。

- TRADITIONAL

TRADITIONAL 等同于 STRICT_TRANS_TABLES、STRICT_ALL_TABLES、NO_ZERO_IN_DATE、NO_ZERO_DATE、ERROR_FOR_DIVISION_BY_ZERO 和 NO_ENGINE_SUBSTITUTION。

#### 严格 SQL 模式

严格模式控制 MySQL 如何处理数据更改语句（如 INSERT 或 UPDATE）中的无效或缺失值。值可能因多种原因而无效。例如，它可能对列具有错误的数据类型，或者可能超出范围。当要插入的新行不包含非 NULL 列的值且该列在其定义中没有显式 DEFAULT 子句时，值是缺失的。（对于 NULL 列，如果值缺失，则插入 NULL。）严格模式还影响 DDL 语句，如 CREATE TABLE。

如果严格模式未生效，MySQL 为无效或缺失值插入调整后的值并产生警告（请参见第 15.7.7.44 节"SHOW WARNINGS 语句"）。在严格模式下，您可以通过使用 INSERT IGNORE 或 UPDATE IGNORE 来产生此行为。

对于不更改数据的语句（如 SELECT），无效值在严格模式下生成警告，而不是错误。

严格模式为尝试创建超过最大键长度的键产生错误。未启用严格模式时，这会导致警告和键截断到最大键长度。

严格模式不影响是否检查外键约束。foreign_key_checks 可用于此。（请参见第 7.1.8 节"服务器系统变量"。）

如果启用了 STRICT_ALL_TABLES 或 STRICT_TRANS_TABLES 中的任何一个，严格 SQL 模式就会生效，尽管这些模式的效果略有不同：

- 对于事务表，当启用 STRICT_ALL_TABLES 或 STRICT_TRANS_TABLES 中的任何一个时，数据更改语句中的无效或缺失值会发生错误。该语句被中止并回滚。

- 对于非事务表，如果坏值出现在要插入或更新的第一行中，两种模式的行为相同：该语句被中止，表保持不变。如果语句插入或修改多行，坏值出现在第二行或后续行中，结果取决于启用的严格模式：

### 7.1.11 服务器 SQL 模式

- 对于 STRICT_ALL_TABLES，MySQL 返回错误并忽略其余行。但是，由于之前的行已被插入或更新，结果是部分更新。为了避免这种情况，请使用单行语句，这些语句可以在不更改表的情况下中止。

- 对于 STRICT_TRANS_TABLES，MySQL 将无效值转换为该列的最接近的有效值并插入调整后的值。如果缺少值，MySQL 会为列数据类型插入隐式默认值。在任何一种情况下，MySQL 都会生成警告而不是错误，并继续处理该语句。隐式默认值在第 13.6 节"数据类型默认值"中进行了描述。

严格模式影响零除、零日期和日期中的零的处理方式如下：

- 严格模式影响零除的处理，包括 MOD(N,0)：

  对于数据更改操作（INSERT、UPDATE）：

  - 如果未启用严格模式，零除会插入 NULL 且不产生警告。

  - 如果启用了严格模式，零除会产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，零除会插入 NULL 并产生警告。

  对于 SELECT，零除返回 NULL。启用严格模式也会产生警告。

- 严格模式影响服务器是否允许 '0000-00-00' 作为有效日期：

  - 如果未启用严格模式，'0000-00-00' 被允许且插入不产生警告。

  - 如果启用了严格模式，'0000-00-00' 不被允许且插入产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，'0000-00-00' 被允许且插入产生警告。

- 严格模式影响服务器是否允许年份部分非零但月份或日期部分为 0 的日期（例如 '2010-00-01' 或 '2010-01-00'）：

  - 如果未启用严格模式，包含零部分的日期被允许且插入不产生警告。

  - 如果启用了严格模式，包含零部分的日期不被允许且插入产生错误，除非同时给出 IGNORE。对于 INSERT IGNORE 和 UPDATE IGNORE，包含零部分的日期被插入为 '0000-00-00'（使用 IGNORE 时被视为有效）并产生警告。

有关严格模式与 IGNORE 的更多信息，请参阅 IGNORE 关键字和严格 SQL 模式的比较。

严格模式影响零除、零日期和日期中的零的处理，结合 ERROR_FOR_DIVISION_BY_ZERO、NO_ZERO_DATE 和 NO_ZERO_IN_DATE 模式。

## IGNORE 关键字和严格 SQL 模式的比较

本节比较 IGNORE 关键字（将错误降级为警告）和严格 SQL 模式（将警告升级为错误）对语句执行的影响。它描述了它们影响的语句以及它们适用的错误。

下表呈现了当默认值是产生错误与警告时语句行为的摘要比较。默认值产生错误的示例是将 NULL 插入 NOT NULL 列。默认值产生警告的示例是将错误数据类型的值插入列（例如将字符串 'abc' 插入整数列）。

| 操作模式 | 当语句默认值为错误时 | 当语句默认值为警告时 |
|---------|------------------|------------------|
| 不使用 IGNORE 或严格 SQL 模式 | 错误 | 警告 |
| 使用 IGNORE | 警告 | 警告（与不使用 IGNORE 或严格 SQL 模式相同） |
| 使用严格 SQL 模式 | 错误（与不使用 IGNORE 或严格 SQL 模式相同） | 错误 |
| 同时使用 IGNORE 和严格 SQL 模式 | 警告 | 警告 |

从该表可以得出的一个结论是，当 IGNORE 关键字和严格 SQL 模式都生效时，IGNORE 优先。这意味着，虽然 IGNORE 和严格 SQL 模式可以被认为对错误处理有相反的影响，但它们一起使用时不会相互抵消。

- IGNORE 对语句执行的影响

- 严格 SQL 模式对语句执行的影响

## IGNORE 对语句执行的影响

MySQL 中的多个语句支持可选的 IGNORE 关键字。此关键字使服务器将某些类型的错误降级并改为生成警告。对于多行语句，将错误降级为警告可能使一行得以处理。否则，IGNORE 会导致语句跳到下一行而不是中止。（对于不可忽略的错误，无论是否使用 IGNORE 关键字，都会发生错误。）

示例：如果表 t 有一个包含唯一值的主键列 i，尝试将相同的 i 值插入多行通常会产生重复键错误：

```
mysql> CREATE TABLE t (i INT NOT NULL PRIMARY KEY);
mysql> INSERT INTO t (i) VALUES(1),(1);
ERROR 1062 (23000): Duplicate entry '1' for key 't.PRIMARY'
```

使用 IGNORE，包含重复键的行仍然不会被插入，但会产生警告而不是错误：

```
mysql> INSERT IGNORE INTO t (i) VALUES(1),(1);
Query OK, 1 row affected, 1 warning (0.01 sec)
Records: 2 Duplicates: 1 Warnings: 1

mysql> SHOW WARNINGS;
+---------+------+-----------------------------------------+
| Level   | Code | Message                                 |
+---------+------+-----------------------------------------+
| Warning | 1062 | Duplicate entry '1' for key 't.PRIMARY' |
+---------+------+-----------------------------------------+
1 row in set (0.00 sec)
```

示例：如果表 t2 有一个 NOT NULL 列 id，尝试插入 NULL 在严格 SQL 模式下会产生错误：

```
mysql> CREATE TABLE t2 (id INT NOT NULL);
mysql> INSERT INTO t2 (id) VALUES(1),(NULL),(3);
ERROR 1048 (23000): Column 'id' cannot be null
mysql> SELECT * FROM t2;
Empty set (0.00 sec)
```

如果 SQL 模式不是严格的，IGNORE 会导致 NULL 被插入为列隐式默认值（在本例中为 0），这使得行可以被处理而不跳过它：

```
mysql> INSERT INTO t2 (id) VALUES(1),(NULL),(3);
mysql> SELECT * FROM t2;
+----+
| id |
+----+
| 1 |
| 0 |
| 3 |
+----+
```

以下语句支持 IGNORE 关键字：

- CREATE TABLE ... SELECT：IGNORE 不适用于语句的 CREATE TABLE 或 SELECT 部分，而是适用于由 SELECT 产生的行插入表中。复制唯一键值上现有行的行被丢弃。

- DELETE：IGNORE 导致 MySQL 在删除行的过程中忽略错误。

- INSERT：使用 IGNORE，复制唯一键值上现有行的行被丢弃。设置为会导致数据转换错误的值的行被设置为最接近的有效值。

  对于分区表，如果未找到与给定值匹配的分区，IGNORE 会导致包含不匹配值的行的插入操作无声地失败。

- LOAD DATA、LOAD XML：使用 IGNORE，复制唯一键值上现有行的行被丢弃。

- UPDATE：使用 IGNORE，在唯一键值上发生重复键冲突的行不被更新。更新为会导致数据转换错误的值的行被更新为最接近的有效值。

IGNORE 关键字适用于以下可忽略的错误：

- ER_BAD_NULL_ERROR

- ER_DUP_ENTRY

- ER_DUP_ENTRY_WITH_KEY_NAME

- ER_DUP_KEY

- ER_NO_PARTITION_FOR_GIVEN_VALUE

- ER_NO_PARTITION_FOR_GIVEN_VALUE_SILENT

- ER_NO_REFERENCED_ROW_2

- ER_ROW_DOES_NOT_MATCH_GIVEN_PARTITION_SET

- ER_ROW_IS_REFERENCED_2

- ER_SUBQUERY_NO_1_ROW

- ER_VIEW_CHECK_FAILED

## 严格 SQL 模式对语句执行的影响

MySQL 服务器可以在不同的 SQL 模式下运行，并可以根据 sql_mode 系统变量的值为不同的客户端以不同方式应用这些模式。在"严格"SQL 模式下，服务器将某些警告升级为错误。

例如，在非严格 SQL 模式下，将字符串 'abc' 插入整数列会导致值转换为 0 和警告：

```
mysql> SET sql_mode = '';
Query OK, 0 rows affected (0.00 sec)

mysql> INSERT INTO t (i) VALUES('abc');
Query OK, 1 row affected, 1 warning (0.01 sec)

mysql> SHOW WARNINGS;
+---------+------+--------------------------------------------------------+
| Level   | Code | Message                                                |
+---------+------+--------------------------------------------------------+
| Warning | 1366 | Incorrect integer value: 'abc' for column 'i' at row 1 |
+---------+------+--------------------------------------------------------+
1 row in set (0.00 sec)
```

在严格 SQL 模式下，无效值被拒绝并产生错误：

```
mysql> SET sql_mode = 'STRICT_ALL_TABLES';
Query OK, 0 rows affected (0.00 sec)

mysql> INSERT INTO t (i) VALUES('abc');
ERROR 1366 (HY000): Incorrect integer value: 'abc' for column 'i' at row 1
```

有关 sql_mode 系统变量可能设置的更多信息，请参阅第 7.1.11 节"服务器 SQL 模式"。

严格 SQL 模式适用于以下语句，条件是某个值可能超出范围或无效行被插入到表中或从表中删除：

- ALTER TABLE

- CREATE TABLE

- CREATE TABLE ... SELECT

- DELETE（单表和多表）

- INSERT

- LOAD DATA

- LOAD XML

- SELECT SLEEP()

- UPDATE（单表和多表）

在存储程序中，如果程序是在严格模式生效时定义的，则刚才列出的类型的各个语句在严格 SQL 模式下执行。

严格 SQL 模式适用于以下错误，这些错误代表一类错误，其中输入值要么无效，要么缺失。如果值的数据类型对列不正确或可能超出范围，则该值无效。如果要插入的新行不包含没有显式 DEFAULT 子句的 NOT NULL 列的值，则该值缺失。

- ER_BAD_NULL_ERROR

- ER_CUT_VALUE_GROUP_CONCAT

- ER_DATA_TOO_LONG

- ER_DATETIME_FUNCTION_OVERFLOW

- ER_DIVISION_BY_ZERO

- ER_INVALID_ARGUMENT_FOR_LOGARITHM

- ER_NO_DEFAULT_FOR_FIELD

- ER_NO_DEFAULT_FOR_VIEW_FIELD

- ER_TOO_LONG_KEY

- ER_TRUNCATED_WRONG_VALUE

- ER_TRUNCATED_WRONG_VALUE_FOR_FIELD

- ER_WARN_DATA_OUT_OF_RANGE

- ER_WARN_NULL_TO_NOTNULL

- ER_WARN_TOO_FEW_RECORDS

- ER_WRONG_ARGUMENTS

- ER_WRONG_VALUE_FOR_TYPE

- WARN_DATA_TRUNCATED

> 注意
>
> 由于 MySQL 的持续开发定义了新的错误，可能存在不在前面列表中的错误，严格 SQL 模式也适用于这些错误。
