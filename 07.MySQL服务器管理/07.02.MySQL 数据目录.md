## 7.2 MySQL 数据目录

MySQL 服务器管理的信息存储在称为数据目录的目录下。以下列表简要描述了数据目录中通常找到的项目，并提供了其他信息的交叉引用：

- 数据目录子目录。数据目录的每个子目录都是一个数据库目录，对应于服务器管理的一个数据库。所有 MySQL 安装都有某些标准数据库：

  - mysql 目录对应于 mysql 系统模式，其中包含 MySQL 服务器运行时所需的信息。此数据库包含数据字典表和系统表。参见第 7.3 节"mysql 系统模式"。

  - performance_schema 目录对应于 Performance Schema，它提供用于在运行时检查服务器内部执行的信息。参见第 29 章"MySQL Performance Schema"。

  - sys 目录对应于 sys 模式，它提供一组对象来帮助更轻松地解释 Performance Schema 信息。参见第 30 章"MySQL sys 模式"。

  - ndbinfo 目录对应于 ndbinfo 数据库，该数据库存储特定于 NDB Cluster 的信息（仅在为包含 NDB Cluster 而构建的安装中存在）。参见第 25.6.15 节"ndbinfo：NDB Cluster 信息数据库"。

  其他子目录对应于用户或应用程序创建的数据库。

  > 注意
  >
  > INFORMATION_SCHEMA 是一个标准数据库，但其实现不使用相应的数据库目录。

- 服务器写入的日志文件。参见第 7.4 节"MySQL 服务器日志"。

- InnoDB 表空间和日志文件。参见第 17 章"InnoDB 存储引擎"。

- 默认/自动生成的 SSL 和 RSA 证书和密钥文件。参见第 8.3.3 节"创建 SSL 和 RSA 证书和密钥"。

- 服务器进程 ID 文件（服务器运行时）。

- mysqld-auto.cnf 文件，存储持久化的全局系统变量设置。参见第 15.7.6.1 节"变量赋值的 SET 语法"。

- mysql_upgrade_history 文件。兼容性版本和已使用数据目录运行的确切更新版本的 JSON 审计记录。

前面列表中的某些项目可以通过重新配置服务器来重新定位到其他位置。此外，--datadir 选项允许更改数据目录本身的位置。对于给定的 MySQL 安装，请检查服务器配置以确定项目是否已被移动。

### mysql_upgrade_history 文件

服务器将 mysql_upgrade_history 作为审计文件进行维护。它不用于允许或拒绝升级或降级，其内容不影响数据字典、复制或其他兼容性决策。

根 upgrade_history 数组包含兼容性版本的父条目。每个新的父条目保留现有的日期、版本、成熟度和（如适用）initialize 成员。version 成员包含三部分兼容性版本。由 MySQL 26.10 创建或更新的每个父条目也有一个 update_history 数组，其条目包含 date 和 version_with_update 成员。

例如：

```
{
        "file_format": "1",
        "upgrade_history": [
          {
            "date": "2026-08-01 10:00:00",
            "version": "26.10.0",
            "maturity": "INNOVATION",
            "initialize": true,
            "update_history": [
              {
                "date": "2026-08-01 10:00:00",
                "version_with_update": "26.10.0.0"
              },
              {
                "date": "2026-08-15 16:45:00",
                "version_with_update": "26.10.0.1"
              },
              {
                "date": "2026-08-25 09:30:00",
                "version_with_update": "26.10.0.0"
              }
            ]
          }
        ]
    }
```

更新 0 的记录方式与任何其他确切版本相同。如果最新的父条目具有运行的兼容性版本，则确切版本的更改会追加一个 update_history 条目。这适用于升级和降级。重新启动相同的确切版本不会添加重复条目。兼容性版本更改或运行时后缀更改会创建新的父条目。

为了与较旧的有效文件兼容，如果最新的匹配父条目没有 update_history 成员，服务器会添加一个包含当前确切版本的初始子条目。存在的空 update_history 数组也是有效的，并接收当前确切版本。

在更新文件之前，服务器验证完整的 JSON 文档，包括每个父条目和每个现有的 update_history 条目。如果解析失败或任何必需的结构具有无效的类型，服务器会记录：

Invalid format of file 'file_name'. The file will be recreated.

然后服务器用仅包含当前兼容性版本父条目和确切版本子条目的文档替换该文件。读取或写入此审计文件的失败会产生警告，但不会阻止初始化或服务器启动。

1000 条目限制适用于兼容性版本父条目。update_history 数组中的条目不适用单独的限制。
