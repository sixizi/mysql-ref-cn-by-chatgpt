# 1.6 如何报告 Bug 或问题

在发布关于问题的 bug 报告之前，请尝试验证它是否是 bug 以及是否已经被报告过：

- 首先在 https://dev.mysql.com/doc/ 搜索 MySQL 在线手册。我们通过频繁更新手册来保持其最新状态，并提供新发现问题的解决方案。此外，手册附带的发行说明特别有用，因为较新版本很可能包含您问题的解决方案。发行说明可在上述手册位置获得。

- 如果您收到 SQL 语句的解析错误，请仔细检查您的语法。如果您找不到任何问题，很可能您当前版本的 MySQL Server 不支持您使用的语法。如果您使用的是当前版本，而手册中没有涵盖您使用的语法，则 MySQL Server 不支持您的语句。

  如果手册涵盖了您使用的语法，但您使用的是较旧版本的 MySQL Server，您应该检查 MySQL 更改历史记录以查看何时实现了该语法。在这种情况下，您可以选择升级到较新版本的 MySQL Server。

- 有关一些常见问题的解决方案，请参见第 B.3 节"问题和常见错误"。

- 在 http://bugs.mysql.com/ 搜索 bug 数据库，查看该 bug 是否已被报告和修复。

- 您也可以使用 http://www.mysql.com/search/ 搜索位于 MySQL 网站上的所有网页（包括手册）。

如果您在手册、bug 数据库或邮件列表存档中找不到答案，请咨询您当地的 MySQL 专家。如果您仍然找不到问题的答案，请使用以下 bug 报告指南。

报告 bug 的常规方式是访问 http://bugs.mysql.com/，这是我们 bug 数据库的地址。该数据库是公开的，任何人都可以浏览和搜索。如果您登录系统，可以输入新报告。

在 http://bugs.mysql.com/ 的 bug 数据库中发布的在给定版本中得到更正的 bug 会在发行说明中注明。

如果您在 MySQL Server 中发现安全 bug，请立即通过发送电子邮件至 <secalert_us@oracle.com> 通知我们。例外：支持客户应将所有问题（包括安全 bug）报告给 Oracle Support，网址为 http://support.oracle.com/。

要与其他用户讨论问题，您可以使用 MySQL Community Slack。

编写好的 bug 报告需要耐心，但第一次做对可以为我们和您自己节省时间。包含 bug 完整测试用例的好报告使我们很可能在下一个版本中修复该 bug。本节帮助您正确编写报告，以便您不会浪费时间做可能对我们帮助不大或完全没有帮助的事情。请仔细阅读本节，并确保此处描述的所有信息都包含在您的报告中。

最好在发布之前使用最新的 MySQL Server 生产版本或开发版本测试问题。任何人都应该能够通过在您的测试用例上运行 mysql test < script_file 或运行您在 bug 报告中包含的 shell 或 Perl 脚本来重复该 bug。任何我们能够重复的 bug 都有很高的机会在下一个 MySQL 版本中被修复。

当 bug 报告中包含对问题的良好描述时最有帮助。也就是说，给出导致问题的所有操作的良好示例，并准确详细地描述问题本身。最好的报告是那些包含完整示例的报告，展示如何重现 bug 或问题。请参见第 7.9 节"调试 MySQL"。

请记住，我们可能会回复包含过多信息的报告，但不会回复包含信息过少的报告。人们经常省略事实，因为他们认为自己知道问题的原因，并假设某些细节无关紧要。一个好的原则是，如果您对陈述某事有疑问，就陈述它。在报告中多写几行比等待更长时间以获得答案要快得多，如果我们必须要求您提供初始报告中缺少的信息。

bug 报告中最常见的错误是 (a) 不包括您使用的 MySQL 发行版的版本号，以及 (b) 不完整地描述安装 MySQL 服务器的平台（包括平台类型和版本号）。这些是高度相关的信息，在 100 个案例中的 99 个中，没有它们的 bug 报告是无用的。我们经常收到诸如"为什么这对我不起作用？"这样的问题。然后我们发现所请求的功能在该 MySQL 版本中未实现，或者报告中描述的 bug 已在较新的 MySQL 版本中修复。错误通常是平台相关的。在这种情况下，如果不知道操作系统和平台的版本号，我们几乎不可能修复任何问题。

如果您从源代码编译了 MySQL，还要记住提供有关编译器的信息（如果它与问题相关）。人们经常在编译器中发现 bug，并认为问题与 MySQL 相关。大多数编译器一直在开发中，版本越来越好。要确定您的问题是否取决于您的编译器，我们需要知道您使用的编译器。请注意，每个编译问题都应被视为 bug 并相应地报告。

如果程序产生错误消息，在报告中包含该消息非常重要。如果我们尝试从存档中搜索某些内容，最好是报告的错误消息与程序产生的错误消息完全匹配。（甚至应该遵守字母大小写。）最好将整个错误消息复制并粘贴到您的报告中。您永远不应该尝试从内存中重现该消息。

如果您对 Connector/ODBC (MyODBC) 有问题，请尝试生成跟踪文件并将其与您的报告一起发送。请参见如何报告 Connector/ODBC 问题或 Bug。

如果您的报告包含使用 mysql 命令行工具运行的测试用例的长查询输出行，您可以使用 --vertical 选项或 \G 语句终止符使输出更易读。本节后面的 EXPLAIN SELECT 示例演示了 \G 的使用。

请在您的报告中包含以下信息：

- 您使用的 MySQL 发行版的版本号（例如，MySQL 5.7.10）。您可以通过执行 mysqladmin version 来找出您运行的版本。mysqladmin 程序可以在您的 MySQL 安装目录下的 bin 目录中找到。

- 您遇到问题的机器的制造商和型号。

- 操作系统名称和版本。如果您使用 Windows，通常可以通过双击"我的电脑"图标并下拉"帮助/关于 Windows"菜单来获取名称和版本号。对于大多数类 Unix 操作系统，您可以通过执行命令 uname -a 来获取此信息。

- 有时内存量（实际和虚拟）是相关的。如有疑问，请包含这些值。

- MySQL 安装中 docs/INFO_BIN 文件的内容。此文件包含有关 MySQL 如何配置和编译的信息。

- 如果您使用的是 MySQL 软件的源代码发行版，请包含您使用的编译器的名称和版本号。如果您有二进制发行版，请包含发行版名称。

- 如果问题在编译期间发生，请包含确切的错误消息，以及发生错误的文件中违规代码周围的几行上下文。

- 如果 mysqld 死亡，您还应该报告导致 mysqld 意外退出的语句。您通常可以通过启用查询日志运行 mysqld，然后在 mysqld 退出后查看日志来获取此信息。请参见第 7.9 节"调试 MySQL"。

- 如果数据库表与问题相关，请在 bug 报告中包含 SHOW CREATE TABLE db_name.tbl_name 语句的输出。这是获取数据库中任何表定义的非常简单的方法。该信息帮助我们创建与您经历的情况相匹配的情况。

- 问题发生时生效的 SQL 模式可能很重要，因此请报告 sql_mode 系统变量的值。对于存储过程、存储函数和触发器对象，相关的 sql_mode 值是创建对象时生效的值。对于存储过程或函数，SHOW CREATE PROCEDURE 或 SHOW CREATE FUNCTION 语句显示相关的 SQL 模式，或者您可以查询 INFORMATION_SCHEMA 以获取信息：
  ```
  SELECT ROUTINE_SCHEMA, ROUTINE_NAME, SQL_MODE
  FROM INFORMATION_SCHEMA.ROUTINES;
  ```

  对于触发器，您可以使用此语句：
  ```
  SELECT EVENT_OBJECT_SCHEMA, EVENT_OBJECT_TABLE, TRIGGER_NAME, SQL_MODE
  FROM INFORMATION_SCHEMA.TRIGGERS;
  ```

- 对于性能相关的 bug 或 SELECT 语句的问题，您应该始终包含 EXPLAIN SELECT ... 的输出，以及 SELECT 语句产生的至少行数。您还应该为涉及的每个表包含 SHOW CREATE TABLE tbl_name 的输出。您提供的关于您情况的信息越多，越有可能有人能帮助您。

  以下是一个非常好的 bug 报告示例。这些语句使用 mysql 命令行工具运行。请注意对会产生非常长的输出行（难以阅读）的语句使用 \G 语句终止符。
  ```
  mysql> SHOW VARIABLES;
  mysql> SHOW COLUMNS FROM ...\G
         <output from SHOW COLUMNS>
  mysql> EXPLAIN SELECT ...\G
         <output from EXPLAIN>
  mysql> FLUSH STATUS;
  mysql> SELECT ...;
         <A short version of the output from SELECT,
         including the time taken to run the query>
  mysql> SHOW STATUS;
         <output from SHOW STATUS>
  ```

- 如果在运行 mysqld 时发生 bug 或问题，请尝试提供重现异常的输入脚本。此脚本应包含任何必要的源文件。脚本越能接近重现您的情况，越好。如果您能制作可重现的测试用例，您应该将其上传以附加到 bug 报告。

  如果您无法提供脚本，您至少应该在报告中包含 mysqladmin variables extended-status processlist 的输出，以提供有关系统性能的一些信息。

- 如果您无法生成只有几行的测试用例，或者测试表太大而无法包含在 bug 报告中（超过 10 行），您应该使用 mysqldump 转储您的表并创建一个描述您问题的 README 文件。使用 tar 和 gzip 或 zip 创建文件的压缩存档。在您在 http://bugs.mysql.com/ 的 bug 数据库中启动 bug 报告后，单击 bug 报告中的"Files"选项卡以获取有关将存档上传到 bug 数据库的说明。

- 如果您认为 MySQL 服务器从语句产生了奇怪的结果，请不仅包含结果，还包含您对结果应该是什么的看法，以及描述您看法基础的解释。

- 当您提供问题示例时，最好使用在您实际情况中存在的表名、变量名等，而不是想出新名称。问题可能与表或变量的名称有关。这些情况很少见，但安全总比后悔好。毕竟，为您提供使用实际情况的示例应该更容易，这对我们来说绝对更好。如果您有不希望在 bug 报告中对他人可见的数据，您可以使用之前描述的"Files"选项卡上传它。如果信息真的是绝密的，您不想甚至向我们展示，请继续使用其他名称提供示例，但请将其视为最后的选择。

- 如果可能，请包含提供给相关程序的所有选项。例如，指示您启动 mysqld 服务器时使用的选项，以及您运行任何 MySQL 客户端程序时使用的选项。mysqld 和 mysql 等程序的选项，以及 configure 脚本的选项，通常是解决问题的关键，并且非常相关。包含它们永远不是坏主意。如果您的问题涉及用 Perl 或 PHP 等语言编写的程序，请包含语言处理器的版本号，以及程序使用的任何模块的版本。例如，如果您有使用 DBI 和 DBD::mysql 模块的 Perl 脚本，请包含 Perl、DBI 和 DBD::mysql 的版本号。

- 如果您的问题与权限系统相关，请包含 mysqladmin reload 的输出，以及尝试连接时收到的所有错误消息。当您测试权限时，您应该执行 mysqladmin reload version 并尝试使用给您带来麻烦的程序进行连接。

- 如果您有 bug 的补丁，请包含它。但不要假设补丁是我们需要的全部，或者如果您不提供一些必要的信息（如显示您的补丁修复的 bug 的测试用例），我们可以使用它。我们可能会发现您的补丁有问题，或者我们可能根本不理解它。如果是这样，我们无法使用它。

  如果我们无法验证补丁的确切目的，我们将不会使用它。测试用例在这里帮助我们。展示补丁处理可能发生的所有情况。如果我们发现补丁不起作用的边界情况（即使是罕见的），它可能是无用的。

- 关于 bug 是什么、为什么发生或取决于什么的猜测通常是错误的。即使是 MySQL 团队也无法在不首先使用调试器确定 bug 的真正原因的情况下猜测这些事情。

- 在您的 bug 报告中指出您已检查参考手册和邮件存档，以便其他人知道您已尝试自己解决问题。

- 如果您的数据似乎损坏或在访问特定表时收到错误，请首先使用 CHECK TABLE 检查您的表。如果该语句报告任何错误：

  - InnoDB 崩溃恢复机制在服务器在被杀死后重新启动时处理清理，因此在典型操作中不需要"修复"表。如果您遇到 InnoDB 表的错误，请重新启动服务器，看看问题是否仍然存在，或者错误是否仅影响内存中的缓存数据。如果数据在磁盘上损坏，请考虑启用 innodb_force_recovery 选项重新启动，以便您可以转储受影响的表。

  - 对于非事务表，请尝试使用 REPAIR TABLE 或 myisamchk 修复它们。请参见第 7 章"MySQL 服务器管理"。

  如果您运行的是 Windows，请使用 SHOW VARIABLES LIKE 'lower_case_table_names' 语句验证 lower_case_table_names 的值。此变量影响服务器如何处理数据库和表名的字母大小写。对于给定值的其影响应如第 11.2.3 节"标识符大小写敏感性"中所述。

- 如果您经常遇到损坏的表，您应该尝试找出何时以及为什么会发生这种情况。在这种情况下，MySQL 数据目录中的错误日志可能包含有关发生了什么的一些信息。（这是名称中带有 .err 后缀的文件。）请参见第 7.4.2 节"错误日志"。请在您的 bug 报告中包含此文件中的任何相关信息。通常，如果没有在更新中途杀死 mysqld，它永远不应该损坏表。如果您能找到 mysqld 死亡的原因，我们就更容易为您提供问题的修复。请参见第 B.3.1 节"如何确定导致问题的原因"。

- 如果可能，下载并安装最新版本的 MySQL Server 并检查它是否解决了您的问题。MySQL 软件的所有版本都经过彻底测试，应该可以正常工作。我们相信尽可能地使一切向后兼容，您应该能够轻松切换 MySQL 版本。请参见第 2.1.2 节"安装哪个 MySQL 版本和发行版"。
