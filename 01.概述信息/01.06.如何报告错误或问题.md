# 1.6 如何报告错误或问题

在提交错误报告之前，请先尽量确认这确实是一个错误，并确认它尚未被报告：

- 先在 MySQL 在线手册（https://dev.mysql.com/doc/）中搜索。MySQL 会持续更新手册，并加入新发现问题的解决方案。此外，手册附带的发行说明也很有用，因为较新版本可能已经包含解决该问题的办法。发行说明也位于上述地址。
- 如果 SQL 语句出现解析错误，请仔细检查语法。若找不到问题，极有可能是因为当前 MySQL Server 版本不支持所使用的语法。如果你使用的是最新版本，而手册又没有覆盖该语法，说明 MySQL Server 不支持这条语句。
- 如果手册覆盖了该语法，但你使用的是较旧版本，请查阅 MySQL 变更历史，确认该语法是在哪个版本中实现的。此时，可以考虑升级到较新的 MySQL Server。
- 一些常见问题的解决方案参见第 B.3 节“问题和常见错误”。
- 搜索错误数据库（http://bugs.mysql.com/），确认该问题是否已被报告或修复。
- 也可以使用 http://www.mysql.com/search/ 搜索 MySQL 网站上的所有页面（包括手册）。

如果在手册、错误数据库或邮件列表归档中都找不到答案，请咨询本地 MySQL 专家。仍无法解决时，请按以下指南报告错误。

## 报告错误的标准方式

报告错误的标准方式是访问 http://bugs.mysql.com/。该数据库公开，任何人都可以浏览和搜索。登录后即可提交新报告。已在某个发行版中修复的错误，会在发行说明中注明。

如果你发现 MySQL Server 的安全漏洞，请立即发送电子邮件至 <secalert_us@oracle.com>。例外情况：Oracle 支持客户应将所有问题（包括安全漏洞）报告给 Oracle 支持（http://support.oracle.com/）。

想与其他用户讨论问题，可使用 MySQL Community Slack。

## 写好错误报告

写一份高质量错误报告需要耐心，但第一次就写好能节省双方时间。包含完整测试用例的错误报告，更有可能在下一个版本中被修复。本节帮助你正确填写报告，避免浪费双方时间。

提交前，最好先使用最新生产版或开发版 MySQL Server 测试问题。理想情况下，任何人都能通过执行 `mysql test < script_file`，或运行报告中附带的 shell 或 Perl 脚本来复现问题。可以复现的错误，更有可能在下一个版本中被修复。

报告中应包含清晰的问题描述，最好包含完整操作步骤和确切的错误现象。最好的报告会提供完整复现示例。参见第 7.9 节“调试 MySQL”。

请记住，信息太多通常仍能处理，信息太少则很难处理。人们常因自以为知道原因而省略细节。判断不清时，宁多勿少。多写几行，比之后等待追问要快。

## 必备信息

报告中最常见的错误是：

- 未提供所使用的 MySQL 发行版版本号。
- 未完整描述 MySQL Server 所在平台，包括平台类型和版本号。

这些信息极其重要。绝大多数错误报告如果没有它们，几乎无法处理。很多“为什么在我这里不行”的问题，最终发现是所请求的功能在该版本中尚未实现，或该问题已在新版本中修复。许多错误还与平台相关，因此不知道操作系统和版本时，我们几乎无法定位问题。

如果你是从源码编译 MySQL，且问题与编译器有关，请提供编译器信息。很多表面上是 MySQL 的问题，实际是编译器缺陷。大多数编译器也在持续改进，因此需要知道你使用的编译器版本。所有编译问题都应视为错误并上报。

如果程序产生了错误消息，请完整复制并粘贴到报告中。不要凭记忆复写，也不要改写大小写。若我们需要在历史记录中检索，精确的错误消息会更有效。

## 提高报告质量

如果问题与 Connector/ODBC 有关，请生成 trace 文件并随报告上传。

如果 `mysql` 输出行过长，可使用 `--vertical` 选项或 `\G` 语句结束符提高可读性。

请在报告中包含以下信息：

- MySQL 发行版版本号，例如 `MySQL 5.7.10`。可执行 `mysqladmin version` 获取。
- 发生问题的机器型号和生产商。
- 操作系统名称和版本。Windows 用户可从“帮助/关于 Windows”获取；多数 Unix-like 系统可执行 `uname -a`。
- 如相关，请提供物理内存和虚拟内存大小。
- MySQL 安装目录中 `docs/INFO_BIN` 文件的内容，其中记录了 MySQL 的配置和编译方式。
- 如果使用源码发行版，请提供编译器名称和版本；如果使用二进制发行版，请提供发行版名称。
- 如果是编译问题，请提供精确错误消息，以及出错代码附近的若干上下文行。
- 如果 `mysqld` 崩溃，请报告导致其异常退出的语句。通常可启用查询日志，并在 `mysqld` 退出后查看日志。参见第 7.9 节“调试 MySQL”。
- 如果与某个表相关，请附上 `SHOW CREATE TABLE db_name.tbl_name` 的输出。这是获取表定义最简单的方法，也能帮助我们重现你的场景。
- 请说明当时的 SQL 模式，即 `sql_mode` 系统变量的值。对于存储过程、函数和触发器，相关 `sql_mode` 是创建对象时的取值。对存储过程或函数，可使用 `SHOW CREATE PROCEDURE` 或 `SHOW CREATE FUNCTION`，也可查询 `INFORMATION_SCHEMA.ROUTINES`：

```sql
SELECT ROUTINE_SCHEMA, ROUTINE_NAME, SQL_MODE
FROM INFORMATION_SCHEMA.ROUTINES;
```

对触发器，可使用：

```sql
SELECT EVENT_OBJECT_SCHEMA, EVENT_OBJECT_TABLE, TRIGGER_NAME, SQL_MODE
FROM INFORMATION_SCHEMA.TRIGGERS;
```

- 对性能问题或 `SELECT` 相关问题，请附上 `EXPLAIN SELECT ...` 的输出，以及该语句返回的行数。也请为每个涉及的表提供 `SHOW CREATE TABLE tbl_name` 的输出。

例如：

```sql
SHOW VARIABLES;
SHOW COLUMNS FROM ... \G
EXPLAIN SELECT ... \G
FLUSH STATUS;
SELECT ...;
SHOW STATUS;
```

- 如果问题发生在 `mysqld` 运行期间，请尽量提供一个可复现的输入脚本，并包含必要的源文件。脚本越接近实际场景，越有助于定位。如果能构建可复现测试用例，请上传并附到报告中。
- 若无法提供脚本，请至少附上 `mysqladmin variables extended-status processlist` 的输出。
- 若测试用例无法只包含少量行，或表太大不便直接放入报告，可用 `mysqldump` 导出表，并写一个描述问题的 `README`。使用 `tar` 和 `gzip` 或 `zip` 打包后，通过错误报告的 Files 页签上传。
- 如果认为 MySQL Server 返回了异常结果，请同时提供实际结果、你期望的结果，以及判断依据。
- 提供示例时，最好使用实际场景中的表名和变量名，而不是虚构新名称。问题可能与表名或变量名有关。若确有保密数据，可在 Files 页签上传。只有在完全无法提供真实数据时，才建议改名示例。
- 尽量列出相关程序的启动选项。例如启动 `mysqld` 和运行 MySQL 客户端时使用的选项。若涉及 Perl、PHP 等程序，请提供语言解释器版本和相关模块版本，例如 Perl、DBI、DBD::mysql。
- 如果问题与权限系统有关，请附上 `mysqladmin reload` 的输出和连接时的所有错误消息。测试权限时可执行 `mysqladmin reload version`，再用遇到问题的客户端尝试连接。
- 如果你有补丁，请附上。但补丁本身不够，还需要提供能证明补丁修复该问题的测试用例。若我们无法确认补丁用途，就不会采用。请说明补丁处理的所有边界情况。

## 数据损坏和表损坏

如果数据看起来损坏，或访问某个表时出错，请先用 `CHECK TABLE` 检查。

- 对 InnoDB 表，崩溃恢复机制会在服务器被杀后重启时自动清理。通常无需“修复”表。如果仍出错，请重启服务器，确认问题是否只出现在内存缓存中。若磁盘数据确实损坏，可考虑启用 `innodb_force_recovery` 再导出相关表。
- 对非事务表，可尝试 `REPAIR TABLE` 或 `myisamchk`。参见第 7 章“MySQL Server 管理”。

在 Windows 上，请用以下语句确认 `lower_case_table_names` 的取值：

```sql
SHOW VARIABLES LIKE 'lower_case_table_names';
```

该变量影响数据库和表名的大小写处理，具体行为见第 11.2.3 节“标识符大小写敏感性”。

如果经常出现表损坏，请找出发生时机和原因。数据目录中的错误日志（文件名后缀为 `.err`）可能包含线索。参见第 7.4.2 节“错误日志”。请在报告中附上相关日志内容。

如果可能，请下载并安装最新版本的 MySQL Server，确认问题是否已解决。所有 MySQL 版本都经过充分测试，应能正常运行。MySQL 尽可能保持向后兼容，因此切换版本通常没有问题。参见第 2.1.2 节“选择安装的 MySQL 版本和发行版”。

官方英文版参见 [How to Report Bugs or Problems](https://dev.mysql.com/doc/refman/9.7/en/bug-reports.html)。
