存储程序（过程、函数、触发器和事件）和视图在使用前定义，被引用时在决定其权限的**安全上下文**（security context）中执行。适用于存储对象执行的权限由其 `DEFINER` 属性和 `SQL SECURITY` 特性控制。

### DEFINER 属性

存储对象定义可以包含一个 `DEFINER` 属性，用于命名一个 MySQL 账户。如果定义省略了 `DEFINER` 属性，默认对象定义者是创建该对象的用户。

以下规则决定可以把哪些账户指定为存储对象的 `DEFINER` 属性：

- 如果具有 `SET_USER_ID` 权限（或已弃用的 `SUPER` 权限），可以把任意账户指定为 `DEFINER` 属性。如果账户不存在，会产生警告。此外，要把存储对象的 `DEFINER` 属性设置为具有 `SYSTEM_USER` 权限的账户，你必须具有 `SYSTEM_USER` 权限。
- 否则，唯一允许的账户是你自己的账户，可以字面指定，也可以使用 `CURRENT_USER` 或 `CURRENT_USER()`。不能把定义者设置为任何其他账户。

使用不存在的 `DEFINER` 账户创建存储对象会创建**孤立对象**（orphan object），这可能带来负面后果；参见[孤立存储对象](#孤立存储对象)。

### SQL SECURITY 特性

对于存储例程（过程和函数）和视图，对象定义可以包含 `SQL SECURITY` 特性，其值为 `DEFINER` 或 `INVOKER`，用于指定对象在定义者上下文还是调用者上下文中执行。如果定义省略了 `SQL SECURITY` 特性，默认为定义者上下文。

触发器和事件没有 `SQL SECURITY` 特性，并且始终在定义者上下文中执行。服务器会在必要时自动调用这些对象，因此不存在调用用户。

定义者和调用者安全上下文的区别如下：

- 在定义者安全上下文中执行的存储对象，以 `DEFINER` 属性命名账户的权限执行。这些权限可能与调用用户的权限完全不同。调用者必须具有引用该对象的适当权限（例如调用存储过程需要 `EXECUTE`，从视图中选择需要 `SELECT`），但在对象执行期间，调用者的权限会被忽略，只有 `DEFINER` 账户的权限起作用。如果 `DEFINER` 账户权限很少，对象能执行的操作也会相应受限。如果 `DEFINER` 账户权限很高（例如管理账户），那么无论谁调用，该对象都能执行强大的操作。
- 在调用者安全上下文中执行的存储例程或视图，只能执行调用者具有权限的操作。`DEFINER` 属性对对象执行没有影响。

### 示例

考虑以下存储过程，它声明为 `SQL SECURITY DEFINER`，在定义者安全上下文中执行：

```mysql
CREATE DEFINER = 'admin'@'localhost' PROCEDURE p1()
SQL SECURITY DEFINER
BEGIN
  UPDATE t1 SET counter = counter + 1;
END;
```

任何对 `p1` 具有 `EXECUTE` 权限的用户都可以用 `CALL` 语句调用它。但是，`p1` 执行时处于定义者安全上下文，因此以 `'admin'@'localhost'`（即其 `DEFINER` 属性指定的账户）的权限执行。该账户必须对 `p1` 具有 `EXECUTE` 权限，并对对象主体中引用的表 `t1` 具有 `UPDATE` 权限。否则过程会失败。

现在考虑以下存储过程，它与 `p1` 相同，只是 `SQL SECURITY` 特性为 `INVOKER`：

```mysql
CREATE DEFINER = 'admin'@'localhost' PROCEDURE p2()
SQL SECURITY INVOKER
BEGIN
  UPDATE t1 SET counter = counter + 1;
END;
```

与 `p1` 不同，`p2` 在调用者安全上下文中执行，因此无论 `DEFINER` 属性值是什么，都以调用用户的权限执行。如果调用者缺少对 `p2` 的 `EXECUTE` 权限或对表 `t1` 的 `UPDATE` 权限，`p2` 会失败。

### 孤立存储对象

**孤立存储对象**是指其 `DEFINER` 属性指定了不存在账户的存储对象：

- 可以在创建对象时指定不存在的 `DEFINER` 账户来创建孤立存储对象。
- 现有存储对象可能因执行 `DROP USER` 语句删除对象定义者账户，或执行 `RENAME USER` 语句重命名对象定义者账户而变成孤立对象。

孤立存储对象可能在以下方面造成问题：

- 由于 `DEFINER` 账户不存在，如果对象在定义者安全上下文中执行，可能无法按预期工作：

  - 对于存储例程，如果 `SQL SECURITY` 值为 `DEFINER` 但定义者账户不存在，例程执行时会发生错误。
  - 对于触发器，在账户实际存在之前触发触发器激活并不是好主意，否则权限检查行为未定义。
  - 对于事件，如果账户不存在，事件执行时会发生错误。
  - 对于视图，如果 `SQL SECURITY` 值为 `DEFINER` 但定义者账户不存在，引用视图时会发生错误。

- 如果不存在的 `DEFINER` 账户后来因与该对象无关的目的被重新创建，对象可能带来安全风险。在这种情况下，该账户会“接管”这个对象，并在具有适当权限时能够执行它，即使这并非预期。

从 MySQL 8.0.22 起，服务器实施额外的账户管理安全检查，旨在防止（可能是无意中）导致存储对象变成孤立对象，或导致当前孤立的存储对象被接管：

- 如果要删除的任何账户被指定为任何存储对象的 `DEFINER` 属性，`DROP USER` 会失败并报错。（也就是说，如果删除账户会导致存储对象变成孤立对象，语句会失败。）
- 如果要重命名的任何账户被指定为任何存储对象的 `DEFINER` 属性，`RENAME USER` 会失败并报错。（也就是说，如果重命名账户会导致存储对象变成孤立对象，语句会失败。）
- 如果要创建的任何账户被指定为任何存储对象的 `DEFINER` 属性，`CREATE USER` 会失败并报错。（也就是说，如果创建账户会导致该账户接管当前孤立的存储对象，语句会失败。）

在某些情况下，可能有必要故意执行这些账户管理语句，即使它们本来会失败。为此，如果用户具有 `SET_USER_ID` 权限，该权限会覆盖孤立对象安全检查，语句会成功但产生警告，而不是失败并报错。

要获取 MySQL 安装中用作存储对象定义者的账户信息，可以查询 `INFORMATION_SCHEMA`。

以下查询识别哪些 `INFORMATION_SCHEMA` 表描述具有 `DEFINER` 属性的对象：

```mysql
mysql> SELECT TABLE_SCHEMA, TABLE_NAME FROM INFORMATION_SCHEMA.COLUMNS
       WHERE COLUMN_NAME = 'DEFINER';
+--------------------+------------+
| TABLE_SCHEMA       | TABLE_NAME |
+--------------------+------------+
| information_schema | EVENTS     |
| information_schema | ROUTINES   |
| information_schema | TRIGGERS   |
| information_schema | VIEWS      |
+--------------------+------------+
```

结果告诉你应查询哪些表，以发现存在哪些存储对象 `DEFINER` 值，以及哪些对象具有特定的 `DEFINER` 值：

- 要识别每张表中存在哪些 `DEFINER` 值，使用以下查询：

  ```mysql
  SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.EVENTS;
  SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.ROUTINES;
  SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.TRIGGERS;
  SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.VIEWS;
  ```

  对于结果中显示的任何账户，其意义如下：

  - 如果账户存在，删除或重命名它会导致存储对象变成孤立对象。如果计划删除或重命名该账户，考虑先删除其关联的存储对象，或重新定义它们以使用不同的定义者。
  - 如果账户不存在，创建它会导致它接管当前孤立的存储对象。如果计划创建该账户，考虑这些孤立对象是否应与其关联。如果不应该，请重新定义它们以使用不同的定义者。

  要用不同的定义者重新定义对象，可以使用 `ALTER EVENT` 或 `ALTER VIEW` 直接修改事件和视图的 `DEFINER` 账户。对于存储过程和函数以及触发器，必须删除对象并重新创建，才能分配不同的 `DEFINER` 账户。

- 要识别哪些对象具有给定的 `DEFINER` 账户，使用以下查询，把 `user_name@host_name` 替换为关注的账户：

  ```mysql
  SELECT EVENT_SCHEMA, EVENT_NAME FROM INFORMATION_SCHEMA.EVENTS
  WHERE DEFINER = 'user_name@host_name';
  SELECT ROUTINE_SCHEMA, ROUTINE_NAME, ROUTINE_TYPE
  FROM INFORMATION_SCHEMA.ROUTINES
  WHERE DEFINER = 'user_name@host_name';
  SELECT TRIGGER_SCHEMA, TRIGGER_NAME FROM INFORMATION_SCHEMA.TRIGGERS
  WHERE DEFINER = 'user_name@host_name';
  SELECT TABLE_SCHEMA, TABLE_NAME FROM INFORMATION_SCHEMA.VIEWS
  WHERE DEFINER = 'user_name@host_name';
  ```

  对于 `ROUTINES` 表，查询包含 `ROUTINE_TYPE` 列，以便输出行区分 `DEFINER` 属于存储过程还是存储函数。

  如果要搜索的账户不存在，这些查询显示的任何对象都是孤立对象。

### 风险最小化指南

要最小化存储对象创建和使用的潜在风险，请遵循以下指南：

- 不要创建孤立存储对象，即 `DEFINER` 属性指定不存在账户的对象。不要通过删除或重命名任何现有对象的 `DEFINER` 属性所指定的账户，使存储对象变成孤立对象。
- 对于存储例程或视图，尽可能在对象定义中使用 `SQL SECURITY INVOKER`，使其只能被具有适合该对象所执行操作的权限的用户使用。
- 如果在使用具有 `SET_USER_ID` 权限（或已弃用的 `SUPER` 权限）的账户创建定义者上下文存储对象时，请指定一个显式的 `DEFINER` 属性，该账户只具有对象所执行操作所需的权限。仅在绝对必要时才指定高权限的 `DEFINER` 账户。
- 管理员可以通过不授予用户 `SET_USER_ID` 权限（或已弃用的 `SUPER` 权限），防止用户创建指定高权限 `DEFINER` 账户的存储对象。
- 编写定义者上下文对象时，应牢记它们可能能够访问调用用户没有权限的数据。在某些情况下，可以通过不向未授权用户授予特定权限来防止对这些对象的引用：

  - 没有 `EXECUTE` 权限的用户不能引用存储例程。
  - 没有适当权限的用户不能引用视图（从中选择需要 `SELECT`，向其中插入需要 `INSERT`，等等）。

  但是，对于触发器和事件不存在这种控制，因为它们始终在定义者上下文中执行。服务器会在必要时自动调用这些对象，用户不会直接引用它们：

  - 触发器在访问与其关联的表时激活，即使用户没有任何特殊权限的普通表访问也会激活。
  - 事件由服务器按计划执行。

  在这两种情况下，如果 `DEFINER` 账户权限很高，对象可能能够执行敏感或危险的操作。即使从创建对象的用户账户撤销了创建对象所需的权限，情况仍然如此。管理员应特别注意授予用户对象创建权限。

- 默认情况下，执行具有 `SQL SECURITY DEFINER` 特性的例程时，MySQL 服务器不会为 `DEFINER` 子句中命名的 MySQL 账户设置任何活动角色，只使用默认角色。例外是启用了 `activate_all_roles_on_login` 系统变量，此时 MySQL 服务器会设置授予 `DEFINER` 用户的所有角色，包括强制角色。因此，默认情况下，发出 `CREATE PROCEDURE` 或 `CREATE FUNCTION` 语句时，不会检查通过角色授予的任何权限。对于存储程序，如果执行时应使用不同于默认的角色，程序主体可以执行 `SET ROLE` 来激活所需角色。必须谨慎执行此操作，因为分配给角色的权限可能会改变。
