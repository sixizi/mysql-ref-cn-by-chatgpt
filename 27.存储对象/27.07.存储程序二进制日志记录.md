## 27.7 存储程序二进制日志记录

二进制日志包含有关修改数据库内容的 SQL 语句的信息。这些信息以描述修改的“**事件**”（event）形式存储（二进制日志事件与调度的**事件**存储对象不同）。二进制日志有两个重要用途：

- **复制**：在源复制服务器上，二进制日志用作要发送到副本服务器的语句记录。源服务器把二进制日志中包含的事件发送给副本，副本执行这些事件，从而做出与源服务器相同的数据更改。参见 [17.2，复制实现](#)。
- **数据恢复**：某些数据恢复操作需要使用二进制日志。恢复备份文件后，会重新执行二进制日志中在备份之后记录的事件。这些事件使数据库从备份点更新到最新状态。参见 [7.3.2，使用备份进行恢复](#)。

但是，如果日志记录发生在**语句级别**，存储程序（存储过程和函数、触发器以及事件）会存在某些二进制日志记录问题：

- 在某些情况下，语句在源服务器和副本上可能影响不同的行集。
- 在副本上执行的复制语句由副本的 **applier 线程**处理。除非实施复制权限检查（MySQL 8.0.18 起可用，参见 [17.3.3，复制权限检查](#)），否则 applier 线程具有完整权限。在这种情况下，过程可能在源服务器和副本服务器上走不同的执行路径，因此用户可能编写包含危险语句的例程，而该语句只在副本上执行。
- 如果修改数据的存储程序是**非确定性的**，它不可重复。这可能导致源服务器和副本上的数据不同，或导致恢复的数据与原始数据不同。

本节介绍 MySQL 如何处理存储程序的二进制日志记录。它说明当前实现对存储程序使用所施加的条件，以及可以采取哪些措施来避免日志记录问题。本节还提供有关这些条件背后原因的附加信息。

除非另有说明，本节假设服务器上启用了二进制日志（参见 [5.4.4，二进制日志](#)）。如果未启用二进制日志，则无法进行复制，二进制日志也不能用于数据恢复。从 MySQL 8.0 起，默认启用二进制日志，只有在启动时指定 `--skip-log-bin` 或 `--disable-log-bin` 选项才会禁用。

通常，这里描述的问题发生在 SQL 语句级二进制日志记录（**基于语句的二进制日志记录**）时。如果使用**基于行的二进制日志记录**，日志包含执行 SQL 语句所导致的各个行的更改。例程或触发器执行时，记录的是行更改，而不是做出更改的语句。对于存储过程，这意味着不记录 `CALL` 语句。对于存储函数，记录函数内部所做的行更改，而不是函数调用。对于触发器，记录触发器所做的行更改。在副本端，只能看到行更改，看不到存储程序的调用。

混合格式二进制日志记录（`binlog_format=MIXED`）使用基于语句的二进制日志记录，除非某些情况下只有基于行的二进制日志记录才能保证正确结果。使用混合格式时，如果存储函数、存储过程、触发器、事件或预处理语句包含任何对基于语句的二进制日志记录不安全的内容，整个语句会被标记为不安全，并以行格式记录。用于创建和删除过程、函数、触发器和事件的语句始终是安全的，并以语句格式记录。有关基于行、混合和基于语句的日志记录，以及如何判定语句安全与否的更多信息，参见 [17.2.1，复制格式](#)。

MySQL 中对存储函数使用的条件可以总结如下。这些条件不适用于存储过程或事件调度器事件，并且只在启用二进制日志时适用。

- 要创建或修改存储函数，除了通常需要的 `CREATE ROUTINE` 或 `ALTER ROUTINE` 权限外，还必须具有 `SET_USER_ID` 权限（或已弃用的 `SUPER` 权限）。（取决于函数定义中的 `DEFINER` 值，无论是否启用二进制日志，都可能需要 `SET_USER_ID` 或 `SUPER`。参见 [15.1.17，CREATE PROCEDURE 和 CREATE FUNCTION 语句](#)。）
- 创建存储函数时，必须声明它是**确定性的**，或声明它**不修改数据**。否则，它可能对数据恢复或复制不安全。

  默认情况下，要接受 `CREATE FUNCTION` 语句，必须显式指定 `DETERMINISTIC`、`NO SQL` 或 `READS SQL DATA` 中的至少一个。否则会产生错误：

  ```text
  ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
  or READS SQL DATA in its declaration and binary logging is enabled
  (you *might* want to use the less safe log_bin_trust_function_creators
  variable)
  ```

  以下函数是确定性的（并且不修改数据），因此是安全的：

  ```mysql
  CREATE FUNCTION f1(i INT)
  RETURNS INT
  DETERMINISTIC
  READS SQL DATA
  BEGIN
    RETURN i;
  END;
  ```

  以下函数使用 `UUID()`，它不是确定性的，因此该函数也不是确定性的，并不安全：

  ```mysql
  CREATE FUNCTION f2()
  RETURNS CHAR(36) CHARACTER SET utf8mb4
  BEGIN
    RETURN UUID();
  END;
  ```

  以下函数修改数据，因此可能不安全：

  ```mysql
  CREATE FUNCTION f3(p_id INT)
  RETURNS INT
  BEGIN
    UPDATE t SET modtime = NOW() WHERE id = p_id;
    RETURN ROW_COUNT();
  END;
  ```

  对函数性质的评估基于创建者的“诚实性”。MySQL 不会检查声明为 `DETERMINISTIC` 的函数是否不含产生非确定性结果的语句。

- 尝试执行存储函数时，如果设置了 `binlog_format=STATEMENT`，函数定义中必须指定 `DETERMINISTIC` 关键字。否则会产生错误，函数不会运行，除非指定 `log_bin_trust_function_creators=1` 覆盖此检查（见下文）。对于递归函数调用，只有最外层调用需要 `DETERMINISTIC` 关键字。如果使用基于行或混合二进制日志记录，即使函数定义时没有 `DETERMINISTIC` 关键字，语句也会被接受并复制。
- 由于 MySQL 在创建时不会检查函数是否真正具有确定性，调用带有 `DETERMINISTIC` 关键字的存储函数时，可能执行对基于语句的日志记录不安全的行为，或调用包含不安全语句的函数或过程。如果设置了 `binlog_format=STATEMENT` 时发生这种情况，会发出警告消息。如果使用基于行或混合二进制日志记录，不会发出警告，语句以行格式复制。
- 要放宽前面关于函数创建的条件（必须具有 `SUPER` 权限，并且函数必须声明为确定性或不修改数据），请把全局系统变量 `log_bin_trust_function_creators` 设置为 `1`。默认情况下，该变量的值为 `0`，可以这样更改：

  ```mysql
  mysql> SET GLOBAL log_bin_trust_function_creators = 1;
  ```

  也可以在服务器启动时设置该变量。

  如果未启用二进制日志，`log_bin_trust_function_creators` 不适用。除非如前所述函数定义中的 `DEFINER` 值需要，否则创建函数不需要 `SUPER`。

- 有关可能对复制不安全的内置函数（因而导致使用它们的存储函数也不安全）的信息，参见 [17.5.1，复制特性和问题](#)。

触发器与存储函数类似，因此前面关于函数的说明也适用于触发器，但有一个例外：`CREATE TRIGGER` 没有可选的 `DETERMINISTIC` 特性，因此触发器被假定为**始终确定性**。但是，在某些情况下这个假设可能无效。例如，`UUID()` 函数是非确定性的（并且不会复制）。在触发器中使用此类函数时要小心。

触发器可以更新表，因此如果没有所需权限，`CREATE TRIGGER` 会产生类似于存储函数的错误消息。在副本端，副本使用触发器的 `DEFINER` 属性来确定哪个用户被视为触发器的创建者。

本节其余部分提供有关日志记录实现及其影响的更多细节。除非你对存储例程使用当前日志记录相关条件背后的理由感兴趣，否则不必阅读。此讨论仅适用于基于语句的日志记录，不适用于基于行的日志记录，但第一项除外：无论日志记录模式如何，`CREATE` 和 `DROP` 语句都作为语句记录。

- 服务器把 `CREATE EVENT`、`CREATE PROCEDURE`、`CREATE FUNCTION`、`ALTER EVENT`、`ALTER PROCEDURE`、`ALTER FUNCTION`、`DROP EVENT`、`DROP PROCEDURE` 和 `DROP FUNCTION` 语句写入二进制日志。
- 如果存储函数修改数据，并且出现在原本不会被记录的语句中，则存储函数调用会作为 `SELECT` 语句记录。这可以防止因在未记录语句中使用存储函数而导致数据更改未被复制。例如，`SELECT` 语句不会写入二进制日志，但 `SELECT` 可能调用一个做出更改的存储函数。为处理这种情况，当给定函数做出更改时，会把 `SELECT func_name()` 语句写入二进制日志。假设在源服务器上执行以下语句：

  ```mysql
  CREATE FUNCTION f1(a INT) RETURNS INT
  BEGIN
    IF (a < 3) THEN
      INSERT INTO t2 VALUES (a);
    END IF;
    RETURN 0;
  END;

  CREATE TABLE t1 (a INT);
  INSERT INTO t1 VALUES (1),(2),(3);

  SELECT f1(a) FROM t1;
  ```

  执行 `SELECT` 语句时，函数 `f1()` 被调用三次。其中两次调用插入一行，MySQL 为每次插入记录一条 `SELECT` 语句。也就是说，MySQL 把以下语句写入二进制日志：

  ```mysql
  SELECT f1(1);
  SELECT f1(2);
  ```

  当存储函数调用导致错误的存储过程时，服务器也会为该存储函数调用记录一条 `SELECT` 语句。在这种情况下，服务器把 `SELECT` 语句连同预期错误码写入日志。在副本上，如果发生相同错误，那就是预期结果，复制继续；否则复制停止。

- 记录存储函数调用而不是函数执行的语句，对复制有安全影响，这源于两个因素：

  - 函数可能在源服务器和副本服务器上走不同的执行路径。
  - 在副本上执行的语句由副本的 applier 线程处理。除非实施复制权限检查（MySQL 8.0.18 起可用，参见 [17.3.3，复制权限检查](#)），否则 applier 线程具有完整权限。

  其含义是，虽然用户必须具有 `CREATE ROUTINE` 权限才能创建函数，但用户可以编写包含危险语句的函数，该语句只在副本上执行，并由具有完整权限的线程处理。例如，如果源服务器和副本服务器的 `server_id` 值分别为 1 和 2，源服务器上的用户可以如下创建并调用不安全的函数 `unsafe_func()`：

  ```mysql
  mysql> delimiter //
  mysql> CREATE FUNCTION unsafe_func () RETURNS INT
      -> BEGIN
      ->   IF @@server_id=2 THEN dangerous_statement; END IF;
      ->   RETURN 1;
      -> END;
      -> //
  mysql> delimiter ;
  mysql> INSERT INTO t VALUES(unsafe_func());
  ```

  `CREATE FUNCTION` 和 `INSERT` 语句被写入二进制日志，因此副本会执行它们。由于副本的 applier 线程具有完整权限，它会执行危险语句。因此，该函数调用在源服务器和副本上产生不同效果，不具备复制安全性。

  为防止启用了二进制日志的服务器出现这种危险，存储函数创建者除了通常需要的 `CREATE ROUTINE` 权限外，还必须具有 `SUPER` 权限。同样，要使用 `ALTER FUNCTION`，除了 `ALTER ROUTINE` 权限外，还必须具有 `SUPER` 权限。没有 `SUPER` 权限会产生错误：

  ```text
  ERROR 1419 (HY000): You do not have the SUPER privilege and
  binary logging is enabled (you *might* want to use the less safe
  log_bin_trust_function_creators variable)
  ```

  如果你不希望要求函数创建者具有 `SUPER` 权限（例如，系统中所有具有 `CREATE ROUTINE` 权限的用户都是经验丰富的应用开发者），请把全局系统变量 `log_bin_trust_function_creators` 设置为 `1`。也可以在服务器启动时设置该变量。如果未启用二进制日志，`log_bin_trust_function_creators` 不适用。除非如前所述函数定义中的 `DEFINER` 值需要，否则创建函数不需要 `SUPER`。

- 无论你如何选择函数创建者的权限，都建议使用可用的复制权限检查（MySQL 8.0.18 起）。可以设置复制权限检查，以确保只授权复制通道执行预期且相关的操作。操作说明参见 [17.3.3，复制权限检查](#)。
- 如果执行更新的函数是非确定性的，它不可重复。这可能导致两种不良后果：

  - 导致副本与源服务器不同。
  - 恢复的数据与原始数据不匹配。

  为处理这些问题，MySQL 强制执行以下要求：在源服务器上，除非声明函数是确定性的或不修改数据，否则拒绝创建和修改函数。这里适用两组函数特性：

  - `DETERMINISTIC` 和 `NOT DETERMINISTIC` 特性表示函数对于给定输入是否始终产生相同结果。如果两个特性都未给出，默认为 `NOT DETERMINISTIC`。要声明函数是确定性的，必须显式指定 `DETERMINISTIC`。
  - `CONTAINS SQL`、`NO SQL`、`READS SQL DATA` 和 `MODIFIES SQL DATA` 特性提供函数是否读取或写入数据的信息。`NO SQL` 或 `READS SQL DATA` 表示函数不更改数据，但由于未给出特性时默认为 `CONTAINS SQL`，必须显式指定其中之一。

  默认情况下，要接受 `CREATE FUNCTION` 语句，必须显式指定 `DETERMINISTIC`、`NO SQL` 或 `READS SQL DATA` 中的至少一个。否则会产生错误：

  ```text
  ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
  or READS SQL DATA in its declaration and binary logging is enabled
  (you *might* want to use the less safe log_bin_trust_function_creators
  variable)
  ```

  如果把 `log_bin_trust_function_creators` 设置为 `1`，则不再要求函数是确定性的或不修改数据。

- 存储过程调用在**语句级别**记录，而不是在 `CALL` 级别记录。也就是说，服务器不记录 `CALL` 语句，而是记录过程中实际执行的语句。因此，源服务器上发生的相同更改也会在副本上发生。这可以防止过程在不同机器上走不同执行路径所导致的问题。

  通常，存储过程内执行的语句使用与单独执行语句时相同的规则写入二进制日志。记录过程语句时需要特别小心，因为过程内的语句执行与非过程上下文并不完全相同：

  - 要记录的语句可能包含对过程局部变量的引用。这些变量在存储过程上下文之外不存在，因此引用此类变量的语句不能按字面记录。相反，为了日志记录，每个局部变量引用都会被替换为以下结构：

    ```sql
    NAME_CONST(var_name, var_value)
    ```

    `var_name` 是局部变量名，`var_value` 是表示记录语句时变量值的常量。`NAME_CONST()` 的值为 `var_value`，名称为 `var_name`。因此，如果直接调用该函数，会得到类似以下结果：

    ```mysql
    mysql> SELECT NAME_CONST('myname', 14);
    +--------+
    | myname |
    +--------+
    |     14 |
    +--------+
    ```

    `NAME_CONST()` 使记录的独立语句能够在副本上执行，并与源服务器存储过程内执行的原语句具有相同效果。

    当源列表达式引用局部变量时，使用 `NAME_CONST()` 可能会给 `CREATE TABLE ... SELECT` 语句带来问题。把这些引用转换为 `NAME_CONST()` 表达式，可能导致源服务器和副本服务器上的列名不同，或名称太长而无法作为合法列标识符。变通方法是给引用局部变量的列提供别名。考虑 `myvar` 值为 1 时的以下语句：

    ```mysql
    CREATE TABLE t1 SELECT myvar;
    ```

    它会被重写为：

    ```mysql
    CREATE TABLE t1 SELECT NAME_CONST(myvar, 1);
    ```

    为确保源表和副本表具有相同的列名，应这样编写语句：

    ```mysql
    CREATE TABLE t1 SELECT myvar AS myvar;
    ```

    重写后的语句变为：

    ```mysql
    CREATE TABLE t1 SELECT NAME_CONST(myvar, 1) AS myvar;
    ```

  - 要记录的语句可能包含对用户定义变量的引用。为处理这种情况，MySQL 会向二进制日志写入一条 `SET` 语句，以确保副本上该变量存在且值与源服务器相同。例如，如果语句引用了变量 `@my_var`，则该语句在二进制日志中会先出现以下语句，其中 `value` 是源服务器上 `@my_var` 的值：

    ```sql
    SET @my_var = value;
    ```

  - 过程调用可能发生在已提交或已回滚的事务中。事务上下文会被考虑在内，以便正确复制过程执行的事务性方面。也就是说，服务器记录过程中实际执行并修改数据的语句，并根据需要记录 `BEGIN`、`COMMIT` 和 `ROLLBACK` 语句。例如，如果过程只更新事务表，并在一个已回滚的事务中执行，则这些更新不会被记录。如果过程发生在已提交事务中，`BEGIN` 和 `COMMIT` 语句会与更新一起记录。对于在已回滚事务中执行的过程，其语句按单独执行时相同的规则记录：

    - 对事务表的更新不记录。
    - 对非事务表的更新会记录，因为回滚不会取消它们。
    - 对事务表和非事务表混合的更新会在 `BEGIN` 和 `ROLLBACK` 包围下记录，以便副本做出与源服务器相同的更改和回滚。

- 如果存储过程是从存储函数内部调用的，则存储过程调用不会在语句级别写入二进制日志。在这种情况下，只记录调用该函数的语句（如果它出现在被记录的语句中），或记录一条 `DO` 语句（如果它出现在未被记录的语句中）。因此，使用调用存储过程的存储函数时应格外小心，即使该过程本身是安全的。
