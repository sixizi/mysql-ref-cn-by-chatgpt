## 27.8 存储对象访问控制

存储程序（过程、函数、触发器和事件）和视图在使用前定义，当被引用时，在确定其权限的安全上下文中执行。存储对象执行的适用权限由其 DEFINER 属性和 SQL SECURITY 特性控制。

### DEFINER 属性

存储对象定义可以包含一个 DEFINER 属性，该属性指定一个 MySQL 账户。如果定义省略了 DEFINER 属性，默认对象定义者是创建它的用户。

以下规则确定可以为存储对象指定哪些账户作为 DEFINER 属性：

- 如果你拥有 SET_ANY_DEFINER 权限，可以指定任何账户作为 DEFINER 属性。如果该账户不存在，将生成警告。此外，要将存储对象 DEFINER 属性设置为具有 SYSTEM_USER 权限的账户，你必须拥有 SYSTEM_USER 权限。

- 否则，唯一允许的账户是你自己的账户，可以按字面指定或指定为 CURRENT_USER 或 CURRENT_USER()。你不能将定义者设置为任何其他账户。

使用不存在的 DEFINER 账户创建存储对象会创建孤立对象，这可能会产生负面后果；请参阅孤立存储对象。

### SQL SECURITY 特性

对于存储例程（过程和函数）和视图，对象定义可以包含一个 SQL SECURITY 特性，其值为 DEFINER 或 INVOKER，以指定对象是在定义者还是调用者上下文中执行。如果定义省略了 SQL SECURITY 特性，默认为定义者上下文。

触发器和事件没有 SQL SECURITY 特性，始终在定义者上下文中执行。服务器根据需要自动调用这些对象，因此没有调用用户。

定义者和调用者安全上下文的区别如下：

- 在定义者安全上下文中执行的存储对象以其 DEFINER 属性命名的账户的权限执行。这些权限可能与调用用户的权限完全不同。调用者必须具有适当的权限来引用该对象（例如，EXECUTE 用于调用存储过程或 SELECT 用于从视图选择），但在对象执行期间，调用者的权限被忽略，只有 DEFINER 账户权限重要。如果 DEFINER 账户权限很少，对象的操作能力相应受限。如果 DEFINER 账户权限很高（例如管理账户），无论谁调用它，对象都可以执行强大的操作。

- 在调用者安全上下文中执行的存储例程或视图只能执行调用者拥有权限的操作。DEFINER 属性对对象执行没有影响。

### 示例

考虑以下存储过程，它使用 SQL SECURITY DEFINER 声明以在定义者安全上下文中执行：

```
CREATE DEFINER = 'admin'@'localhost' PROCEDURE p1()
SQL SECURITY DEFINER
BEGIN
  UPDATE t1 SET counter = counter + 1;
END;
```

任何拥有 p1 的 EXECUTE 权限的用户都可以用 CALL 语句调用它。但是，当 p1 执行时，它在定义者安全上下文中执行，因此以其 DEFINER 属性命名的账户 'admin'@'localhost' 的权限执行。该账户必须拥有 p1 的 EXECUTE 权限以及对象体内引用的表 t1 的 UPDATE 权限。否则，过程失败。

现在考虑这个存储过程，它与 p1 相同，除了其 SQL SECURITY 特性是 INVOKER：

```
CREATE DEFINER = 'admin'@'localhost' PROCEDURE p2()
SQL SECURITY INVOKER
BEGIN
  UPDATE t1 SET counter = counter + 1;
END;
```

与 p1 不同，p2 在调用者安全上下文中执行，因此以调用用户的权限执行，无论 DEFINER 属性值如何。如果调用者缺少 p2 的 EXECUTE 权限或表 t1 的 UPDATE 权限，p2 失败。

### 孤立存储对象

孤立存储对象是其 DEFINER 属性命名不存在的账户的对象：

- 孤立存储对象可以通过在对象创建时指定不存在的 DEFINER 账户来创建。

- 现有存储对象可以通过执行删除对象 DEFINER 账户的 DROP USER 语句或重命名对象 DEFINER 账户的 RENAME USER 语句而变成孤立。

孤立存储对象可能以以下方式产生问题：

- 因为 DEFINER 账户不存在，如果对象在定义者安全上下文中执行，它可能无法按预期工作：

  - 对于存储例程，如果 SQL SECURITY 值是 DEFINER 但定义者账户不存在，在例程执行时会发生错误。

  - 对于触发器，在账户实际存在之前触发器激活发生不是个好主意。否则，关于权限检查的行为是未定义的。

  - 对于事件，如果账户不存在，在事件执行时会发生错误。

  - 对于视图，如果 SQL SECURITY 值是 DEFINER 但定义者账户不存在，当引用视图时会发生错误。

- 如果不存在的 DEFINER 账户随后为与对象无关的目的而重新创建，对象可能会带来安全风险。在这种情况下，该账户"采用"该对象，具有适当的权限，即使这不是预期的，也能够执行它。

服务器实施以下账户管理安全检查，旨在防止可能（也许无意中）导致存储对象变成孤立或导致当前孤立的存储对象被采用的操作：

- 如果任何要删除的账户被命名为任何存储对象的 DEFINER 属性，DROP USER 失败并出现错误。（即，如果删除账户会导致存储对象变成孤立，该语句失败。）

- 如果任何要重命名的账户被命名为任何存储对象的 DEFINER 属性，RENAME USER 失败并出现错误。（即，如果重命名账户会导致存储对象变成孤立，该语句失败。）

- 如果任何要创建的账户被命名为任何存储对象的 DEFINER 属性，CREATE USER 失败并出现错误。（即，如果创建账户会导致该账户采用当前孤立的存储对象，该语句失败。）

在某些情况下，可能需要故意执行那些账户管理语句，即使它们本来会失败。为了使这成为可能，如果用户拥有 ALLOW_NONEXISTENT_DEFINER 权限，该权限会覆盖孤立对象安全检查，语句以警告而不是错误成功。

要获取有关 MySQL 安装中用作存储对象定义者的账户的信息，查询 INFORMATION_SCHEMA。

此查询标识哪些 INFORMATION_SCHEMA 表描述具有 DEFINER 属性的对象：

```
mysql> SELECT TABLE_SCHEMA, TABLE_NAME FROM INFORMATION_SCHEMA.COLUMNS
       WHERE COLUMN_NAME = 'DEFINER';
+--------------------+------------+
| TABLE_SCHEMA       | TABLE_NAME |
+--------------------+------------+
| information_schema | EVENTS     |
| information_schema | ROUTINES   |
| information_schema | TRIGGERS   |
| information_schema | VIEWS      |
+--------------------+------------+
```

结果告诉你要查询哪些表以发现存在哪些存储对象 DEFINER 值以及哪些对象具有特定的 DEFINER 值：

- 要标识每个表中存在哪些 DEFINER 值，使用这些查询：

```
SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.EVENTS;
SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.ROUTINES;
SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.TRIGGERS;
SELECT DISTINCT DEFINER FROM INFORMATION_SCHEMA.VIEWS;
```

查询结果对于以下方式显示的任何账户都很重要：

- 如果账户存在，删除或重命名它会导致存储对象变成孤立。如果你计划删除或重命名该账户，考虑首先删除其关联的存储对象或将它们重新定义为具有不同的定义者。

- 如果账户不存在，创建它会导致它采用当前孤立的存储对象。如果你计划创建该账户，考虑孤立对象是否应该与它关联。如果不应该，将它们重新定义为具有不同的定义者。

要使用不同的定义者重新定义对象，可以使用 ALTER EVENT 或 ALTER VIEW 直接修改事件和视图的 DEFINER 账户。对于存储过程和函数以及触发器，必须删除对象并重新创建它以分配不同的 DEFINER 账户。

- 要标识具有给定 DEFINER 账户的对象，使用这些查询，用感兴趣的账户替换 user_name@host_name：

```
SELECT EVENT_SCHEMA, EVENT_NAME FROM INFORMATION_SCHEMA.EVENTS
WHERE DEFINER = 'user_name@host_name';
SELECT ROUTINE_SCHEMA, ROUTINE_NAME, ROUTINE_TYPE
FROM INFORMATION_SCHEMA.ROUTINES
WHERE DEFINER = 'user_name@host_name';
SELECT TRIGGER_SCHEMA, TRIGGER_NAME FROM INFORMATION_SCHEMA.TRIGGERS
WHERE DEFINER = 'user_name@host_name';
SELECT TABLE_SCHEMA, TABLE_NAME FROM INFORMATION_SCHEMA.VIEWS
WHERE DEFINER = 'user_name@host_name';
```

对于 ROUTINES 表，查询包括 ROUTINE_TYPE 列，以便输出行区分 DEFINER 是用于存储过程还是存储函数。

如果你搜索的账户不存在，这些查询显示的任何对象都是孤立对象。

### 风险最小化指南

要最小化存储对象创建和使用的风险潜力，遵循这些指南：

- 不要创建孤立存储对象；即，DEFINER 属性命名不存在的账户的对象。不要通过删除或重命名任何现有对象的 DEFINER 属性命名的账户来导致存储对象变成孤立。

- 对于存储例程或视图，在可能的情况下在对象定义中使用 SQL SECURITY INVOKER，以便它只能被拥有适当权限的用户使用，这些权限适用于对象执行的操作。

- 如果在使用拥有 SET_ANY_DEFINER 权限的账户时创建定义者上下文存储对象，指定一个显式 DEFINER 属性，该属性命名一个仅拥有对象执行的操作所需权限的账户。仅在绝对必要时指定高权限 DEFINER 账户。

- 管理员可以通过不授予用户 SET_ANY_DEFINER 权限来防止用户创建指定高权限 DEFINER 账户的存储对象。

- 定义者上下文对象应该编写时考虑到它们可能能够访问调用用户没有权限的数据。在某些情况下，可以通过不授予未授权用户特定权限来防止对这些对象的引用：

  - 没有 EXECUTE 权限的用户无法引用存储例程。

  - 没有适当权限的用户无法引用视图（SELECT 用于从视图选择，INSERT 用于插入到视图中，等等）。

但是，对于触发器和事件不存在这样的控制，因为它们始终在定义者上下文中执行。服务器根据需要自动调用这些对象，用户不直接引用它们：

- 触发器由对与其关联的表的访问激活，即使是没有特殊权限的用户的普通表访问。

- 事件由服务器按计划执行。

在这两种情况下，如果 DEFINER 账户权限很高，对象可能能够执行敏感或危险的操作。如果创建对象所需的权限从创建它的用户账户中被撤销，这仍然成立。管理员应该特别小心授予用户对象创建权限。

- 默认情况下，当执行具有 SQL SECURITY DEFINER 特性的例程时，MySQL 服务器不为 DEFINER 子句中命名的 MySQL 账户设置任何活跃角色，仅设置默认角色。例外是如果启用了 activate_all_roles_on_login 系统变量，在这种情况下 MySQL 服务器设置授予 DEFINER 用户的所有角色，包括强制角色。因此，默认情况下，当发出 CREATE PROCEDURE 或 CREATE FUNCTION 语句时，不检查通过角色授予的任何权限。对于存储程序，如果执行应该使用与默认不同的角色发生，程序体可以执行 SET ROLE 来激活所需的角色。这必须谨慎进行，因为分配给角色的权限可以被更改。
