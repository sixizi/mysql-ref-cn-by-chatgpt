### 27.7.2.2 JSON 二元性视图—并发

DML 操作对 JSON 二元性视图支持无锁乐观并发控制（LOCC）。

LOCC 的使用可以防止并发操作的冲突和数据不一致。这对于使用单独无状态调用（如 REST 请求）的读写操作尤为重要。

考虑以下示例：

- 用户通过 REST GET 请求在移动应用程序中访问数据，然后稍后决定通过 REST PUT 请求更新某些信息。

- 如果另一个用户在前一个 REST GET 和 REST PUT 请求之间通过另一个 REST PUT 请求更新了底层数据，第二个 REST PUT 请求将覆盖该数据，导致数据不一致。

这种情况发生是因为在两个 REST 请求之间的不确定时间内无法锁定资源。更重要的是，REST 调用是无状态的，无法保证这些调用将使用与事务开始时相同的数据库连接。

为了解决这个问题，LOCC 在更新时检查数据自上次读取以来是否已更改。如果数据已更改，更新将被拒绝，这允许应用程序适当地处理冲突。

#### JSON 二元性视图上的 DML 操作

LOCC 使用内置的 ETAG() 计算支持，并使用存储在 _metadata 子对象的 etag 字段中的 ETAG() 值。该值从有效注解为 CHECK 的投影列计算得出。_metadata 默认被排除。表级 CHECK 是默认值，未注解的列继承其表的设置。显式列级 CHECK 或 NO CHECK 注解会覆盖表设置。对有效注解为 NO CHECK 的列的更改不会改变文档的 ETAG，无论该列是通过 JSON 二元性视图还是直接在底层基表中更新。

注意

BLOB 类型以二进制形式存储，但在作为 SELECT 输出投影时以 base64 编码格式表示。这意味着使用相同的 BLOB 输入和手工制作的 base64 格式字符串运行时，etag 值可能不同。

并发处理如下：

1. 用户读取数据（使用 SELECT），将其存储在本地。

2. 用户修改数据的本地副本，保持生成的 etag 值不变。

3. 执行 UPDATE 语句使用 SELECT 重新构造对象（包括元数据），仅当重新构造的状态（即对重新构造的对象执行 ETAG() 的结果）与上次读取的状态匹配时才持久化任何更改。

4. 如果 etag 值不匹配，MySQL 会引发错误，应用程序可以通过重新读取数据并在需要时重试操作来处理该错误。

etag 值仅用作控制值，不被存储；它在 SELECT 或 UPDATE 执行时生成。
