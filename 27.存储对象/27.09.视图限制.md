# 27.9 存储程序二进制日志

二进制日志包含修改数据库内容的 SQL 语句的信息。这些信息以"事件"的形式存储，描述这些修改。（二进制日志事件不同于计划事件存储对象。）二进制日志有两个重要用途：

- 对于复制，二进制日志在源复制服务器上用作要发送到副本服务器的语句记录。源将其二进制日志中包含的事件发送到其副本，副本执行这些事件以进行与源上相同的数据更改。请参阅第 19.2 节"复制实现"。

- 某些数据恢复操作需要使用二进制日志。恢复备份文件后，备份后记录在二进制日志中的事件会被重新执行。这些事件将数据库从备份点更新到最新状态。请参阅第 9.3.2 节"使用备份进行恢复"。

但是，如果日志记录在语句级别进行，存储程序（存储过程和函数、触发器和事件）存在某些二进制日志问题：

- 在某些情况下，一个语句可能会影响源和副本上的不同行集。

- 在副本上执行的复制语句由副本的应用线程处理。除非您实现复制权限检查（请参阅第 19.3.3 节"复制权限检查"），否则应用线程具有完全权限。在这种情况下，过程可能在源和副本服务器上遵循不同的执行路径，因此用户可以编写包含仅在副本上执行的危险语句的例程。

- 如果修改数据的存储程序是非确定性的，则它不可重复。这可能导致源和副本上的数据不同，或导致恢复的数据与原始数据不同。

本节描述 MySQL 如何处理存储程序的二进制日志。它说明了实现对存储程序使用的当前条件，以及您可以采取什么措施来避免日志问题。它还提供了有关这些条件原因的其他信息。

除非另有说明，此处的备注假设在服务器上启用了二进制日志（请参阅第 7.4.4 节"二进制日志"。）如果未启用二进制日志，则复制不可能，二进制日志也不可用于数据恢复。二进制日志默认启用，仅在使用 --skip-log-bin 或 --disable-log-bin 启动服务器时才禁用。

一般来说，此处描述的问题在二进制日志记录在 SQL 语句级别（基于语句的二进制日志）进行时出现。如果使用基于行的二进制日志，日志包含执行 SQL 语句导致的对各个行的更改。当例程或触发器执行时，记录的是行更改，而不是进行更改的语句。对于存储过程，这意味着不记录 CALL 语句。对于存储函数，记录的是函数内进行的行更改，而不是函数调用。对于触发器，记录的是触发器进行的行更改。在副本端，只能看到行更改，看不到存储程序调用。

混合格式二进制日志（binlog_format=MIXED）使用基于语句的二进制日志，除非只有基于行的二进制日志才能保证得到正确结果的情况。使用混合格式时，如果存储函数、存储过程、触发器、事件或预处理语句包含任何对基于语句的二进制日志不安全的内容，整个语句被标记为不安全并以行格式记录。用于创建和删除过程、函数、触发器和事件的语句始终是安全的，并以语句格式记录。有关基于行、混合和基于语句的日志记录以及如何确定安全和不安全语句的更多信息，请参阅第 19.2.1 节"复制格式"。

MySQL 中存储函数使用的条件可以总结如下。这些条件不适用于存储过程或事件调度器事件，也不适用于未启用二进制日志的情况。

- 要创建或修改存储函数，除了通常需要的 CREATE ROUTINE 或 ALTER ROUTINE 权限外，您还必须具有 SET_ANY_DEFINER 权限。（根据函数定义中的 DEFINER 值，无论是否启用二进制日志，可能都需要 SET_ANY_DEFINER。请参阅第 15.1.22 节"CREATE PROCEDURE 和 CREATE FUNCTION 语句"。）

- 创建存储函数时，必须声明它是确定性的或不修改数据。否则，它可能对数据恢复或复制不安全。

  默认情况下，要接受 CREATE FUNCTION 语句，必须显式指定 DETERMINISTIC、NO SQL 或 READS SQL DATA 中的至少一个。否则会发生错误：
  ```
  ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
  or READS SQL DATA in its declaration and binary logging is enabled
  (you *might* want to use the less safe log_bin_trust_function_creators
  variable)
  ```

  此函数是确定性的（不修改数据），因此是安全的：
  ```
  CREATE FUNCTION f1(i INT)
  RETURNS INT
  DETERMINISTIC
  READS SQL DATA
  BEGIN
    RETURN i;
  END;
  ```

  此函数使用 UUID()，这是非确定性的，因此函数也是非确定性的且不安全：
  ```
  CREATE FUNCTION f2()
  RETURNS CHAR(36) CHARACTER SET utf8mb4
  BEGIN
    RETURN UUID();
  END;
  ```

  此函数修改数据，因此可能不安全：
  ```
  CREATE FUNCTION f3(p_id INT)
  RETURNS INT
  BEGIN
    UPDATE t SET modtime = NOW() WHERE id = p_id;
    RETURN ROW_COUNT();
  END;
  ```

  对函数性质的评估基于创建者的"诚实性"。MySQL 不检查声明为 DETERMINISTIC 的函数是否不含产生非确定性结果的语句。

- 当尝试执行存储函数时，如果设置了 binlog_format=STATEMENT，必须在函数定义中指定 DETERMINISTIC 关键字。如果不是这样，会生成错误且函数不运行，除非指定 log_bin_trust_function_creators=1 来覆盖此检查（见下文）。对于递归函数调用，仅在最外层调用上需要 DETERMINISTIC 关键字。如果使用基于行或混合的二进制日志，即使函数定义时不含 DETERMINISTIC 关键字，语句也会被接受并复制。

- 因为 MySQL 在创建时不检查函数是否真正是确定性的，使用 DETERMINISTIC 关键字调用存储函数可能执行对基于语句的日志记录不安全的操作，或调用包含不安全语句的函数或过程。如果在设置 binlog_format=STATEMENT 时发生这种情况，会发出警告消息。如果使用基于行或混合的二进制日志，不会发出警告，语句以基于行的格式复制。

- 要放宽对函数创建的前述条件（必须具有 SUPER 权限且函数必须声明为确定性或不修改数据），将全局 log_bin_trust_function_creators 系统变量设置为 1。默认情况下，此变量的值为 0，但您可以像这样更改它：
  ```
  mysql> SET GLOBAL log_bin_trust_function_creators = 1;
  ```

  您也可以在服务器启动时设置此变量。

  如果未启用二进制日志，log_bin_trust_function_creators 不适用。除非如前所述函数定义中的 DEFINER 值需要，否则不需要 SUPER 来创建函数。

- 有关可能对复制不安全的内置函数的信息（因此也会导致使用它们的存储函数不安全），请参阅第 19.5.1 节"复制功能和问题"。

触发器类似于存储函数，因此前面关于函数的备注也适用于触发器，但以下例外：CREATE TRIGGER 没有可选的 DETERMINISTIC 特性，因此触发器被假定为始终确定性的。但是，这个假设在某些情况下可能无效。例如，UUID() 函数是非确定性的（不复制）。在触发器中使用此类函数时要小心。

触发器可以更新表，因此如果您没有所需的权限，CREATE TRIGGER 会出现类似于存储函数的错误消息。在副本端，副本使用触发器 DEFINER 属性来确定哪个用户被认为是触发器的创建者。

本节的其余部分提供了有关日志记录实现及其含义的其他详细信息。除非您对当前日志记录相关条件对存储例程使用的原理背景感兴趣，否则无需阅读。此讨论仅适用于基于语句的日志记录，不适用于基于行的日志记录，第一项除外：CREATE 和 DROP 语句无论日志记录模式如何都作为语句记录。

- 服务器将 CREATE EVENT、CREATE PROCEDURE、CREATE FUNCTION、ALTER EVENT、ALTER PROCEDURE、ALTER FUNCTION、DROP EVENT、DROP PROCEDURE 和 DROP FUNCTION 语句写入二进制日志。

- 如果存储函数改变数据并在不会被记录的语句中发生，存储函数调用被记录为 SELECT 语句。这防止了存储函数在未记录语句中使用导致的数据更改不被复制。例如，SELECT 语句不写入二进制日志，但 SELECT 可能调用进行更改的存储函数。为了处理这种情况，当给定函数进行更改时，SELECT func_name() 语句被写入二进制日志。假设在源服务器上执行了以下语句：

  ```
  CREATE FUNCTION f1(a INT) RETURNS INT
  BEGIN
    IF (a < 3) THEN
       INSERT INTO t2 VALUES (a);
    END IF;
    RETURN 0;
  END;

  CREATE TABLE t1 (a INT);
  INSERT INTO t1 VALUES (1),(2),(3);

  SELECT f1(a) FROM t1;
  ```

  当 SELECT 语句执行时，函数 f1() 被调用三次。其中两次调用插入一行，MySQL 为每一行记录一个 SELECT 语句。也就是说，MySQL 将以下语句写入二进制日志：

  ```
  SELECT f1(1);
  SELECT f1(2);
  ```

  当存储函数调用导致错误的存储过程时，服务器也会为存储函数调用记录 SELECT 语句。在这种情况下，服务器将 SELECT 语句连同预期的错误代码一起写入日志。在副本上，如果发生相同的错误，这是预期的结果，复制继续。否则，复制停止。

- 记录存储函数调用而不是函数执行的语句对复制有安全含义，这源于两个因素：

  - 函数可能在源和副本服务器上遵循不同的执行路径。

  - 在副本上执行的语句由副本的应用线程处理。除非您实现复制权限检查（请参阅第 19.3.3 节"复制权限检查"），否则应用线程具有完全权限。

  其含义是，虽然用户必须具有 CREATE ROUTINE 权限才能创建函数，但用户可以编写包含仅在副本上执行的危险语句的函数，其中由具有完全权限的线程处理。例如，如果源和副本服务器的服务器 ID 值分别为 1 和 2，源服务器上的用户可以创建并调用不安全函数 unsafe_func()，如下所示：

  ```
  mysql> delimiter //
  mysql> CREATE FUNCTION unsafe_func () RETURNS INT
      -> BEGIN
      ->   IF @@server_id=2 THEN dangerous_statement; END IF;
      ->   RETURN 1;
      -> END;
      -> //
  mysql> delimiter ;
  mysql> INSERT INTO t VALUES(unsafe_func());
  ```

  CREATE FUNCTION 和 INSERT 语句被写入二进制日志，因此副本执行它们。因为副本的应用线程具有完全权限，它执行危险语句。因此，函数调用在源和副本上有不同的效果，不是复制安全的。

  为了防止启用了二进制日志的服务器出现这种危险，存储函数创建者除了通常需要的 CREATE ROUTINE 权限外，还必须具有 SUPER 权限。类似地，要使用 ALTER FUNCTION，除了 ALTER ROUTINE 权限外，您还必须具有 SUPER 权限。没有 SUPER 权限，会发生错误：

  ```
  ERROR 1419 (HY000): You do not have the SUPER privilege and
  binary logging is enabled (you *might* want to use the less safe
  log_bin_trust_function_creators variable)
  ```

  如果您不想要求函数创建者具有 SUPER 权限（例如，如果系统上具有 CREATE ROUTINE 权限的所有用户都是经验丰富的应用开发人员），将全局 log_bin_trust_function_creators 系统变量设置为 1。您也可以在服务器启动时设置此变量。如果未启用二进制日志，log_bin_trust_function_creators 不适用。除非如前所述函数定义中的 DEFINER 值需要，否则不需要 SUPER 来创建函数。

- 建议使用复制权限检查，无论您对函数创建者权限做出什么选择。复制权限检查可以设置为确保只有预期和相关的操作被授权用于复制通道。有关如何执行此操作的说明，请参阅第 19.3.3 节"复制权限检查"。

- 如果执行更新的函数是非确定性的，则它不可重复。这可能产生两个不良影响：

  - 它导致副本与源不同。

  - 恢复的数据与原始数据不匹配。

  为了处理这些问题，MySQL 强制执行以下要求：在源服务器上，除非声明函数是确定性的或不修改数据，否则拒绝函数的创建和修改。这里适用两组函数特性：

  - DETERMINISTIC 和 NOT DETERMINISTIC 特性指示函数是否对给定输入始终产生相同结果。如果未给出任何特性，默认值为 NOT DETERMINISTIC。要声明函数是确定性的，必须显式指定 DETERMINISTIC。

  - CONTAINS SQL、NO SQL、READS SQL DATA 和 MODIFIES SQL DATA 特性提供有关函数是否读取或写入数据的信息。NO SQL 或 READS SQL DATA 都表示函数不改变数据，但必须显式指定其中之一，因为如果未给出特性，默认值为 CONTAINS SQL。

  默认情况下，要接受 CREATE FUNCTION 语句，必须显式指定 DETERMINISTIC、NO SQL 或 READS SQL DATA 中的至少一个。否则会发生错误：

  ```
  ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
  or READS SQL DATA in its declaration and binary logging is enabled
  (you *might* want to use the less safe log_bin_trust_function_creators
  variable)
  ```

  如果将 log_bin_trust_function_creators 设置为 1，则删除函数必须是确定性或不修改数据的要求。

- 存储过程调用在语句级别而不是 CALL 级别记录。也就是说，服务器不记录 CALL 语句，它记录过程中实际执行的那些语句。因此，源服务器上发生的相同更改也会在副本上发生。这防止了过程在不同机器上具有不同执行路径可能导致的问题。

  一般来说，存储过程中执行的语句使用与语句以独立方式执行时相同的规则写入二进制日志。在记录过程语句时采取一些特殊措施，因为过程中的语句执行与非过程上下文中的执行不完全相同：

  - 要记录的语句可能包含对本地过程变量的引用。这些变量在存储过程上下文之外不存在，因此引用此类变量的语句不能按字面意思记录。相反，对于日志记录目的，对本地变量的每个引用都被替换为以下构造：

    ```
    NAME_CONST(var_name, var_value)
    ```

    var_name 是本地变量名，var_value 是一个常数，指示变量在记录语句时的值。NAME_CONST() 的值为 var_value，"名称"为 var_name。因此，如果直接调用此函数，您会得到如下结果：

    ```
    mysql> SELECT NAME_CONST('myname', 14);
    +--------+
    | myname |
    +--------+
    |     14 |
    +--------+
    ```

    NAME_CONST() 使记录的独立语句能够在副本上执行，效果与在源上的存储过程中执行的原始语句相同。

    当源列表达式引用本地变量时，NAME_CONST() 的使用可能导致 CREATE TABLE ... SELECT 语句出现问题。将这些引用转换为 NAME_CONST() 表达式可能导致源和副本服务器上的列名不同，或名称太长而不是合法的列标识符。解决方法是为引用本地变量的列提供别名。考虑当 myvar 的值为 1 时的此语句：

    ```
    CREATE TABLE t1 SELECT myvar;
    ```

    这被重写为：

    ```
    CREATE TABLE t1 SELECT NAME_CONST(myvar, 1);
    ```

    要确保源和副本表具有相同的列名，请像这样编写语句：

    ```
    CREATE TABLE t1 SELECT myvar AS myvar;
    ```

    重写的语句变为：

    ```
    CREATE TABLE t1 SELECT NAME_CONST(myvar, 1) AS myvar;
    ```

  - 要记录的语句可能包含对用户定义变量的引用。为了处理这种情况，MySQL 将 SET 语句写入二进制日志以确保变量在副本上存在且值与源上相同。例如，如果语句引用变量 @my_var，该语句在二进制日志中前面有以下语句，其中 value 是源上 @my_var 的值：

    ```
    SET @my_var = value;
    ```

  - 过程调用可能在已提交或已回滚的事务中发生。考虑事务上下文以便正确复制过程执行的事务方面。也就是说，服务器记录过程中实际执行并修改数据的那些语句，并根据需要记录 BEGIN、COMMIT 和 ROLLBACK 语句。例如，如果过程仅更新事务表并在被回滚的事务中执行，这些更新不被记录。如果过程在已提交的事务中发生，BEGIN 和 COMMIT 语句与更新一起被记录。对于在已回滚事务中执行的过程，其语句使用与语句以独立方式执行时相同的规则记录：

    - 对事务表的更新不被记录。

    - 对非事务表的更新被记录，因为回滚不会取消它们。

    - 对事务表和非事务表混合的更新被记录，并由 BEGIN 和 ROLLBACK 包围，以便副本进行与源上相同的更改和回滚。

  - 如果从存储函数中调用过程，存储过程调用不在语句级别写入二进制日志。在这种情况下，唯一记录的是调用函数的语句（如果它在记录的语句中发生）或 DO 语句（如果它在不记录的语句中发生）。因此，在使用调用过程的存储函数时应谨慎，即使过程本身是安全的。
