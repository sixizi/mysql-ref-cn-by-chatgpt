## 27.9 视图限制

视图定义中最多可以引用 **61 张表**。

视图处理不会被优化：

- 不能在视图上创建索引。
- 使用 `merge` 算法处理的视图可以使用索引。但是，使用 `temptable` 算法处理的视图无法利用其底层表上的索引，不过在生成临时表的过程中可以使用索引。

有一个通用原则：不能在子查询中修改一张表，同时又从同一张表中选择数据。参见 [13.2.15.12，子查询限制](#)。

如果视图从某张表中选择数据，而该选择发生在子查询中，并且视图使用 `merge` 算法求值，那么同一原则也适用于从该视图中选择数据的情况。例如：

```mysql
CREATE VIEW v1 AS
SELECT * FROM t2 WHERE EXISTS (SELECT 1 FROM t1 WHERE t1.a = t2.a);

UPDATE t1, v2 SET t1.a = 1 WHERE t1.b = v2.b;
```

如果视图使用临时表求值，那么可以在视图子查询中从某张表中选择数据，同时仍可在外部查询中修改该表。在这种情况下，视图存储在临时表中，因此实际上并不是在子查询中选择该表并同时修改它。（这也是你可能希望通过在视图定义中指定 `ALGORITHM = TEMPTABLE` 强制 MySQL 使用 `temptable` 算法的另一个原因。）

可以使用 `DROP TABLE` 或 `ALTER TABLE` 删除或修改视图定义中使用的表。即使这样做会使视图失效，`DROP` 或 `ALTER` 操作也不会产生警告。相反，错误会在以后使用该视图时发生。可以使用 `CHECK TABLE` 检查因 `DROP` 或 `ALTER` 操作而失效的视图。

关于视图可更新性，总体目标是：如果某个视图在理论上可更新，那么在实践中也应可更新。许多理论上可更新的视图现在可以更新，但仍存在限制。详情参见 [27.5.3，可更新和可插入视图](./27.05.使用视图/27.05.03.可更新和可插入视图.md)。

当前视图实现存在一个缺点。如果用户被授予创建视图所需的基本权限（`CREATE VIEW` 和 `SELECT` 权限），那么除非还授予该用户 `SHOW VIEW` 权限，否则该用户不能对此对象调用 `SHOW CREATE VIEW`。

这一缺点可能导致使用 `mysqldump` 备份数据库时出现问题，备份可能因权限不足而失败。此问题在 Bug #22062 中有所描述。

该问题的解决方法是：由管理员手动向已被授予 `CREATE VIEW` 的用户授予 `SHOW VIEW` 权限，因为 MySQL 在创建视图时不会隐式授予该权限。

视图没有索引，因此索引提示不适用。从视图中选择数据时不允许使用索引提示。

`SHOW CREATE VIEW` 使用 `AS alias_name` 子句为每一列显示视图定义。如果某列由表达式创建，则默认别名是该表达式的文本，可能相当长。`CREATE VIEW` 语句中列名的别名会按照最大列长度 **64 个字符**进行检查（而不是最大别名长度 256 个字符）。因此，如果任何列别名超过 64 个字符，从 `SHOW CREATE VIEW` 的输出创建视图就会失败。对于别名过长的视图，这可能在以下情况下引发问题：

- 视图定义无法复制到执行列长度限制的较新副本。
- 使用 `mysqldump` 创建的转储文件无法加载到执行列长度限制的服务器。

针对任一问题的一种解决方法是修改每个有问题的视图定义，改用能提供较短列名的别名。这样视图就能正确复制，也可以在不引发错误的情况下转储并重新加载。要修改定义，可以使用 `DROP VIEW` 和 `CREATE VIEW` 删除并重新创建视图，或者使用 `CREATE OR REPLACE VIEW` 替换定义。

对于重新加载转储文件中的视图定义时出现的问题，另一种解决方法是编辑转储文件，修改其中的 `CREATE VIEW` 语句。不过，这不会改变原始视图定义，可能给后续转储操作带来问题。
