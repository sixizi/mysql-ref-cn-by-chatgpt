### 10.2.1.12 块嵌套循环和批量键访问连接

在 MySQL 中，提供了批量键访问（BKA）连接算法，该算法同时使用对被连接表的索引访问和连接缓冲区。BKA 算法支持内连接、外连接和半连接操作，包括嵌套外连接。BKA 的优势包括由于表扫描更高效而改进的连接性能。此外，之前仅用于内连接的块嵌套循环（BNL）连接算法已扩展，可用于外连接和半连接操作，包括嵌套外连接。

以下部分讨论了支持原始 BNL 算法扩展的连接缓冲区管理、扩展的 BNL 算法和 BKA 算法。有关半连接策略的信息，请参见第 10.2.2.1 节"使用半连接和反连接转换优化 IN 和 EXISTS 子查询谓词"

#### 块嵌套循环和批量键访问算法的连接缓冲区管理

MySQL 可以使用连接缓冲区执行不仅是对内表没有索引访问的内连接，还可以执行子查询展平后出现的外连接和半连接。此外，当存在对内表的索引访问时，连接缓冲区也可以被有效使用。

连接缓冲区管理代码在存储有趣行列的值时略微更有效地利用连接缓冲区空间：如果行列的值为 NULL，则不在缓冲区中为该行列分配额外字节，并且为任何 VARCHAR 类型的值分配最少字节数。

代码支持两种类型的缓冲区，常规和增量。假设连接缓冲区 B1 用于连接表 t1 和 t2，此操作的结果使用连接缓冲区 B2 与表 t3 连接：

- 常规连接缓冲区包含来自每个连接操作数的列。如果 B2 是常规连接缓冲区，放入 B2 的每一行 r 由来自 B1 的行 r1 的列和来自表 t3 的匹配行 r2 的有趣列组成。

- 增量连接缓冲区仅包含由第二个连接操作数生成的表的行中的列。即，它相对于第一个操作数缓冲区中的一行是增量的。如果 B2 是增量连接缓冲区，它包含行 r2 的有趣列以及指向来自 B1 的行 r1 的链接。

增量连接缓冲区始终相对于来自较早连接操作的连接缓冲区是增量的，因此来自第一个连接操作的缓冲区始终是常规缓冲区。在刚才给出的示例中，用于连接表 t1 和 t2 的缓冲区 B1 必须是常规缓冲区。

用于连接操作的增量缓冲区的每一行仅包含来自要连接的表的行的有趣列。这些列通过对来自第一个连接操作数生成的表的匹配行的有趣列的引用进行增强。增量缓冲区中的多行可以引用同一行 r，其列存储在先前的连接缓冲区中，只要所有这些行都与行 r 匹配。

增量缓冲区使得从用于先前连接操作的缓冲区复制列的频率降低。这在缓冲区空间中提供了节省，因为在一般情况下，由第一个连接操作数生成的行可以由由第二个连接操作数生成的多行匹配。无需对来自第一个操作数的行进行多次复制。增量缓冲区还由于复制时间的减少而在处理时间中提供了节省。

optimizer_switch 系统变量的 block_nested_loop 标志控制哈希连接。

batched_key_access 标志控制优化器如何使用批量键访问连接算法。

默认情况下，block_nested_loop 为开启，batched_key_access 为关闭。请参见第 10.9.2 节"可切换的优化"。也可以应用优化器提示；请参见块嵌套循环和批量键访问算法的优化器提示。

有关半连接策略的信息，请参见第 10.2.2.1 节"使用半连接和反连接转换优化 IN 和 EXISTS 子查询谓词"

#### 外连接和半连接的块嵌套循环算法

MySQL BNL 算法的原始实现已扩展以支持外连接和半连接操作（后来被哈希连接算法取代；请参见第 10.2.1.4 节"哈希连接优化"）。

当这些操作使用连接缓冲区执行时，放入缓冲区的每一行都配有一个匹配标志。

如果使用连接缓冲区执行外连接操作，第二个操作数生成的表的每一行都会针对连接缓冲区中的每一行进行匹配检查。找到匹配时，会形成一个新的扩展行（原始行加上来自第二个操作数的列）并发送以供剩余连接操作进一步扩展。此外，缓冲区中匹配行的匹配标志被启用。检查完要连接的表的所有行后，连接缓冲区被扫描。缓冲区中没有启用匹配标志的每一行都通过 NULL 补充（第二个操作数中每列的 NULL 值）进行扩展，并发送以供剩余连接操作进一步扩展。

optimizer_switch 系统变量的 block_nested_loop 标志控制哈希连接。

有关更多信息，请参见第 10.9.2 节"可切换的优化"。也可以应用优化器提示；请参见块嵌套循环和批量键访问算法的优化器提示。

在 EXPLAIN 输出中，当 Extra 值包含 Using join buffer (Block Nested Loop) 且 type 值为 ALL、index 或 range 时，表示对表使用了 BNL。

有关半连接策略的信息，请参见第 10.2.2.1 节"使用半连接和反连接转换优化 IN 和 EXISTS 子查询谓词"

#### 批量键访问连接

MySQL 实现了一种称为批量键访问（BKA）连接算法的表连接方法。当存在对由第二个连接操作数生成的表的索引访问时，可以应用 BKA。与 BNL 连接算法类似，BKA 连接算法使用连接缓冲区来累积由连接操作的第一个操作数生成的行的有趣列。然后 BKA 算法为缓冲区中的所有行构建键以访问要连接的表，并将这些键批量提交到数据库引擎以进行索引查找。键通过多范围读取（MRR）接口提交到引擎（请参见第 10.2.1.11 节"多范围读取优化"）。提交键后，MRR 引擎函数以最优方式执行索引中的查找，获取由这些键找到的被连接表的行，并开始向 BKA 连接算法提供匹配行。每个匹配行与连接缓冲区中的行的引用相关联。

使用 BKA 时，join_buffer_size 的值定义了对存储引擎的每个请求中键批次的大小。缓冲区越大，对连接操作右表的顺序访问就越多，这可以显著改进性能。

要使用 BKA，optimizer_switch 系统变量的 batched_key_access 标志必须设置为开启。BKA 使用 MRR，因此 mrr 标志也必须为开启。目前，MRR 的成本估计过于悲观。因此，还需要 mrr_cost_based 为关闭才能使用 BKA。以下设置启用 BKA：

```
mysql> SET optimizer_switch='mrr=on,mrr_cost_based=off,batched_key_access=on';
```

MRR 函数执行有两种场景：

- 第一种场景用于传统的基于磁盘的存储引擎，如 InnoDB 和 MyISAM。对于这些引擎，通常来自连接缓冲区的所有行的键一次性提交到 MRR 接口。特定于引擎的 MRR 函数对提交的键执行索引查找，从中获取行 ID（或主键），然后根据 BKA 算法的请求逐个获取所有这些选定行 ID 的行。每一行都返回一个关联引用，该引用使得能够访问连接缓冲区中的匹配行。MRR 函数以最优方式获取行：它们按行 ID（主键）顺序获取。这改进了性能，因为读取是按磁盘顺序而不是随机顺序进行的。

- 第二种场景用于远程存储引擎，如 NDB。来自连接缓冲区的一部分行的键包及其关联由 MySQL Server（SQL 节点）发送到 MySQL Cluster 数据节点。作为回报，SQL 节点接收一个包（或多个包）的匹配行及相应的关联。BKA 连接算法获取这些行并构建新的连接行。然后将一组新的键发送到数据节点，并使用返回的包中的行来构建新的连接行。该过程继续进行，直到连接缓冲区中的最后一个键被发送到数据节点，并且 SQL 节点已接收并连接了与这些键匹配的所有行。这改进了性能，因为 SQL 节点发送到数据节点的键承载包更少意味着它与数据节点之间的往返次数更少以执行连接操作。

在第一种场景中，连接缓冲区的一部分被保留以存储由索引查找选择并作为参数传递给 MRR 函数的行 ID（主键）。

没有特殊的缓冲区来存储为连接缓冲区中的行构建的键。相反，为缓冲区中的下一行构建键的函数作为参数传递给 MRR 函数。

在 EXPLAIN 输出中，当 Extra 值包含 Using join buffer (Batched Key Access) 且 type 值为 ref 或 eq_ref 时，表示对表使用了 BKA。

#### 块嵌套循环和批量键访问算法的优化器提示

除了使用 optimizer_switch 系统变量在会话范围内控制优化器对 BNL 和 BKA 算法的使用外，MySQL 还支持优化器提示以在每个语句的基础上影响优化器。请参见第 10.9.3 节"优化器提示"。

要使用 BNL 或 BKA 提示为外连接的任何内表启用连接缓冲，必须为外连接的所有内表启用连接缓冲。
