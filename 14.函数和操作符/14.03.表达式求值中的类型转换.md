### 14.3 表达式求值中的类型转换

当操作符与不同类型的操作数一起使用时，会发生类型转换以使操作数兼容。某些转换是隐式发生的。例如，MySQL 会根据需要自动将字符串转换为数字，反之亦然。

```
mysql> SELECT 1+'1';
        -> 2
mysql> SELECT CONCAT(2,' test');
        -> '2 test'
```

也可以使用 CAST() 函数显式地将数字转换为字符串。CONCAT() 函数会隐式发生转换，因为它期望字符串参数。

```
mysql> SELECT 38.8, CAST(38.8 AS CHAR);
        -> 38.8, '38.8'
mysql> SELECT 38.8, CONCAT(38.8);
        -> 38.8, '38.8'
```

有关隐式数字到字符串转换的字符集信息，以及适用于 CREATE TABLE ... SELECT 语句的修改规则，请参阅本节后面的内容。

以下规则描述了比较操作中如何发生转换：

- 如果一个或两个参数都是 NULL，比较结果为 NULL，除了 NULL 安全的 <=> 相等比较操作符。对于 NULL <=> NULL，结果为真。不需要转换。

- 如果比较操作中的两个参数都是字符串，则将它们作为字符串进行比较。

- 如果两个参数都是整数，则将它们作为整数进行比较。

- 十六进制值在与数字比较时被视为二进制字符串。

- 如果其中一个参数是 TIMESTAMP 或 DATETIME 列，另一个参数是常量，则在执行比较之前将常量转换为时间戳。这样做是为了更符合 ODBC 标准。这不适用于 IN() 的参数。为了安全起见，在进行比较时始终使用完整的日期时间、日期或时间字符串。例如，在使用 BETWEEN 与日期或时间值时要获得最佳结果，请使用 CAST() 显式将值转换为所需的数据类型。

  来自表或多个表的单行子查询不被视为常量。例如，如果子查询返回一个整数以与 DATETIME 值进行比较，则比较作为两个整数进行。整数不会转换为时间值。要将操作数作为 DATETIME 值进行比较，请使用 CAST() 显式将子查询值转换为 DATETIME。

- 如果其中一个参数是十进制值，比较取决于另一个参数。如果另一个参数是十进制或整数值，则将参数作为十进制值进行比较；如果另一个参数是浮点值，则作为浮点值进行比较。

- 在所有其他情况下，参数作为浮点（双精度）数字进行比较。例如，字符串和数字操作数的比较作为浮点数的比较进行。

有关从一个时间类型转换为另一个时间类型的值的信息，请参阅第 13.2.8 节"日期和时间类型之间的转换"。

JSON 值的比较在两个级别进行。比较的第一个级别基于所比较值的 JSON 类型。如果类型不同，比较结果仅由哪个类型具有更高优先级决定。如果两个值具有相同的 JSON 类型，则使用特定于类型的规则进行第二级比较。对于 JSON 和非 JSON 值的比较，非 JSON 值被转换为 JSON，然后将值作为 JSON 值进行比较。有关详细信息，请参阅 JSON 值的比较和排序。

以下示例说明了用于比较操作的字符串到数字的转换：

```
mysql> SELECT 1 > '6x';
        -> 0
mysql> SELECT 7 > '6x';
        -> 1
mysql> SELECT 0 > 'x6';
        -> 0
mysql> SELECT 0 = 'x6';
        -> 1
```

对于字符串列与数字的比较，MySQL 无法使用该列上的索引快速查找值。如果 str_col 是一个索引字符串列，在执行以下语句中的查找时无法使用索引：

```
SELECT * FROM tbl_name WHERE str_col=1;
```

原因是有许多不同的字符串可能转换为值 1，例如 '1'、' 1' 或 '1a'。

当将字符串列与整数 0 进行比较时，可能会出现另一个问题。考虑如下创建和填充的表 t1：

```
mysql> CREATE TABLE t1 (
    ->   c1 INT NOT NULL AUTO_INCREMENT,
    ->   c2 INT DEFAULT NULL,
    ->   c3 VARCHAR(25) DEFAULT NULL,
    ->   PRIMARY KEY (c1)
    -> );
Query OK, 0 rows affected (0.03 sec)

mysql> INSERT INTO t1 VALUES ROW(1, 52, 'grape'), ROW(2, 139, 'apple'),
    ->                       ROW(3, 37, 'peach'), ROW(4, 221, 'watermelon'),
    ->                       ROW(5, 83, 'pear');
Query OK, 5 rows affected (0.01 sec)
Records: 5 Duplicates: 0 Warnings: 0
```

观察从此表中选择并将 VARCHAR 列 c3 与整数 0 进行比较时的结果：

```
mysql> SELECT * FROM t1 WHERE c3 = 0;
+----+------+------------+
| c1 | c2    | c3        |
+----+------+------------+
| 1 |     52 | grape     |
| 2 | 139 | apple        |
| 3 |     37 | peach     |
| 4 | 221 | watermelon |
| 5 |     83 | pear      |
+----+------+------------+
5 rows in set, 5 warnings (0.00 sec)
```

即使使用严格 SQL 模式，也会发生这种情况。要防止这种情况发生，请引用该值，如下所示：

```
mysql> SELECT * FROM t1 WHERE c3 = '0';
Empty set (0.00 sec)
```

当 SELECT 是数据定义语句（如 CREATE TABLE ... SELECT）的一部分时，不会发生这种情况；在严格模式下，由于无效比较，语句会失败：

```
mysql> CREATE TABLE t2 SELECT * FROM t1 WHERE c3 = 0;
ERROR 1292 (22007): Truncated incorrect DOUBLE value: 'grape'
```

当 0 被引用时，语句成功，但创建的表不包含任何行，因为没有匹配 '0' 的行，如下所示：

```
mysql> CREATE TABLE t2 SELECT * FROM t1 WHERE c3 = '0';
Query OK, 0 rows affected (0.03 sec)
Records: 0 Duplicates: 0 Warnings: 0

mysql> SELECT * FROM t2;
Empty set (0.00 sec)
```

这是一个已知问题，原因是在处理 SELECT 时不应用严格模式。另请参阅严格 SQL 模式。

浮点数与大整数值之间的比较是近似的，因为整数在比较前被转换为双精度浮点，这不能精确表示所有 64 位整数。例如，整数值 2^53 + 1 不能表示为浮点数，在浮点比较前会根据平台舍入为 2^53 或 2^53 + 2。

为了说明这一点，以下比较中只有第一个比较相等的值，但两个比较都返回真 (1)：

```
mysql> SELECT '9223372036854775807' = 9223372036854775807;
        -> 1
mysql> SELECT '9223372036854775807' = 9223372036854775806;
        -> 1
```

当从字符串到浮点的转换和从整数到浮点的转换发生时，它们不一定以相同的方式发生。整数可能由 CPU 转换为浮点，而字符串则逐位转换，涉及浮点乘法的操作。此外，结果可能受到计算机体系结构、编译器版本或优化级别等因素的影响。避免此类问题的一种方法是使用 CAST()，以便值不会隐式转换为浮点数：

```
mysql> SELECT CAST('9223372036854775807' AS UNSIGNED) = 9223372036854775806;
        -> 0
```

有关浮点比较的更多信息，请参阅第 B.3.4.8 节"浮点值的问题"。

服务器包含 dtoa，一个转换库，为字符串或 DECIMAL 值与近似值 (FLOAT/DOUBLE) 数字之间的改进转换提供基础：

- 跨平台的一致转换结果，这消除了例如 Unix 与 Windows 转换差异。

- 在以前结果没有提供足够精度的情况下准确表示值，例如对于接近 IEEE 限制的值。

- 将数字转换为字符串格式，具有最佳可能的精度。dtoa 的精度总是与标准 C 库函数的精度相同或更好。

因为此库产生的转换在某些情况下与非 dtoa 结果不同，依赖于以前结果的应用程序中存在不兼容的可能性。例如，依赖于以前转换的特定精确结果的应用程序可能需要调整以适应额外的精度。

dtoa 库提供具有以下属性的转换。D 表示具有 DECIMAL 或字符串表示的值，F 表示本机二进制 (IEEE) 格式的浮点数。

- F -> D 转换以最佳可能的精度完成，返回 D 作为最短字符串，当读回并舍入到 IEEE 指定的本机二进制格式中的最近值时产生 F。

- D -> F 转换完成使得 F 是输入十进制字符串 D 的最近本机二进制数。

这些属性意味着 F -> D -> F 转换是无损的，除非 F 是 -inf、+inf 或 NaN。后者的值不受支持，因为 SQL 标准将它们定义为 FLOAT 或 DOUBLE 的无效值。

对于 D -> F -> D 转换，无损的充分条件是 D 使用 15 位或更少的精度数字，不是非正规值、-inf、+inf 或 NaN。在某些情况下，即使 D 的精度超过 15 位，转换也是无损的，但这并非总是如此。

数字或时间值到字符串的隐式转换产生一个值，其字符集和排序规则由 character_set_connection 和 collation_connection 系统变量决定。（这些变量通常通过 SET NAMES 设置。有关连接字符集的信息，请参阅第 12.4 节"连接字符集和排序规则"。）

这意味着此类转换导致字符（非二进制）字符串（CHAR、VARCHAR 或 LONGTEXT 值），除非连接字符集设置为二进制的情况。在这种情况下，转换结果是二进制字符串（BINARY、VARBINARY 或 LONGBLOB 值）。

对于整数表达式，关于表达式求值的前面的备注对表达式赋值的应用方式有所不同；例如，在这样的语句中：

```
CREATE TABLE t SELECT integer_expr;
```

在这种情况下，从表达式产生的列中的表具有类型 INT 或 BIGINT，取决于整数表达式的长度。如果表达式的最大长度不适合 INT，则改用 BIGINT。长度取自 SELECT 结果集元数据的 max_length 值（参阅 C API 基本数据结构）。这意味着您可以通过使用足够长的表达式来强制 BIGINT 而不是 INT：

```
CREATE TABLE t SELECT 000000000000000000000;
```
