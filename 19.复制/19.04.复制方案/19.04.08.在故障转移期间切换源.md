### 19.4.8 故障转移期间切换源

你可以使用 CHANGE REPLICATION SOURCE TO 语句告诉副本切换到新的源。副本不会检查源上的数据库是否与副本上的数据库兼容；它只是开始从新源的二进制日志中的指定坐标读取和执行事件。在故障转移情况下，组中的所有服务器通常从同一二进制日志文件执行相同的事件，因此更改事件的源不应该影响数据库的结构或完整性，前提是你在进行更改时要谨慎。

副本应该启用二进制日志（--log-bin 选项），这是默认设置。如果你没有使用 GTIDs 进行复制，那么副本也应该使用 --log-replica-updates=OFF 运行（记录副本更新是默认设置）。这样，副本就可以在不重启副本 mysqld 的情况下成为源。假设你有图 19.4"使用复制的冗余，初始结构"中所示的结构。

图 19.4 使用复制的冗余，初始结构

在此图中，Source 保存源数据库，Replica* 主机是副本，Web Client 机器发出数据库读写。仅发出读操作的 Web 客户端（通常会连接到副本）未显示，因为在发生故障时它们不需要切换到新服务器。有关读/写扩展复制结构的更详细示例，请参见第 19.4.5 节"使用复制进行扩展"。

每个 MySQL 副本（Replica 1、Replica 2 和 Replica 3）都是启用了二进制日志的副本，并且使用 --log-replica-updates=OFF。因为当指定 --log-replica-updates=OFF 时，副本从源接收的更新不会写入二进制日志，所以每个副本上的二进制日志最初是空的。如果由于某种原因 Source 变得不可用，你可以选择其中一个副本成为新的源。例如，如果你选择 Replica 1，所有 Web Clients 应该重定向到 Replica 1，它将更新写入其二进制日志。Replica 2 和 Replica 3 应该从 Replica 1 进行复制。

使用 --log-replica-updates=OFF 运行副本的原因是防止副本在你使其中一个副本成为新源的情况下收到两次更新。如果 Replica 1 启用了 --log-replica-updates（这是默认设置），它会将从 Source 接收的任何更新写入其自己的二进制日志。这意味着，当 Replica 2 从 Source 更改为 Replica 1 作为其源时，它可能会从 Replica 1 接收已经从 Source 接收过的更新。

确保所有副本都已处理其中继日志中的任何语句。在每个副本上，发出 STOP REPLICA IO_THREAD，然后检查 SHOW PROCESSLIST 的输出，直到你看到 Has read all relay log。当所有副本都为真时，可以将它们重新配置为新的设置。在被提升为源的副本 Replica 1 上，发出 STOP REPLICA 和 RESET BINARY LOGS AND GTIDS。

在其他副本 Replica 2 和 Replica 3 上，使用 STOP REPLICA 和 CHANGE REPLICATION SOURCE TO SOURCE_HOST='Replica1'（其中 'Replica1' 代表 Replica 1 的真实主机名）。要使用 CHANGE REPLICATION SOURCE TO，添加有关如何从 Replica 2 或 Replica 3 连接到 Replica 1 的所有信息（用户、密码、端口）。在此场景中发出该语句时，无需指定 Replica 1 二进制日志文件的名称或要读取的日志位置，因为第一个二进制日志文件和位置 4 是默认值。最后，在 Replica 2 和 Replica 3 上执行 START REPLICA。

一旦新的复制设置就位，你需要告诉每个 Web Client 将其语句定向到 Replica 1。从那时起，Web Client 发送给 Replica 1 的所有更新都会写入 Replica 1 的二进制日志，其中包含自 Source 变得不可用以来发送给 Replica 1 的每个更新。

当 Source 再次可用时，你应该使其成为 Replica 1 的副本。要执行此操作，在 Source 上发出与之前在 Replica 2 和 Replica 3 上发出的相同的 CHANGE REPLICATION SOURCE TO 语句。Source 然后成为 Replica 1 的副本，并获取它离线时错过的 Web Client 写入。

要再次使 Source 成为源，使用前面的过程，就像 Replica 1 不可用且 Source 将成为新源一样。在此过程中，不要忘记在使 Replica 1、Replica 2 和 Replica 3 成为 Source 的副本之前在 Source 上运行 RESET BINARY LOGS AND GTIDS。如果你未能执行此操作，副本可能会从 Web Client 应用程序获取陈旧的写入，这些写入来自 Source 变得不可用之前的时间点。

你应该意识到副本之间没有同步，即使它们共享同一源，因此某些副本可能远远领先于其他副本。这意味着在某些情况下，前面示例中概述的过程可能无法按预期工作。但在实践中，所有副本上的中继日志应该相对接近。

保持应用程序了解源位置的一种方法是为源主机设置动态 DNS 条目。使用 BIND，你可以使用 nsupdate 动态更新 DNS。

### 19.4.9 使用异步连接故障转移切换源和副本

你可以使用异步连接故障转移机制在副本与其源的现有连接失败后，自动建立到新源的异步（源到副本）复制连接。异步连接故障转移机制可用于保持副本与共享数据的多个 MySQL 服务器或服务器组同步。潜在源服务器的列表存储在副本上，在发生连接故障时，根据你设置的加权优先级从列表中选择新源。
