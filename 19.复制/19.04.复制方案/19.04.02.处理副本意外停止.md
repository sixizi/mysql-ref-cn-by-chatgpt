## 19.4.2 处理副本的意外停止

为了使复制能够抵御服务器的意外停止（有时称为崩溃安全），副本必须能够在停止前恢复其状态。本节描述了副本在复制过程中意外停止的影响，以及如何配置副本以获得最佳的恢复机会以继续复制。

副本意外停止后，重启时复制 SQL 线程必须恢复有关已执行事务的信息。恢复所需的信息存储在副本的应用程序元数据存储库中。此存储库默认创建为名为 mysql.slave_relay_log_info 的 InnoDB 表。通过使用此事务存储引擎，信息在重启时始终可恢复。对应用程序元数据存储库的更新与事务一起提交，这意味着该存储库中记录的副本进度信息始终与已应用到数据库的内容一致，即使在服务器意外停止的情况下也是如此。有关应用程序元数据存储库的更多信息，请参见第 19.2.5 节"中继日志和复制元数据存储库"。

DML 事务以及原子 DDL 在副本的应用程序元数据存储库中的 mysql.slave_relay_log_info 表中更新复制位置，与应用更改到数据库一起，作为原子操作。在所有其他情况下，包括不完全原子的 DDL 语句和不支持原子 DDL 的豁免存储引擎，如果服务器意外停止，mysql.slave_relay_log_info 表可能会缺少与复制数据相关的更新。在这种情况下恢复更新是一个手动过程。有关 MySQL 26.10 中原子 DDL 支持的详细信息以及某些语句复制的相应行为，请参见第 15.1.1 节"原子数据定义语句支持"。

副本从意外停止恢复的恢复过程因副本的配置而异。恢复过程的详细信息受所选复制方法、副本是单线程还是多线程以及相关系统变量的设置的影响。恢复过程的总体目标是确定在意外停止之前已在副本数据库上应用了哪些事务，并检索和应用副本在意外停止后错过的事务。

- 对于基于 GTID 的复制，恢复过程需要副本已接收或提交的事务的 GTID。缺失的事务可以使用 GTID 自动定位从源检索，它自动比较源的事务与副本的事务并识别缺失的事务。

- 对于基于文件位置的复制，恢复过程需要准确的复制 SQL 线程（应用程序）位置，显示在副本上应用的最后一个事务。基于该位置，复制 I/O 线程（接收器）从源的二进制日志检索从该点开始应在副本上应用的所有事务。

使用基于 GTID 的复制最容易配置复制以抵御意外停止。GTID 自动定位意味着副本可以可靠地识别和检索缺失的事务，即使应用事务的序列中存在间隙。

以下信息提供了适合不同类型副本的设置组合，以保证恢复（在复制控制范围内）。

> 重要
>
> 复制控制范围之外的某些因素可能会影响复制恢复过程和恢复过程后复制的总体状态。特别是，影响各个存储引擎恢复过程的设置可能导致在副本意外停止时事务丢失，因此对复制恢复过程不可用。下面列表中提到的 innodb_flush_log_at_trx_commit=1 设置是使用 InnoDB 和事务的复制设置的关键设置。但是，特定于 InnoDB 或其他存储引擎的其他设置，特别是与刷新或同步相关的设置，也可能产生影响。始终检查并应用所选存储引擎关于崩溃安全设置的建议。

副本上以下设置组合对意外停止最具弹性：

- 当使用基于 GTID 的复制时（gtid_mode=ON），设置 SOURCE_AUTO_POSITION=1，这激活到源的连接的 GTID 自动定位以自动识别和检索缺失的事务。此选项使用 CHANGE REPLICATION SOURCE TO 语句设置。如果副本有多个复制通道，需要为每个通道单独设置此选项。有关 GTID 自动定位工作原理的详细信息，请参见第 19.1.3.3 节"GTID 自动定位"。当使用基于文件位置的复制时，不使用 SOURCE_AUTO_POSITION=1，而是使用二进制日志位置或中继日志位置来控制复制的起始位置。

- 当使用基于 GTID 的复制时（gtid_mode=ON），设置 GTID_ONLY=1，这使副本在恢复过程中仅使用 GTID，并停止在复制元数据存储库中持久化二进制日志和中继日志文件名及文件位置。此选项使用 CHANGE REPLICATION SOURCE TO 语句设置。如果副本有多个复制通道，需要为每个通道单独设置此选项。使用 GTID_ONLY=1，在恢复期间，文件位置信息被忽略，GTID 自动跳过用于跳过已提供的事务，而不是识别正确的文件位置。此策略更高效，前提是使用 relay_log_purge 的默认设置清除中继日志，这意味着只需检查一个中继日志文件。

- 设置 sync_relay_log=1，这指示复制接收器线程在每个接收的事务写入中继日志后将其同步到磁盘。这意味着副本对从源的二进制日志读取的当前位置的记录（在应用程序元数据存储库中）永远不会超过中继日志中保存的事务记录。请注意，虽然此设置最安全，但由于涉及的磁盘写入次数，它也是最慢的。使用 sync_relay_log > 1 或 sync_relay_log=0（其中同步由操作系统处理），在副本意外停止时，可能存在尚未同步到磁盘的已提交事务。如果恢复的副本基于其在中继日志中作为最后同步到磁盘的信息，尝试检索和应用事务而不是跳过它们，这些事务可能导致恢复过程失败。对于多线程副本，设置 sync_relay_log=1 特别重要，其中如果无法使用中继日志中的信息填充事务序列中的间隙，恢复过程会失败。对于单线程副本，仅当相关信息在应用程序元数据存储库中不可用时，恢复过程才需要使用中继日志。

- 设置 innodb_flush_log_at_trx_commit=1，这在每个事务提交前将 InnoDB 日志同步到磁盘。此设置是默认设置，确保 InnoDB 表和 InnoDB 日志保存在磁盘上，因此不再需要中继日志中关于事务的信息。结合 sync_relay_log=1 的设置，此设置进一步确保 InnoDB 表和 InnoDB 日志的内容始终与中继日志的内容一致，以便在副本意外停止时清除中继日志文件不会导致副本事务历史中无法填充的间隙。

- 设置 relay_log_recovery = ON，这在服务器启动后立即启用自动中继日志恢复。此全局变量默认为 OFF 并在运行时为只读，但在副本意外停止后的副本启动时，可以使用 --relay-log-recovery 选项将其设置为 ON。请注意，此设置忽略现有中继日志文件，以防它们损坏或不一致。中继日志恢复过程启动新的中继日志文件并从应用程序元数据存储库中记录的复制 SQL 线程位置开始从源获取事务。先前的中继日志文件随着时间推移由副本的正常清除机制删除。

对于多线程副本，设置 relay_log_recovery = ON 自动处理已从中继日志执行的事务序列中的任何不一致和间隙。当使用基于文件位置的复制时，这些间隙可能发生。（有关更多详细信息，请参见第 19.5.1.35 节"复制和事务不一致"。）中继日志恢复过程使用与 START REPLICA UNTIL SQL_AFTER_MTS_GAPS 语句相同的方法处理间隙。当副本达到一致的无间隙状态时，中继日志恢复过程继续从复制 SQL 线程位置开始从源获取进一步的事务。当使用基于 GTID 的复制时，多线程副本首先检查 SOURCE_AUTO_POSITION 是否设置为 ON，如果是，则省略计算应跳过或不跳过的事务的步骤，以便恢复过程不需要旧的中继日志。
