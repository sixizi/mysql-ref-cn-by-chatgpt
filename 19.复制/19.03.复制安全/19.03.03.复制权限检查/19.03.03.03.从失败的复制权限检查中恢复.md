### 19.3.3.3 从复制权限检查失败中恢复

如果针对 PRIVILEGE_CHECKS_USER 账户的权限检查失败，事务将不被执行，复制通道将停止。错误的详细信息和最后应用的事务被记录在 Performance Schema 的 replication_applier_status_by_worker 表中。按照以下步骤从错误中恢复：

1. 识别导致错误的复制事件，并验证该事件是否符合预期以及是否来自可信源。您可以使用 mysqlbinlog 检索和显示在错误发生时间附近记录的事件。有关如何执行此操作的说明，请参见第 9.5 节"Point-in-Time (Incremental) Recovery"。

2. 如果复制事件不符合预期或不是来自已知的可信源，请调查原因。如果您能够确定事件发生的原因且没有安全考虑，请按照下面所述继续修复错误。

3. 如果 PRIVILEGE_CHECKS_USER 账户本应被允许执行该事务，但配置错误，请向该账户授予缺失的权限，使用 FLUSH PRIVILEGES 语句或执行 mysqladmin flush-privileges 或 mysqladmin reload 命令重新加载授权表，然后重新启动该通道的复制。

4. 如果事务需要被执行且您已验证其可信，但 PRIVILEGE_CHECKS_USER 账户通常不应具有此权限，您可以临时向 PRIVILEGE_CHECKS_USER 账户授予所需的权限。在复制事件被应用后，从该账户移除该权限，并采取任何必要的步骤以确保该事件不会再次发生（如果可以避免的话）。

5. 如果事务是仅应在源上进行而不应在副本上进行的管理操作，或仅应在单个复制组成员上进行，请在复制停止的服务器上跳过该事务，然后发出 START REPLICA 以重新启动该通道的复制。为了在将来避免这种情况，您可以在此类管理语句之前发出 SET sql_log_bin = 0，在之后发出 SET sql_log_bin = 1，以便它们不会在源上被记录。

6. 如果事务是不应在源或副本上进行的 DDL 或 DML 语句，请在复制停止的服务器上跳过该事务，在事务最初发生的服务器上手动撤销该事务，然后发出 START REPLICA 以重新启动复制。

要跳过事务，如果使用了 GTID，请提交一个具有失败事务的 GTID 的空事务，例如：

SET GTID_NEXT='aaa-bbb-ccc-ddd:N';
BEGIN;
COMMIT;
SET GTID_NEXT='AUTOMATIC';

如果未使用 GTID，请发出 SET GLOBAL sql_replica_skip_counter 语句来跳过该事件。有关使用此替代方法的说明和有关跳过事务的更多详细信息，请参见第 19.1.7.3 节"Skipping Transactions"。
