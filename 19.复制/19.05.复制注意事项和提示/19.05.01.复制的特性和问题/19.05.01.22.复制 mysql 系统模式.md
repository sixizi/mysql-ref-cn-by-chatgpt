### 19.5.1.22 复制和 MEMORY 表

当复制源服务器关闭并重新启动时，其 MEMORY 表会变为空。为了将此效果复制到副本，源在启动后第一次使用给定的 MEMORY 表时，会记录一个事件，通知副本必须通过向二进制日志写入该表的 DELETE 或 TRUNCATE TABLE 语句来清空该表。此生成的事件可通过二进制日志中的注释识别，如果服务器上使用了 GTID，它会被分配一个 GTID。该语句始终以语句格式记录，即使二进制日志格式设置为 ROW，并且即使在服务器上设置了 read_only 或 super_read_only 模式也会被写入。请注意，在源重新启动和首次使用该表之间的间隔内，副本的 MEMORY 表中仍然包含过时数据。为了避免此间隔期间对副本的直接查询可能返回陈旧数据，可以将 init_file 系统变量设置为指向一个文件，该文件包含在启动时填充源上 MEMORY 表的语句。

当副本服务器关闭并重新启动时，其 MEMORY 表会变为空。这会导致副本与源不同步，可能导致其他故障或导致副本停止：

- 从源接收的行格式更新和删除可能会失败，错误为 Can't find record in 'memory_table'。

- 诸如 INSERT INTO ... SELECT FROM memory_table 之类的语句可能会在源和副本上插入不同的行集。

副本还会向其自己的二进制日志写入 DELETE 或 TRUNCATE TABLE 语句，该语句会传递给任何下游副本，导致它们清空自己的 MEMORY 表。

重新启动复制 MEMORY 表的副本的安全方法是首先删除或清空源上 MEMORY 表中的所有行，并等待这些更改复制到副本。然后可以安全地重新启动副本。

在某些情况下，可能适用替代重新启动方法。当 binlog_format=ROW 时，如果在再次启动副本之前设置 replica_exec_mode=IDEMPOTENT，可以防止副本停止。这允许副本继续复制，但其 MEMORY 表仍然与源上的表不同。如果应用程序逻辑使得 MEMORY 表的内容可以安全丢失（例如，如果 MEMORY 表用于缓存），这是可以接受的。replica_exec_mode=IDEMPOTENT 全局应用于所有表，因此它可能会隐藏非 MEMORY 表中的其他复制错误。

（刚才描述的方法不适用于 NDB Cluster，其中 replica_exec_mode 始终为 IDEMPOTENT，无法更改。）

MEMORY 表的大小受 max_heap_table_size 系统变量的值限制，该变量不被复制（参见第 19.5.1.41 节"复制和变量"）。max_heap_table_size 的更改对在更改后使用 ALTER TABLE ... ENGINE = MEMORY 或 TRUNCATE TABLE 创建或更新的 MEMORY 表生效，或对服务器重新启动后的所有 MEMORY 表生效。如果在源上增加此变量的值而不在副本上这样做，源上的表可能会增长到大于其在副本上的对应表，导致在源上成功的插入在副本上失败，错误为 Table is full。这是一个已知问题（Bug #48666）。在这种情况下，必须在副本和源上都设置 max_heap_table_size 的全局值，然后重新启动复制。还建议重新启动源和副本 MySQL 服务器，以确保新值在每个服务器上完全生效（全局）。

有关 MEMORY 表的更多信息，请参见第 18.3 节"MEMORY 存储引擎"。
