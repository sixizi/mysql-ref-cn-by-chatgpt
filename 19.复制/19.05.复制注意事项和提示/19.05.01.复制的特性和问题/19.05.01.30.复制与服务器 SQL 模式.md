## 19.5.1.30 复制期间的副本错误

如果一条语句在源和副本上产生相同的错误（相同的错误代码），该错误会被记录，但复制继续进行。

如果一条语句在源和副本上产生不同的错误，复制 SQL 线程会终止，副本会向其错误日志写入一条消息，并等待数据库管理员决定如何处理该错误。这包括语句在源或副本上产生错误，但不是两者都产生错误的情况。要解决此问题，请手动连接到副本并确定问题的原因。SHOW REPLICA STATUS 对此很有用。然后修复问题并运行 START REPLICA。例如，在重新启动副本之前，您可能需要创建一个不存在的表。

> 注意
>
> 如果在副本的错误日志中记录了临时错误，您不一定必须采取引用的错误消息中建议的任何操作。临时错误应该由客户端重试事务来处理。例如，如果复制 SQL 线程记录了与死锁相关的临时错误，您不需要在副本上手动重新启动事务，除非复制 SQL 线程随后以非临时错误消息终止。

如果不需要此错误代码验证行为，可以使用 --replica-skip-errors 选项屏蔽（忽略）某些或所有错误。

对于 MyISAM 等非事务性存储引擎，可能会出现只部分更新表并返回错误代码的语句。例如，这可能发生在多行插入中，其中一行违反了键约束，或者如果长更新语句在更新某些行后被杀死。如果这发生在源上，副本期望语句的执行会产生相同的错误代码。如果没有，复制 SQL 线程会如前所述停止。

如果您在源和副本上使用不同存储引擎的表之间进行复制，请记住相同的语句在针对一个版本的表运行时可能会产生不同的错误，但对另一个版本不会，或者可能对一个版本的表产生错误，但对另一个版本不会。例如，由于 MyISAM 忽略外键约束，访问源上 InnoDB 表的 INSERT 或 UPDATE 语句可能会导致外键违反，但在副本上对相同表的 MyISAM 版本执行的相同语句不会产生此类错误，导致复制停止。

复制过滤规则首先被应用，在进行任何权限或行格式检查之前，这使得可以过滤掉任何验证失败的事务；对于已被过滤出的事务，不执行任何检查，因此不会引发任何错误。这意味着副本只能接受给定用户被授予访问权限的数据库部分（只要对数据库的这部分的任何更新都使用基于行的复制格式）。这在执行升级或迁移到使用管理表的系统或应用程序时可能很有帮助，入站复制用户对这些表没有访问权限。另请参见第 19.2.6 节"服务器如何评估复制过滤规则"。
