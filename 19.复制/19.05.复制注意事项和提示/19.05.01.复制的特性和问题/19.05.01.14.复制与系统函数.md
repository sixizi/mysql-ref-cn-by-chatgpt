### 19.5.1.14 复制和系统函数

某些函数在某些条件下复制效果不佳：

- USER()、CURRENT_USER()（或 CURRENT_USER）、UUID()、VERSION() 和 LOAD_FILE() 函数不加改变地进行复制，因此除非启用基于行的复制，否则在副本上不能可靠地工作。（参见第 19.2.1 节"复制格式"。）

  在使用 MIXED 模式时，USER() 和 CURRENT_USER() 会自动使用基于行的复制进行复制，在 STATEMENT 模式下会生成警告。（另见第 19.5.1.8 节"CURRENT_USER() 的复制"。）VERSION() 和 RAND() 也是如此。

- 对于 NOW()，二进制日志包含时间戳。这意味着源上此函数调用返回的值被复制到副本。为了避免在不同时区的 MySQL 服务器之间复制时出现意外结果，请在源和副本上都设置时区。有关更多信息，请参见第 19.5.1.34 节"复制和时区"。

  为了说明在位于不同时区的服务器之间复制时可能出现的问题，假设源位于纽约，副本位于斯德哥尔摩，两个服务器都使用本地时间。进一步假设在源上创建表 mytable，对该表执行 INSERT 语句，然后从表中选择，如下所示：
  ```
  mysql> CREATE TABLE mytable (mycol TEXT);
  Query OK, 0 rows affected (0.06 sec)

  mysql> INSERT INTO mytable VALUES ( NOW() );
  Query OK, 1 row affected (0.00 sec)

  mysql> SELECT * FROM mytable;
  +---------------------+
  | mycol               |
  +---------------------+
  | 2009-09-01 12:00:00 |
  +---------------------+
  1 row in set (0.00 sec)
  ```

  斯德哥尔摩的本地时间比纽约晚 6 小时；因此，如果在完全相同的时刻在副本上执行 SELECT NOW()，返回的值是 2009-09-01 18:00:00。因此，如果在刚才所示的 CREATE TABLE 和 INSERT 语句被复制后从副本的 mytable 副本中选择，你可能期望 mycol 包含值 2009-09-01 18:00:00。但情况并非如此；当从副本的 mytable 副本中选择时，你获得的结果与源上完全相同：
  ```
  mysql> SELECT * FROM mytable;
  +---------------------+
  | mycol               |
  +---------------------+
  | 2009-09-01 12:00:00 |
  +---------------------+
  1 row in set (0.00 sec)
  ```

  与 NOW() 不同，SYSDATE() 函数不是复制安全的，因为它不受二进制日志中 SET TIMESTAMP 语句的影响，并且如果使用基于语句的日志记录，则是非确定性的。如果使用基于行的日志记录，这不是问题。

  另一种方法是使用 --sysdate-is-now 选项使 SYSDATE() 成为 NOW() 的别名。必须在源和副本上都这样做才能正确工作。在这种情况下，此函数仍会发出警告，但只要在源和副本上都使用 --sysdate-is-now，就可以安全地忽略该警告。

  在使用 MIXED 模式时，SYSDATE() 会自动使用基于行的复制进行复制，在 STATEMENT 模式下会生成警告。

  另见第 19.5.1.34 节"复制和时区"。

- 以下限制仅适用于基于语句的复制，不适用于基于行的复制。处理用户级锁的 GET_LOCK()、RELEASE_LOCK()、IS_FREE_LOCK() 和 IS_USED_LOCK() 函数在副本不知道源上并发上下文的情况下进行复制。因此，这些函数不应用于插入到源表中，因为副本上的内容会有所不同。例如，不要执行诸如 INSERT INTO mytable VALUES(GET_LOCK(...)) 这样的语句。

  在使用 MIXED 模式时，这些函数会自动使用基于行的复制进行复制，在 STATEMENT 模式下会生成警告。

当基于语句的复制生效时，对于前面的限制，一个解决方法是将有问题的函数结果保存在用户变量中，并在后续语句中引用该变量。例如，以下单行 INSERT 由于引用了 UUID() 函数而有问题：
```
INSERT INTO t VALUES(UUID());
```

要解决此问题，请改为这样做：
```
SET @my_uuid = UUID();
INSERT INTO t VALUES(@my_uuid);
```

该语句序列可以复制，因为 @my_uuid 的值在 INSERT 语句之前作为用户变量事件存储在二进制日志中，可用于 INSERT。

相同的想法适用于多行插入，但使用起来更加繁琐。对于两行插入，你可以这样做：
```
SET @my_uuid1 = UUID(); @my_uuid2 = UUID();
INSERT INTO t VALUES(@my_uuid1),(@my_uuid2);
```

但是，如果行数很大或未知，解决方法就很困难或不切实际。例如，你无法将以下语句转换为与每行关联给定的单个用户变量的语句：
```
INSERT INTO t2 SELECT UUID(), * FROM t1;
```

在存储函数中，只要在函数执行期间仅调用一次 RAND()，它就能正确复制。（你可以将函数执行时间戳和随机数种子视为源和副本上相同的隐式输入。）

使用基于语句的复制，FOUND_ROWS() 和 ROW_COUNT() 函数不能可靠地复制。解决方法是将函数调用的结果存储在用户变量中，然后在 INSERT 语句中使用该变量。例如，如果你希望将结果存储在名为 mytable 的表中，你通常可能会这样做：
```
SELECT SQL_CALC_FOUND_ROWS FROM mytable LIMIT 1;
INSERT INTO mytable VALUES( FOUND_ROWS() );
```

但是，如果你正在复制 mytable，你应该使用 SELECT ... INTO，然后将变量存储在表中，如下所示：
```
SELECT SQL_CALC_FOUND_ROWS INTO @found_rows FROM mytable LIMIT 1;
INSERT INTO mytable VALUES(@found_rows);
```

这样，用户变量作为上下文的一部分进行复制，并在副本上正确应用。

在使用 MIXED 模式时，这些函数会自动使用基于行的复制进行复制，在 STATEMENT 模式下会生成警告。（Bug #12092、Bug #30244）
