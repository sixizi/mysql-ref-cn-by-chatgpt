### 19.1.6.3 副本服务器选项和变量

本节说明适用于副本服务器的服务器选项和系统变量，包含以下内容：

- 副本服务器的启动选项

- 副本服务器上使用的系统变量

复制和二进制日志选项和变量

在命令行或选项文件中指定这些选项。许多选项可以通过使用 CHANGE REPLICATION SOURCE TO 语句在服务器运行时设置。使用 SET 指定系统变量值。

**服务器 ID。** 在源和每个副本上，必须设置 server_id 系统变量以建立范围从 1 到 2³² − 1 的唯一复制 ID。"唯一"意味着每个 ID 必须与复制拓扑中任何其他源或副本使用的其他 ID 不同。示例 my.cnf 文件：

```
[mysqld]
server-id=3
```

## 副本服务器的启动选项

本节说明用于控制副本服务器的启动选项。许多这些选项可以通过使用 CHANGE REPLICATION SOURCE TO 语句在服务器运行时设置。其他选项，如 --replicate-* 选项，只能在副本服务器启动时设置。复制相关的系统变量将在本节后面讨论。

- **--master-retry-count=count**

  命令行格式：--master-retry-count=#
  已弃用：是
  类型：整数
  默认值：10
  最小值：0
  最大值（64 位平台）：18446744073709551615
  最大值（32 位平台）：4294967295

  此选项已弃用；预计将在未来的 MySQL 版本中删除。请改用 CHANGE REPLICATION SOURCE TO 语句的 SOURCE_RETRY_COUNT 选项。

- **--max-relay-log-size=size**

  命令行格式：--max-relay-log-size=#
  系统变量：max_relay_log_size
  作用域：全局
  动态：是
  SET_VAR 提示适用：否
  类型：整数
  默认值：0
  最小值：0
  最大值：1073741824
  单位：字节
  块大小：4096

  服务器自动轮换中继日志文件的大小。如果此值非零，当中继日志的大小超过此值时，中继日志会自动轮换。如果此值为零（默认值），中继日志轮换发生的大小由 max_binlog_size 的值决定。有关更多信息，请参见第 19.2.5.1 节"中继日志"。

- **--relay-log-purge={0|1}**

  命令行格式：--relay-log-purge[={OFF|ON}]
  系统变量：relay_log_purge
  作用域：全局
  动态：是
  SET_VAR 提示适用：否
  类型：布尔值
  默认值：ON

  禁用或启用中继日志的自动清除，一旦不再需要它们。默认值为 1（启用）。这是一个全局变量，可以使用 SET GLOBAL relay_log_purge = N 动态更改。在启用 --relay-log-recovery 选项时禁用中继日志清除会冒数据一致性风险，因此不是崩溃安全的。

- **--relay-log-space-limit=size**

  命令行格式：--relay-log-space-limit=#
  系统变量：relay_log_space_limit
  作用域：全局
  动态：否
  SET_VAR 提示适用：否
  类型：整数
  默认值：0
  最小值：0
  最大值：18446744073709551615
  单位：字节

  此选项对副本上所有中继日志的总大小（以字节为单位）设置上限。值为 0 表示"无限制"。这对磁盘空间有限的副本服务器主机很有用。当达到限制时，I/O（接收器）线程停止从源服务器读取二进制日志事件，直到 SQL 线程赶上并删除一些未使用的中继日志。请注意，此限制不是绝对的：在某些情况下，SQL（应用器）线程需要更多事件才能删除中继日志。在这种情况下，接收器线程会超过限制，直到应用器线程可以删除一些中继日志，因为不这样做会导致死锁。不应将 --relay-log-space-limit 设置为小于 --max-relay-log-size 值的两倍（或如果 --max-relay-log-size 为 0，则为 --max-binlog-size）。在这种情况下，接收器线程可能会因为超过 --relay-log-space-limit 而等待可用空间，但应用器线程没有中继日志可清除，无法满足接收器线程。这会强制接收器线程暂时忽略 --relay-log-space-limit。

- **--replicate-do-db=db_name**

  命令行格式：--replicate-do-db=name
  类型：字符串

  使用数据库名称创建复制过滤器。也可以使用 CHANGE REPLICATION FILTER REPLICATE_DO_DB 创建此类过滤器。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-do-db:channel_1:db_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是字面冒号。有关更多信息，请参见第 19.2.6.4 节"基于复制通道的过滤器"。

  注意

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成一致。特定于通道的复制过滤器可以用于与组复制不直接相关的复制通道，例如组成员也充当组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

此复制过滤器的精确效果取决于是否使用基于语句的复制或基于行的复制。

**基于语句的复制。** 告诉复制 SQL 线程限制复制到默认数据库（即由 USE 选择的数据库）为 db_name 的语句。要指定多个数据库，请多次使用此选项，每个数据库一次；但是，这样做不会复制跨数据库语句，例如在选择不同数据库（或不选择数据库）时 UPDATE some_db.some_table SET foo='bar'。

  警告

  要指定多个数据库，必须使用此选项的多个实例。因为数据库名称可以包含逗号，如果提供逗号分隔的列表，则该列表被视为单个数据库的名称。

使用基于语句的复制时，一个不按预期工作的示例：如果副本以 --replicate-do-db=sales 启动，并在源上发出以下语句，则不会复制 UPDATE 语句：

```
USE prices;
UPDATE sales.january SET amount=amount+1000;
```

这种"仅检查默认数据库"行为的主要原因是从语句本身很难知道是否应该复制它（例如，如果使用多表 DELETE 语句或跨多个数据库的多表 UPDATE 语句）。如果不需要，仅检查默认数据库也比检查所有数据库更快。

**基于行的复制。** 告诉复制 SQL 线程限制复制到数据库 db_name。只有属于 db_name 的表会被更改；当前数据库对此没有影响。假设副本以 --replicate-do-db=sales 启动，基于行的复制生效，然后在源上运行以下语句：

```
USE prices;
UPDATE sales.february SET amount=amount+100;
```

副本上 sales 数据库中的 february 表会根据 UPDATE 语句进行更改；无论是否发出 USE 语句，都会发生这种情况。但是，在源上发出以下语句在使用基于行的复制和 --replicate-do-db=sales 时对副本没有影响：

```
USE prices;
UPDATE prices.march SET amount=amount-25;
```

即使将 USE prices 语句更改为 USE sales，UPDATE 语句的效果仍然不会被复制。

在基于语句的复制中处理 --replicate-do-db 与基于行的复制相比的另一个重要区别发生在涉及多个数据库的语句中。假设副本以 --replicate-do-db=db1 启动，并在源上执行以下语句：

```
USE db1;
UPDATE db1.table1, db2.table2 SET db1.table1.col1 = 10, db2.table2.col2 = 20;
```

如果使用基于语句的复制，则两个表都会在副本上更新。但是，使用基于行的复制时，只有 table1 在副本上受影响；由于 table2 在不同的数据库中，副本上的 table2 不会被 UPDATE 更改。现在假设使用了 USE db4 语句而不是 USE db1 语句：

```
USE db4;
UPDATE db1.table1, db2.table2 SET db1.table1.col1 = 10, db2.table2.col2 = 20;
```

在这种情况下，使用基于语句的复制时，UPDATE 语句对副本没有影响。但是，如果使用基于行的复制，UPDATE 会更改副本上的 table1，但不会更改 table2——换句话说，只有由 --replicate-do-db 命名的数据库中的表会被更改，默认数据库的选择对此行为没有影响。

如果需要跨数据库更新工作，请改用 --replicate-wild-do-table=db_name.%。请参见第 19.2.6 节"服务器如何评估复制过滤规则"。

  注意

  此选项以与 --binlog-do-db 影响二进制日志相同的方式影响复制，复制格式对 --replicate-do-db 如何影响复制行为的影响与日志格式对 --binlog-do-db 行为的影响相同。

  此选项对 BEGIN、COMMIT 或 ROLLBACK 语句没有影响。

- **--replicate-ignore-db=db_name**

  命令行格式：--replicate-ignore-db=name
  类型：字符串

  使用数据库名称创建复制过滤器。也可以使用 CHANGE REPLICATION FILTER REPLICATE_IGNORE_DB 创建此类过滤器。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-ignore-db:channel_1:db_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是字面冒号。有关更多信息，请参见第 19.2.6.4 节"基于复制通道的过滤器"。

  注意

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成一致。特定于通道的复制过滤器可以用于与组复制不直接相关的复制通道，例如组成员也充当组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

要指定多个要忽略的数据库，请多次使用此选项，每个数据库一次。因为数据库名称可以包含逗号，如果提供逗号分隔的列表，则将其视为单个数据库的名称。

与 --replicate-do-db 一样，此过滤的精确效果取决于是否使用基于语句的复制或基于行的复制，并在接下来的几段中描述。

**基于语句的复制。** 告诉复制 SQL 线程不复制任何默认数据库（即由 USE 选择的数据库）为 db_name 的语句。

**基于行的复制。** 告诉复制 SQL 线程不更新数据库 db_name 中的任何表。默认数据库没有影响。

使用基于语句的复制时，以下示例不按预期工作。假设副本以 --replicate-ignore-db=sales 启动，并在源上发出以下语句：

```
USE prices;
UPDATE sales.january SET amount=amount+1000;
```

在这种情况下，UPDATE 语句会被复制，因为 --replicate-ignore-db 仅适用于默认数据库（由 USE 语句确定）。因为 sales 数据库在语句中明确指定，所以该语句未被过滤。但是，使用基于行的复制时，UPDATE 语句的效果不会传播到副本，副本的 sales.january 表副本保持不变；在这种情况下，--replicate-ignore-db=sales 导致对源的 sales 数据库副本中的表所做的所有更改都被副本忽略。

如果使用跨数据库更新且不希望复制这些更新，则不应使用此选项。请参见第 19.2.6 节"服务器如何评估复制过滤规则"。

如果需要跨数据库更新工作，请改用 --replicate-wild-ignore-table=db_name.%。请参见第 19.2.6 节"服务器如何评估复制过滤规则"。

  注意

  此选项以与 --binlog-ignore-db 影响二进制日志相同的方式影响复制，复制格式对 --replicate-ignore-db 如何影响复制行为的影响与日志格式对 --binlog-ignore-db 行为的影响相同。

  此选项对 BEGIN、COMMIT 或 ROLLBACK 语句没有影响。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-do-table:channel_1:db_name.tbl_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是字面冒号。请参见第 19.2.6.4 节"基于复制通道的过滤器"以获取更多信息。

  注意

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成一致。特定于通道的复制过滤器可以用于与组复制不直接相关的复制通道，例如组成员也充当组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

  此选项仅影响适用于表的语句。它不影响仅适用于其他数据库对象（如存储例程）的语句。要过滤对存储例程进行操作的语句，请使用一个或多个 --replicate-*-db 选项。

- **--replicate-ignore-table=db_name.tbl_name**

  命令行格式：--replicate-ignore-table=name
  类型：字符串

  通过告诉复制 SQL 线程不复制任何更新指定表的语句来创建复制过滤器，即使同一语句可能更新任何其他表。要指定多个要忽略的表，请多次使用此选项，每个表一次。这适用于跨数据库更新，与 --replicate-ignore-db 相反。请参见第 19.2.6 节"服务器如何评估复制过滤规则"。也可以通过发出 CHANGE REPLICATION FILTER REPLICATE_IGNORE_TABLE 语句来创建此类过滤器。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-ignore-table:channel_1:db_name.tbl_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是字面冒号。请参见第 19.2.6.4 节"基于复制通道的过滤器"以获取更多信息。

  注意

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成一致。特定于通道的复制过滤器可以用于与组复制不直接相关的复制通道，例如组成员也充当组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

  此选项仅影响适用于表的语句。它不影响仅适用于其他数据库对象（如存储例程）的语句。要过滤对存储例程进行操作的语句，请使用一个或多个 --replicate-*-db 选项。

- **--replicate-rewrite-db=from_name->to_name**

  命令行格式：--replicate-rewrite-db=old_name->new_name
  类型：字符串

  告诉副本创建复制过滤器，如果在源上是 from_name，则将指定的数据库转换为 to_name。只有涉及表的语句受影响，不包括 CREATE DATABASE、DROP DATABASE 和 ALTER DATABASE 等语句。

  要指定多个重写，请多次使用此选项。服务器使用第一个与 from_name 值匹配的。数据库名称转换在测试 --replicate-* 规则之前完成。也可以通过发出 CHANGE REPLICATION FILTER REPLICATE_REWRITE_DB 语句来创建此类过滤器。

  如果在命令行上使用 --replicate-rewrite-db 选项，且 > 字符对命令解释器特殊，请引用选项值。例如：

  ```
  $> mysqld --replicate-rewrite-db="olddb->newdb"
  ```

  --replicate-rewrite-db 选项的效果取决于用于查询的是基于语句的还是基于行的二进制日志格式。使用基于语句的格式，DML 语句根据当前数据库（由 USE 语句指定）进行转换。使用基于行的格式，DML 语句根据修改的表所在的数据库进行转换。无论二进制日志格式如何，DDL 语句始终根据当前数据库（由 USE 语句指定）进行过滤。

  为了确保重写产生预期的结果，特别是与其他复制过滤选项结合使用时，在使用 --replicate-rewrite-db 选项时遵循以下建议：

  - 在源和副本上手动创建 from_name 和 to_name 数据库，使用不同的名称。

  - 如果使用基于语句的或混合二进制日志格式，不要使用跨数据库查询，不要在查询中指定数据库名称。对于 DDL 和 DML 语句，依靠 USE 语句指定当前数据库，在查询中仅使用表名。

  - 如果仅使用基于行的二进制日志格式，对于 DDL 语句，依靠 USE 语句指定当前数据库，在查询中仅使用表名。对于 DML 语句，如果需要，可以使用完全限定的表名 (db.table)。

  如果遵循这些建议，可以安全地将 --replicate-rewrite-db 选项与表级复制过滤选项（如 --replicate-do-table）结合使用。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。指定通道名称，后跟冒号，后跟过滤器规范。第一个冒号被解释为分隔符，任何后续冒号被解释为字面冒号。例如，要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用：

  ```
  $> mysqld --replicate-rewrite-db=channel_1:db_name1->db_name2
  ```

  如果使用冒号但不指定通道名称，该选项为默认复制通道配置复制过滤器。请参见第 19.2.6.4 节"基于复制通道的过滤器"以获取更多信息。

  注意

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成一致。特定于通道的复制过滤器可以用于与组复制不直接相关的复制通道，例如组成员也充当组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

- **--replicate-same-server-id**

  命令行格式：--replicate-same-server-id[={OFF|ON}]
  类型：布尔值
  默认值：OFF

  此选项用于副本。默认值为 0（FALSE）。将此选项设置为 1（TRUE），副本不会跳过具有其自己的服务器 ID 的事件。此设置通常仅在罕见的配置中有用。

  在副本上启用二进制日志时，副本上 --replicate-same-server-id 和 --log-replica-updates 选项的组合可能会在服务器是循环复制拓扑的一部分时导致复制中的无限循环。（在 MySQL 26.7 中，二进制日志默认启用，当启用二进制日志时，副本更新日志是默认的。）但是，全局事务标识符 (GTID) 的使用通过跳过已应用的事务的执行来防止这种情况。如果在副本上设置了 gtid_mode=ON，可以使用此选项组合启动服务器，但在服务器运行时无法更改为任何其他 GTID 模式。如果设置了任何其他 GTID 模式，服务器不会使用此选项组合启动。

  默认情况下，复制 I/O（接收器）线程不会将具有副本服务器 ID 的二进制日志事件写入中继日志（此优化有助于节省磁盘使用）。如果要使用 --replicate-same-server-id，请确保在使副本读取要由复制 SQL（应用器）线程执行的自己的事件之前使用此选项启动副本。

- **--replicate-wild-do-table=db_name.tbl_name**

  命令行格式：--replicate-wild-do-table=name
  类型：字符串

  通过告诉复制 SQL（应用器）线程限制复制到任何更新的表与指定的数据库和表名模式匹配的语句来创建复制过滤器。模式可以包含 % 和 _ 通配符，它们与 LIKE 模式匹配运算符具有相同的含义。要指定多个表，请多次使用此选项，每个表一次。这适用于跨数据库更新。请参见第 19.2.6 节"服务器如何评估复制过滤规则"。也可以通过发出 CHANGE REPLICATION FILTER REPLICATE_WILD_DO_TABLE 语句来创建此类过滤器。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同的源使用特定的过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-wild-do-table:channel_1:db_name.tbl_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是字面冒号。请参见第 19.2.6.4 节"基于复制通道的过滤器"以获取更多信息。

  重要

### 19.1.6.3 副本服务器选项和变量

全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成共识。特定于通道的复制过滤器可以用于不直接涉及组复制的复制通道，例如组成员也充当来自组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

--replicate-wild-do-table 选项指定的复制过滤器适用于表、视图和触发器。它不适用于存储过程和函数或事件。要过滤对后者对象的语句，请使用一个或多个 --replicate-*-db 选项。

例如，--replicate-wild-do-table=foo%.bar% 仅复制使用数据库名称以 foo 开头且表名称以 bar 开头的表的更新。

如果表名称模式是 %，它匹配任何表名称，该选项也适用于数据库级语句（CREATE DATABASE、DROP DATABASE 和 ALTER DATABASE）。例如，如果使用 --replicate-wild-do-table=foo%.%，当数据库名称与模式 foo% 匹配时，数据库级语句会被复制。

重要

表级复制过滤器仅应用于在查询中显式提及和操作的表。它们不适用于由查询隐式更新的表。例如，GRANT 语句更新 mysql.user 系统表但不提及该表，不受指定 mysql.% 作为通配符模式的过滤器影响。

要在数据库或表名称模式中包含文字通配符字符，请用反斜杠转义它们。例如，要复制名为 my_own%db 的数据库的所有表，但不复制来自 my1ownAABCdb 数据库的表，应该像这样转义 _ 和 % 字符：--replicate-wild-do-table=my\_own\%db。如果在命令行上使用该选项，可能需要加倍反斜杠或引用选项值，具体取决于命令解释器。例如，使用 bash shell，需要输入 --replicate-wild-do-table=my\\_own\\%db。

- --replicate-wild-ignore-table=db_name.tbl_name

  命令行格式：--replicate-wild-ignore-table=name
  类型：String

  创建一个复制过滤器，防止复制 SQL 线程复制任何表与给定通配符模式匹配的语句。要指定多个要忽略的表，请多次使用此选项，每个表一次。这适用于跨数据库更新。参见第 19.2.6 节"服务器如何评估复制过滤规则"。也可以通过发出 CHANGE REPLICATION FILTER REPLICATE_WILD_IGNORE_TABLE 语句来创建此类过滤器。

  此选项支持特定于通道的复制过滤器，使多源副本能够为不同源使用特定过滤器。要在名为 channel_1 的通道上配置特定于通道的复制过滤器，请使用 --replicate-wild-ignore:channel_1:db_name.tbl_name。在这种情况下，第一个冒号被解释为分隔符，后续冒号是文字冒号。有关更多信息，请参见第 19.2.6.4 节"基于复制通道的过滤器"。

  重要

  全局复制过滤器不能用于配置为组复制的 MySQL 服务器实例，因为在某些服务器上过滤事务会使组无法就一致状态达成共识。特定于通道的复制过滤器可以用于不直接涉及组复制的复制通道，例如组成员也充当来自组外源的副本的情况。它们不能用于 group_replication_applier 或 group_replication_recovery 通道。

  例如，--replicate-wild-ignore-table=foo%.bar% 不复制使用数据库名称以 foo 开头且表名称以 bar 开头的表的更新。有关匹配工作原理的信息，请参见 --replicate-wild-do-table 选项的描述。在选项值中包含文字通配符字符的规则与 --replicate-wild-ignore-table 相同。

  重要

  表级复制过滤器仅应用于在查询中显式提及和操作的表。它们不适用于由查询隐式更新的表。例如，GRANT 语句更新 mysql.user 系统表但不提及该表，不受指定 mysql.% 作为通配符模式的过滤器影响。

  如果需要过滤掉 GRANT 语句或其他管理语句，一个可能的解决方法是使用 --replicate-ignore-db 过滤器。此过滤器对当前有效的默认数据库进行操作，由 USE 语句确定。因此，可以创建一个过滤器来忽略不被复制的数据库的语句，然后发出 USE 语句将默认数据库切换到该数据库，紧接着发出任何要忽略的管理语句。在管理语句中，命名应用该语句的实际数据库。

  例如，如果在副本服务器上配置了 --replicate-ignore-db=nonreplicated，以下语句序列会导致 GRANT 语句被忽略，因为默认数据库 nonreplicated 有效：

  USE nonreplicated;
  GRANT SELECT, INSERT ON replicated.t1 TO 'someuser'@'somehost';

- relay_log_recovery

  命令行格式：--relay-log-recovery[={OFF|ON}]
  系统变量：relay_log_recovery
  作用域：Global
  动态：No
  SET_VAR 提示适用：No
  类型：Boolean
  默认值：OFF

  如果启用，此变量在服务器启动后立即启用自动中继日志恢复。恢复过程创建一个新的中继日志文件，将 SQL（应用器）线程位置初始化为此新中继日志，并将 I/O（接收器）线程初始化为应用器线程位置。然后继续从源读取中继日志。如果使用 CHANGE REPLICATION SOURCE TO 语句为复制通道设置了 SOURCE_AUTO_POSITION=1，用于启动复制的源位置可能是在连接中接收的位置，而不是在此过程中分配的位置。

  当 relay_log_recovery 被禁用时，服务器在启动时通过执行以下操作来清理中继日志：

  - 删除日志末尾保留的任何未完成的事务

  - 删除任何仅包含未完成事务部分的中继日志文件

  - 从中继日志索引文件中删除对已删除的任何中继日志文件的任何引用

  - 当从中继日志获得有效的源位置和源文件名时，更新接收器线程的位置以匹配此文件和位置；否则，更新接收器线程的位置以匹配应用器的位置

  此全局变量在运行时为只读。其值可以在副本服务器启动时使用 --relay-log-recovery 选项设置，应在副本意外停止后使用此选项以确保不处理可能损坏的中继日志，并且必须使用此选项以保证副本是崩溃安全的。默认值为 0（禁用）。有关副本上最能抵御意外停止的设置组合的信息，请参见第 19.4.2 节"处理副本的意外停止"。

  在启动时设置 --relay-log-recovery 会自动处理已从中继日志执行的事务序列中的任何不一致和间隙。当使用基于文件位置的复制时，可能会出现这些间隙。（有关更多详情，请参见第 19.5.1.35 节"复制和事务不一致"。）中继日志恢复过程使用与 START REPLICA UNTIL SQL_AFTER_MTS_GAPS 语句相同的方法处理间隙。当副本达到一致的无间隙状态时，中继日志恢复过程继续从源开始从 SQL（应用器）线程位置获取进一步的事务。当使用基于 GTID 的复制时，多线程副本首先检查 SOURCE_AUTO_POSITION 是否设置为 ON，如果是，则省略计算应跳过或不应跳过的事务的步骤，以便恢复过程不需要旧的中继日志。

  注意

  此变量不影响以下组复制通道：

  - group_replication_applier

  - group_replication_recovery

  组上运行的任何其他通道都会受到影响，例如从外部源或另一个组复制的通道。

- **replica_parallel_workers**

  命令行格式：`--replica-parallel-workers=#`
  系统变量：`replica_parallel_workers`
  作用域：全局
  动态：是
  SET_VAR 提示适用：否
  类型：整数
  默认值：4
  最小值：1
  最大值：1024

  replica_parallel_workers 启用多线程并为使用 APPLIER_VERSION = 1 的通道设置工作线程数。对于使用 APPLIER_VERSION = 2 的新创建通道，如果省略该选项，此变量初始化 APPLIER_WORKER_COUNT。现有 Change Stream Applier 通道使用其持久化的每通道工作线程计数，当 replica_parallel_workers 更改时不会更改。

  默认值为 4，这意味着副本默认是多线程的。

  对于单个工作线程，将 replica_parallel_workers 设置为 1。

  当 replica_preserve_commit_order 为 ON（默认值）时，副本上的事务在副本上外部化的顺序与它们在副本的中继日志中出现的顺序相同。这些系统变量也为多线程设置了适当的默认值。

  要禁用并行执行，将 replica_parallel_workers 设置为 1，在这种情况下副本使用一个读取事务的协调器线程和一个应用事务的工作线程，这意味着事务按顺序应用。当 replica_parallel_workers 等于 1 时，replica_preserve_commit_order 无效且被忽略。使用一个并行工作线程，replica_preserve_commit_order 系统变量也无效。

  NDB 集群 26.7 也支持多线程副本。有关更多信息，请参见第 25.7.11 节"NDB 集群复制使用多线程应用器"。

  增加工作线程数提高了并行性的潜力。通常，这会改进性能直到某个点，超过该点增加工作线程数会因为锁争用等并发效应而降低性能。理想数量取决于硬件和工作负载；很难预测，通常必须通过测试找到。没有主键的表总是会损害性能，在具有 replica_parallel_workers > 1 的副本上可能会产生更大的负面性能影响；因此请确保所有表都有主键。

- **replica_preserve_commit_order**

  命令行格式：`--replica-preserve-commit-order[={OFF|ON}]`
  系统变量：`replica_preserve_commit_order`
  作用域：全局
  动态：是
  SET_VAR 提示适用：否
  类型：布尔值
  默认值：ON

  设置 replica_preserve_commit_order=ON 确保事务在副本上执行和提交的顺序与它们在副本的中继日志中出现的顺序相同。这防止了从副本的中继日志执行的事务序列中出现间隙，并在副本上保留与源相同的事务历史记录（受下面列出的限制）。此变量对未启用多线程的副本无效。

  在 MySQL 26.7 中，多线程默认为副本服务器启用（replica_parallel_workers=4 默认值），因此 replica_preserve_commit_order=ON 是默认值。此外，如果 replica_parallel_workers 设置为 1，则忽略 replica_preserve_commit_order 的设置，因为在这种情况下事务的顺序无论如何都会保留。

  在副本上不需要二进制日志和副本更新日志来设置 replica_preserve_commit_order=ON，如果需要可以禁用。在更改 replica_preserve_commit_order 的值之前，必须停止复制应用器线程（如果使用多个复制通道，则为所有复制通道）。

  当设置 replica_preserve_commit_order=OFF 时，多线程副本并行应用的事务可能无序提交。因此，检查最近执行的事务不能保证源的所有先前事务都已在副本上执行。从副本的中继日志执行的事务序列中可能出现间隙。这对使用多线程副本时的日志记录和恢复有影响。有关更多信息，请参见第 19.5.1.35 节"复制和事务不一致"。

  当设置 replica_preserve_commit_order=ON 时，事务在其前面的事务已为提交注册之前无法提交。使用 APPLIER_VERSION = 1，执行工作线程等待前面的事务。使用 APPLIER_VERSION = 2，应用的事务在 Change Stream Applier 调度器中等待，工作线程可以应用另一个就绪事务。提交顺序管理器保留源提交顺序。使用此模式，多线程副本永远不会进入源未处于的已提交状态。这支持将复制用于读取扩展。请参见第 19.4.5 节"使用复制进行扩展"和第 19.2.4 节"Change Stream Applier"。

  注意

  - replica_preserve_commit_order=ON 不防止源二进制日志位置滞后，其中 Exec_master_log_pos 落后于已执行事务的位置。请参见第 19.5.1.35 节"复制和事务不一致"。

  - 如果副本在其二进制日志上使用过滤器（如 --binlog-do-db），replica_preserve_commit_order=ON 不保留提交顺序和事务历史记录。

  - replica_preserve_commit_order=ON 不保留非事务性 DML 更新的顺序。这些可能在中继日志中先于它们的事务之前提交，这可能导致从副本的中继日志执行的事务序列中出现间隙。

  - 如果使用基于语句的复制，并且事务性和非事务性存储引擎参与在源上回滚的非 XA 事务，则保留副本上的提交顺序可能会受到限制。通常，在源上回滚的非 XA 事务不会复制到副本，但在这种特殊情况下，事务可能会复制到副本。如果确实发生这种情况，没有二进制日志的多线程副本不处理事务回滚，因此副本上的提交顺序与该情况下中继日志的事务顺序不同。

  - Group Replication—MySQL 8.0.41 及更高版本：当组主从外部源通过异步通道接收和应用事务，并且新成员加入组时，replica_preserve_commit_order=ON 不保证尊重非冲突事务的提交顺序。因此，可能在次要副本上存在从未在源上存在的临时状态；由于这仅涉及非冲突事务，不存在实际的分歧。

- sync_source_info

  命令行格式：--sync-source-info=#
  系统变量：sync_source_info
  作用域：Global
  动态：Yes
  SET_VAR 提示适用：No
  类型：Integer
  默认值：10000
  最小值：0
  最大值：4294967295

  sync_source_info 指定副本更新连接元数据存储库后的事件数。当连接元数据存储库存储为 InnoDB 表（默认值）时，它在此多个事件后更新。如果连接元数据存储库存储为文件（已弃用），副本会在此多个事件后将其 master.info 文件同步到磁盘（使用 fdatasync()）。默认值为 10000，零值表示存储库永远不会更新。设置此变量会立即对所有复制通道生效，包括正在运行的通道。

- terminology_use_previous

  命令行格式：--terminology-use-previous=#
  系统变量：terminology_use_previous
  作用域：Global, Session
  动态：Yes
  SET_VAR 提示适用：No
  类型：Enumeration
  默认值：NONE
  有效值：NONE

  BEFORE_8_0_26

  BEFORE_8_2_0

  在 MySQL 8.0 中对包含术语 master、slave 和 mts（"Multi-Threaded Slave"）的工具名称进行了不兼容的更改，这些术语分别更改为 source、replica 和 mta（"Multi-Threaded Applier"）。如果这些不兼容的更改影响您的应用程序，请将 terminology_use_previous 设置为 BEFORE_8_0_26，使 MySQL 服务器对前面列表中指定的对象使用旧版本的名称。这使依赖旧名称的监控工具能够继续工作，直到可以更新为使用新名称。

  MySQL 26.7 通常在 SHOW CREATE EVENT、SHOW EVENTS 的输出和针对信息架构 EVENTS 表的查询中显示 REPLICA_SIDE_DISABLED 而不是 SLAVESIDE_DISABLED。您可以通过将 terminology_use_previous 设置为 BEFORE_8_0_26 或 BEFORE_8_2_0 来改为显示 SLAVESIDE_DISABLED。

  使用会话作用域设置 terminology_use_previous 系统变量以支持单个用户，或使用全局作用域作为所有新会话的默认值。使用全局作用域时，慢查询日志包含旧版本的名称。

  受影响的工具名称在以下列表中给出。terminology_use_previous 系统变量仅影响这些项。它不影响 MySQL 8.0 中也引入的系统变量、状态变量和命令行选项的新别名，启用它时仍可使用这些别名。

  - 工具化锁（互斥体），在 mutex_instances 和 events_waits_* Performance Schema 表中可见，前缀为 wait/synch/mutex/

  - 读/写锁，在 rwlock_instances 和 events_waits_* Performance Schema 表中可见，前缀为 wait/synch/rwlock/

  - 工具化条件变量，在 cond_instances 和 events_waits_* Performance Schema 表中可见，前缀为 wait/synch/cond/

  - 工具化内存分配，在 memory_summary_* Performance Schema 表中可见，前缀为 memory/sql/

  - 线程名称，在 threads Performance Schema 表中可见，前缀为 thread/sql/

  - 线程阶段，在 events_stages_* Performance Schema 表中可见，前缀为 stage/sql/，在 threads 和 processlist Performance Schema 表、SHOW PROCESSLIST 语句的输出、信息架构 processlist 表和慢查询日志中无前缀可见

  - 线程命令，在 events_statements_history* 和 events_statements_summary_*_by_event_name Performance Schema 表中可见，前缀为 statement/com/，在 threads 和 processlist Performance Schema 表、SHOW PROCESSLIST 语句的输出、信息架构 processlist 表和 SHOW REPLICA STATUS 语句的输出中无前缀可见
