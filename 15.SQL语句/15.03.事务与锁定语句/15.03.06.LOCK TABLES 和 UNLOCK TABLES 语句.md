### 15.3.6 LOCK TABLES 和 UNLOCK TABLES 语句

```
LOCK {TABLE | TABLES}
    tbl_name [[AS] alias] lock_type
    [, tbl_name [[AS] alias] lock_type] ...

lock_type: {
    READ [LOCAL]
  | WRITE
}

UNLOCK {TABLE | TABLES}
```

MySQL 使客户端会话能够显式获取表锁，以便与其他会话协作访问表，或在会话需要独占访问表的期间防止其他会话修改表。一个会话只能为自己获取或释放锁。一个会话不能为另一个会话获取锁或释放另一个会话持有的锁。

锁可用于模拟事务或在更新表时获得更快的速度。这在表锁定限制和条件中有更详细的说明。

LOCK TABLES 为当前客户端会话显式获取表锁。表锁可以为基表或视图获取。您必须具有 LOCK TABLES 权限，以及要锁定的每个对象的 SELECT 权限。

对于视图锁定，LOCK TABLES 将视图中使用的所有基表添加到要锁定的表集合中，并自动锁定它们。对于任何被锁定视图的基础表，LOCK TABLES 检查视图定义者（对于 SQL SECURITY DEFINER 视图）或调用者（对于所有视图）是否对这些表具有适当的权限。

如果使用 LOCK TABLES 显式锁定表，触发器中使用的任何表也会隐式锁定，如 LOCK TABLES 和触发器中所述。

如果使用 LOCK TABLES 显式锁定表，外键约束相关的任何表也会隐式打开和锁定。对于外键检查，在相关表上采用共享只读锁（LOCK TABLES READ）。对于级联更新，在涉及该操作的相关表上采用共享无锁写锁（LOCK TABLES WRITE）。

UNLOCK TABLES 显式释放当前会话持有的任何表锁。LOCK TABLES 在获取新锁之前隐式释放当前会话持有的任何表锁。

UNLOCK TABLES 的另一个用途是释放使用 FLUSH TABLES WITH READ LOCK 语句获取的全局读锁，这使您能够锁定所有数据库中的所有表。请参阅第 15.7.8.3 节"FLUSH 语句"。（如果您有 Veritas 等可以进行时间点快照的文件系统，这是获取备份的一种非常便捷的方式。）

LOCK TABLE 是 LOCK TABLES 的同义词；UNLOCK TABLE 是 UNLOCK TABLES 的同义词。

表锁仅防止其他会话的不当读取或写入。持有 WRITE 锁的会话可以执行表级操作，如 DROP TABLE 或 TRUNCATE TABLE。对于持有 READ 锁的会话，不允许 DROP TABLE 和 TRUNCATE TABLE 操作。

以下讨论仅适用于非 TEMPORARY 表。LOCK TABLES 对 TEMPORARY 表是允许的（但被忽略）。该表可以由创建它的会话自由访问，无论可能生效的其他锁定如何。不需要锁，因为没有其他会话可以看到该表。

## 表锁获取

要在当前会话中获取表锁，请使用 LOCK TABLES 语句，该语句获取元数据锁（请参阅第 10.11.4 节"元数据锁定"）。

以下锁类型可用：

READ [LOCAL] 锁：

- 持有锁的会话可以读取表（但不能写入）。

- 多个会话可以同时为表获取 READ 锁。

- 其他会话可以读取表，无需显式获取 READ 锁。

- LOCAL 修饰符使其他会话能够执行不冲突的 INSERT 语句（并发插入），同时持有锁。（请参阅第 10.11.3 节"并发插入"。）但是，如果您在持有锁时将使用服务器外部的进程操作数据库，则不能使用 READ LOCAL。对于 InnoDB 表，READ LOCAL 与 READ 相同。

WRITE 锁：

- 持有锁的会话可以读取和写入表。

- 只有持有锁的会话可以访问表。在释放锁之前，其他会话都无法访问它。

- 其他会话对表的锁请求在持有 WRITE 锁时会阻塞。

WRITE 锁通常比 READ 锁具有更高的优先级，以确保尽快处理更新。这意味着如果一个会话获取 READ 锁，然后另一个会话请求 WRITE 锁，后续 READ 锁请求将等待，直到请求 WRITE 锁的会话获取锁并释放它。（对于 max_write_lock_count 系统变量的较小值，此策略可能有例外；请参阅第 10.11.4 节"元数据锁定"。）

如果 LOCK TABLES 语句必须等待其他会话对任何表持有的锁，它将阻塞，直到可以获取所有锁。

需要锁的会话必须在单个 LOCK TABLES 语句中获取它需要的所有锁。持有这些获取的锁时，会话只能访问锁定的表。例如，在以下语句序列中，尝试访问 t2 时会出现错误，因为它未在 LOCK TABLES 语句中锁定：

```
mysql> LOCK TABLES t1 READ;
mysql> SELECT COUNT(*) FROM t1;
+----------+
| COUNT(*) |
+----------+
|        3 |
+----------+
mysql> SELECT COUNT(*) FROM t2;
ERROR 1100 (HY000): Table 't2' was not locked with LOCK TABLES
```

INFORMATION_SCHEMA 数据库中的表是例外。即使会话持有使用 LOCK TABLES 获取的表锁，也可以在不显式锁定的情况下访问它们。

在单个查询中，不能使用相同的名称多次引用锁定的表。改用别名，并为表和每个别名获取单独的锁：

```
mysql> LOCK TABLE t WRITE, t AS t1 READ;
mysql> INSERT INTO t SELECT * FROM t;
ERROR 1100: Table 't' was not locked with LOCK TABLES
mysql> INSERT INTO t SELECT * FROM t AS t1;
```

第一个 INSERT 出现错误是因为对锁定表的同一名称有两个引用。第二个 INSERT 成功是因为对表的引用使用不同的名称。

如果您的语句通过别名引用表，您必须使用该相同的别名锁定表。不使用别名锁定表是行不通的：

```
mysql> LOCK TABLE t READ;
mysql> SELECT * FROM t AS myalias;
ERROR 1100: Table 'myalias' was not locked with LOCK TABLES
```

反之，如果使用别名锁定表，您必须在语句中使用该别名引用它：

```
mysql> LOCK TABLE t AS myalias READ;
mysql> SELECT * FROM t;
ERROR 1100: Table 't' was not locked with LOCK TABLES
mysql> SELECT * FROM t AS myalias;
```

## 表锁释放

当会话持有的表锁被释放时，它们同时全部释放。会话可以显式释放其锁，或在某些条件下隐式释放锁。

- 会话可以使用 UNLOCK TABLES 显式释放其锁。

- 如果会话在已持有锁的情况下发出 LOCK TABLES 语句以获取锁，其现有锁在授予新锁之前隐式释放。

- 如果会话开始事务（例如，使用 START TRANSACTION），执行隐式 UNLOCK TABLES，导致现有锁被释放。（有关表锁定和事务之间交互的其他信息，请参阅表锁定和事务的交互。）

如果客户端会话的连接正常或异常终止，服务器隐式释放会话持有的所有表锁（事务性和非事务性）。如果客户端重新连接，锁不再生效。此外，如果客户端有活跃事务，服务器在断开连接时回滚事务，如果重新连接，新会话以启用自动提交开始。因此，客户端可能希望禁用自动重新连接。启用自动重新连接后，如果重新连接发生，客户端不会收到通知，但任何表锁或当前事务都会丢失。禁用自动重新连接后，如果连接断开，发出的下一个语句会出现错误。客户端可以检测错误并采取适当的操作，如重新获取锁或重做事务。请参阅自动重新连接控制。

注意

如果对锁定的表使用 ALTER TABLE，它可能变为解锁。例如，如果尝试第二个 ALTER TABLE 操作，结果可能是错误"Table 'tbl_name' was not locked with LOCK TABLES"。要处理此问题，在第二次更改之前再次锁定表。另请参阅第 B.3.6.1 节"ALTER TABLE 的问题"。

## 表锁定和事务的交互

LOCK TABLES 和 UNLOCK TABLES 与事务的使用交互如下：

- LOCK TABLES 不是事务安全的，在尝试锁定表之前隐式提交任何活跃事务。

- UNLOCK TABLES 隐式提交任何活跃事务，但仅当已使用 LOCK TABLES 获取表锁时。例如，在以下语句集中，UNLOCK TABLES 释放全局读锁，但不提交事务，因为没有表锁生效：

```
FLUSH TABLES WITH READ LOCK;
START TRANSACTION;
SELECT ... ;
UNLOCK TABLES;
```

- 开始事务（例如，使用 START TRANSACTION）隐式提交任何当前事务并释放现有表锁。

- FLUSH TABLES WITH READ LOCK 获取全局读锁而不是表锁，因此不受与 LOCK TABLES 和 UNLOCK TABLES 相同的表锁定和隐式提交行为的约束。例如，START TRANSACTION 不释放全局读锁。请参阅第 15.7.8.3 节"FLUSH 语句"。

- 隐式导致事务提交的其他语句不释放现有表锁。有关此类语句的列表，请参阅第 15.3.3 节"导致隐式提交的语句"。

- 使用事务性表（如 InnoDB 表）的 LOCK TABLES 和 UNLOCK TABLES 的正确方法是使用 SET autocommit = 0（不是 START TRANSACTION）开始事务，然后是 LOCK TABLES，并在显式提交事务之前不调用 UNLOCK TABLES。例如，如果需要写入表 t1 并从表 t2 读取，可以这样做：

```
SET autocommit=0;
LOCK TABLES t1 WRITE, t2 READ, ...;
... do something with tables t1 and t2 here ...
COMMIT;
UNLOCK TABLES;
```

当调用 LOCK TABLES 时，InnoDB 在内部获取自己的表锁，MySQL 获取自己的表锁。InnoDB 在下一次提交时释放其内部表锁，但为了让 MySQL 释放其表锁，您必须调用 UNLOCK TABLES。您不应该有 autocommit = 1，因为那样 InnoDB 会在调用 LOCK TABLES 后立即释放其内部表锁，死锁很容易发生。如果 autocommit = 1，InnoDB 根本不获取内部表锁，以帮助旧应用程序避免不必要的死锁。

- ROLLBACK 不释放表锁。

## LOCK TABLES 和触发器

如果使用 LOCK TABLES 显式锁定表，触发器中使用的任何表也会隐式锁定：

- 锁与使用 LOCK TABLES 语句显式获取的锁同时获取。

- 触发器中使用的表上的锁取决于该表是否仅用于读取。如果是，读锁就足够了。否则，使用写锁。

- 如果使用 LOCK TABLES 为读取显式锁定表，但由于可能在触发器中修改而需要为写入锁定，则采用写锁而不是读锁。（即，由于表在触发器中出现而需要的隐式写锁导致表的显式读锁请求转换为写锁请求。）

假设使用此语句锁定两个表 t1 和 t2：

```
LOCK TABLES t1 WRITE, t2 READ;
```

如果 t1 或 t2 有任何触发器，触发器中使用的表也会被锁定。假设 t1 有这样定义的触发器：

```
CREATE TRIGGER t1_a_ins AFTER INSERT ON t1 FOR EACH ROW
BEGIN
  UPDATE t4 SET count = count+1
      WHERE id = NEW.id AND EXISTS (SELECT a FROM t3);
  INSERT INTO t2 VALUES(1, 2);
END;
```

LOCK TABLES 语句的结果是 t1 和 t2 被锁定，因为它们出现在语句中，t3 和 t4 被锁定，因为它们在触发器中使用：

- t1 根据 WRITE 锁请求为写入锁定。

- t2 为写入锁定，即使请求是 READ 锁。这是因为 t2 在触发器中被插入，所以 READ 请求转换为 WRITE 请求。

- t3 为读取锁定，因为它仅在触发器中读取。

- t4 为写入锁定，因为它可能在触发器中更新。

## 表锁定限制和条件

您可以安全地使用 KILL 终止等待表锁的会话。请参阅第 15.7.8.4 节"KILL 语句"。

LOCK TABLES 和 UNLOCK TABLES 不能在存储程序中使用。

performance_schema 数据库中的表不能使用 LOCK TABLES 锁定，除了 setup_xxx 表。

LOCK TABLES 生成的锁的范围是单个 MySQL 服务器。它与 NDB Cluster 不兼容，NDB Cluster 无法在多个 mysqld 实例中强制执行 SQL 级锁。您可以在 API 应用程序中改为强制执行锁定。有关更多信息，请参阅第 25.2.7.10 节"与多个 NDB Cluster 节点相关的限制"。

LOCK TABLES 语句生效时禁止以下语句：CREATE TABLE、CREATE TABLE ... LIKE、CREATE VIEW、DROP VIEW 以及存储函数、过程和事件上的 DDL 语句。

对于某些操作，必须访问 mysql 数据库中的系统表。例如，HELP 语句需要服务器端帮助表的内容，CONVERT_TZ() 可能需要读取时区表。服务器根据需要隐式锁定系统表以供读取，因此您无需显式锁定它们。这些表的处理方式如下所述：

- mysql.help_category

- mysql.help_keyword

- mysql.help_relation

- mysql.help_topic

- mysql.time_zone

- mysql.time_zone_leap_second

- mysql.time_zone_name

- mysql.time_zone_transition

- mysql.time_zone_transition_type

如果要使用 LOCK TABLES 语句在这些表中的任何一个上显式放置 WRITE 锁，该表必须是唯一锁定的表；同一语句中不能锁定其他表。

通常，您不需要锁定表，因为所有单个 UPDATE 语句都是原子的；没有其他会话可以干扰任何其他当前执行的 SQL 语句。但是，在某些情况下，锁定表可能会提供优势：

- 如果要对一组 MyISAM 表运行许多操作，锁定要使用的表会快得多。锁定 MyISAM 表加快了对它们的插入、更新或删除，因为 MySQL 不会刷新锁定表的键缓存，直到调用 UNLOCK TABLES。通常，键缓存在每个 SQL 语句后刷新。

  锁定表的缺点是没有会话可以更新 READ 锁定的表（包括持有锁的表），也没有会话可以访问 WRITE 锁定的表，除了持有锁的表。

- 如果使用非事务性存储引擎的表，如果要确保在 SELECT 和 UPDATE 之间没有其他会话修改表，必须使用 LOCK TABLES。此处显示的示例需要 LOCK TABLES 才能安全执行：

```
LOCK TABLES trans READ, customer WRITE;
SELECT SUM(value) FROM trans WHERE customer_id=some_id;
UPDATE customer
  SET total_value=sum_from_previous_statement
  WHERE customer_id=some_id;
UNLOCK TABLES;
```

没有 LOCK TABLES，另一个会话可能在 SELECT 和 UPDATE 语句执行之间在 trans 表中插入新行。

在许多情况下，您可以通过使用相对更新（UPDATE customer SET value=value+new_value）或 LAST_INSERT_ID() 函数来避免使用 LOCK TABLES。

您还可以在某些情况下通过使用用户级别的咨询锁函数 GET_LOCK() 和 RELEASE_LOCK() 来避免锁定表。这些锁保存在服务器中的哈希表中，并使用 pthread_mutex_lock() 和 pthread_mutex_unlock() 实现以获得高速。请参阅第 14.14 节"锁定函数"。

有关锁定策略的更多信息，请参阅第 10.11.1 节"内部锁定方法"。
