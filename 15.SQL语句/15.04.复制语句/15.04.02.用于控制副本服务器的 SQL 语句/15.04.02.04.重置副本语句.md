### 15.4.2.4 START REPLICA 语句

```
START REPLICA [thread_types] [until_option] [connection_options] [channel_option]

thread_types:
    [thread_type [, thread_type] ... ]

thread_type:
    IO_THREAD | SQL_THREAD

until_option:
    UNTIL {   {SQL_BEFORE_GTIDS | SQL_AFTER_GTIDS} = gtid_set
          |   SOURCE_LOG_FILE = 'log_name', SOURCE_LOG_POS = log_pos
          |   RELAY_LOG_FILE = 'log_name', RELAY_LOG_POS = log_pos
          |   SQL_AFTER_MTS_GAPS }

connection_options:
    [USER='user_name'] [PASSWORD='user_pass'] [DEFAULT_AUTH='plugin_name'] [PLUGIN_DIR='plugin_dir']

channel_option:
    FOR CHANNEL channel

gtid_set:
    uuid_set [, uuid_set] ...
    | ''

uuid_set:
    uuid:interval[:interval]...

uuid:
    hhhhhhhh-hhhh-hhhh-hhhh-hhhhhhhhhhhh

h:
    [0-9,A-F]

interval:
    n[-n]

    (n >= 1)
```

START REPLICA 启动复制线程，可以一起启动或分别启动。

START REPLICA 需要 REPLICATION_SLAVE_ADMIN 权限（或已弃用的 SUPER 权限）。START REPLICA 会导致正在进行的事务隐式提交。参见第 15.3.3 节"导致隐式提交的语句"。

对于线程类型选项，你可以指定 IO_THREAD、SQL_THREAD、两者都指定或都不指定。只有被启动的线程会受到该语句的影响。

- 不带线程类型选项的 START REPLICA 启动所有复制线程，带有两个线程类型选项的 START REPLICA 也是如此。

- IO_THREAD 启动复制接收器线程，该线程从源服务器读取事件并将其存储在中继日志中。

- SQL_THREAD 启动复制应用器线程，该线程从中继日志读取事件并执行它们。副本使用协调器线程和多个应用器线程应用事务，SQL_THREAD 启动所有这些线程。

重要

START REPLICA 在所有复制线程启动后向用户发送确认。但是，复制接收器线程可能尚未成功连接到源服务器，或应用器线程可能在启动后立即应用事件时停止。START REPLICA 在线程启动后不继续监视它们，因此如果它们随后停止或无法连接，不会向你发出警告。你必须检查副本的错误日志以查看复制线程生成的错误消息，或使用 SHOW REPLICA STATUS 检查它们是否正常运行。成功的 START REPLICA 语句会导致 SHOW REPLICA STATUS 显示 Replica_SQL_Running=Yes，但可能显示也可能不显示 Replica_IO_Running=Yes，因为只有当接收器线程既在运行又已连接时才显示 Replica_IO_Running=Yes。有关更多信息，参见第 19.1.7.1 节"检查复制状态"。

可选的 FOR CHANNEL channel 子句使你能够指定该语句应用于哪个复制通道。提供 FOR CHANNEL channel 子句会将 START REPLICA 语句应用于特定的复制通道。如果未指定子句且不存在额外通道，该语句应用于默认通道。如果在使用多个通道时 START REPLICA 语句未定义通道，该语句会为所有通道启动指定的线程。参见第 19.2.2 节"复制通道"了解更多信息。

Group Replication 的复制通道（group_replication_applier 和 group_replication_recovery）由服务器实例自动管理。START REPLICA 根本不能与 group_replication_recovery 通道一起使用，仅当 Group Replication 未运行时才应与 group_replication_applier 通道一起使用。group_replication_applier 通道仅有应用器线程，没有接收器线程，因此如果需要，可以使用 SQL_THREAD 选项而不使用 IO_THREAD 选项来启动它。

START REPLICA 支持可插拔的用户密码认证（参见第 8.2.17 节"可插拔认证"），使用 USER、PASSWORD、DEFAULT_AUTH 和 PLUGIN_DIR 选项，如下列表所述。使用这些选项时，你必须启动接收器线程（IO_THREAD 选项）或所有复制线程；你不能单独启动复制应用器线程（SQL_THREAD 选项）。

| 选项 | 说明 |
|------|------|
| USER | 账户的用户名。如果使用了 PASSWORD，则必须设置此项。该选项不能设置为空字符串或 null。 |
| PASSWORD | 指定用户账户的密码。 |
| DEFAULT_AUTH | 认证插件的名称。默认为 MySQL 原生认证。 |
| PLUGIN_DIR | 认证插件的位置。 |

重要

使用 START REPLICA 设置的密码在写入 MySQL Server 的日志、Performance Schema 表和 SHOW PROCESSLIST 语句时会被掩盖。但是，它以明文形式通过连接发送到副本服务器实例。为了保护传输中的密码，请使用 SSL/TLS 加密、SSH 隧道或其他方法保护副本服务器实例与用于发出 START REPLICA 的客户端之间的连接免受未授权查看。

UNTIL 子句使副本启动复制，然后处理事务直到你在 UNTIL 子句中指定的点，然后再次停止。UNTIL 子句可用于使副本继续进行直到你想要跳过的不需要的事务之前的点，然后跳过该事务，如第 19.1.7.3 节"跳过事务"所述。要识别事务，你可以使用 mysqlbinlog 处理源的二进制日志或副本的中继日志，或使用 SHOW BINLOG EVENTS 语句。

你也可以使用 UNTIL 子句来调试复制，一次处理一个事务或分段处理。如果你使用 UNTIL 子句来执行此操作，请使用 --skip-replica-start 启动副本以防止 SQL 线程在副本服务器启动时运行。在过程完成后删除该选项或系统变量设置，以防在意外服务器重启时被遗忘。

SHOW REPLICA STATUS 语句包括显示 UNTIL 条件当前值的输出字段。UNTIL 条件在受影响的线程仍在运行时持续存在，并在它们停止时被移除。

UNTIL 子句在复制应用器线程（SQL_THREAD 选项）上运行。你可以使用 SQL_THREAD 选项或让副本默认启动两个线程。如果单独使用 IO_THREAD 选项，UNTIL 子句会被忽略，因为应用器线程未启动。

对于配置了 APPLIER_VERSION = 2 的通道，Change Stream Applier 仅支持 SQL_BEFORE_GTIDS 和 SQL_AFTER_GTIDS UNTIL 条件。对此类通道使用 SOURCE_LOG_FILE、SOURCE_LOG_POS、RELAY_LOG_FILE、RELAY_LOG_POS 或 SQL_AFTER_MTS_GAPS 会导致语句失败。

你在 UNTIL 子句中指定的点可以是以下选项中的任何一个（且仅限一个）：

| 选项 | 说明 |
|------|------|
| SOURCE_LOG_FILE 和 SOURCE_LOG_POS | 这些选项使复制应用器处理事务直到其中继日志中的一个位置，该位置由源服务器上二进制日志中对应点的文件名和文件位置标识。应用器线程找到指定位置处或之后的最近事务边界，完成应用该事务，然后停止。对于压缩的事务负载，指定压缩 Transaction_payload_event 的结束位置。这些选项仍然可以在 CHANGE REPLICATION SOURCE TO 语句上设置了 GTID_ONLY 选项时使用，以停止复制通道在复制元数据存储库中持久化文件名和文件位置。文件名和文件位置在内存中被跟踪。 |
| RELAY_LOG_FILE 和 RELAY_LOG_POS | 这些选项使复制应用器处理事务直到副本的中继日志中的一个位置，该位置由中继日志文件名和该文件中的位置标识。应用器线程找到指定位置处或之后的最近事务边界，完成应用该事务，然后停止。对于压缩的事务负载，指定压缩 Transaction_payload_event 的结束位置。这些选项仍然可以在 CHANGE REPLICATION SOURCE TO 语句上设置了 GTID_ONLY 选项时使用，以停止复制通道在复制元数据存储库中持久化文件名和文件位置。文件名和文件位置在内存中被跟踪。 |
| SQL_BEFORE_GTIDS | 此选项使复制应用器开始处理事务，并在遇到指定 GTID 集中的任何事务时停止。来自 GTID 集的遇到的事务不被应用，GTID 集中的任何其他事务也不被应用。该选项以包含一个或多个全局事务标识符的 GTID 集作为参数（参见 GTID 集）。GTID 集中的事务不一定按其 GTID 的顺序出现在复制流中，因此应用器停止的事务不一定是最早的。 |
| SQL_AFTER_GTIDS | 此选项使复制应用器开始处理事务，并在处理完指定 GTID 集中的所有事务后停止。该选项以包含一个或多个全局事务标识符的 GTID 集作为参数（参见 GTID 集）。使用 SQL_AFTER_GTIDS，复制线程在处理完 GTID 集中的所有事务后停止。事务按接收顺序处理，因此可能包括不属于 GTID 集但在集中的所有事务都被提交之前被接收（和处理）的事务。例如，执行 START REPLICA UNTIL SQL_AFTER_GTIDS = 3E11FA47-71CA-11E1-9E33-C80AA9429562:11-56 会导致副本从源获取（和处理）所有事务，直到所有具有序列号 11 到 56 的事务都被处理，然后停止而不处理该点之后的任何其他事务。 |
| SQL_AFTER_MTS_GAPS | 此选项使副本处理事务直到中继日志中执行的事务序列中没有更多间隙的点。使用多线程副本时，在以下情况下可能出现间隙：协调器线程被停止。应用器线程中发生错误。mysqld 意外关闭。当复制通道有间隙时，副本的数据库处于可能从未在源上存在过的状态。副本在内部跟踪间隙，并禁止会删除间隙信息的 CHANGE REPLICATION SOURCE TO 语句（如果它们执行的话）。所有副本默认都是多线程的。当副本上的 replica_preserve_commit_order=ON（默认值）时，除了此变量的说明中列出的特定情况外，不应出现间隙。如果 replica_preserve_commit_order 为 OFF，事务的提交顺序不被保留，因此出现间隙的可能性要大得多。 |
