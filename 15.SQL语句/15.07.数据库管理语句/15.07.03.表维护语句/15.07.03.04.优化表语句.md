### 15.7.3.4 OPTIMIZE TABLE 语句

```
OPTIMIZE [NO_WRITE_TO_BINLOG | LOCAL]
    TABLE tbl_name [, tbl_name] ...
```

OPTIMIZE TABLE 重新组织表数据和关联索引数据的物理存储，以减少存储空间并提高访问表时的 I/O 效率。对每个表所做的确切更改取决于该表使用的存储引擎。

根据表的类型，在以下情况下使用 OPTIMIZE TABLE：

- 在具有自己的 .ibd 文件的 InnoDB 表上执行大量插入、更新或删除操作后（因为它是在启用 innodb_file_per_table 选项的情况下创建的）。表和索引被重新组织，磁盘空间可以被回收供操作系统使用。

- 在 InnoDB 表中对属于 FULLTEXT 索引的列执行大量插入、更新或删除操作后。首先设置配置选项 innodb_optimize_fulltext_only=1。为了将索引维护周期保持在合理的时间内，设置 innodb_ft_num_word_optimize 选项以指定要在搜索索引中更新多少个单词，并运行一系列 OPTIMIZE TABLE 语句，直到搜索索引完全更新。

- 删除 MyISAM 或 ARCHIVE 表的大部分内容后，或对具有可变长度行的 MyISAM 或 ARCHIVE 表进行许多更改后（具有 VARCHAR、VARBINARY、BLOB 或 TEXT 列的表）。已删除的行在链表中维护，后续的 INSERT 操作重用旧的行位置。您可以使用 OPTIMIZE TABLE 回收未使用的空间并对数据文件进行碎片整理。在对表进行大量更改后，此语句还可能改进使用该表的语句的性能，有时会显著改进。

此语句需要对表的 SELECT 和 INSERT 权限。

OPTIMIZE TABLE 适用于 InnoDB、MyISAM 和 ARCHIVE 表。OPTIMIZE TABLE 也支持内存中 NDB 表的动态列。它不适用于内存表的固定宽度列，也不适用于磁盘数据表。NDB Cluster 表上 OPTIMIZE 的性能可以使用 --ndb-optimization-delay 进行调整，该选项控制 OPTIMIZE TABLE 处理行批次之间的等待时间长度。

对于 NDB Cluster 表，OPTIMIZE TABLE 可以被中断（例如）通过终止执行 OPTIMIZE 操作的 SQL 线程。

默认情况下，OPTIMIZE TABLE 不适用于使用任何其他存储引擎创建的表，并返回指示缺乏支持的结果。您可以通过使用 --skip-new 选项启动 mysqld 来使 OPTIMIZE TABLE 适用于其他存储引擎。在这种情况下，OPTIMIZE TABLE 只是映射到 ALTER TABLE。

此语句不适用于视图。

OPTIMIZE TABLE 支持分区表。有关将此语句与分区表和表分区一起使用的信息，请参见第 26.3.4 节"分区的维护"。

默认情况下，服务器将 OPTIMIZE TABLE 语句写入二进制日志，以便它们复制到副本。要禁止日志记录，请指定可选的 NO_WRITE_TO_BINLOG 关键字或其别名 LOCAL。您必须具有 OPTIMIZE_LOCAL_TABLE 权限才能使用此选项。

## OPTIMIZE TABLE 输出

OPTIMIZE TABLE 返回一个结果集，其列如下表所示。

| 列 | 值 |
|---|---|
| Table | 表名 |
| Op | 始终为 optimize |
| Msg_type | status、error、info、note 或 warning |
| Msg_text | 信息消息 |

OPTIMIZE TABLE table 捕获并抛出在将表统计信息从旧文件复制到新创建的文件时发生的任何错误。例如，如果 .MYD 或 .MYI 文件所有者的用户 ID 与 mysqld 进程的用户 ID 不同，OPTIMIZE TABLE 会生成"无法更改文件所有权"错误，除非 mysqld 由 root 用户启动。

## InnoDB 详情

对于 InnoDB 表，OPTIMIZE TABLE 映射到 ALTER TABLE ... FORCE，它重建表以更新索引统计信息并释放聚集索引中的未使用空间。当您在 InnoDB 表上运行它时，这会显示在 OPTIMIZE TABLE 的输出中，如下所示：

```
mysql> OPTIMIZE TABLE foo;
+----------+----------+----------+-------------------------------------------------------------------+
| Table    | Op       | Msg_type | Msg_text                                                          |
+----------+----------+----------+-------------------------------------------------------------------+
| test.foo | optimize | note     | Table does not support optimize, doing recreate + analyze instead |
| test.foo | optimize | status   | OK                                                                |
+----------+----------+----------+-------------------------------------------------------------------+
```

OPTIMIZE TABLE 对常规和分区 InnoDB 表使用在线 DDL，这减少了并发 DML 操作的停机时间。由 OPTIMIZE TABLE 触发的表重建在原地完成。排他表锁仅在操作的准备阶段和提交阶段短暂获取。在准备阶段，元数据被更新并创建中间表。在提交阶段，表元数据更改被提交。

OPTIMIZE TABLE 在以下条件下使用表复制方法重建表：

- 当启用 old_alter_table 系统变量时。

- 当服务器使用 --skip-new 选项启动时。

OPTIMIZE TABLE 使用在线 DDL 不支持包含 FULLTEXT 索引的 InnoDB 表。改用表复制方法。

InnoDB 使用页面分配方法存储数据，不会以与旧存储引擎（如 MyISAM）相同的方式遭受碎片化。在考虑是否运行优化时，请考虑服务器预期处理的事务工作负载：

- 某种程度的碎片化是预期的。InnoDB 仅填充 93% 的页面，为不必分割页面的更新留出空间。

- 删除操作可能会留下间隙，使页面填充不如所需的那样充分，这可能值得优化表。

- 行更新通常在同一页面内重写数据，取决于数据类型和行格式，当有足够的空间可用时。请参见第 17.9.1.5 节"InnoDB 表压缩的工作原理"和第 17.10 节"InnoDB 行格式"。

- 高并发工作负载可能会随着时间的推移在索引中留下间隙，因为 InnoDB 通过其 MVCC 机制保留相同数据的多个版本。请参见第 17.3 节"InnoDB 多版本控制"。

## MyISAM 详情

对于 MyISAM 表，OPTIMIZE TABLE 的工作方式如下：

1. 如果表有已删除或分割的行，修复表。

2. 如果索引页未排序，对其进行排序。

3. 如果表的统计信息不是最新的（并且修复无法通过排序索引来完成），更新它们。

## 其他注意事项

OPTIMIZE TABLE 对常规和分区 InnoDB 表在线执行。否则，MySQL 在 OPTIMIZE TABLE 运行期间锁定表。

OPTIMIZE TABLE 不排序 R-tree 索引，例如 POINT 列上的空间索引。（Bug #23578）
