# 3.5 MySQL 8.0 中的变化

升级到 MySQL 8.0 前，应阅读本节，识别适用于当前安装和应用程序的变化，并执行所有建议操作。

标记为“不兼容变化”的条目与较早的 MySQL 版本不兼容，升级前可能需要处理。官方尽量避免这类变化，但有时为了修复比版本间不兼容更严重的问题，它们是必要的。

## 数据字典变化

MySQL Server 8.0 引入全局数据字典，在事务表中存储数据库对象信息。在以前的 MySQL 系列中，字典数据存储在元数据文件和非事务系统表中。因此，升级过程要求通过特定前置检查确认安装已准备好升级。参见 [3.6 为升级准备安装](./03.06.为升级准备安装.md)。

启用数据字典的服务器在运维上也存在一些差异，例如某些元数据文件不再存在、部分 `INFORMATION_SCHEMA` 查询方式变化等。

## `caching_sha2_password` 成为首选认证插件

`caching_sha2_password` 和 `sha256_password` 提供比 `mysql_native_password` 更安全的密码加密，而 `caching_sha2_password` 又比 `sha256_password` 性能更好。因此，MySQL 8.0 将 `caching_sha2_password` 设为首选和默认认证插件，而不是 `mysql_native_password`。

该变化影响服务器和 `libmysqlclient` 客户端库：

- 服务器端 `default_authentication_plugin` 的默认值从 `mysql_native_password` 变为 `caching_sha2_password`。
- `libmysqlclient` 也把 `caching_sha2_password` 视为默认认证插件。

这个变化只影响安装或升级到 MySQL 8.0 或更高版本后创建的新账户；升级安装中的既有账户认证插件保持不变。既有用户可使用 `ALTER USER` 切换：

```sql
ALTER USER user
  IDENTIFIED WITH caching_sha2_password
  BY 'password';
```

### 兼容性问题与解决方案

未更新以识别 `caching_sha2_password` 的客户端或连接器，可能无法连接到默认认证插件为 `caching_sha2_password` 的 MySQL 8.0 服务器，即使账户本身并不使用该插件。服务器会向客户端指定默认认证插件；如果客户端实现不能优雅处理未知默认认证插件，可能报出类似以下错误：

```text
Authentication plugin 'caching_sha2_password' is not supported
```

使用 `caching_sha2_password` 账户的客户端必须使用安全连接，或支持 RSA 密钥对密码交换的非加密连接。安全连接可基于 TCP 的 TLS/SSL、Unix socket 文件或共享内存建立。

如果必须服务 8.0 之前的客户端，可临时把服务器默认认证插件改回 `mysql_native_password`：

```ini
[mysqld]
default_authentication_plugin=mysql_native_password
```

这应视为临时方案，而不是长期方案，因为它会让在该设置生效期间创建的新账户失去 `caching_sha2_password` 提供的更强认证安全性。

### 支持的客户端和连接器

以下客户端和连接器已支持 `caching_sha2_password`：

- MySQL 8.0（8.0.4 或更高）和 MySQL 5.7（5.7.23 或更高）的 `libmysqlclient`，以及基于它的 `mysql`、`mysqladmin` 等标准客户端。
- MySQL Connector/C++ 1.1.11 或更高，或 8.0.7 或更高。
- MySQL Connector/J 8.0.9 或更高。
- MySQL Connector/NET 8.0.10 或更高，通过经典 MySQL 协议。
- MySQL Connector/Node.js 8.0.9 或更高。
- PHP 的 X DevAPI 扩展 `mysql_xdevapi`。

PHP 的 `PDO_MySQL` 和 `ext/mysqli` 不支持 `caching_sha2_password`。

### root 管理账户

升级到 MySQL 8.0 时，既有账户的认证插件保持不变，包括 `'root'@'localhost'`。新建安装初始化数据目录时，`'root'@'localhost'` 默认使用 `caching_sha2_password`。如果希望 root 账户改用 `mysql_native_password`，可在初始化后执行：

```sql
ALTER USER 'root'@'localhost'
  IDENTIFIED WITH mysql_native_password
  BY 'password';
```

如果当前客户端或连接器尚不支持 `caching_sha2_password`，也可以在初始化数据目录时通过 `--default-authentication-plugin=mysql_native_password`，或在选项文件中设置 `default_authentication_plugin=mysql_native_password`。

### 复制

当复制拓扑中所有服务器都已升级到 MySQL 8.0.4 或更高时，副本连接源服务器可使用 `caching_sha2_password` 账户。与普通客户端相同，这类连接必须使用安全连接或基于 RSA 的密码交换。

源/副本复制可使用以下 `CHANGE MASTER TO` 选项之一：

```sql
MASTER_SSL = 1;
GET_MASTER_PUBLIC_KEY = 1;
MASTER_PUBLIC_KEY_PATH = 'path to RSA public key file';
```

组复制可按需设置：

```sql
SET GLOBAL group_replication_recovery_use_ssl = ON;
SET GLOBAL group_replication_recovery_get_public_key = 1;
SET GLOBAL group_replication_recovery_public_key_path = 'path to RSA public key file';
```

## 配置变化

- **不兼容变化**：MySQL 存储引擎现在必须自行提供分区处理器，服务器不再提供通用分区支持。MySQL 8.0 中只有 InnoDB 和 NDB 提供受支持的原生分区处理器。使用其他存储引擎的分区表必须在升级前改为 InnoDB 或 NDB，或移除分区，否则升级后无法使用。
- 若将 MySQL 5.7 或更早版本的 `mysqldump` 导出文件导入 MySQL 8.0，必须确保创建分区表的语句没有指定不受支持的存储引擎；可以移除分区定义，或显式指定 InnoDB，或让它默认使用 InnoDB。
- 多个未使用的服务器错误代码已移除；专门测试这些错误代码的应用应更新。
- **重要变化**：默认字符集从 `latin1` 变为 `utf8mb4`；默认排序规则从 `latin1_swedish_ci` 变为 `utf8mb4_0900_ai_ci`。未显式指定字符集和排序规则的新对象会受影响。可在 `my.cnf` 中设置旧默认值以保留旧行为。
- 升级前应确保表、文件和索引注释中不存在当前字符集未定义的字符；可修改字符集，或移除问题字符。
- **不兼容变化**：从 MySQL 8.0.11 起，禁止以与初始化服务器时不同的 `lower_case_table_names` 设置启动服务器。该限制是必要的，因为数据字典表字段使用的排序规则基于初始化时的设置。

## 服务器变化

- MySQL 8.0.11 移除了多个已弃用的账户管理特性，包括用 `GRANT` 修改用户账户非权限特性、`NO_AUTO_CREATE_USER` SQL 模式、`PASSWORD()` 函数和 `old_passwords` 系统变量。使用这些特性的应用应改为使用替代方案。
- 从 MySQL 5.7 复制到 MySQL 8.0 时，引用这些已移除特性的语句可能导致复制失败。
- 应从选项文件的 `sql_mode` 设置中移除 `NO_AUTO_CREATE_USER`，否则 MySQL 8.0 可能无法启动。
- MySQL 8.0.11 移除了 `DB2`、`MAXDB`、`MSSQL`、`MYSQL323`、`MYSQL40`、`ORACLE`、`POSTGRESQL`、`NO_FIELD_OPTIONS`、`NO_KEY_OPTIONS`、`NO_TABLE_OPTIONS` 等兼容 SQL 模式。移除 `MAXDB` 后，`CREATE TABLE` 或 `ALTER TABLE` 中的 `TIMESTAMP` 不再被当作 `DATETIME`。
- 许多错误消息的文本被修改和改进。依赖特定错误消息内容或格式的应用应在升级前测试并调整。
- 从 MySQL 8.0.3 起，空间数据类型允许 SRID 属性。有显式 SRID 的空间列只接受该 SRID 的值，优化器可使用其上的 `SPATIAL` 索引；没有 SRID 属性的空间列上的 `SPATIAL` 索引会被优化器忽略。
- MySQL 8.0.0 移除了多个旧空间函数，改为使用带 `ST_` 或 `MBR` 前缀的命名空间。生成列定义中使用旧空间函数可能导致升级失败；升级前应运行 `mysqlcheck --check-upgrade` 并替换。
- 执行到 MySQL 8.0.3 或更高版本的原地升级时，具有 `RELOAD` 权限的用户会自动获得 `BACKUP_ADMIN` 权限。
- 从 MySQL 8.0.13 起，运行时切换二进制日志格式受到新限制，特别是存在打开的临时表或复制通道应用器正在运行时。
- 从 MySQL 8.0.30 起，启动时 `log_error_services` 中列出的错误日志组件会在服务器启动序列早期隐式加载。此前通过 `INSTALL COMPONENT` 安装并在启动配置中列出这些组件的环境，应更新配置以避免启动警告。

## InnoDB 变化

- 基于 InnoDB 系统表的 `INFORMATION_SCHEMA` 视图被数据字典表上的内部系统视图替代。例如：
  - `INNODB_SYS_COLUMNS` 改名为 `INNODB_COLUMNS`
  - `INNODB_SYS_DATAFILES` 改名为 `INNODB_DATAFILES`
  - `INNODB_SYS_FIELDS` 改名为 `INNODB_FIELDS`
  - `INNODB_SYS_FOREIGN` 改名为 `INNODB_FOREIGN`
  - `INNODB_SYS_INDEXES` 改名为 `INNODB_INDEXES`
  - `INNODB_SYS_TABLES` 改名为 `INNODB_TABLES`
  - `INNODB_SYS_TABLESPACES` 改名为 `INNODB_TABLESPACES`
- 升级到 MySQL 8.0.3 或更高后，应更新引用旧视图名的脚本。
- 随附 zlib 从 1.2.3 升级到 1.2.11。新的 `compressBound()` 会给出略高的压缩缓冲区估计值，因此接近最大行长的压缩 InnoDB 表在 `CREATE TABLE ... ROW_FORMAT=COMPRESSED`、`INSERT` 或 `UPDATE` 时可能失败。升级前应在测试实例中测试大行压缩表。
- 使用 `--innodb-directories` 后，使用绝对路径或位于数据目录之外创建的 file-per-table 和常规表空间文件，应添加到 `innodb_directories`，否则恢复期间 InnoDB 无法找到这些文件。
- undo 日志不能再位于系统表空间。MySQL 8.0 默认使用两个 undo 表空间。从 MySQL 5.7 升级到 8.0 时，既有 undo 表空间会被移除并替换为两个新的默认 undo 表空间。
- **不兼容变化**：从 MySQL 8.0.17 起，`CREATE TABLESPACE ... ADD DATAFILE` 不允许循环目录引用。升级前应移除表空间数据文件路径中的循环引用。
- MySQL 8.0.19 起，所有文件系统上的分区和子分区分隔符统一为小写 `#p#` 和 `#sp#`；由用户指定的分区名生成的表空间名和文件名也统一小写。升级过程会检查并按需修改磁盘和数据字典中的分区文件名。
- 从 MySQL 8.0.21 起，如果发现表空间数据文件位于未知目录，服务器在启动或从 MySQL 5.7 升级时会向错误日志写警告。应将相关目录添加到 `innodb_directories`。
- **重要变化**：从 MySQL 8.0.30 起，`innodb_redo_log_capacity` 控制 redo 日志占用的磁盘空间。InnoDB 默认在数据目录的 `#innodb_redo` 中维护 32 个 redo 日志文件；`innodb_log_files_in_group` 和 `innodb_log_file_size` 被弃用。升级前同样要求干净关机。
- MySQL 5.7.35 之前，Redundant 或 Compact 行格式表的索引没有大小限制；从 MySQL 5.7.35 起限制为 767 字节。从更早版本升级到 MySQL 8.0 前，应删除并重建超过该限制的索引。

## SQL 变化

- **不兼容变化**：从 MySQL 8.0.13 起，已弃用的 `GROUP BY` 子句 `ASC` 或 `DESC` 限定符被移除。需要指定排序时，应使用 `ORDER BY`。旧查询和存储程序定义应在升级前修改，否则升级或复制到 MySQL 8.0.13 或更高可能失败。
- 一些在 MySQL 5.7 中不是保留字的词在 MySQL 8.0 中可能成为保留字。受影响的标识符应使用反引号引用。
- 升级后应测试应用程序中的优化器提示；优化器增强可能使某些提示不再必要，甚至产生反效果。
- MySQL 8.0.16 之前，InnoDB 对未指定 `CONSTRAINT symbol` 的外键使用生成名称；之后曾改用 `FOREIGN KEY index_name`，并因约束名必须每个 schema 唯一而引发错误。MySQL 8.0.16 恢复为生成约束名。依赖旧行为的应用可能受影响。
- 从 MySQL 8.0.22 起，`IFNULL()` 和 `CASE()` 等流控制函数将系统变量值视为具有相同字符集和排序规则的列值，而不是常量。某些查询可能出现 `Illegal mix of collations`，此时应将系统变量转换为正确的字符集和排序规则。
- **不兼容变化**：MySQL 8.0.28 修复了 `CONVERT()` 有时允许 `BINARY` 值无效转换为非二进制字符集的问题。依赖旧行为的应用应在升级前检查并修改。若 `CONVERT()` 出现在索引生成列表达式中，升级到 8.0.28 可能导致索引损坏；应先修正无效输入数据，再删除并重建索引或强制重建表。

## 服务器默认值变化

MySQL 8.0 改进了许多默认值，以提供更好的开箱即用体验。主要变化包括：

| 类别 | 选项/参数 | 旧默认值 | 新默认值 |
|---|---|---|---|
| 服务器 | `character_set_server` | `latin1` | `utf8mb4` |
| 服务器 | `collation_server` | `latin1_swedish_ci` | `utf8mb4_0900_ai_ci` |
| 服务器 | `explicit_defaults_for_timestamp` | `OFF` | `ON` |
| 服务器 | `optimizer_trace_max_mem_size` | `16KB` | `1MB` |
| 服务器 | `validate_password_check_user_name` | `OFF` | `ON` |
| 服务器 | `max_allowed_packet` | `4MB` | `64MB` |
| 服务器 | `max_error_count` | `64` | `1024` |
| 服务器 | `event_scheduler` | `OFF` | `ON` |
| 服务器 | `table_open_cache` | `2000` | `4000` |
| 服务器 | `log_error_verbosity` | `3` | `2` |
| InnoDB | `innodb_undo_tablespaces` | `0` | `2` |
| InnoDB | `innodb_undo_log_truncate` | `OFF` | `ON` |
| InnoDB | `innodb_autoinc_lock_mode` | `1`（连续） | `2`（交错） |
| InnoDB | `innodb_flush_neighbors` | `1`（启用） | `0`（禁用） |
| 复制 | `log_bin` | `OFF` | `ON` |
| 复制 | `server_id` | `0` | `1` |
| 复制 | `log_slave_updates` | `OFF` | `ON` |
| 复制 | `expire_logs_days` | `0` | `30` |
| 组复制 | `group_replication_autorejoin_tries` | `0` | `3` |
| 组复制 | `group_replication_exit_state_action` | `ABORT_SERVER` | `READ_ONLY` |

其中，`innodb_autoinc_lock_mode` 默认改为交错模式与默认复制类型从语句复制转为行复制相符；但它与语句复制不兼容。`innodb_undo_tablespaces` 最小值为 2，且回滚段不能再位于系统表空间，因此无法回退到 MySQL 5.7 行为。

Performance Schema 的元数据锁、内存和事务检测默认开启。二进制日志默认开启，几乎适用于所有需要复制或时间点恢复的生产环境；生产环境通常还应按需设置唯一的 `server_id`。

多数默认值适用于开发和生产环境。例外是 `--innodb-dedicated-server`，其默认值仍为 `OFF`，因为它可能占用专用服务器上所有可用内存。在 MySQL 服务器独占的机器上，建议生产环境启用该选项。

## 有效的性能回退

MySQL 5.7 与 8.0 之间可能出现性能回退。以下是一些合理原因及缓解方法：

- 二进制日志在 5.7 默认关闭，在 8.0 默认开启。若不需要，可使用 `--skip-log-bin` 或 `--disable-log-bin`。
- 默认字符集从 `latin1` 变为 `utf8mb4`。`utf8mb4` 在 8.0 中已显著改进，但 `latin1` 仍更快；不需要 `utf8mb4` 时可在 8.0 中继续使用 `latin1`。
- 事务性数据字典提供原子 DDL 和更高可靠性，但会增加密集 `CREATE`/`DROP` 负载的 DDL 开销；对 DML 负载通常没有影响。该权衡没有通用缓解方法。
- 从 MySQL 5.7.28 起统一使用 OpenSSL 和更强的 TLS 加密算法，启用 TLS 时可能带来性能回退。如果出于安全原因需要 TLS，则不建议关闭。
- Performance Schema 检测范围更广。如不需要，可设置 `performance_schema = OFF`，或按更细粒度关闭部分检测。
- undo 表空间自动截断默认开启，可能带来永久开销并可能造成停顿。可设置 `innodb_undo_log_truncate = OFF`，并按需手动截断 undo 表空间。
- ICU 正则库内部使用 UTF-16，`[[:alpha:]]`、`[[:digit:]]` 等字符类性能不如 Spencer 库。可用 `[a-zA-Z]` 和 `[0-9]` 替代。
