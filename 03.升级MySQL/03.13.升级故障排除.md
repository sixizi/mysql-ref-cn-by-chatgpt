# 3.13 升级故障排除

- MySQL 5.7 实例中表的 `.frm` 文件与 InnoDB 数据字典不匹配时，可能导致升级到 MySQL 8.0 失败。`.frm` 文件损坏可能引发这种不匹配。重新尝试升级前，应先导出并恢复受影响的表。
- 如果新 `mysqld` 服务器无法启动，请确认没有沿用旧安装的 `my.cnf` 文件。可用 `mysqld --print-defaults` 检查；如果输出除程序名外还有其他内容，说明存在影响服务器或客户端的 `my.cnf`。
- 升级后，如果编译的客户端程序出现 `Commands out of sync` 或意外 core dump，通常说明编译时使用了旧的头文件或库文件。检查 `mysql.h` 和 `libmysqlclient.a` 是否来自新发行版；否则应用新的头文件和库重新编译。如果共享客户端库主版本号变化，例如从 `libmysqlclient.so.20` 到 `libmysqlclient.so.21`，也可能需要重新编译。
- 如果已创建某个名称的可加载函数，而新版本 MySQL 实现了同名内置函数，该可加载函数会变得不可访问。应使用 `DROP FUNCTION` 删除可加载函数，再用 `CREATE FUNCTION` 以不冲突的新名称重建。存储函数与新版内置函数同名时同理。
- 如果升级因为 [3.6 为升级准备安装](./03.06.为升级准备安装.md)中列出的任何问题失败，服务器会回滚对数据目录的所有更改。此时应删除所有 redo 日志文件，并在原数据目录上重新启动 MySQL 5.7 服务器修复错误。默认情况下，redo 日志文件 `ib_logfile*` 位于 MySQL 数据目录。错误修复后，设置 `innodb_fast_shutdown=0` 执行慢关机，再重新尝试升级。
