### 3.6 为升级准备您的安装

在升级到最新的 MySQL 26.7 版本之前，请通过执行下面描述的初步检查来确保您当前的 MySQL 26.7 或 MySQL 26.7 服务器实例的升级就绪情况。否则升级过程可能会失败。

提示

考虑使用 MySQL Shell 升级检查器实用程序，它使您能够验证 MySQL 服务器实例是否已准备好升级。您可以选择计划升级到的目标 MySQL Server 版本，范围从 MySQL Server 8.0.11 到与当前 MySQL Shell 版本号相匹配的 MySQL Server 版本号。升级检查器实用程序执行与指定目标版本相关的自动检查，并建议您应该手动进行的进一步相关检查。升级检查器适用于 MySQL 的所有 Bugfix、Innovation 和 LTS 版本。MySQL Shell 的安装说明可以在此处找到。

初步检查：

1. 以下问题不得存在：

   - 不得有使用过时数据类型或函数的表。

   - 不得有孤立的 .frm 文件。

   - 触发器不得有缺失或空的定义者，或无效的创建上下文（由 SHOW TRIGGERS 或 INFORMATION_SCHEMA TRIGGERS 表显示的 character_set_client、collation_connection、Database Collation 属性指示）。任何此类触发器必须转储并恢复以修复问题。

   要检查这些问题，请执行此命令：

   ```
   mysqlcheck -u root -p --all-databases --check-upgrade
   ```

   如果 mysqlcheck 报告任何错误，请更正这些问题。

2. 不得有使用不支持本地分区的存储引擎的分区表。要识别此类表，请执行此查询：

   ```
   SELECT TABLE_SCHEMA, TABLE_NAME
       FROM INFORMATION_SCHEMA.TABLES
       WHERE ENGINE NOT IN ('innodb', 'ndbcluster')
           AND CREATE_OPTIONS LIKE '%partitioned%';
   ```

   查询报告的任何表必须更改为使用 InnoDB 或改为非分区表。要将表存储引擎更改为 InnoDB，请执行此语句：

   ```
   ALTER TABLE table_name ENGINE = INNODB;
   ```

   有关将 MyISAM 表转换为 InnoDB 的信息，请参见第 17.6.1.5 节"从 MyISAM 转换表到 InnoDB"。

   要使分区表变为非分区表，请执行此语句：

   ```
   ALTER TABLE table_name REMOVE PARTITIONING;
   ```

3. 在 MySQL 26.7 中可能保留了一些在之前未保留的关键字。请参见第 11.3 节"关键字和保留字"。这可能导致以前用作标识符的字词变为非法。要修复受影响的语句，请使用标识符引用。请参见第 11.2 节"模式对象名称"。

4. MySQL 26.7 mysql 系统数据库中不得有与 MySQL 26.7 数据字典使用的表同名的表。要识别具有这些名称的表，请执行此查询：

   ```
   SELECT TABLE_SCHEMA, TABLE_NAME
   FROM INFORMATION_SCHEMA.TABLES
   WHERE
       LOWER(TABLE_SCHEMA) = 'mysql'
       AND
       LOWER(TABLE_NAME) IN
       (
       'catalogs',
       'character_sets',
       'check_constraints',
       'collations',
       'column_statistics',
       'column_type_elements',
       'columns',
       'dd_properties',
       'events',
       'foreign_key_column_usage',
       'foreign_keys',
       'index_column_usage',
       'index_partitions',
       'index_stats',
       'indexes',
       'parameter_type_elements',
       'parameters',
       'resource_groups',
       'routines',
       'schemata',
       'st_spatial_reference_systems',
       'table_partition_values',
       'table_partitions',
       'table_stats',
       'tables',
       'tablespace_files',
       'tablespaces',
       'triggers',
       'view_routine_usage',
       'view_table_usage'
       );
   ```

   查询报告的任何表必须删除或重命名（使用 RENAME TABLE）。这也可能需要对使用受影响表的应用程序进行更改。

5. 不得有外键约束名称长于 64 个字符的表。使用此查询来识别具有过长约束名称的表：

   ```
   SELECT TABLE_SCHEMA, TABLE_NAME
   FROM INFORMATION_SCHEMA.TABLES
   WHERE TABLE_NAME IN
     (SELECT LEFT(SUBSTR(ID,INSTR(ID,'/')+1),
                  INSTR(SUBSTR(ID,INSTR(ID,'/')+1),'_ibfk_')-1)
     FROM INFORMATION_SCHEMA.INNODB_SYS_FOREIGN
     WHERE LENGTH(SUBSTR(ID,INSTR(ID,'/')+1))>64);
   ```

   对于约束名称超过 64 个字符的表，删除该约束并使用不超过 64 个字符的约束名称重新添加它（使用 ALTER TABLE）。

6. 不得有由 sql_mode 系统变量定义的过时 SQL 模式。尝试使用过时 SQL 模式会阻止 MySQL 26.7 启动。使用过时 SQL 模式的应用程序应该被修改以避免使用它们。

7. 仅升级已正确关闭的 MySQL 服务器实例。如果实例意外关闭，则在升级前重新启动实例并使用 innodb_fast_shutdown=0 进行缓慢关闭。

8. 不得有显式定义的列名超过 64 个字符的视图（MySQL 5.7 中允许列名最多 255 个字符的视图）。为避免升级错误，应在升级前修改此类视图。目前，识别列名超过 64 个字符的视图的唯一方法是使用 SHOW CREATE VIEW 检查视图定义。您也可以通过查询信息模式 VIEWS 表来检查视图定义。

9. 不得有表或存储过程具有超过 255 个字符或 1020 字节长度的单个 ENUM 或 SET 列元素。在 MySQL 26.7 之前，ENUM 或 SET 列元素的最大组合长度为 64K。在 MySQL 26.7 中，单个 ENUM 或 SET 列元素的最大字符长度为 255 个字符，最大字节长度为 1020 字节。（1020 字节限制支持多字节字符集）。在升级到 MySQL 8.0 之前，修改任何超过新限制的 ENUM 或 SET 列元素。不这样做会导致升级失败并出现错误。

10. 您的 MySQL 26.7 安装不得使用 MySQL 26.7 不支持的功能。这里的任何更改必然是特定于安装的，但以下示例说明了要查找的内容：

    在 MySQL 26.7 中已删除了一些服务器启动选项和系统变量。请参见 MySQL 26.7 中删除的功能和第 1.5 节"MySQL 26.7 中添加、弃用或删除的服务器和状态变量及选项"。如果您使用其中任何一个，升级需要配置更改。

11. 如果您打算在升级时将 lower_case_table_names 设置更改为 1，请确保在升级前模式和表名称为小写。否则，由于模式或表名称大小写不匹配，可能会发生故障。您可以使用以下查询来检查包含大写字符的模式和表名称：

    ```
    mysql> select TABLE_NAME, if(sha(TABLE_NAME) !=sha(lower(TABLE_NAME)),'Yes','No') as UpperCase from
    ```

    如果 lower_case_table_names=1，升级过程会检查表和模式名称以确保所有字符都是小写。如果发现表或模式名称包含大写字符，升级过程将失败并出现错误。

    注意

    不建议在升级时更改 lower_case_table_names 设置。

如果升级到 MySQL 26.7 因上述任何问题而失败，服务器会将所有更改恢复到数据目录。在这种情况下，删除所有重做日志文件并在现有数据目录上重新启动 MySQL 26.7 服务器以解决错误。重做日志文件（ib_logfile*）默认驻留在 MySQL 数据目录中。修复错误后，在尝试升级前执行缓慢关闭（通过设置 innodb_fast_shutdown=0）。

### 3.7 在 Unix/Linux 上升级 MySQL 二进制或基于包的安装

本节描述如何在 Unix/Linux 上升级 MySQL 二进制和基于包的安装。描述了就地升级和逻辑升级方法。

- 就地升级

- 逻辑升级

- MySQL Cluster 升级

#### 就地升级

就地升级涉及关闭旧的 MySQL 服务器，用新的 MySQL 二进制文件或包替换旧的，在现有数据目录上重新启动 MySQL，并升级现有安装中需要升级的任何剩余部分。有关可能需要升级的详细信息，请参见第 3.4 节"MySQL 升级过程升级的内容"。

注意

如果您升级的安装最初是通过安装多个 RPM 包生成的，请升级所有包，而不仅仅是某些包。例如，如果您之前安装了服务器和客户端 RPM，请不要仅升级服务器 RPM。

对于某些 Linux 平台，从 RPM 或 Debian 包安装的 MySQL 包括用于管理 MySQL 服务器启动和关闭的 systemd 支持。在这些平台上，mysqld_safe 未被安装。在这种情况下，使用 systemd 进行服务器启动和关闭，而不是在以下说明中使用的方法。请参见第 2.5.9 节"使用 systemd 管理 MySQL 服务器"。

对于升级到 MySQL Cluster 安装，另请参见 MySQL Cluster 升级。

要执行就地升级：

1. 查看第 3.1 节"开始之前"中的信息。

2. 通过完成第 3.6 节"为升级准备您的安装"中的初步检查来确保您的安装的升级就绪情况。

3. 如果您使用 InnoDB 的 XA 事务，在升级前运行 XA RECOVER 以检查未提交的 XA 事务。如果返回结果，通过发出 XA COMMIT 或 XA ROLLBACK 语句提交或回滚 XA 事务。

4. 如果您通常运行配置了 innodb_fast_shutdown 设置为 2（冷关闭）的 MySQL 服务器，请通过执行以下任一语句将其配置为执行快速或缓慢关闭：

   ```
   SET GLOBAL innodb_fast_shutdown = 1; -- fast shutdown
   SET GLOBAL innodb_fast_shutdown = 0; -- slow shutdown
   ```

   通过快速或缓慢关闭，InnoDB 将其撤销日志和数据文件保留在可以处理版本之间文件格式差异的状态中。

5. 关闭旧的 MySQL 服务器。例如：

   ```
   mysqladmin -u root -p shutdown
   ```

6. 升级 MySQL 二进制文件或包。如果升级二进制安装，请解包新的 MySQL 二进制分发包。请参见获取并解包分发。对于基于包的安装，请安装新包。
