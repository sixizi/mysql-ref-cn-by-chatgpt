# 3.6 为升级准备安装

升级到最新 MySQL 8.0 版本前，应完成以下前置检查，确保当前 MySQL 5.7 或 MySQL 8.0 服务器实例已准备好升级。否则升级过程可能失败。

**提示**

可以考虑使用 MySQL Shell 升级检查器。它支持选择目标 MySQL Server 版本，自动执行与该目标相关的检查，并提示需要手动完成的相关检查。

## 前置检查

1. 以下问题必须不存在：

   - 没有使用过时数据类型或函数的表。
   - 如果表包含 5.6.4 之前格式的旧时间列，即不支持小数秒精度的 `TIME`、`DATETIME` 和 `TIMESTAMP` 列，则不支持原地升级到 MySQL 8.0。应先使用 `REPAIR TABLE` 升级这些表。
   - 没有孤立的 `.frm` 文件。
   - 触发器没有缺失或空的 definer，也没有无效创建上下文。可通过 `SHOW TRIGGERS` 或 `INFORMATION_SCHEMA.TRIGGERS` 中的 `character_set_client`、`collation_connection`、`Database Collation` 属性识别。此类触发器应先导出并恢复。

   执行以下命令检查这些问题：

   ```terminal
   $ mysqlcheck -u root -p --all-databases --check-upgrade
   ```

   如果报告错误，应先修正。

2. 不得存在使用不支持原生分区的存储引擎的分区表。使用以下查询识别：

   ```sql
   SELECT TABLE_SCHEMA, TABLE_NAME
   FROM INFORMATION_SCHEMA.TABLES
   WHERE ENGINE NOT IN ('innodb', 'ndbcluster')
   AND CREATE_OPTIONS LIKE '%partitioned%';
   ```

   查询到的表必须改为 InnoDB 或取消分区：

   ```sql
   ALTER TABLE table_name ENGINE = INNODB;
   ALTER TABLE table_name REMOVE PARTITIONING;
   ```

3. 一些在 MySQL 5.7 中不是保留字的词可能在 MySQL 8.0 中成为保留字。受影响语句中的标识符应加引号。

4. MySQL 5.7 的 `mysql` 系统数据库中，不得存在与 MySQL 8.0 数据字典表同名的表。相关表必须删除或重命名，并同步调整使用这些表的应用程序。

5. 外键约束名不得超过 64 个字符。超长的约束应删除后用更短名称重建。

6. `sql_mode` 中不得包含已过时的 SQL 模式，否则 MySQL 8.0 无法启动。使用这些模式的应用程序应修改。

7. 只能升级正常关机的 MySQL 实例。如果实例曾意外停机，应先重启并用 `innodb_fast_shutdown=0` 执行关机，再升级。

8. 不应存在显式定义超过 64 个字符的视图列名。MySQL 5.7 允许最多 255 个字符，但 MySQL 8.0 不允许；应在升级前修改视图。

9. 表或存储过程中，单个 `ENUM` 或 `SET` 元素不得超过 255 个字符或 1020 字节。MySQL 8.0 之前这些元素的最大组合长度为 64KB；超出新限制会导致升级失败。

10. 升级到 MySQL 8.0.13 或更高前，不得存在位于共享 InnoDB 表空间（包括系统表空间和常规表空间）的表分区。应使用 `ALTER TABLE ... REORGANIZE PARTITION` 将其移到 file-per-table 表空间。

11. 来自 MySQL 8.0.12 或更低的查询和存储程序定义中，不得对 `GROUP BY` 使用 `ASC` 或 `DESC` 限定符；否则升级或复制到 MySQL 8.0.13 或更高可能失败。

12. MySQL 5.7 安装不得使用 MySQL 8.0 不支持的特性。例如，`--ignore-db-dir` 已被移除，应从启动配置中删除；对应的数据目录子目录也应移除，或让 8.0 服务器将其加入数据字典后使用 `DROP DATABASE` 删除。

13. 如果打算在升级时把 `lower_case_table_names` 改为 `1`，应确保 schema 和表名已全部小写。从 MySQL 8.0.19 起，当 `lower_case_table_names=1` 时，升级过程会检查表和 schema 名称是否全为小写，发现大写即失败。一般不建议在升级时更改该设置。

如果升级因上述问题失败，服务器会回滚对数据目录的所有更改。此时应删除所有 redo 日志文件，在原数据目录上重新启动 MySQL 5.7 服务器并修复错误，再设置 `innodb_fast_shutdown=0` 执行慢关机，然后重新尝试升级。
